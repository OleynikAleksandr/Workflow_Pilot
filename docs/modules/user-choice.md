# Выбор пользователя и режимы плана

В Workflow Pilot 0.5.39 (Workflow Kit 1.10.4, ролевой протокол 13) важные решения принимает пользователь одним нажатием. Приложение показывает карточку выбора по событиям, которые оно уже отслеживает, записывает решение и передаёт его агенту внутренним каналом. Агенты не решают за пользователя и не присваивают себе роль.

## Карточка «Выбор пользователя»

Один запрос показывается в основной панели ChatGPT. Кнопка и клиентская область «Текущие действия» удалены; HTTP без MCP iframe не имеет прежнего fallback выбора. В sidebar нет полной карточки, оранжевой отметки выбора и допланового плана. `src/contracts/user-choice.mjs` строит choiceView/renderChoiceCard/choiceCardCss; [компонент текущей работы](current-actions.md) сохраняет одну карточку в панели.

- Вопрос, 2–3 строки: название, пояснение, «Выбрать». Первая строка — рекомендуемая: «(рекомендую)», залитая кнопка.
- Оранжевый `--wp-choice` (обе темы) означает необходимое действие пользователя; смысл дополнен текстом/значком. Обычное сохранённое решение и ожидание доставки нейтральны.
- Новая карточка пульсирует 3 раза, затем ровная рамка; при `prefers-reduced-motion` без анимации. Повторная отрисовка той же карточки не пульсирует.
- Подсказка «или напишите ответ в чат своими словами».

## Модель (Control)

`src/control/workflow/user-choices.mjs`: `UserChoices` и чистая `collectChoiceFacts`. Причины собираются из фактов coordination: пауза ExecutionControl, план ждёт приёмки, состояние Review, запись режима и владелец Kit, ручные отправки страниц. Записи (`choice_id`, вид, получатель, ключ причины, поколение, варианты, состояние, источник нажатия) сохраняются в снимке настроек coordination вместе с остальным состоянием выполнения: перезапуск службы не теряет предложенный или выбранный выбор; после перезапуска предложения сверяются с фактами.

Одна карточка на сессию; при нескольких причинах показывается старшая доступная: Review → отказ Kit → приёмка → режим → вторая сессия. Состояния:

1. **offered** — показана; **postponed** — свёрнута «Проверю сам», кнопка «Показать варианты».
2. В пути — нейтральное **saving**, без заявления о сохранённом решении. Только после долговечной записи **chosen**: компактное нейтральное «Выбрано: … · передаётся агенту», без прежнего вопроса/вариантов/большой рамки; затем отдельная доставка. CAS по choice_id/generation отклоняет повтор (`USER_CHOICE_CHANGED`). Отказ записи возвращает offered с причиной и не выполняет эффект. Ошибка уже принятого действия или UNKNOWN не предлагают повторить Send. Вариант без сообщения завершается после эффекта; сообщение по read один раз уходит в историю.
3. **declined** — пользователь сам отправил сообщение в этот чат (рост `manualSendRevision`): карточка снимается, в Истории «Пользователь ответил в чате сам; выбор снят».
4. **stale** — причина исчезла: «выбор неактуален».

Устойчивые причины (отказ Kit, приёмка, Review) после declined предлагаются снова после подтверждённого конца хода получателя, не чаще раза на ручную отправку. Вторая сессия показывается один раз; выбор режима — только по новому запросу агента.

## События

| Вид | Причина | Получатель | Варианты (первый — рекомендуемый) |
|---|---|---|---|
| refused | пауза `refused` orchestrated-плана | владелец плана | поручить устранить причину; «Причина устранена — продолжить» (кнопка «Продолжить»); обсудить |
| acceptance | план `awaiting-acceptance` | владелец плана | принять и закрыть (`archive` с approval-note выбора); доработка; «Проверю сам» |
| second-session | нет плана, владелец — другая сессия, ручная отправка после захвата | эта сессия | остаться обсуждением; передать планирование (как меню «Назначить оркестратором») |
| review | `NEEDS_USER` и `notification_handled` | получатель Review | обсудить спор; опубликовать с позицией автора (`review:resolve --action publish`); принять замечания (`--action retry`) |
| mode | запрос `plan:mode-request` без выбора | владелец планирования | рекомендация агента первой (причина под строкой); второй режим; «Сначала доработать спецификацию» |

Действия — только существующие операции: «Продолжить», передача владельца, запись режима в Kit, отложить.

## Доставка

Успешная долговечная запись нажатия завершает решение пользователя для всех трёх вариантов режима, включая «Сначала доработать спецификацию». CAS choice_id/generation/recipient и запись до эффекта сохраняются: отказ записи не запускает действие; ошибка доставки не возвращает вопрос и не разрешает повтор неизвестной отправки. Saving ещё не означает chosen. Приёмка «Проверю сам» сохраняет собственное состояние postponed.

Сообщение агенту — вид `user-choice`, ключ `choice:<choice_id>`. Отдельный путь доставки: WAL → панель чата получателя → `claim_ready` → SDK → `read_message`. Сохранённое решение и получение агентом различаются; task:start, task yield и конец следующего ответа не требуются. Отличия:

- `enqueue` не требует grant и совпадения scope; допуск DialogueDelivery и `claim_ready` не требуют plugin-v1 и running/pausing, проверяются свежая identity/документ, ручной Stop, один in-flight и legacy UNKNOWN без повтора; busy, черновик и команды не задерживают SDK;
- получатель любой роли; `read_message` возвращает ролевой текст из `recipient_role` сообщения (для выбора режима — новая роль: orchestrator или self);
- пока у получателя есть недоставленный `user-choice`, статус панели не «остановлен», и панель ждёт его даже без плана, на паузе и после complete.

После read `user-choice`, включая `review-preference`, не удерживает first/choicePending/incoming, reserved/gate, settled/channelSettled и finalization/cleanup/complete. Правило одинаково для scope=null и текущего scope. Общий communicationMessageComplete учитывает kind/read и подтверждённый исход; reply_observed не подделывается. Старый accepted/read UI-gate нормализуется штатно при восстановлении или адресном событии без ручной правки WAL. Unread, latest revision и настоящие gates task/result/acceptance сохраняются. Новый notification_version=1 освобождает транспорт по read без выдуманного SDK accepted; исход неизвестной попытки остаётся в истории.

Готовность следующего SDK независима от обработки решения: перед claim/verify проверяются identity/document/attempt, manual Stop и действующее разрешение сообщения. После accepted следующий pending доступен без read/yield/idle. Непрочитанный UI-вход не удерживает транспорт; его read нужен для истории и отдельного завершения. PageStateSource, события очереди, SDK и Start/Continue переоценивают точного адресата. Терминальные квитанции назначения продолжают защищать cleanup/complete, а не диспетчеризацию SDK.

### Переключение Review

Kit сохраняет `preference` и событие с ID/версией/ON-OFF/временем/точной сессией до постановки в WAL. PlanReviewClient сериализует доставку через прежний `user-choice`, ключ `review-policy:<id>`, явный `ui_event.type=review-preference`. Недоступная панель откладывает SDK, активный ответ и команда — нет; сохранение и accepted не означают read. При restart повторяется идемпотентная постановка для исходного получателя, без второго поручения. SDK-уведомление того же message_id восстанавливается по ограниченному [контракту](sdk-messaging.md); сбой Review не удерживает последующий выбор. Read возвращает также pending_incoming текущего адресата.

Перед intent устаревшее решение может быть снято по актуальной версии Kit. После неизвестной отправки её исход не угадывается; позднее чтение старой версии возвращает инструкции сверить review:status. Выбранный затем проект/чат не меняет получателя. Ошибка записи не запускает доставку; удалённая сессия не создаётся заново. Иные клики автоматически не превращаются в модельные сообщения.

Событие Review не меняет роль и не даёт Start/реализацию. Агент читает актуальную политику перед prepare/публикацией; защита Kit действует независимо от SDK. Канонические инструкции роли, startup, read_message, PLAN и MCP согласованы. Для изменения роли после выбора режима сохраняется отдельный прежний путь.

Нажатие: в панели — инструмент `workflow_communication_choose` (`binding`, `choice_id`, `option_id`, `generation`; `reopen` для свёрнутой карточки), протокол панели 7; совместимое действие `pilot:choose` сохраняется в API. Проверяется, что выбор предложен, поколение актуально, а сессия — получатель.

## Режимы и владелец (Kit 1.9.8)

- `plan:mode-request --session ID --recommended sequential|orchestrated --reason "…"` — агент, когда спецификация готова. Атомарно занимает владельца планирования; чужая сессия — `PLANNING_OWNED` без записи; при опубликованном плане — `EXECUTION_MODE_ACTIVE_PLAN`. Повторный запрос сбрасывает выбор.
- `plan:mode-choose` вызывает только приложение после нажатия (CAS поколения и владельца, approval-note).
- При существующей записи режима `plan:create`, `scope:create`, `review:prepare` требуют origin этой сессии, выбор и совпадение стратегии (`EXECUTION_MODE_REQUIRED`/`MISMATCH`) до любой записи, включая `applyConfig`. План с origin всегда требует запись своей сессии; legacy parallel и CLI без origin не затронуты. Выбор попадает в решения пользователя плана.
- Передача и освобождение владельца, `archive` удаляют запись режима. Приложение наблюдает `execution-mode.json` и `planning-owner.json`.
- Ограничение: Kit не отличает вызов приложения от вызова агентом; гарантия — ролевой текст и источник нажатия в приложении.

**sequential (сам)** — владелец выполняет задачи по порядку в main (`task:start` → `commit --task`); кнопка «Начать выполнение плана» продолжает план в сессии из `execution_origin_session_id`, какой бы чат ни был выбран. **orchestrated** — как прежде.

## Роли и подписи

| Состояние | Роль | Подпись |
|---|---|---|
| нет владельца, плана нет | planning | Агент |
| владелец, режим не выбран | planning | Агент |
| владелец, sequential | self | Агент |
| владелец, orchestrated | orchestrator | Оркестратор |
| другая сессия при владельце или плане | discussion | Агент |

Канальная роль planning и self — O (один run через выбор режима), discussion — S. Внутренние роли и права не меняются ради имени. Функция/этап отделены от участника: обсуждение неизвестной операции, подготовка плана и реально начавшееся рецензирование различаются. После выбора orchestrated подпись «Оркестратор» меняется сразу. Перед публикацией нет имитации готового плана; старые Kit сохраняют свой порядок владения.

Правило развилок (ролевой протокол 13, все роли чатов с пользователем, кроме исполнителя): 2–3 варианта, рекомендуемый первым с «(рекомендую)», кнопками Intelligent UI, если модель их умеет, иначе списком; не предлагать выбор, когда решение очевидно.

Read/SDK accepted не смешиваются. История имеет устойчивые ID и сохранённые даты; старая неизвестная дата остаётся пустой. ExecutionControl и UserChoices действительно восстанавливаются из настроек. Семантический memo renderer сохраняет focus при SSE; ticking не повторяет live-объявление. Native/HTTP отвечают тем же backend CAS, второй книги решений нет.
