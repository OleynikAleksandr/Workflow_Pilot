# Постоянная доставка сообщений через SDK

Контракт Workflow Pilot 0.5.40, Kit 1.10.4, роли 13, панель `0.5.40-communication-7`, протокол панели 7. Все рабочие сообщения O/E/приложения используют один SDK. Очерёдность обработки определяет ChatGPT; busy/idle, конец ответа, команды, черновик, read/yield предыдущего входа не планируют отправку. Режимов включения, активирующих скриптов и DOM fallback нет.

## Границы и идентичность

WorkflowChannel хранит сообщения и попытки в существующем WAL; PluginCommunication связывает подтверждённую панель и получателя; AssignmentDialogue проверяет смысл и полномочия; DialogueDelivery связывает доставку с планом. Панель получает пакет через sync/wait и вызывает закреплённый `createMessage.send` / `ui/message` с role=user, target=active, send=true. Содержимое получатель читает через MCP. API клиента, локальные команды, Git и управление процессами сохраняют прежние границы.

Канал общий для task/context, question/clarification, decision/revision_request/acceptance, result, assignment-start/continue, integration/finalization, ready/recovery/diagnostic, выбора пользователя и Review. Единственное исключение до появления SDK — короткий [URL-bootstrap](chat-only-startup.md) открытия панели с ticket; рабочий контекст не передаётся повторным q или composer. Только Chat; публичные DOM-экспорты сохранены как библиотечный контракт.

projectId обозначает проект Kit, workspaceId — конкретную рабочую копию, sessionId — разговор. Worktree имеет собственный workspaceId и parentWorkspaceId. Имя и путь не удостоверяют владельца. Claim/read/recovery, grant, история и cleanup сверяют точные ID вместе со scope/participant/assignment/attempt/generation и host identity. Две копии одного проекта и повторное использование пути не наследуют историю, выбор или допуск удалённой копии. Legacy WAL дополняется только по доказанной живой сессии без противоречащей identity. [Миграция и обратный переход](project-compatibility.md), [жизненный цикл](project-lifecycle.md).

## Сообщение и попытка уведомления

Текст, context_ref, message_id и idempotency key сохраняются до эффекта один раз. SDK передаёт ссылку на чтение этого сообщения. Повтор ключа с тем же содержимым возвращает существующее состояние; повтор уведомления не создаёт нового поручения, назначения или выбора.

Уведомления `notification_version:1` имеют долговечные notification_attempts: ID, время, исход и очищенный код ошибки. На адресата допускается один активный claim/SDK-вызов. Две панели не становятся двумя отправителями. После завершения попытки следующие допустимые сообщения доступны независимо от её успеха; новые pending приоритетнее подошедшего повтора. Исторический UNKNOWN этого контракта не является общим замком. После SDK accepted следующий pending доступен без ожидания read/yield.

До каждого claim/verify проверяются адресат, документ, версия, разрешение и Stop. До Start доступны только bootstrap и разрешённые события настройки/выбора. Рабочее поручение не получает grant от подключения панели. Пауза позволяет сохранить result в outbox, но не начать новую рабочую доставку. После restart нужен свежий Continue. [Prepared task](prepared-tasks.md) согласован до Review/публикации и связывается с настоящим назначением после Start без нового хода O для сочинения.

## Ограниченное восстановление

SDK timeout — 90 с, claim — 120 с; lease поддерживается sync каждые 20 с во время Promise. Это границы транспортной попытки, не время ответа модели. Потеря report, restart/remount или истечение claim сохраняют UNKNOWN исходной попытки.

Для совместимого сохранённого уведомления допустимо не более трёх автоматических попыток того же message_id. После первого сбоя задержка 2 с, после второго — 5 с; существующий wait/sync обслуживает срок без нового scheduler. Reconnect и restart не обнуляют бюджет. Постоянный отказ, неверные аргументы/отсутствующий метод SDK, утрата lease и отказ полномочий не получают слепого повтора. Stop, отмена, stale/scope/identity/grant/version/storage не обходятся. Старые прямые DOM/URL Send неизвестного исхода и непроверенный legacy SDK сохраняют запрет повтора и удержание своего адресата.

Переход старого рабочего SDK-сообщения на version 1 разрешён только после проверки живого адресата, context_ref, idempotency key и корреляции начатой попытки. Startup не переводится в этот контракт. Нельзя сбросить неизвестный реальный эффект ради продолжения.

Поздний отчёт сохраняется у своей попытки и не переписывает более новую. После тайм-аута сам SDK может уже игнорировать поздний ответ хоста; отсутствие поздней квитанции не означает отказ хоста. Подтверждённый адресный read прекращает повторные уведомления и освобождает транспорт, сохраняя UNKNOWN в истории, без фиктивного accepted или DONE. После исчерпания бюджета автоматические попытки прекращаются; другие допустимые входящие не блокируются.

## Чтение, обработка и реальные эффекты

`workflow_communication_read_message` возвращает pending_incoming текущего адресата, включая доплановые UI-события; чужие/устаревшие данные исключаются. `workflow_communication_participants` и сведения назначения также позволяют восстановить входящие без копирования ID пользователем. Получив один SDK-сигнал, агент читает перечисленные входы в том же ходе, не опрашивая будущие сообщения. Review и выбор сверяются с каноническим текущим Kit-состоянием.

Повтор чтения уже подтверждённого обработанного сообщения возвращает already_handled без исполнительного контекста. Незавершённая обработка продолжается по сохранённому состоянию Kit. Защита эффектов использует существующие operation/idempotency keys, result receipts, acceptance точного SHA и подтверждённую интеграцию; повтор уведомления не повторяет task:start, создание назначения, выбор или merge. Неизвестный исход конкретной операции сохраняет её адресную блокировку. Exactly-once произвольных внешних команд модели не обещается.

| Факт | Доказательство |
| --- | --- |
| pending / intent | Сообщение сохранено приложением |
| SDK accepted | Хост принял вызов, не обязательно обработал его |
| MCP read | Адресат прочитал содержимое |
| yield / already_handled | Подтверждение обработки входа, отдельно от эффекта Kit |
| physical_complete | Коррелированный конец обработки для terminal/cleanup |
| checked result | Проверенный результат E и точный SHA |
| acceptance / integration | Отдельные принятие SHA и подтверждение интеграции в main |
| terminal receipt / cleanup / complete | Условия безопасного завершения выполнены отдельно |

Read/yield/physical_complete не управляют очередью SDK. Terminal/cleanup/complete сохраняют проверку окончания нужного E/O и отсутствия активных команд. Нажатие кнопки долговечно завершает [выбор пользователя](user-choice.md); получение и обработка — другие факты.

## Диагностика и интерфейс

Backend принимает только ограниченные структурированные сведения: стадия invocation/response/timeout/lease/restart, допустимые тип/код/категория, время и correlation IDs. Текст исключения не сохраняется произвольно: body, tokens, ticket, query и raw host metadata исключены. При следующем сбое доступен код и стадия; точную причину старого SDK_ERROR версии 0.5.38 восстановить задним числом нельзя.

До и после плана проекция показывает нейтральное восстановление либо конкретный исчерпанный/неповторяемый отказ с действием прочитать входящие. Ошибка не скрывается карточкой выбранного режима. История текущего workspace содержит попытки по устойчивым message_id/attempt ID и их настоящим датам. Сохранение сообщения, SDK accepted и read различаются; нет ложной галочки получения. Оранжевый обозначает требуемое внимание. Второй панели действий и режимных переключателей нет.

Канонический NOTIFICATION_RULE находится в packages/workflow-kit/src/lib/role-protocol.mjs и приходит через recovery/startup/адресные чтения. MCP read/participants/assignment status согласованы с ним. Обновление инструкций не повторяет recovery или исполнение. Несовместимый старый iframe отклоняется явно; переустановка bundle не меняет уже открытый ресурс хоста.

## Проверки и поставка

[Автоматические доказательства](../acceptance/sdk-messaging.md) включают реальный закреплённый SDK в изолированном host: JSON-RPC error, isError, timeout, поздний ответ; Review→ошибка→выбор; restart/две панели/Stop; полный цикл пяти E с injected отказом result, зависимую задачу, DOCS, точные SHA, cleanup/complete. Идентичность проверена для одинаковых имён, общего projectId и повторного пути. Это не живая приёмка ChatGPT.

Три ОС собираются из одного sourceCommit. Manifest/семь assets/подпись/установка/GitHub проверяются отдельными delivery-задачами. При работающей службе installer оставляет verified pending; переключает пользователь. Native Windows/Linux и живая приёмка 0.5.40 — NOT_RUN. Автоматического отката bundle/данных нет.
