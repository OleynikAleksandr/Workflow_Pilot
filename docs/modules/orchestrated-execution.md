# Оркестрованное выполнение плана

Новые планы Workflow Pilot 0.5.22 используют `execution_strategy: orchestrated` и `dialogue_version: 1`. O ведёт план, E выполняют задачи в отдельных worktree, Kit подтверждает Git-интеграции. Один Start/Пауза/Continue и Review сохранены. [Полный протокол и роли](assignment-dialogue.md), [Kit](../../packages/workflow-kit/docs/modules/orchestrated-plans.md), [координация](workflow-execution.md), [приёмка A–D](automatic-agent-dialogue-acceptance.md).

## Роли и принадлежность

Новая сессия без плана — кандидат O: короткое приглашение через DOM и полный [recovery через панель](orchestrator-startup.md), обсуждение spec/to-do, Review при ON, публикация без запуска. `execution_origin_session_id` выбирает опубликованного O по сохранённой роли; Settings не меняют снимок плана. Другие новые сессии активного проекта — обсуждение: план не меняют, документы создают только по просьбе в `.workflow-temp/` вне Git.

E работает в Chat независимо от режима O Chat/Work. Bootstrap содержит обязательные правила, собственный worktree/назначение и приглашение панели. O заранее готовит и разрешает отправку собственного поручения; backend доставляет его после service ready. task.context_pack служит O списком для отбора, не автоматическим вложением E. E не начинает task:start по bootstrap.

Роли — поля хранилища сессий v6, recovery кешируется отдельно по роли. Прямой внешний разговор плагина не создаёт backend-страницу и не становится исполнителем. Сессия/выбор sidebar не меняют владельца плана или адресата. Несогласованная роль показывает «Требует внимания»; меню «Назначить оркестратором» остаётся явным действием.

## Волны и работа

ParallelExecution остаётся единственным scheduler. Он механически создаёт допустимые назначения при активном разрешении scope, учитывает зависимости, max_workers и пересечение путей. `parallel_safe: false` — исключительная задача после всего предыдущего; обе категории выполняются E. DOCS добавляется всегда. При release=true настроенный delivery_tail идёт после DOCS и выполняется O в main.

Страница → bootstrap → registration → живой SDK/bind → конец bootstrap предшествуют готовности доставки. Сразу после назначения O получает уведомление и сохраняет prepare с dispatch_when_ready=true одновременно с bootstrap. Это явная авторизация: backend повторно проверяет готовность и отправляет неизменяемый пакет без дополнительного ready-хода O. Без флага сохраняется только черновик; старые разрешения после смены поколения требуют подтверждения. Два-пять E не требуют select/show/focus, посещения карточек, ID или Enable. Поздний editor обрабатывается ограниченным повтором подготовки до Send. Отправленные/sending/unknown не повторяются. Исполнитель, которому действительно ничего не отправлялось, может получить новый чистый Chat draft; наличие адреса или начатого Send запрещает такое восстановление.

O отправляет task/context конкретному E; Kit сохраняет grant назначения. E выполняет task:start → работа → commit --task → result O. При нехватке данных спрашивает O, при блокировке ведёт коррелированный диалог до decision; после yield заканчивает ход. Обычное ожидание не запускает модельный polling. Канонические правила — role-protocol.mjs, версия 6.

O проверяет result/diff/proof и принимает точный source_commit либо открывает revision_request новой попытки. Только затем выполняет integration:start/continue. Автоматического merge по READY в версии 1 нет; main DONE требует доказательства Git. Зависимая задача выдаётся после интеграций предшественников. Конфликт/check failure сохраняет операцию для исправления O без принудительного ours/theirs.

## Пауза и завершение

ExecutionControl хранит not-started/running/pausing/paused/complete, причину manual/escalation/unknown/restart и маршрут. Публикация не включает работу. Новый диалог при паузе запрещает назначения, входящие SDK-пробуждения и интеграции; уже принятый ход может безопасно сохранить outbox и закончить команды. Блокировка без активных команд может быть припаркована; Continue возобновляет актуальный scope без повторного задания.

Закрытие окна не останавливает backend и не отзывает допуск. Restart требует одного Continue. Stop панели останавливает отправки всего плана; поздние callbacks старого поколения не восстанавливают допуск. UNKNOWN не повторяется, а уточняется фактическими квитанциями и проверкой состояния.

Интегрированные E нового режима сохраняются до завершения сообщений и итоговой очистки. После обычных задач O поручает DOCS: её bootstrap может перекрываться с текстовым ответом O при чистом main и отсутствии команд; Kit сохраняет одного writer. После её интеграции O получает delivery-шаги и cleanup/итог. Итог может начаться до последних acceptance E, но complete требует все DONE, терминальные квитанции, cleanup DONE, чистый main и физический конец итогового O. `assignment:cleanup` проверяет INTEGRATED и transport proof; null/PENDING автоматически продолжается после квитанции/окончания команд. Пока идёт финализация, UI различает 3/3 интеграции и завершение плана, показывает причину и наблюдаемое время. После complete нет «Паузы», явно ожидается приёмка пользователя; restart сохраняет complete. [Измерения и оставшиеся ограничения](dialogue-timing.md).

Если код требует исправления во время delivery, plan:extend откладывает delivery, добавляет новый DOCS-раунд; сборка выполняется после него из нового sourceCommit. Уже завершённые delivery-записи сохраняются.

## Legacy и переход

Существующие sequential/parallel и orchestrated без dialogue_version=1 сохраняют прежний маршрут и доказательства. Их backend assignment-start, сигналы CLI, автоматическая интеграция готовых источников и прежняя семантика паузы не выдаются за новый O-authored протокол. Одна кнопка управления остаётся и у них.

Переход активного orchestrated 0.5.7 выполняет O отдельной штатной миграцией только в безопасной паузе; installer сохраняет старые коммиты, READY требует отчёта E по просьбе O, INTEGRATED не повторяется. [Условия и отказы](assignment-dialogue-reliability.md#переход-старого-плана). Обычная подготовка проекта обновляет Kit до 1.9.3 при допустимом состоянии, managed-файлы вручную не меняются.

## Интерфейс и удаление

Дерево показывает O и чаты обсуждения; задачи доступны из to-do plan с состоянием, попыткой, таймером и меткой parallel/sequential/main. Выбор E сохраняет слева карточку плана O. Sidebar различает bootstrap, SDK, ожидание задачи O, работу, вопрос, result/review, доработку и интеграцию. Панель показывает авторов/адресатов, корреляции, разные receipt и причины ожидания. Native/HTTP используют один контракт.

Отдельный архив активного O запрещён ORCHESTRATOR_ACTIVE. Архив всего проекта проверяет свежие project/scope/execution: complete со всеми DONE не требует остановки даже при ACTIVE scope. Возврат такого проекта не возобновляет grant. Running/paused/finalizing и неподтверждённое состояние требуют подтверждения stopExecution; после возврата незавершённого выполнения нужен Continue. Подтверждённое удаление незавершённого проекта прекращает только его операции и удаляет собственные пути/ссылки; «Убрать из списка» сохраняет папки. Dirty/UNKNOWN не требуют сначала завершить невыполнимый план. [Жизненный цикл](project-lifecycle.md).

## Проверки

Реальные Kit/Git, HTTP Start, Python MCP, staged SDK и Control проходят автоматические fixtures с двумя и пятью E, без пользовательских bubbles на каждом SDK-ходе. Скрытый Electron проверяет фоновый bootstrap/observer/composer без select/show. Legacy assertions сохранены отдельными случаями. [Матрица восстановления](assignment-dialogue-reliability.md#проверки-и-граница-доказательств).

Test_02 0.5.7 — FAIL нового целевого workflow; A–D 0.5.22 — NOT_RUN. Host confirmations не обходятся. Native Windows/Linux и живые ChatGPT-панели подтверждает пользователь, автоматические fixtures их не принимают.


Старт всех новых локальных сессий — [единый канал панели](orchestrator-startup.md), независимо от стратегии и состояния плана. DOM содержит только приглашение; ролевые правила E тоже читаются через MCP. Старый генератор вложений отключён. Получение пакета не назначает O и не разрешает выполнение задач.
