# Оркестрованное выполнение плана

С 0.4.0 новая сессия проекта без активного плана — оркестратор: обсуждает задачу, сохраняет спецификацию, публикует план оркестратора и ведёт его до выпуска. Микрозадачи выполняют отдельные исполнители в своих worktree; запуск и паузу задаёт одна кнопка пользователя. Контракт плана, назначений и сигналов в Kit — [план оркестратора](../../packages/workflow-kit/docs/modules/orchestrated-plans.md); координация — [workflow execution](workflow-execution.md); интерфейс — [Desktop](desktop.md); живая приёмка — [сценарий](../acceptance/orchestrated-execution.md).

## Роли сессий

| Роль | Когда | Что делает | Контекст |
| --- | --- | --- | --- |
| Оркестратор | Новая сессия без активного плана | Обсуждение, спецификация, план `orchestrated`, метки и context_pack задач, Review, интеграции, ответы на блокировки, эскалация, итоговая проверка main, delivery и очистка, ответ пользователю | Полный recovery с блоком роли |
| Исполнитель | Приложение выдаёт задачу | Одна задача в своём worktree: task:start → работа → commit --task; при невозможности — task:block | Служебная часть Kit, задача и её context_pack |
| Чат обсуждения | Новая сессия при активном плане; прежние сессии после публикации плана оркестратора | Обсуждение параллельно с выполнением; план не меняет; документы — только по просьбе пользователя в `.workflow-temp/` вне Git | Полный recovery с блоком роли |

- Роль назначает Control по состоянию Kit (`newSessionRole`). Сессия без плана — кандидат; после публикации кандидат из `execution_origin_session_id` получает scope плана, прочие кандидаты и сессии без роли становятся чатами обсуждения, оркестраторы прежних планов не меняются. Несовпадение — «Требует внимания» и команда меню «Назначить оркестратором».
- Рядом с legacy-планом новая сессия роли не получает и работает по прежним правилам. Внешняя сессия плагина ChatGPT в ролях не участвует.
- Роль хранится дополнительными полями хранилища сессий v6 (`role`, `orchestratorScopeId`, `closedPlanCommit`); старое приложение читает файл. Recovery запрашивается с `--role`, кеш контекста разделён по ролям.
- Оркестратора активного плана отдельно архивировать нельзя (`ORCHESTRATOR_ACTIVE`). Проект с активным планом архивируется только после подтверждения пользователя: без него backend отвечает `PLAN_ACTIVE`, боковая панель спрашивает и повторяет команду с `stopExecution`. Подтверждённый архив сразу ставит выполнение на паузу (без ожидания исполнителей); план, назначения и worktree в Kit не меняются. После возврата из архива план на паузе и продолжается кнопкой. Архивный проект удаляется с диска вместе с worktree исполнителей.

## План и волны

- Метки: `parallel_safe: true` — параллельная задача, `false` — последовательная. Обе выполняют исполнители в worktree, слияние в main проверяет Kit. Последовательная задача стартует после интеграции всего предыдущего и работает одна; параллельные — до «Максимум одновременно работающих исполнителей» без пересечения путей.
- DOCS добавляется всегда; при `release: true` после неё идёт `delivery_tail` проекта. Delivery-задачи выполняет оркестратор в main после всех остальных задач.
- Контекст исполнителя задаёт оркестратор через `context_pack` задачи; Kit документы исполнителю не подбирает.
- Исполнитель всегда работает в режиме Chat, независимо от режима оркестратора (Chat или Work).
- Исполнитель, в чат которого ни разу ничего не отправлялось (нет адреса чата, начатой отправки и ручного старта), при восстановлении открывается заново в Chat с новым черновиком и получает задачу по кнопке плана. Исполнитель с адресом чата или начатой отправкой автоматически не переотправляется (`EXECUTOR_CHAT_UNKNOWN`).

## Кнопка и выполнение

`ExecutionControl` хранит по проекту и плану: не начат → выполняется → пауза запрошена → пауза → выполняется … → выполнен; причина паузы — manual, escalation или unknown. Публикация выполнение не запускает. Состояние переживает перезапуск backend; очищается с проектом. В новой схеме нет AutoPlan: прежний переключатель на план оркестратора не действует (`PLAN_EXECUTION_BUTTON`), а первое сообщение исполнителя (контекст задачи) и его продолжения разрешает только кнопка — в состояниях «выполняется» и «пауза запрошена». Смена состояния кнопки сразу применяется к живым исполнителям.

- `ParallelExecution` выдаёт задачи только в состоянии «выполняется». В паузе работающие исполнители получают свои продолжения, готовые результаты вливаются; пауза наступает, когда исполнителей и интеграций нет.
- После проверенного слияния Kit удаляет worktree и ветку, а страница исполнителя закрывается; чат открывается из to-do plan.
- Когда обычные задачи готовы, оркестратор получает итоговое поручение: завершить последние интеграции и проверить main. Затем приложение по одной передаёт ему delivery-задачи, пауза срабатывает между ними, и в конце — поручение `assignment:cleanup` и итогового ответа. Ответ на него завершает план.
- Исправляющая задача, добавленная после итогового поручения, открывает новый раунд: поручение повторяется после её интеграции.

## Сбои

1. Исполнитель исправляет сбой сам.
2. Не может — `task:block`: оркестратор один раз получает задачу, причину и сессию исполнителя.
3. Оркестратор отвечает `assignment:message` (сообщение доходит до исполнителя один раз), разрешает конфликт интеграции или добавляет исправляющую задачу через plan:extend.
4. Не может — `plan:escalate`: выполнение встаёт на паузу, оркестратор описывает проблему пользователю.

Исход UNKNOWN отправки, назначения, слияния или команды записи сразу ставит паузу без повторов. Сбой delivery по причине в коде исправляется задачей перед повтором сборки: plan:extend откладывает начатую delivery-задачу, Kit добавляет следующий раунд DOCS, затем сборка повторяется из нового коммита.

## Интерфейс

Дерево проекта показывает оркестраторов (состояние, счётчик, назначения в ожидании очистки) и чаты обсуждения; группа «Исполнители» остаётся для legacy parallel-планов. To-do plan в карточке плана: ✓/●/○, метка (→, ∥, main), состояние и таймер; начатая или завершённая задача открывает сессию исполнителя, delivery — оркестратора; не начатая не кликабельна. Выбор задачи меняет только диалог справа: слева остаются дерево и карточка плана с выделенной строкой выбранной задачи, отдельной карточки исполнителя нет; клик по оркестратору в дереве возвращает его диалог. Для выполненного плана to-do plan читается из коммита закрытия. Кнопка «Начать выполнение плана» / «Пауза» / «Продолжить» — в шапке плана, тот же интерфейс в веб-клиенте iPad при праве управления.

## Проверка

`tests/orchestrated-execution.test.mjs` проводит план через настоящий Kit CLI и Git, очередь Control и кнопку: волны, лимит, блокировку с ответом, паузу с доработкой, DOCS в worktree с закреплением спецификации, итоговое поручение, эскалацию, delivery и очистку до одного main. Отдельно: `parallel-execution.test.mjs` (волны, пауза, delivery, сигналы, UNKNOWN), `execution-control.test.mjs` (исполнитель следует кнопке, а не AutoPlan), `workspace-session.test.mjs` (исполнитель в Chat), `session-roles.test.mjs`, `sidebar.test.mjs` (to-do plan остаётся при выбранном исполнителе, возврат к оркестратору), Kit-fixtures. Живые чаты ChatGPT в fixtures не участвуют.

## Ограничения

- Задача с npm-проверками готовит `node_modules` в своём worktree (около 410 МБ) до удаления worktree.
- Обновление Kit проекта до 1.8.0 выполняет подготовка проекта в приложении; `delivery_tail` задаётся через config:apply после неё.
- Тест файлового наблюдателя F04 изредка превышает 5 с под полной нагрузкой suite.
