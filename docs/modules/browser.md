# Browser — страницы backend и их представление

## Ответственность и поведение

`src/execution/browser/` владеет техническими страницами, навигацией, первым открытием, observer/IPC, состоянием документа, отправкой текста и вложений. Здесь же DOM-селекторы, pageScript, цвета, прокрутка, фильтр инструментов и изменение заголовка. Привязка проекта к чату, подготовка recovery, решение о повторе, таймер работы агента и выполнение плана остаются вне браузера.

С 0.2.0 страницы живут в backend ([Backend](backend.md)). `BackendBrowserHost` (`src/execution/browser/backend-host.mjs`) владеет страницами и popups (режим выбирается при старте службы: во всех выпусках — WebContentsView в скрытых окнах-хостах, которые [встроенное окно](native-window.md) показывает без перезагрузки, кадры для зрителей через CDP; скрытые offscreen-окна — флаг разработки для будущей службы без экрана), partition, observer, ожиданиями и cleanup. Зрители только наблюдают страницу по ключу: подключение, отключение и ноль зрителей не меняют срок жизни страницы, не вызывают release/dispose/recovery reset/cancel и не останавливают observer или выполнение плана. Crash renderer отличается от detach и отмечается отдельно. В backend (`BrowserSessions` с `recoverCrashed`) страница, чей renderer погиб (crashed, внешний kill, OOM), через 1 с перезагружается по своему адресу, не более 3 раз за 10 минут; событие `crashed` несёт reason, exitCode и `recovering`. Перезагрузка восстанавливает только страницу: прерванный Send остаётся UNKNOWN, ничего не вводится и не отправляется повторно; готовность, подтверждённая до сбоя, возвращается после загрузки, и уведомление о сбое исчезает. После исчерпания попыток страница остаётся закрытой с прежним сообщением. Прежний `DesktopBrowserHost` (`src/frontend/desktop/browser-host.mjs`, WebContentsView в окне) используется только in-process smoke-стендом разработки.

`src/control/sessions/service.mjs` координирует логические сессии. Это координатор ContextSession/ConversationRecovery: он получает порт через ExecutionFacade и не имеет доступа к WebContents, изменяемому источнику наблюдений или карте браузерных записей. Открытие прежнего чата не отправляет recovery повторно. Скрытие страницы не останавливает её работу и не меняет рабочую папку фоновой сессии.

Обычный выбор сессии или задачи сначала ищет её живой backend record. При сохранённой identity он показывается без навигации, повторной readiness и cancel, включая sending/busy и временный `/c/local-chatgpt…` до chatUrl. Наблюдение продолжает сохранять постоянный адрес исходного назначения. После restart/crash отсутствие известного адреса не разрешает новый Send: показывается неизвестный исход. Явная перезагрузка остаётся отдельной операцией. Изолированный Electron проверяет настоящий обработчик выбора между отправкой и постоянным URL, повторные переключения и сохранение одной отправки для O Chat/Work и Chat-исполнителей.

Для нового диалога readiness bootstrap E повторяется ограниченно до Send при позднем editor, без select/show/focus. Composer предоставляет read-only observeSnapshot; документ/seq и физическая занятость сопоставляются с read/yield текущего SDK-хода. Два свежих спокойных наблюдения не требуют новой user revision. Эта сверка не отправляет DOM-сообщений и не отменяет UNKNOWN. [Транспорт](assignment-dialogue-reliability.md#sdk-fifo-и-конец-хода).

## Контракт и порядок вызовов

Backend создаёт `BackendBrowserHost` и один раз вызывает `ExecutionFacade.attachBrowser({host, ipc})` (smoke-стенд — с `DesktopBrowserHost`). `openBrowserSession(id)` возвращает тот же порт для живого ID; после release новый вызов создаёт новую страницу. ID формируется координатором из workspace/session/assignment/task, но Execution не интерпретирует эти поля и не принимает stores или планы.

Порт предоставляет:

- `snapshot()` — отдельный объект `{id, loading, epoch, disposed, url, inFlight}`;
- `pageState.current/version`, `subscribe(listener)` и `waitForChange(version, options)` — копии сериализуемых наблюдений, без доступа к `accept/reset/listeners`;
- `composer.getURL/hasFilled/inspect/deliver/sendUserMessage/clearNewSessionDraft` и readonly `inFlight` — операции прежнего composer без ссылки на Chromium;
- `navigate(url, {reload, startup, isCurrent})` — навигацию с защитой от позднего результата; `startup` сохраняет существующую диагностику первого документа;
- `subscribe(listener)` — сериализуемые события navigation-start/loaded/navigated/error/crashed со snapshot и ошибкой `{code,message}`; возвращает отписку;
- `setDiagnostic(listener)` — прежние метаданные composer без текста сообщения; `release()` — адресное завершение страницы.

Callbacks `canContinue/onBeforeFill/onBeforeSend` являются локальными операциями допуска и сохранения checkpoint; они не входят в snapshots/события. После начала Send неопределённый исход не разрешает второй клик. Composer вставляет текст один раз для данного request/document. Ограниченное ожидание вложений сохранено, но стартовый ContextSession всегда передаёт пустой массив файлов.

Явный `retryAttachments` до Send заменяет только pending/failed-карточки собственной попытки: проверяются request, полный payload, документ, ссылка на точную карточку и неизменённый черновик. После единственного удаления и подтверждения исчезновения повтор получает уникальное транспортное имя с прежним расширением и неизменным UTF-8 содержимым. Только для этого собственного имени разрешён числовой суффикс дубликата ChatGPT. Совпадения канонизируются по кнопке удаления; несколько разных карточек остаются неоднозначностью. Готовые части сохраняются, появление каждой повторной карточки ожидается до замены следующей. Доверенные ручные файловые paste/drop/change и удаление отзывают автоматическое владение. Утрата владения, правка черновика, навигация или UNKNOWN запрещают замену и Send. `ATTACHMENTS_CHANGED` предлагает новую сессию; `ATTACHMENT_REMOVE_PENDING` означает неподтверждённое удаление. Автоматического повторного клика после неопределённого результата нет.

`onUploadProgress` сообщает только число готовых/всех частей. Composer пишет состояния missing/ambiguous/failed/pending/ready, индексы и способ сопоставления без текста и имён файлов. Каждые 15 с ожидания — elapsed/unchanged. Краткий remount карточки допускается до 750 мс; дальнейшее отсутствие завершает ожидание ошибкой. Send разрешён один раз после готовности всех частей. Composer/context fixtures проверяют позднее переименование, замену DOM-карточки, асинхронный повтор нескольких частей, сохранность готовых, ручное вмешательство, чужие/неоднозначные карточки и UNKNOWN.

`attachment-diagnostics.mjs` наблюдает CDP Network без дополнительных запросов. В chromium-events.jsonl источник `attachments` различает create (POST files), upload (PUT oaiusercontent) и processing (POST files/id). Пишет requestId, статус, stream, количество порций/байтов, elapsed/idle, finished/failed/canceled. URL, заголовки и тела в эти записи не попадают. Проверка каждые 15 с отмечает 30 с без наблюдаемого прогресса, повторяет не чаще 30 с, фиксирует resumed при новых данных. Это не доказательство зависания сервера. Не более 256 запросов, срок наблюдения 10 минут; навигация, detach, renderer-gone и закрытие очищают реестр/таймер. Очередной документ/поток событий возобновляет наблюдение. Fixture проверяет границы памяти, stall/resume, завершение/отмену, очистку и реальную доставку CDP-метаданных в журнал. Первоначальная причина живого зависания остаётся неизвестной; переименование живого retry пока гипотеза, подтверждённая только изолированным воспроизведением.

Host создаёт страницу по ID и закрывает её только по запросу Execution. Координатор получает лишь `show(id)/hide()` — выбор страницы, которую показывают клиенты; представление доступно backend через `host.view(id)`, но не через запись сессии. Окно клиента и его декорации принадлежат `src/frontend/desktop/client.mjs`.

Перед release координатор отменяет ContextSession и завершает учёт времени. Execution помечает страницу закрытой, отменяет ожидания PageStateSource, снимает observer/IPC и lifecycle-подписки, закрывает своё представление. Запоздалый результат не оживляет страницу; повторный release старого порта не закрывает новый с тем же ID. `SESSION_RUNTIME_RELEASED` означает использование закрытого порта; crash и ошибки observer отменяют продуктовую операцию через события.

## Представление страницы клиенту

ChatGPT загружается только в backend; интерфейс ChatGPT не реконструируется. Транспорт выбран в T001 и подтверждён пользователем: Electron offscreen → PNG-кадры через аутентифицированный loopback API → отдельный клиент; ввод адресуется странице через Chromium DevTools Protocol (`src/execution/browser/presentation/{host,input,transport}.mjs`, клиент — `src/frontend/client/browser-view.mjs`). Собственного видеокодека и стороннего display server нет; Xpra (нет seamless-сервера на macOS) и noVNC (нужен VNC-сервер всего рабочего стола) отклонены.

Плотность кадра выбирается автоматически при создании страницы: максимальный `scaleFactor` дисплеев (`offscreen.deviceScaleFactor`), логический viewport не меняется. Кадр несёт `{browserSessionId, documentGeneration, frameSequence, logicalWidth/Height, pixelWidth/Height, scale}`; координаты клиента переводятся в логические CSS-пиксели (`clientPointToBrowser`), а не по размеру PNG. Пользователь подтвердил одинаковую чёткость текста кадра и UI клиента на Retina 2x. Удалённое устройство запрашивает `format=jpeg&quality&maxScale`: кадр уменьшается до нужной плотности и кодируется JPEG (меньше PNG); окно Mac по-прежнему получает PNG. Для удалённого устройства viewer принадлежит ему, а ввод требует, чтобы держателем lease было оно ([удалённый доступ](remote-access.md)).

| Маршрут `/v1/browser/*` | Контракт |
| --- | --- |
| `GET pages` | Страницы и popups backend, выбранная страница |
| `POST viewers`, `DELETE viewers/<id>` | Подключение/отключение зрителя; отключение отпускает зажатый им ввод |
| `GET frame?viewer&after` | PNG с заголовком `x-browser-frame`; ожидание нового кадра до 1 с, иначе 204 |
| `POST input` | `{viewerId, input}`: pointer/wheel/key/text/composition с browserSessionId, documentGeneration, sequence, leaseGeneration |
| `POST viewport` | Размер 320–4096 задаёт только управляющий клиент; наблюдатели масштабируют кадры |
| `POST clipboard/selection`, `POST clipboard/paste` | Выделение страницы (фиксированный скрипт в изолированном мире) и вставка текста до 60 КБ по явному действию |
| `transfers`, `transfers/<id>`, `transfers/<id>/attach`, `choosers/cancel` | Загрузка файла клиента частями и прикрепление к перехваченному выбору; скачивание |
| `POST drop` | `{viewerId, transferIds, x, y, leaseGeneration}`: 1–10 полностью переданных файлов сбрасываются в точку страницы |

Ввод другого документа отвергается `BROWSER_DOCUMENT_CHANGED`, повтор или старый sequence — `BROWSER_INPUT_REPLAY`, старый lease — `BACKEND_LEASE_STALE`; поздний ввод никогда не попадает на другую страницу. При разрыве, отключении зрителя или смене lease зажатые клавиши и кнопки отпускаются, ввод не переигрывается. Указатель, удержание, прокрутка, клавиатура, русский и составной ввод (`Input.imeSetComposition`), меню и выделение проходят через CDP без фокусировки окна ОС.

Выбор файла страницы перехватывается (`Page.setInterceptFileChooserDialog`) с момента создания страницы, нативный диалог в backend не открывается. Клиент получает событие `file-chooser`, показывает диалог своего устройства, передаёт файл до 32 МБ по transferId и прикрепляет его после полной передачи; устаревший выбор — `BROWSER_CHOOSER_STALE`. Перетаскивание и вставка файла клиента: файлы до 32 МБ передаются теми же transfers, затем `POST drop` проверяет lease и полноту каждой передачи (`BACKEND_TRANSFER_INCOMPLETE`, неизвестная — `BACKEND_TRANSFER_NOT_FOUND`, неверные параметры — `BROWSER_PRESENTATION_INVALID`) и выполняет CDP `Input.dispatchDragEvent` (dragEnter, dragOver, drop) с путями файлов; страница видит обычный drop. Скачивание сохраняется во временный приватный каталог backend, клиент получает `download-ready` и сохраняет файл через свой диалог. Popups и авторизация — скрытые окна backend (только https/about:blank), клиент показывает их отдельным окном просмотра; видимое серверное окно не нужно. Branch/Delete/Retry передаются странице без новой политики.

Новый Chat запускается отдельной одноразовой навигацией с bootstrapToken через `startChat`; composer не заполняет редактор и не вызывает Send. Полный контекст идёт через [панель](orchestrator-startup.md). Общие методы текста/вложений и внешние DOM-экспорты сохранены, но старт не использует их. Последующий рабочий диалог — SDK без запасного DOM Send. Observer по-прежнему сообщает вход, режим, busy и draft.

## Ресурсы и совместимость

Chromium sessionData находится в Workflow Pilot/browser, partition persist:workflow-pilot-chatgpt. Smoke использует временный профиль и непостоянный partition; donor cookies и внешние профили не импортируются.

Observer генерируется `stage:page-observer` из Execution/browser в `resources/chatgpt-page-observer-preload.cjs`, перед запуском/проверкой. Dev и packaged preload-пути сохранены. Проверка установленного пакета извлекает реализации из нового каталога. Старые внутренние browser/page-state мосты удалены. Корневые `chatgpt-dom.mjs`, `chatgpt-composer.mjs`, `chatgpt-experience.mjs` остаются публичными re-export входами Sidebar с прежними именами и pageScript; второй реализации в них нет. Сам Sidebar не меняется.

DOM-адаптер `account()` возвращает `login` и `loginEvidence`: фиксированную причину и булевы признаки профиля, входа, личной истории/проекта и редактора. `normalizePageObservation` отбрасывает посторонние поля доказательства. Селекторы и доступные имена профиля проверяются только вне сообщений; запасное подтверждение требует редактор и обе категории личной навигации. Наблюдение aria-label/aria-labelledby/title/href/role позволяет распознавать позднее появление признаков без polling. Вызовы account API и чтение токенов для проверки входа не используются.

Диагностика первого запуска сохраняет отдельные события `account-observation`, `startup-state`, `account-check`, `page-observer-error`. Последние состояния включаются в отчёт независимо от окна последних событий, с временными метками. Переход на новый документ сбрасывает последнее доказательство аккаунта. Передаются только допустимые причины, булевы признаки и поколение; исходные имена, тексты, атрибуты и личные URL в новые записи не копируются. Проверку неизвестного входа пользователь может повторить без навигации; UI-контракт описан в [первом запуске](first-run-onboarding.md).

## Проверка

`npm test`: `browser-presentation` (Electron e2e на fixture-странице: меню, русский и составной ввод, выделение, clipboard, файлы, drop двух файлов, popup, поколения и lease), `backend-browser-lifecycle` (detach, reconnect без reload, продолжение плана при нуле зрителей, crash), `backend-browser-prototype` (протокол T001: отдельный процесс клиента, Retina-плотность); точная принадлежность скрытых сессий, копии событий, освобождение подписок/ожиданий, поздняя навигация, crash, полный контекст once и UNKNOWN no-retry через ExecutionFacade. `npm run smoke`: скрытый Electron fixture проходит пользовательские IPC/renderer-входы и проверяет настоящий sandbox preload, вложения и Chat/Work. `npm run check:architecture` запрещает импорт внутренних браузерных/desktop-модулей координатором и импорт продуктового слоя из Execution. Живой ChatGPT, меню ответов, физическую клавиатуру/IME и настоящую авторизацию проверяет пользователь. Изменение состава мониторов после создания страницы плотность кадра не пересчитывает (отложено).

[Контракт URL-start](chat-only-startup.md) определяет единый порт навигации (URL/mainFrame/redirect/sequence/incarnation/epoch), прекращение владельца и post-navigation proof. Refresh/recovery, включая native shortcuts, никогда не повторяют адрес с q: текущий и целевой URL заменяются чистым корнем. Это Execution-инвариант без доступа к attempt/store. SafeUrl исключает значения query из диагностики.
