# Плагин Workflow Pilot 0.5.6 — приёмка

**S1–S3 — NOT_RUN.** Главный сценарий выпуска — [автоматическое подключение и диалог](automatic-agent-dialogue-acceptance.md). Технические проверки, сборка и установка не подтверждают автономность реального ChatGPT.

## Среда и версии

Встроенный Workflow Pilot: приложение/backend 0.5.6, Kit 1.8.2, панель `0.5.6-communication-2`, протокол 2. Installer может оставить pending; пользователь штатно останавливает старую службу, завершает установку и открывает новую копию по [контракту поставки](release.md). Обновить существующее подключение MCP штатным действием хоста, проверить свежий каталог и видимый build. Нового туннеля не требуется.

Опыт проходит в новом изолированном workspace, созданном подготовщиком S1–S3. Новые разговоры: O в Chat либо Work, исполнители в Chat; второй режим O — отдельный опыт. Вход и общая настройка MCP выполнены заранее. Индивидуальное подключение каждого исполнителя не является допустимой подготовкой. Пользователь запускает опыт и передаёт отчёт; разработка автоматически модели не запускает.

## Проверка перехода на новую панель

После запуска службы 0.5.6 обновить инструменты существующего подключения и попросить O выполнить новый `workflow_pilot_panel {}`. Сохранённый старый результат не использовать как доказательство обновления. Ожидаются `0.5.6-communication-2`, протокол 2, подключённый SDK и подтверждённая привязка без ввода ID/Enable. Записать версии, время вызова и диагностику до дальнейших действий. Если осталась старая панель, зафиксировать это как FAIL перехода; историю и профиль не очищать.

Это восстановление существующего разговора. Проверка автоматического bootstrap нового O выполняется отдельно: панель должен открыть сам агент из первоначального контекста, без дополнительного поручения пользователя. Успех ручного восстановления не засчитывает этот пункт.

Fixtures проверяют настоящий HTML/SDK/Python MCP, реестр O+5E и полный Kit/Git-путь двух параллельных E, блокировки, третьей задачи и DOCS для O Chat/Work. Физический хост и действия модели симулируются. Внешний SDK должен подтвердить свои capabilities/metadata и адресацию; target:active не атомарен с verify. Разрешения хоста не обходить. Ручное открытие панели E или подтверждение в каждом новом чате означает FAIL S1, даже если последующий обмен успешен.

## Предшествующие наблюдения

На установленном 0.5.5 пользователь увидел панель `0.5.2-communication-1` с отказом совместимости. Проверенные bundle/runtime и свежий MCP отдавали HTML 0.5.5; O зарегистрирован, привязки панели нет. Адрес ресурса оставался общим для выпусков. Это отказ до S1, не результат S1–S3; точное хранилище старой копии не установлено. Исправление 0.5.6 проверено изолированным кэшем, живая проверка перехода ожидается.

Пользователь подтвердил обмен прежней пары O/E, в том числе при свёрнутом Chrome, а позднее сообщил о завершении обмена при закрытом интерфейсе Workflow Pilot и живых службах. Build заключительного опыта отдельно не снят. Ранее повторное открытие Chrome давало пустую панель; на 0.5.3 диагностика показывала подключённый SDK и несовместимость. Эти сведения не подтверждают автоматическое подключение новых исполнителей или восстановление любого уничтоженного iframe. История подробных опытов — в Git и пользовательских отчётах.

## Возврат результата

Заполнить REPORT.md подготовщика: PASS/FAIL/NOT_RUN каждого сценария, фактические версии/sourceCommit, project/scope, роли/назначения, все ручные действия, времена, коммиты и интеграции, очищенный JSONL с фиксированным through_seq и gaps. Accepted, read, решение и выполненная задача — разные доказательства. Не включать приглашения, raw metadata, cookies, токены или bridge descriptor.

После отчёта пользователь принимает результат либо поручает plan:extend. План автоматически не архивируется. Codex, Chrome, сон компьютера и остановленная служба не подменяют приёмку встроенного Chat/Work.
