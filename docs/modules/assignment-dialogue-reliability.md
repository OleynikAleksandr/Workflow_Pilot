# Надёжность рабочего диалога

Дополнение [контракта O/E](assignment-dialogue.md) для Workflow Pilot 0.5.38 / Kit 1.10.3. Версия рабочего диалога 1 отделена от протокола панели 6 и версии ролей 12. Legacy sequential/parallel и прежний orchestrated сохраняют семантику Kit, но рабочая доставка также идёт только SDK. Ручной протокол P0/P1 остаётся отдельным исследовательским API, не fallback рабочего плана.

## Источники состояния и восстановление операций

Kit хранит задачи, назначения, попытки, блокировки, result proof и acceptance. PluginCommunication WAL хранит авторский текст, выбранный контекст, intent и квитанции. UI показывает их проекцию. SessionRuntimes, ParallelExecution, DialogueDelivery и PluginCommunication сохраняют прежние границы; второго scheduler и отдельного плана диалога нет. IO выполняет Execution, frontend обращается к contracts/API.

Порядок изменяющего сообщения: durable intent с payload и единым operation_id → проверяемый идемпотентный эффект Kit → публикация сообщения в WAL → SDK-доставка. До публикации SDK не получает сообщение. Сбой между шагами продолжает тот же ID/receipt. Это журнал согласования двух владельцев, не обещание общей транзакции Git/WAL.

Фазы intent: draft/prepared/authorized/needs_confirmation/deferred/published/failed/retired. Авторизация связана с generation/boot/recipient/assignment/attempt/digest. Для новых [плановых пакетов](prepared-tasks.md) backend связывает согласованный до Review снимок и после Continue может авторизовать его заново по свежему допуску; старый поздний draft требует сверки O. Intent→Kit→WAL и единый operation/idempotency key закрывают разрыв между хранилищами. Временный lock/команда удерживает эффект, постоянный отказ остаётся failed, удаление — retired. Незавершённая подготовка/доставка удерживает complete, failed/retired не держат исправленный план навсегда. Опубликованное и UNKNOWN не отправляются повторно; read требует yield без выдуманных квитанций.

`assignment:dialogue` применяет эффект под блокировками main/назначения; `assignment:dialogue-status` читает состояние. Корреляция сигналов CLI и MCP исключает второй вопрос/ответ. Проверка источника, attempt, block_id, proof, SHA, роли и разрешённых путей не ослабляется ради recovery.

## Фоновые страницы и запуск

Путь готовности: Start → Kit assignment/worktree → page → URL-bootstrap → registration → mount/SDK/bind → подтверждённый документ/identity → разрешённый task O → E. Ни сессия, ни composer, ни регистрация не доказывают живую панель. Сохранённый авторизованный пакет отправляется по готовности без отдельного ready-хода O.

Для новых планов поручения всех обычных задач и DOCS готовы до Review/Start. После создания назначения backend механически связывает согласованные body/contexts с фактическими assignment/attempt; bootstrap E и binding идут независимо, публикация ждёт свежей готовности. Только существующий brief-only план уведомляет O о поздней подготовке. DOCS создаётся после проверенных интеграций без ожидания конца независимого текстового ответа O. Чистый main, отсутствие команд и свободный writer обязательны; Kit сверяет scope/revision/base под lock. WORKFLOW_LOCKED — ожидание той же операции, не разрешение удалить lock.

ContextSession повторяет только проверку/подготовку до Send при позднем editor: ограниченные попытки, актуальная identity и epoch, без select/show/focus. Sending/sent/unknown не повторяются. Stop, удаление и смена поколения отменяют дальнейшую подготовку; поздний callback не открывает новую работу. Настоящий скрытый Electron fixture проверяет два и пять исполнителей без посещения карточек.

Координатор ограниченно перечитывает снимок Kit/Git при замене плана во время commit/merge, включая промежуточное несовпадение DONE/proof. Активная parent/child operation.lock даёт WORKFLOW_LOCKED; стабильная порча без writer остаётся UNKNOWN. Свежие HEAD/revision/proof сверяются, неподтверждённое DONE не проецируется как выполненное.

Проверка принадлежности участника допускает до трёх новых чтений с паузой 50 мс при временно отсутствующем снимке, ENOENT или ошибке чтения плана/Kit. Старый успешный grant не кешируется как замена проверки; устойчивый отказ остаётся отказом. Kit-операции отдельно ограниченно перечитывают промежуточные ошибки проекции плана.

При generation-mismatch/lease-expired/sdk-unavailable/plan-paused status, progress и admission используют один предикат живой панели. Исторический handshake и running не удостоверяют SDK. Единственный recovery/listen использует epoch/abort/single-flight/backoff: поздний ответ не меняет новый binding, sync не выдаёт grant и не снимает ручную паузу. Binding/version/store/project removal дают точную терминальную причину, transient network — безопасные чтения с backoff. Ошибки не маскируются произвольным NETWORK_ERROR и не повторяют Send.

## SDK и отдельное завершение обработки

[Постоянный SDK](sdk-messaging.md) используется всеми ролями и типами рабочего сообщения. pending → claimed → accepted/rejected/unknown — транспортные факты. На адресате один незавершённый вызов; после accepted следующий pending доступен немедленно, даже если прежний не прочитан или агент занят. Разные адресаты независимы. Нет ожидания busy/idle, writable/canSend, черновика, lastRole, команды, read/yield или конца bootstrap ради SDK. Остаются свежие identity/document/assignment/attempt/grant, Stop, доступность панели и UNKNOWN.

Нажатие завершает решение пользователя после долговечной записи. `user-choice`/Review имеют собственный read, без task yield. Уведомление может прийти до плана или на паузе в пределах авторизации UI-события. Это не разрешение новой реализации. [Контракт выбора](user-choice.md#доставка).

SDK timeout — 90 с, claimed — 120 с, lease — 60 с, sync во время Promise — каждые 20 с. Сбой report/restart/remount/lease loss сохраняет UNKNOWN. Поздний accepted/rejected журналируется отдельно и не переписывает неизвестный исход. Фактический read уточняет чтение, но не разрешает повтор SDK и не стирает UNKNOWN.

Каждое сообщение хранит независимый handlingGate; старый member.deliveryGate читается совместимо без транспортного барьера. Read, коррелированный yield и свежий физический конец требуются для terminal receipt/cleanup/complete, а не для следующего входа. Read-only сверка ограничена 120 наблюдениями с интервалом 1 с и двумя спокойными наблюдениями не менее чем через 500 мс; истечение срока не создаёт квитанцию.

Один ход может прочитать несколько входов, в том числе pending без отдельного уведомления. Для каждого сохраняются собственные read/yield/окончание; фиктивный accepted не записывается. Уже прочитанный вход не посылается повторно. Старое UNKNOWN остаётся неизвестным даже после read. Устаревшее недоставленное сообщение снимается, но уже начатая отправка не получает выдуманной квитанции. Модель не опрашивает очередь в цикле.

## Терминальные квитанции и очистка

После INTEGRATED последняя acceptance должна получить read/yield/reply_observed E. Backend вызывает внутреннюю `assignment:transport` с точными message_id/attempt/source_commit; Kit проверяет текущий scope/допуск, родительскую acceptance и отсутствие активных команд. Агент не вызывает эту операцию и не формирует доказательства наблюдения.

`assignment:cleanup` без transport proof возвращает PENDING / terminal-receipt-pending, при активной команде — executor-command-active. Удаление не происходит; backend повторяет согласование и автоматически продолжает ранее запрошенную очистку. Повтор ack идемпотентен. Успешная cleanup хранит commands_idle=true. Нет цикла, в котором конец E ожидает удаления, а удаление ожидает его несуществующей страницы.

Уже очищенный worktree не разрешает новые вызовы E. Узкий terminalTarget обслуживает только прежнюю acceptance с read/yield: сверяет identity сохранённой сессии, родителя O, scope/task/assignment, INTEGRATED, cleanup DONE/commands_idle, точные message/attempt/source_commit. Физический конец всё равно требует актуального документа и свежего idle. Отсутствие доказательства не превращается в observed или complete. Одинаковые denied дедуплицируются ограниченным буфером.

После обязательных интеграций/delivery итоговое поручение O может перекрываться с последними acceptance E. Оно содержит актуальные SHA/proof/cleanup; смена состава или результата плана отменяет прежнее итоговое доказательство, UNKNOWN не повторяется. O пропускает cleanup только при явном DONE всех назначений; null/PENDING требует штатной команды. Сам transport_closed не доказывает очистку. Неизменившиеся проверки точного SHA повторно не запускаются без причины.

Complete по-прежнему требует channelSettled, INTEGRATED/cleanup DONE всех назначений, чистого подтверждённого main, отсутствия команд и физического конца итогового O. Delivery с побочными эффектами сохраняет барьеры. Повтор/restart не возвращает complete в paused. До complete UI показывает интеграции и текущую стадию; после — приёмку пользователя без «Паузы». O читает доказательства из родительских записей после удаления worktree. Архив проекта при свежем complete не требует остановки и не означает приёмку scope.

## Пауза, restart и удаление

Start/Continue разрешает scope и его generation. Backend зеркалирует разрешение в Kit с идентичностью собственного процесса; Kit проверяет его перед новыми назначениями, task:start/dispatch, resume/revision и integration. UI-флаг не заменяет этот допуск. При сбое выдачи grant выполняется компенсация; startup отзывает прежнее разрешение.

В версии диалога 1 пауза запрещает новые назначения, пробуждения и интеграции. Уже принятый хостом ход не отменяется; агент может сохранить вопрос/result в outbox и закончить команды. Пауза не требует ждать бизнес-ответа на уже сохранённую блокировку. Continue восстанавливает актуальное поколение и очередь без повторного задания. Для legacy остаётся прежняя семантика паузы.

Закрытие клиентского окна не отзывает grant, не уничтожает backend-страницы и не останавливает службу. Restart сохраняет назначения, черновики, текст, receipts и proof; незавершённая работа требует общего Continue, complete сохраняется. Плановая подготовка переавторизуется только по свежему разрешению, поздний draft — после сверки O. Отправленный URL-bootstrap и UNKNOWN не повторяются. Если хост уничтожил iframe, новый mount должен подтвердить SDK; DOM fallback не появляется.

Архив/«Убрать из списка»/удаление незавершённого проекта не требуют DONE или чистых worktree. Подтверждённое действие прекращает только собственные операции, отзывает разрешение, закрывает intent и сохраняет запрет позднего восстановления ссылки. При «Убрать из списка» папки сохраняются; удаление с диска проверяет пути и очищает собственные worktree. Соседи, donor, общий backend и чужие процессы не затрагиваются. [Полный контракт удаления](project-lifecycle.md).

## Переход старого плана

Новый scope автоматически получает dialogue_version=1; чтение/расширение существующего сохраняет прежнее значение (отсутствие — legacy). Обычный installer обновляет Kit только при допустимом состоянии. Активные назначения старого 0.5.7 требуют отдельного `workflow_assignment_migrate` от подтверждённого O после общей паузы.

Перед миграцией backend проверяет все назначения, физическую остановку агентов и команд, отсутствие незавершённой/UNKNOWN доставки. Dirty, busy, незавершённая операция или неизвестный исход дают предметный отказ, без сброса журнала и без обхода защиты. Удаление проекта остаётся доступным.

Миграция использует штатный installer и собственный журнал: закрепляет исходные HEAD/контракты → обновляет parent/child runtime → записывает новую версию диалога → подтверждает Git-квитанции → завершает. После прерывания продолжает тот же operation_id и сверяет сохранённые файлы/коммиты; новый параллельный переход запрещён. Только собственная доказанная оставшаяся блокировка миграции может восстанавливаться по журналу; чужие locks не удаляются. Нет ручной правки managed-runtime.

Старый checked source_commit сохраняется. Допускаются только подтверждённые служебные installer-коммиты поверх него, не произвольный новый код. Уже INTEGRATED задачи не исполняются снова. Для READY без отчёта backend сообщает O служебный факт; O просит E прислать result существующего коммита. Backend не придумывает отчёт E. После новой приёмки O выполняет integration или разрешённую доработку; Continue общий, без ID/Enable и повторного bootstrap. Test_02 и пользовательский профиль разработкой не меняются.

## Наблюдаемость

Панель O показывает все собственные назначения, E — только свой диалог: task/title/assignment/attempt, автора и адресата, корреляцию, состояния SDK и доставки, вопрос, ожидание O, проверку результата, доработку и интеграцию. Read-only preview текста не создаёт read-квитанцию. Persisted, SDK accepted, read, handled, физический конец, result, acceptance и INTEGRATED — разные факты.

Диагностика содержит build/protocol, URI текущего MCP snapshot, SDK, generation и очищенные наблюдения страницы. URI текущего каталога не выдаётся за доказательство того, какой старый iframe показывает хост. Панель имеет content-addressed HTML; старый ресурс не заменяется молча. [Обновление ресурса](chatgpt-plugin.md#ресурс-панели-и-обновление).

Экспорт фиксирует through_seq, страницу/границы и полноту; ошибка сохраняет предыдущий экспорт. O получает журнал своего run, E — разрешённую видимость своего назначения. frontend.gap описывает клиентскую телеметрию, diagnostic.gap — переполнение backend-буфера измерений; это не потеря серверных seq. Последние события уничтоженной панели могут отсутствовать. Enrollment tickets, bearer, raw host metadata, cookies и секреты не включаются в диагностику. [Точный контракт таймингов, быстрого пути и UI](dialogue-timing.md).

## Проверки и граница доказательств

Подготовленные task_brief/prepared_task проверяются на roundtrip, UTF-8/размер, неизменность байтов, author/project/scope и Review/semantic digest. Сквозной цикл выдаёт две согласованные задачи без нового O-хода, затем проходит DOCS/cleanup/complete. Старые brief-only планы сохраняют позднюю preparation_queue. SDK fixtures проводят STOPPED через isError/JSON-RPC; при утрате кода свежий status проверяет lease/generation, затем единственный sync. Pause/Stop, новый scope и complete не обходятся.

Автоматические suites используют реальные API Start, Control, Execution adapters, Kit CLI/Git, HTTP Python MCP, staged HTML и SDK; физический ChatGPT, модель и lifecycle-команды заменены на обозначенной границе. Нет рабочих профилей или новых модельных команд.

| Проверка | Покрытие |
| --- | --- |
| automatic-agent-dialogue | Два и пять одновременно адресуемых E, O-selected task/context, result/acceptance/integration, зависимая задача, DOCS/cleanup; SDK без новых user bubbles |
| preparation/finalization regression | Авторизация до binding без лишнего ready-хода, inline/ref, медленный сосед, DOCS при ответе O, итог до terminal E, cleanup null/PENDING/DONE и полный complete |
| conversation fixture | context_request до task:start, question → clarification → facts → decision по одному block_id, безопасный ремонт, revision и новая приёмка |
| executor-background-startup / Electron | Настоящие скрытые страницы, composer/observer, 2/5 E без select/show, поздний editor, Stop и отсутствие повторного Send |
| workflow-channel / plugin / store | SDK без busy/read/yield барьеров, отдельные terminal receipts, intent/Kit/WAL/receipt fault injection, дубли, UNKNOWN, identity, чужой адрес, удаление |
| Kit fixtures | Проверки source/attempt/acceptance, запреты main/чужих путей, dirty/transaction, конфликты/check failure, последовательные merge, DOCS и доказательства Git |
| dialogue-migration / upgrade | Неизменяемый выпущенный Kit 1.8.2, пять точек прерывания, повтор worker/installer, сохранение готового SHA, revision и integrated без повторной работы |

Полный контроль Kit состоит из kit-check и kit-assignments. Для изменений выбираются затронутые suites и сквозной сценарий; уже успешные проверки неизменённой части не повторяются без причины. При полном контроле доступны unit-all, architecture, electron-smoke, executor-channel, chatgpt-plugin, release-tooling и kit-upgrade. Проверки фактических релизных пакетов обязательны. Неизменяемый Kit 1.9.2 из v0.5.11 обновляется до 1.9.3 с сохранением начатой задачи/сигналов; незавершённые назначения/интеграции запрещают обычный update. Старые upgrade fixtures сохраняются. Windows/Linux на Mac проверяются адаптерами и составом пакетов, не native-запуском. Review/fixtures не являются PASS живого ChatGPT. [A–D](automatic-agent-dialogue-acceptance.md) принимает пользователь отдельно.
