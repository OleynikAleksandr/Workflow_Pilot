# Стартовый контекст оркестратора

Контракт Workflow Pilot 0.5.21: протокол панели 4, build `0.5.21-communication-4`, Kit 1.9.3 без изменения ролей. Полный recovery O передаётся через MCP без загрузки файлов ChatGPT. Это смена транспорта, не доказанное исправление внешней обработки вложений. Путь E, Review, legacy и начатые SDK-попытки сохраняются.

## Последовательность и границы

1. ContextSession проверяет recovery workspace и сохраняет полный пакет с identity, ролью, scope, состоянием плана и обязательными инструкциями до DOM Send. Попытка имеет requestId и contextTransport=panel. DialogueDelivery резервирует приглашение точной локальной O-сессии.
2. StartupContext сохраняет startup-context в WAL, текст целиком по SHA-256 в content store. Максимум 220000 байт; превышение отклоняется без усечения. Один requestId не может иметь другое содержимое.
3. DOM отправляет только приглашение открыть workflow_pilot_panel и продолжить чтение в этом же ходе. Файлов нет. Host identity и приглашение связывают разговор с сессией; ручные ID/join/Enable не нужны.
4. Новый пакет имеет delivery_mode=model-pull. После регистрации, проверки получателя, актуальной попытки, отсутствия отмены и свежести пакета ответ panel включает startup_context: message_id, context_ref/sha256, text первой части, part=0, total, bytes и инструкции. Read и возврат первой части сохраняются одной WAL-транзакцией до ответа. Это выдача через аутентифицированный MCP, а не подтверждение готовности iframe/SDK. Для прямого чтения инструментом iframe не нужен. Grant плана не создаётся.
5. O читает включённый текст, остальные части получает через workflow_communication_read_context в том же ходе. Независимые части допустимо запросить параллельно. read_message повторно не нужен; при восстановлении он также возвращает первую часть. Текст части до 24000 байт UTF-8, с запасом под оформление в бюджете 28000 байт; символы не повреждаются. Пакет не объединяется в один огромный ответ. Каждая часть проверяет текущего получателя и SHA. Receipt означает возврат части, а не измерение понимания модели.
6. После всех частей O вызывает workflow_startup_complete(message_id, context_sha256=context_ref). Чужой адресат, неверный digest и неполный пакет отклоняются. Повтор того же актуального подтверждения идемпотентен. O кратко подтверждает восстановление и заканчивает ход; assignment_yield и модельный опрос не нужны.
7. ContextSession показывает готовность. Ack не подделывает физический конец ответа. Обсуждение/spec/Review/планирование используют правила Kit; выполнение плана разрешается только пользовательским Start.

## Восстановление и ошибки

WAL, content store и identity используются без второго scheduler. Рестарт сохраняет пакет и номера прочитанных частей. Для model-pull pending не означает очередь SDK: claim запрещён даже до первого чтения. Потерянный ответ восстанавливается повторным panel/read_message того же пакета; повтор первой части идемпотентен. Ошибка чтения/сохранения не оставляет ложной квитанции.

Пакеты 0.5.20 без delivery_mode сохраняют SDK-протокол: доставка после bind, SDK, сохранённого DOM sent, конца bootstrap и отсутствия активных команд. Claimed после рестарта становится UNKNOWN. UNKNOWN/accepted/rejected не разрешают повтор Send. При повторном открытии панели возвращается startup_resume. Начатый SDK-пакет нельзя перевести в model-pull. Требования готовности/конца хода, intent и подтверждения рабочих поручений E не меняются.

Отмена до DOM Send сохраняет паузу. Удаление проекта/сессии, замена requestId или изменение контекста запрещают чтение и ack старого пакета. Начатый неизвестный SDK-исход либо начатое model-pull чтение запрещают подменять незавершённый пакет новым. Закрытие окна/панели не удаляет receipts. Для будущих рабочих уведомлений панель подтверждает SDK независимо; старый build получает VERSION.

Ошибки PLUGIN_COMMUNICATION_: INPUT — параметры; CONTEXT — размер/digest/байты; READ_DENIED — адресат/непрочитанное сообщение; INCOMPLETE — не все части; STALE_MESSAGE — контекст изменился; CONFLICT — подмена пакета; BINDING — identity; STOPPED — SDK-канал; MODE — неверная смена транспорта. Отсутствующий backend-порт подготовки даёт STARTUP_CHANNEL_UNAVAILABLE. Ошибка не разрешает fallback к файлам или повтор неизвестного Send.

## Отображение и диагностика

Sidebar и панель различают подключение, чтение X из N, подтверждение и неопределённый старый SDK-исход. DOM sent не означает готовность контекста. Для model-pull панель отображает прогресс без wait/claim/Send; sync остаётся для наблюдения будущего Start. После complete плана ожидание останавливается по прежнему контракту.

События startup.prepared/resumed/open_returned/part_returned/complete и message.read дополняются operation.timing для startupOpen/Part/Complete. Поля — message_id, число байт/частей и номер части; текст пакета, identity и приглашение не выводятся в диагностику. Отсутствие send.intent/SDK для model-pull ожидаемо. Startup complete не означает выполнение или приёмку плана. Клиентские spans и серверные отметки не смешиваются; скрытое рассуждение не измеряется.

## Проверки и живая приёмка

Адресные fixtures проверяют реальный panel/read_context/startup_complete через MCP до готовности iframe и конца загрузочного хода: первый блок сразу, без SDK/grant, UTF-8/бюджет, весь пакет, ранний ack, чужие O/E, stale/удаление, ошибку чтения без receipt, повтор/restart и старый UNKNOWN без повторной отправки. Проверены sidebar/progress, архитектура, прежняя подготовка/вложения и каталог инструментов. Сквозной fixture: новый старт O → два E → интеграции → DOCS → cleanup/complete. Модели и рабочие профили не запускались. Полная suite/Kit не требовались: Kit не менялся.

Пользователь подтвердил функциональный старт 0.5.20; Test_06 до startup.complete занял 97,317 с. Это не время скрытого рассуждения. Ускорение 0.5.21 требует живого опыта: новые workspace/Chat/Work без ручного открытия карточек, приглашение без файлов, первая часть в panel, остаток и ack в одном ходе, отсутствие автоматического старта плана. Отдельно — восстановление частичного чтения и два E/DOCS. Fixtures не доказывают скорость хоста; native Windows/Linux pending.
