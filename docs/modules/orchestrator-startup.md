# Стартовый контекст оркестратора

Контракт Workflow Pilot 0.5.20: протокол панели 4, build `0.5.20-communication-4`, Kit 1.9.3 без изменения ролей. Новый O получает полный recovery через существующий канал панели; загрузка файлов ChatGPT для этого запуска не используется. Это смена транспорта, а не доказанное исправление внешней обработки вложений. Путь E, Review, legacy и уже отправленные попытки сохраняются.

## Последовательность и границы

1. ContextSession получает и проверяет recovery текущего workspace, формирует пакет с identity, ролью, scope, состоянием плана и обязательными инструкциями. Сохраняет попытку с requestId, `contextTransport=panel` и полный текст до DOM Send.
2. DialogueDelivery резервирует адресное приглашение. StartupContext записывает сообщение `startup-context` от backend в прежний WAL; текст хранится целиком по SHA-256 в content store. Один requestId не может получить другое содержимое. Размер до 220000 байт; превышение отклоняется без усечения.
3. DOM отправляет только короткое поручение открыть `workflow_pilot_panel` с приглашением и закончить bootstrap. Вложения отсутствуют. Приглашение связывает текущий разговор с точной локальной O-сессией; ручных ID/join/Enable нет.
4. После регистрации, свежего bind/SDK, сохранённого исхода DOM `sent` и физической готовности разговора канал сохраняет intent и передаёт уведомление с message_id. Проверяются текущая попытка, отсутствие отмены, свежесть пакета и отсутствие активных команд. Допуск startup действует отдельно от grant плана; выполнение задач он не разрешает.
5. O вызывает `workflow_communication_read_message`, затем `workflow_communication_read_context` для всех частей 0…total−1. Стартовые части до 24000 байт UTF-8, границы символов сохранены. Каждая часть проверяет текущего получателя и SHA. Backend сохраняет факт возврата части; он не измеряет понимание или скрытое рассуждение модели.
6. После всех частей O вызывает model-only `workflow_startup_complete(message_id, context_sha256=context_ref)`. Другой адресат, неверный digest и неполный пакет отвергаются. Повтор подтверждения того же актуального пакета идемпотентен. Агент кратко подтверждает восстановление и заканчивает ход; assignment_yield и модельный опрос не нужны.
7. Startup-транспорт закрыт, ContextSession показывает готовность. Квитанция не подделывает физический конец ответа. Дальнейшие обсуждение/spec/Review/планирование используют полные правила Kit. Только пользовательский Start разрешает план; последующий диалог O/E остаётся прежним.

## Восстановление и ошибки

Существующие WAL, content store, lease, поколения и identity используются без второго scheduler. Рестарт сохраняет пакет и номера прочитанных частей. Pending продолжается после свежего bind; claimed после рестарта становится UNKNOWN. UNKNOWN, accepted и rejected не превращаются в разрешение повторить SDK Send. При повторном открытии панели зарегистрированному O возвращается `startup_resume` для того же сообщения, чтобы дочитать пакет без нового уведомления и bootstrap.

Отмена подготовки до DOM Send сохраняет паузу. Удаление сессии/проекта, замена requestId или изменение контекста запрещают чтение и подтверждение старого пакета. Начатый неизвестный исход не позволяет подменить пакет новым. Частичный пакет остаётся неподтверждённым. Закрытие окна/панели не удаляет сохранённые receipts; новая панель должна подтвердить SDK. Старый протокол получает VERSION с инструкцией обновления подключения и панели.

Ошибки с префиксом `PLUGIN_COMMUNICATION_`: INPUT — параметры; CONTEXT — размер, digest или сохранённые байты; READ_DENIED — адресат/непрочитанное сообщение; INCOMPLETE — не все части возвращены; STALE_MESSAGE — контекст изменился; CONFLICT — попытка заменить пакет; BINDING/STOPPED — канал не подтверждён. Отсутствующий backend-порт подготовки даёт STARTUP_CHANNEL_UNAVAILABLE. Ни одна ошибка не запускает обход через загрузку файлов или повтор неизвестного Send.

## Отображение и диагностика

Sidebar и панель различают подключение/ожидание, передачу, чтение X из N частей, подтверждённый контекст и неопределённый исход. DOM `sent` не означает готовность контекста. Стартовые события `startup.prepared`, `startup.resumed`, `startup.part_returned`, `startup.complete` дополняют прежние send/read/binding/timing. Новые поля — message_id, число байт/частей и номер части; текст пакета и приглашение не включаются в диагностику. Выполненный startup не означает выполнение или приёмку плана.

## Проверки

Адресные fixtures проверяют короткий bootstrap без вложений, настоящий MCP/SDK, UTF-8, весь пакет, ранний ack, чужую identity, stale/удаление, повтор, reconnect/restart и UNKNOWN без повторной отправки. Проверены sidebar/progress, архитектурные границы, прежняя подготовка/вложения и каталог исполнителя. Сквозной автоматический fixture проходит старт O → два E → проверенные интеграции → DOCS → cleanup/complete. Модели и рабочие профили не запускаются. Общий suite проекта и полный Kit не требовались: исходники Kit не изменены.

## Живая приёмка

Ожидается пользовательская проверка установленной 0.5.20 и свежей панели протокола 4. Создать несколько новых workspace/Chat/Work-сессий без ручного открытия карточек. Убедиться: в composer только короткое приглашение, файлов нет; панель открылась; O прочитал весь recovery и подтвердил проект; план сам не запустился. Отдельно проверить восстановление панели во время частичного чтения и затем обычный тест двух E/DOCS. Fixtures не доказывают доступность SDK настоящего ChatGPT; native Windows/Linux также pending.
