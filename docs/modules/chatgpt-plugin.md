# Плагин Workflow Pilot для ChatGPT — первый прототип

Плагин включён в исходники выпуска 0.1.5. Готовность пакетов подтверждает release-manifest.json, установку — delivery-проверка. Целевые режимы — Chat и Work в ChatGPT Desktop; Codex исключён пользователем из приёмки.

## Назначение и границы

Плагин находится в этом репозитории и использует существующий MCP и backend Workflow Pilot. Панель показывает зарегистрированные локальные проекты, открывает выбранный проект и просит ChatGPT создать новый разговор. Агент подключает разговор к проекту и получает полный recovery. Разговор может оставаться в Recents: связь с локальной папкой хранит Workflow Pilot. Принадлежность к облачным проектам ChatGPT не изменяется.

Для проверки MCP отдельно от интерфейса можно подключить уже открытый разговор прямой просьбой агенту. Плагин не переносит историю, не обнаруживает автоматически все разговоры ChatGPT, не управляет его окнами. Существующие внешние сессии пока показаны списком без перехода по ссылке: анонимизированный идентификатор разговора не является URL. Режим нового разговора выбирает хост; переключение Chat/Work/Codex не реализовано. Автовыполнение через DOM для внешних сессий не поддерживается. Встроенный браузер и прежние сессии сохраняются.

## Контракт

- `workflow_pilot_panel {project_id?}` — список зарегистрированных активных корневых проектов и панель `ui://workflow-pilot/projects-v1.html`. При точном project_id также проверяет identity и возвращает выбранный проект со свежими сессиями; недоступный проект возвращает ошибку. Без аргумента сохраняется прежний список. Объявлены global/thread entrypoints.
- `workflow_open_project {project_id}` — открытие существующего проекта в панели, проверка его identity. Не меняет выбранную в Desktop сессию.
- `workflow_connect_project {project_id, request_id?}` — связь текущего разговора с проектом, проверка и возврат полного recovery. Панель передаёт свой request_id; при прямой просьбе в чате его создаёт сервер. Повторы в том же разговоре возвращают ту же локальную сессию.

Каноническая последовательность новой сессии: выбрать проект в панели → запросить новый разговор → первым вызовом в новом разговоре workflow_pilot_panel с переданным project_id → workflow_connect_project → прочитать весь полученный контекст → повторный workflow_pilot_panel с тем же project_id для обновления сессий → подтвердить готовность и ждать задачи пользователя. Этот порядок записан в пользовательском сообщении кнопки и описании MCP-инструмента. Он просит хост открыть панель до чтения recovery; скорость отображения и исполнение просьбы реальной моделью проверяются пользователем. Для прямого подключения существующего разговора без известного project_id сначала запрашивается список. Нельзя выдумывать project_id или идентификатор разговора. Противоречащую принадлежность нельзя перепривязать молча.

«Обновить» перерисовывает список сессий выбранного проекта из свежего ответа, сохраняя выбор. Пропавший проект скрывает старые сведения. Ответ с project_id сразу раскрывает проект в новом экземпляре панели; прежнее состояние другого разговора не требуется. Успешный MCP-вызов не доказывает видимость панели, а ошибка не должна скрываться заявлением об успехе. Закрепления правой панели между разговорами и автоматического перехода без Open плагин не обещает.

UI использует официальный `@modelcontextprotocol/ext-apps` и `@openai/mcp-extensions`, встроенные в HTML. Он проверяет наличие `openai/message`, затем посылает пользовательское сообщение с `target: new, send: true`. Поддержка capability сама по себе не доказывает поддержку target:new конкретным хостом: возможный отказ показывается пользователю. Неопределённый результат отправки не повторяется автоматически. Связь появляется после успешного MCP-вызова агентом, а не сразу по нажатию кнопки. Если новый разговор не получил подключение MCP, нужно включить плагин в нём и повторить исходную просьбу.

Привязка требует `_meta["openai/session"]` из MCP-запроса клиента. Из session/subject/organization сохраняется только SHA-256, исходные значения не записываются. Это идентификатор связи, а не авторизация и не транспортный Mcp-Session-Id. MCP остаётся stateless HTTP; доступ по-прежнему защищает собственное подключение туннеля. Если клиент не передал metadata, возвращается PLUGIN_SESSION_REQUIRED без создания сессии. Другой проект, архивная сессия или чужое повторное использование request_id дают PLUGIN_BINDING_CONFLICT.

Control остаётся единственным владельцем workspaces.json и очереди записи. Python MCP обращается к Execution через 127.0.0.1 со случайным портом и токеном; descriptor находится в собственном runtime, имеет права 0600 и удаляется при корректном закрытии. Запросы с Origin, неверным Host или токеном отклоняются. Закрытое приложение возвращает PLUGIN_DESKTOP_REQUIRED/UNAVAILABLE. Профиль донора не используется.

Контекст проверяется по существующему inline-context-v1: identity, полнота, размер, SHA-256 и состав частей; повреждённый пакет не создаёт сессию. Полный текст возвращается отдельным MCP TextContent, summary содержит проверочные значения. Успех транспорта не доказывает, что реальная модель прочла весь recovery: это пункт живой приёмки. Выбор внешней сессии в Desktop не создаёт DOM-клиент и не пересылает контекст.

## Подключение для живой проверки

1. После установки 0.1.5 полностью завершить прежний Workflow Pilot и самостоятельно открыть `/Applications/Workflow Pilot.app`. Installer не завершает и не перезапускает открытое приложение.
2. В Workflow Pilot открыть существующий подготовленный локальный тестовый проект. Приложение должно оставаться открытым: оно владеет хранилищем проектов. Его обычный запуск обновляет исходники собственного MCP.
3. В [ChatGPT Plugins](https://chatgpt.com/plugins) открыть существующее подключение Workflow Pilot и выбрать **Refresh**. Проверить, что появились три инструмента ниже. Затем в ChatGPT Desktop открыть новый разговор, набрать `@` и выбрать этот плагин. Новый туннель, ключ и отдельный backend не нужны. Старая сессия может удерживать прежний набор tools. Это обновление custom MCP-плагина; отдельный marketplace-пакет устанавливать не требуется.
4. Проверить наличие workflow_pilot_panel с необязательным project_id, workflow_open_project, workflow_connect_project. Открыть панель, выбрать проект, нажать «Новая сессия». При необходимости перейти через Open или Recents. Проверить первый вызов открытия панели до подключения и чтения контекста, затем обновление её сессий перед подтверждением готовности. Кнопка «Обновить» должна обновлять и раскрытый проект. Повторить в Chat и Work; время появления панели оценивать отдельно от времени чтения recovery.
5. Отдельно проверить обычный Chat без панели: «Покажи мои проекты Workflow Pilot. Подключи этот разговор к проекту [имя] и прочитай его контекст. Пока ничего не меняй». Если имя неоднозначно, выбрать проект из полученного списка. Повторить подключение — локальная сессия должна остаться одна.

Если подключения ещё нет в данном аккаунте/workspace: на странице Plugins выбрать **+ → Add custom MCP server**, указать имя, в Connection выбрать **Tunnel** и уже созданный собственный туннель Workflow Pilot, затем **Create as a plugin**, проверить инструменты и установить. Подключение донора не использовать. Точное расположение этих настроек внутри конкретной версии Desktop документация не уточняет; настройку можно выполнить на указанной веб-странице, затем проверить доступность через `@` в Desktop. Отсутствие плагина в отдельном режиме фиксируется как результат проверки, а не обходится новым туннелем.

## Матрица ручной приёмки

14.10.2026 пользователь подтвердил работу панели, создание разговора и получение контекста в Chat и Work на 0.1.3, затем быстрое открытие и обновление панели 0.1.4. После перезапуска Desktop при выборе диалога панель восстанавливается, если её открывал агент; одно ручное открытие не даёт такого результата. Глобальный автозапуск панели не подтверждён. На iPad/iPhone родное приложение открывает плагин в основном поле, диалог — карточкой; первоначальное предположение о недоступности панели на iPad опровергнуто проверкой пользователя.

Записывать точную версию клиента, режим, видимость интерфейса, создание разговора, результат подключения и сохранение связи после перезапуска. Секреты и полную metadata не копировать. Успех в Codex не считается подтверждением Chat/Work.

| Среда | Панель и новый разговор | Прямая привязка через MCP | Что требуется подтвердить |
|---|---|---|---|
| ChatGPT Desktop / Chat | 0.1.4 подтверждено пользователем | отдельно проверить | 0.1.5: переход в прежний диалог |
| ChatGPT Desktop / Work | 0.1.4 подтверждено пользователем | отдельно проверить | 0.1.5: переход в прежний диалог |
| ChatGPT Web на iPad | панель подтверждена пользователем | проверить отдельно | режим и переходы записывать отдельно |
| ChatGPT iPad/iPhone | панель в основном поле, диалог карточкой | виден ответ о подключении проекта | навигация в прежние диалоги не проверена |

Дополнительные проверки: второй проект; повтор и двойное нажатие; закрытый Workflow Pilot; повторный запуск; отсутствие расширений; отсутствие metadata; сохранение прежнего встроенного Chat/Work. Windows/Linux пока не приняты пользователем.

Фактические доступность и ограничения устанавливаются указанными проверками; отсутствие режима в прежней документационной матрице не опровергает проверку пользователя.

## Проверка переходов в 0.1.5

Сворачиваемый раздел «Проверка переходов» не меняет привязки сессий. Пользователь в диалоге A вводит обычную ссылку на диалог B из адресной строки Web и по очереди проверяет:

1. `app.openLink({url})` — стандартный MCP Apps `ui/open-link`, только при host capability openLinks.
2. `window.openai.openExternal({href})` — совместимый ChatGPT API, если он предоставлен.
3. Тот же вызов с `redirectUrl:false`.
4. HTML-ссылка с `target=_blank`, noopener/noreferrer.
5. HTML-ссылка с `target=_top`. Sandbox может отклонить её; панель может закрыться. Это эксперимент обычной навигации, без изменения sandbox или доступа к родительскому DOM.

По официальному контракту первые вызовы предназначены для внешнего браузера. Эксперимент выясняет, перехватывает ли конкретный Desktop собственный URL. Deep link расширения ведёт внутрь самого плагина; параметра выбора произвольного старого разговора в message.send нет. Не выдумывать native URI и не строить URL из openai/session. Если обычная ссылка уйдёт во внешний браузер, это не успех сценария Desktop.

Разрешены только HTTPS chatgpt.com `/c/<id>` либо `/g/<id>/c/<id>`, без credentials/query/fragment; публичные Share и сторонние адреса отклоняются. Введённый адрес остаётся только в текущем UI и передаётся выбранному навигационному механизму, не в MCP backend или модель. CSP для совместимого openExternal содержит только redirect_domains chatgpt.com; остальные сетевые доступы не расширены.

Журнал до 20 событий фиксирует способ, время, фазу и ручное наблюдение. API без ошибки означает только принятие вызова; визуальный результат отмечает пользователь. Через 10 секунд ошибка/timeout дают UNKNOWN, повтор не запускается. При доступном localStorage журнал переживает повторное открытие UI в том же origin; хранение зависит от хоста, междиалоговая синхронизация не обещается. URL, идентификаторы и текст диалога в отчёт не входят. Его можно выделить и скопировать вручную. После каждого перехода вернуться в A, выбрать проверенный способ и фактический результат; записать версию клиента и Chat/Work отдельно.

Критерий успеха: из панели A открыть именно прежний B с его историей внутри ChatGPT Desktop, без создания нового разговора; затем повторить в обратном направлении и после перезапуска. Даже успех по вручную введённому URL не доказывает автоматическое получение адреса при создании сессии. Этот второй вопрос остаётся отдельным этапом исследования.

Источники: [официальная спецификация Extensions](https://github.com/openai/mcp-extensions/blob/main/docs/spec.md), [руководство](https://developers.openai.com/plugins/build/extensions), [metadata клиента](https://developers.openai.com/plugins/reference#_meta-fields-the-client-provides), [подключение](https://developers.openai.com/plugins/deploy/connect-chatgpt).

## Автоматическая проверка и поставка

`npm run stage:chatgpt-plugin` и `node --test tests/chatgpt-plugin.test.mjs` проверяют настоящий Python FastMCP, JS MCP Client, loopback-мост и Control с изолированным профилем. Проверены metadata, контекст, идемпотентность, конкуренция, restart, повреждение пакета и закрытый backend. Полный HTML, полученный через MCP resources/read, исполняется в jsdom с настоящим SDK: handshake через postMessage, список проектов, открытие проекта и ui/message target:new. Хост тестовый; это не приёмка ChatGPT. Отдельный regression сохраняет $&, $`, $' и $$ буквально. Сборка отказывает при синтаксически неверном JavaScript до записи ресурса. Electron smoke проверяет выбор внешней сессии без нового браузера/отправки контекста.

Проверки 0.1.4 дополнительно подтверждают порядок просьб в исходящем сообщении, открытие выбранного проекта в новом экземпляре полного HTML, свежие сессии после реального MCP-подключения и нажатия «Обновить», сброс пропавшего проекта и отказ неизвестного project_id. Они не запускают модель и не доказывают её следование просьбе в ChatGPT Desktop.

Для MCP-тестов требуется изолированный `.harness/runtime/test-python` с зависимостями `tools/codex-app-server-mcp/requirements.txt`, как в существующих проверках проекта. `stage:chatgpt-plugin` собирает автономный HTML с лицензиями; он вызывается перед start/test/smoke и общей/платформенной сборкой. Generated HTML не хранится в Git, входит в существующий комплект tools MCP и копируется штатным Runtime.syncSource. Перед production build документацию и результаты живой приёмки актуализировать; затем выпускать три платформы из одного sourceCommit и выполнять отдельную macOS delivery-задачу.
