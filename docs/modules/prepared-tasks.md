# Подготовленные поручения до запуска плана

Контракт Workflow Pilot 0.5.35 / Workflow Kit 1.10.1, ролевой протокол 10. Новый orchestrated-план с `dialogue_version:1` имеет `preparation_version:1`: авторское поручение и выбранный контекст каждой обычной задачи и DOCS готовы **до Review и публикации**, а не после нажатия Start. Исполнение разрешает только пользователь. [Рабочий диалог](assignment-dialogue.md), [надёжность](assignment-dialogue-reliability.md), [Kit](../../packages/workflow-kit/docs/modules/orchestrated-plans.md).

## Авторский снимок

O явно передаёт в `plan:create`/`review:prepare` полный `task_brief` и `prepared_task` каждой задачи. Для DOCS эти поля задаются явно; нормализация сохраняет их. Допустимая исходная форма:

```json
{
  "task_brief": "Полное стабильное поручение: цель, границы, результат, критерии и проверки.",
  "prepared_task": {
    "version": 1,
    "contexts": [{"source":"docs/modules/example.md","text":"Полный выбранный текст"}],
    "dependency_task_ids": []
  }
}
```

`contexts:[]` допустим, если дополнительный выбранный текст не нужен. Источник — безопасный относительный путь; необязательный `commit` — точный Git SHA. Это сведения автора о происхождении; hash подтверждает байты, но не истинность текста. `task.context_pack` остаётся рекомендацией O для отбора, не автоматическим вложением всего проекта E. Обязательные ограничения передаются полностью через startup/recovery независимо от выбранного контекста.

`prepared-task.mjs` после нормализации сохраняет:

- version, project_id, scope_id и author_session_id владельца плана;
- SHA-256 полного task_brief;
- буквальные неизменяемые тексты contexts, их source/commit, SHA-256 и число UTF-8 байт;
- точный список отложенных dependencies;
- `contract_digest` семантического договора задачи.

Коммит плана — хранилище снимка; одна ссылка/hash без доступных байтов не считается подготовкой. При выдаче изменившийся файл не перечитывается вместо согласованного текста. Неизвестная версия, другой автор/project/scope, испорченный текст/hash или изменившиеся требования дают `TASK_PREPARATION` с task ID до публикации. Чтение плана не дописывает подготовку и не переписывает её digest.

Digest использует детерминированную канонизацию ключей и домен `workflow-pilot/prepared-task/v1`. Он охватывает принадлежность, автора, цель, пути, проверки/acceptance, зависимости, parallel_safe, verification_kind, ожидаемое сообщение коммита, context_pack, body и манифест выбранных байтов. Runtime-статусы, commit_ref, счётчик plan_revision и revision-ссылки документов контекста не меняют смысл договора. Review проверяет подготовку как часть пары spec/plan; наличие digest не заменяет полномочия автора и согласование.

## Пределы и актуализация

`task_brief` — непустой полный текст до 12000 UTF-8 байт. До 16 выбранных источников; при зависимостях один слот резервируется для их проверенных фактов. Каждая часть с оформлением — до `budget.document_bytes` (обычно 28000). Сумма body/contexts — в `hard_bytes` проекта (не выше 180000), также соблюдается транспортный предел 1 MiB. Сериализованный манифест части учитывается с запасом; обрезки нет. При позднем добавлении фактов зависимостей бюджет проверяется снова.

Не допускаются NUL, приватные пути, известные формы bearer/API keys, enrollment tickets и адреса чатов. Автор также отвечает за отсутствие иных секретов. Подготовка не передаёт identity чужого разговора и не расширяет область задачи.

Для ещё не начатой задачи `task:update` явно передаёт актуальный task_brief и новый prepared_task без прежнего contract_digest. `plan:extend` принимает подготовку новых задач и `prepared_tasks` по ID для изменившихся задач/DOCS. Смена семантического договора без нового согласованного снимка отклоняется. Содержательная актуализация до исполнения требует нового согласования; DONE, активные попытки и прежние proof не сбрасываются.

Публикация нового плана не допускается без подготовки всех обычных задач и DOCS. Delivery-задачи `package`/`installed` выполняет O в main, для них авторский пакет E не требуется. Sequential-план без выдачи E не получает это требование.

## После Start

1. ExecutionControl выполняет свежий preflight и разрешает текущий scope/generation. Scheduler создаёт допустимые настоящие assignment/worktree/attempt; подготовленный текст сам не создаёт назначения.
2. DialogueDelivery вызывает доверенную внутреннюю привязку `assignmentPlanBind`. Проверяются текущие O/E identity и принадлежность, согласованный digest, реальные assignment/attempt и действующий grant. Публичный prepare не может подделать признак плановой подготовки.
3. Тот же авторский текст и байты переносятся в существующий draft/WAL. Устойчивый ключ включает project/scope/task/preparation_digest/assignment/attempt. Записывается `task.plan_bound`; отдельная авторизация связана с актуальными generation/boot/recipient.
4. Перед публикацией повторно проверяются договор, разрешение, pause/cancel/revoke, SDK/binding конкретного E, конец bootstrap и отсутствие команд. Intent → идемпотентный Kit → WAL предшествуют SDK. До bind рабочего сообщения E нет. Ни worktree, ни авторизация не означают accepted/read/task:start.
5. Каждый готовый E получает свой пакет независимо от медленного соседа. Обязательного модельного хода O для сочинения или ready-подтверждения нет; уже согласованную выдачу O не дублирует.

После Continue/restart неизменённая плановая подготовка может быть авторизована для текущего назначения без нового хода O, только при свежем пользовательском допуске и прежних проверках. Ручная пауза сама не снимается. Опубликованный пакет не отправляется заново, UNKNOWN остаётся на разборе, закрытый failed/retired intent не возрождается. Повторные callbacks и сбой между intent, Kit и WAL продолжают тот же effect, а не новую выдачу.

Автоматическая плановая привязка относится к первой попытке. Revision — новое авторское решение O; она не подменяется начальным поручением. Непредусмотренное содержательное уточнение, изменение области или противоречие результатов адресуется O обычным каналом.

## Зависимые задачи и совместимость

T003 и DOCS заранее содержат полные стабильные инструкции и явные ID зависимостей. При выдаче backend добавляет отдельный `workflow-kit-dependencies.json` только с проверенными фактами интеграций и точными SHA. Нет доказанной зависимости — нет выдачи. Backend не пишет новый смысл задания и не принимает результат вместо O. DOCS стартует после проверенных интеграций, её bootstrap может перекрываться с независимым текстовым ответом O при чистом main и свободном writer.

Существующий Chat-план без `preparation_version:1` и согласованного prepared_task сохраняет поздний путь: O читает service recovery/preparation_queue, явно готовит и разрешает `prepare(dispatch_when_ready:true)` либо `dispatch(when_ready:true)`. После смены поколения старому авторизованному draft требуется сверка O (`needs_confirmation`). Brief сам по себе не получает автоматической авторизации. Чтение, update Settings или простое расширение старого плана не делают его новым. В UI показывается фактический этап и адресат, включая ожидание канала O.

## Проверки

Если собственное назначение уже известно, но участник E ещё не зарезервирован, bindPlan возвращает participant-reservation после проверки авторского пакета. Подготовка остаётся сохранённой, следующий проход связывает тот же пакет без нового авторского хода O. Отзыв приглашения, чужая identity, stale/digest и UNKNOWN остаются отказами. Подтверждённый успех того же восстановления снимает только его старый RECIPIENT, не другие ошибки.

`prepared-task-flow.test.mjs` проверяет roundtrip, бюджеты/UTF-8, явную DOCS, неизменность байтов, author/scope/hash/договор и старые brief-only планы. Kit core/assignments проверяют Review, дочерний контракт, зависимости и интеграции. `workflow-channel.test.mjs` и `automatic-agent-dialogue.test.mjs` проходят плановую привязку, Kit→WAL crash/restart, stale/pause/UNKNOWN и полный цикл двух/пяти E без дополнительной подготовки O. Настоящие API/MCP/SDK adapters, stores, Kit/Git используются с подставленной моделью; скорость настоящего ChatGPT не доказана. [Повторная приёмка D010/D011](../acceptance/release-0534-defects.md).
