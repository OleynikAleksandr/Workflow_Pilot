# Эксперимент: основная панель и отдельный PiP

Workflow Pilot 0.5.16 содержит пассивный пробник 1.3.0 в обычном MCP-подключении. Цель — настоящее плавающее окно одновременно с основной панелью, без влияния закрытия пробника на агентов. Совместная видимость пока не подтверждена. Рабочий план остаётся в sidebar; настоящая лента O/E/Review ещё не реализована.

## Контракт опыта

`pip_probe_open_dialogue` возвращает отдельный immutable HTML и синтетический structuredContent. Как в официальном примере request-display-mode, App получает capabilities `{}`, диалоговый ресурс не ограничивает availableDisplayModes и не задаёт preferredDisplayMode. У инструмента нет preferredModelDisplayMode и thread entrypoint. Начальное представление выбирает хост: оно служит площадкой запуска и не считается успешным PiP.

После подключения SDK и получения tool-result доступны две независимые кнопки:

1. **Запросить PiP через MCP** — прямой `app.requestDisplayMode({mode:'pip'})` из обработчика нажатия, без предшествующего await.
2. **Запросить PiP через window.openai** — отдельный прямой вызов совместимого API, только если он предоставлен компоненту. Его отсутствие показывается явно.

Автоматического запроса при mount, автоматического fallback и запросов других режимов нет. Одновременно выполняется только одна попытка. Кнопка MCP доступна даже если хост не объявил pip: это диагностический запрос, а не обещание поддержки. Открытие компонента агентом само по себе не выполняет пользовательское нажатие.

UI различает начальный режим, актуальный host context, режим window.openai, непосредственный ответ API и последующие hostcontextchanged/openai:set_globals. Ответ без mode, включая undefined, не трактуется как отказ или успех. Ответ mode=pip также требует визуальной проверки. Совместимый API может использовать тот же внутренний транспорт; две кнопки не доказывают наличие двух независимых реализаций.

Последние 50 событий сохраняются только в компоненте: время, путь API, номер попытки, requested/returned mode, тип ответа, доступные режимы, trustedClick/userActivation и монотонная длительность. Ошибка выводит ограниченные name/code/message с удалением URL и длинных токеноподобных строк; error.data, полный host context, identity, содержимое tool-result и сообщения агентов не сериализуются. Журнал можно выделить и скопировать вручную. Он исчезает вместе с экземпляром компонента.

## Изоляция и поставка

`pip_probe_open_plan` — необязательная синтетическая основная панель для проверки двух счётчиков. Настоящая основная панель — `workflow_pilot_panel`; уже открытую панель повторно вызывать не нужно. `pip_probe_status` — app-only синтетическое время, счётчик и идентификатор процесса; рабочих данных и backend-моста нет.

Node-стенд и Python-регистрация используют общую реализацию `tools/experiments/pip-probe`. Staging собирает HTML; `tools/codex-app-server-mcp/pip_probe.py` фиксирует их байты и SHA-256 URI при старте MCP. SDK и зависимости не обновлялись. Основной канал O/E и протокол 3 сохранены.

Пробник не содержит openai/message, join/bind, Stop, разрешения плана, read-квитанций или очереди доставки. Teardown/pagehide прекращают только его polling, снимают слушатели событий; поздние ответы не изменяют закрытое представление. Работа настоящих агентов после закрытия требует отдельного живого подтверждения.

## Проверка пользователем

1. Запустить установленную 0.5.16 после штатной остановки прежней службы. Installer службу не останавливает; при pending после остановки нужно завершить штатную установку. Обновить инструменты подключения ChatGPT и получить новый вызов пробника, а не старый результат разговора.
2. Оставить актуальную основную панель открытой. Попросить оркестратора вызвать только `pip_probe_open_dialogue`, не создавать план и не запускать агентов. На компоненте должна быть метка «Опыт 0.5.16: PiP по кнопке».
3. Дождаться «Результат инструмента получен», нажать кнопку **1** один раз. Зафиксировать ответ, события режима, видимость основной панели и расположение окна. Inline/fullscreen или замещение основной панели не подтверждают совместное отображение. Не маскировать это повторным открытием основной панели.
4. Если настоящий PiP не появился и кнопка **2** доступна, после завершения первой попытки нажать её один раз. Это отдельный опыт; сохранить диагностику обоих. Если API недоступен, зафиксировать результат без обхода хоста.
5. При настоящем PiP дождаться обновлений счётчика и закрыть только его. Основная панель должна остаться видимой и работоспособной. Затем проверить повторное открытие. Для двух синтетических счётчиков отдельно использовать pip_probe_open_plan.
6. Лишь после успеха UI выполнить отдельный контрольный план: новое адресное сообщение после закрытия PiP и дальнейшая работа без Stop, повторного bind или дублирующих Send. Синтетический счётчик этого не доказывает.

Окнами управляет пользователь. Ответ SDK не подтверждает расположение окна.

## Основания и ограничения

Официальные [request-display-mode](https://github.com/openai/openai-apps-sdk-examples/blob/main/src/request-display-mode/App.tsx) и [cards-against-ai](https://github.com/openai/openai-apps-sdk-examples/blob/main/src/cards-against-ai/App.tsx) вызывают запрос по кнопке после готовности компонента. Пробник воспроизводит этот порядок без игровой логики.

Источники противоречат друг другу: [UI guidelines](https://developers.openai.com/plugins/concepts/ui-guidelines#picture-in-picture-pip) описывает плавающий PiP, а [mcp-extensions spec](https://github.com/openai/mcp-extensions/blob/main/docs/spec.md#display-modes), проверенный 21.10.2026, говорит о поддержке inline/fullscreen без pip. Установленная схема mcp-extensions 0.2.0 допускает pip в metadata ресурса. Это не установленная причина отказа. [Reference](https://developers.openai.com/plugins/reference#request-another-presentation-mode) описывает window.openai API. [Issue 87](https://github.com/openai/openai-apps-sdk-examples/issues/87) сообщает похожее превращение pip в fullscreen, но не содержит подтверждённого исправления.

Предыдущие пользовательские опыты дали inline со скроллом либо замещение основной правой панели, включая запрос только pip. Кнопка повторного запроса уже существовала: отсутствие user gesture не доказано как единственная причина. В 0.5.16 устранены автоматический запрос до tool-result и потеря подробностей ошибки; сравниваются два явных API. Живой результат новой версии — **NOT_RUN**.

`scripts/check-pip-probe.mjs` прошёл 7 адресных проверок: lifecycle двух viewer, другой режим/отказ/undefined, gate connect+tool-result и две кнопки без fallback, ранний result/повторный клик/поздний ответ, pagehide во время polling, настоящий Node MCP и настоящий Python MCP с основной панелью. Проверены immutable ресурсы и отсутствие доступа к backend state. Lifecycle использует mock-хост и не является приёмкой ChatGPT. Проверка архитектуры пройдена. Полная suite для изолированного пробника не повторяется.

Экспериментальный комплект трёх ОС собирается из одного sourceCommit, затем готовая macOS-копия устанавливается штатно. GitHub-публикация в этом раунде не требуется. Состав и ограничения — release-manifest.json и [поставка](release.md).
