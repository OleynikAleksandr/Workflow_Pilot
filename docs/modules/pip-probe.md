# Эксперимент: основная панель и отдельный PiP

В экспериментальной сборке Workflow Pilot 0.5.15 пробник входит в обычное MCP-подключение. Это проверка возможностей хоста ChatGPT, а не готовая лента переписки. Рабочий план пока остаётся в sidebar, основная панель сохраняет прежнюю функцию связи. Перенос плана и показ сообщений O/E/Review будут отдельной работой после успешного опыта.

## Инструменты и изоляция

- `workflow_pilot_panel` — настоящая основная панель, открывается обычным способом. При уже открытой актуальной панели повторный вызов не нужен.
- `pip_probe_open_dialogue` — отдельный пассивный ресурс с синтетическими данными. Единственный поддерживаемый режим ресурса и SDK initialize — `pip`, предпочтение ресурса также `pip`. У инструмента нет `preferredModelDisplayMode` (это поле SDK допускает лишь inline/fullscreen) и thread entrypoint. После подключения SDK явно запрашивается `pip`, отображаются начальный и текущий фактические режимы. Видимая метка — «Режим эксперимента: только PiP». Кнопка «Запросить PiP» повторяет запрос по действию пользователя; другие режимы пробник не запрашивает.
- `pip_probe_open_plan` — необязательная синтетическая основная панель для изолированной проверки двух счётчиков. Не является планом проекта.
- `pip_probe_status` — app-only чтение времени, монотонного счётчика и случайного идентификатора процесса. Не читает проект и не обращается к backend-мосту.

Python-регистрация находится в `tools/codex-app-server-mcp/pip_probe.py`. Staging собирает два HTML из общей реализации `tools/experiments/pip-probe`; самостоятельный stdio server остаётся разработческим стендом. Runtime получает готовые HTML и не требует Node-сборки при открытии. Каждый URI содержит SHA-256 полных байтов; содержимое и URI фиксируются при старте MCP.

PiP не содержит отправки `openai/message`, join/bind, Stop, разрешения плана или второй очереди доставки. Teardown/pagehide останавливают только собственный таймер; поздний ответ не возобновляет polling. Пробник не перехватывает сообщения агентов, не ставит read-квитанции и не запускает модели.

## Пользовательский опыт

1. После установки остановить прежнюю фоновую службу штатным меню и запустить новую установленную версию. Если installer оставил pending, после остановки повторить штатную установку. Проверить версию 0.5.15. Обновить инструменты подключения Workflow Pilot в ChatGPT, чтобы появились новые инструменты.
2. В тестовом чате оставить настоящую основную панель открытой. Попросить оркестратора вызвать только `pip_probe_open_dialogue`, не создавая новый план и не начиная работу.
3. Проверить, что основная панель и отдельное окно одновременно видны. Записать фактические «Начальный режим», «Режим» и «Доступны»: целевой режим только pip. Если автоматический запрос отклонён, нажать «Запросить PiP» один раз. Отсутствие компонента, другой режим или замещение основной панели означают, что опыт не прошёл; не маскировать результат повторным открытием основной панели. Объявление только pip не гарантирует поддержку хостом.
4. Дождаться нескольких обновлений тестового счётчика и закрыть только PiP. Основная панель должна остаться доступной. Повторное открытие пробника не должно повторно запускать основной workflow.
5. Для проверки обновления двух независимых окон вместо настоящей панели можно отдельно открыть `pip_probe_open_plan`, затем PiP; после закрытия PiP счётчик первой панели должен продолжать расти.
6. Сохранение работы настоящих агентов проверяется отдельным контрольным планом: при живом основном канале закрыть PiP, затем подтвердить новое сообщение, чтение и дальнейший прогресс без Stop, потери основной панели или повторного запуска. Успех синтетического счётчика не является этим доказательством.

Окнами управляет пользователь. Пробник сообщает ответ SDK, но не может сам доказать совместную видимость. Нельзя автоматически считать режим `pip` вторым независимым представлением или обещать одинаковое поведение всех клиентов.

## Проверки и ограничения

Адресный `scripts/check-pip-probe.mjs` собирает HTML и запускает пять проверок: независимое обновление основной панели после teardown PiP; отказ/другой режим; поздний ответ после pagehide; настоящий Node MCP; настоящий Python MCP рабочего плагина с основной панелью и двумя пробниками. Python-проверка подтверждает неизменяемость ресурсов, синтетический ответ и отсутствие доступа к папке состояния. Lifecycle проверяется на mock-хосте. Архитектурная проверка также пройдена.

Предыдущий опыт с fullscreen заменял основную панель. В опыте 0.5.14 с inline/pip пользователь показал: начальный режим inline, текущий inline, доступен только inline; запрос PiP вернул inline. Компонент обновлялся, но прокручивался вместе с разговором. Причина ограничения хоста не установлена. В 0.5.15 убран запасной inline; адресные Node/Python MCP-тесты проверяют единственный pip и отсутствие предпочтения inline/fullscreen. Новый живой опыт и продолжение настоящего диалога после закрытия PiP — **NOT_RUN**. Выпуск экспериментальный, публикация GitHub в этом раунде не требуется. Подробности установки и состав — [поставка](release.md) и release-manifest.json.

Если опыт успешен, следующая реализация разделит панель плана и пассивную ленту сохранённых сообщений с автором, адресатом, временем и квитанциями. Источник Review подключается отдельно; второй UI не становится владельцем доставки. Чтение человеком не означает чтение агентом. При ограничении хоста фиксируется результат опыта, альтернативный интерфейс выбирается отдельно.

Официальные контракты: [запрос режима](https://developers.openai.com/plugins/reference#request-another-presentation-mode), [PiP](https://developers.openai.com/plugins/concepts/ui-guidelines#picture-in-picture-pip).
