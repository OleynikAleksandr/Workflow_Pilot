# Workflow execution — координация в Control

Review нового плана по умолчанию OFF. При ON Kit согласует пару spec/plan через Claude CLI; успешный отзыв требует позиции автора, изменение пары — нового раунда. Execution запускает процесс, Control координирует ожидание и продолжение, Kit единственный публикует план. Неизменённое согласие не требует лишнего раунда. Ошибка/спор сохраняются для явного решения, OFF возвращает обычную публикацию.

В review:prepare получатель recipient_session_id задаётся на верхнем уровне, execution_origin_session_id находится внутри scope и обозначает происхождение снимка настроек, а не владельца плана. Выбранная строка другого чата не подменяет получателя. parallel_allowed/max_workers/strategy/reason сохраняются для плана; изменение Settings не перенастраивает текущий снимок. Подробный CLI-контракт — [Workflow Kit](../../packages/workflow-kit/docs/modules/workflow-kit-package.md#опциональный-review).

Control содержит PlanContinuation (продолжение sequential/parallel-плана), ProjectPlanContinuation (разрешение проекта), ReviewContinuation, PlanReviewClient, ParallelExecution/Kit, исполнителей, подтверждение плана и его проекции в src/control/workflow. Алгоритмы базы 0.6.115 сохранены: sequential работает в основном checkout, parallel использует отдельные worktree. С 0.4.4 отдельного переключателя запуска нет ни в интерфейсе, ни в IPC: у любого активного плана одна кнопка `setPlanExecution` («Начать выполнение плана» / «Пауза» / «Продолжить»). У sequential/parallel-плана кнопка включает и выключает механизм продолжений (PlanContinuation/ProjectPlanContinuation) с его проверками; пауза немедленная, состояние кнопки берётся из этого механизма. Без плана, во время планирования и после выполнения кнопки нет. С 0.4.0 план оркестратора ведут ExecutionControl (кнопка запуска и паузы) и ParallelExecution с волнами, delivery-фазой, сигналами Kit и автопаузой — [оркестрованное выполнение](orchestrated-execution.md). Отложенная ротация 0.6.113/114 не включена.

DialogueDelivery связывает существующую coordination с [каналом](chatgpt-plugin.md), без второго scheduler. В новых orchestrated-планах dialogue_version=1: короткий DOM-bootstrap O и полный [контекст через панель](orchestrator-startup.md), минимальный bootstrap E; ready требует SDK/bind и физического конца. O сам отправляет task/context, E result, O acceptance и Kit integration. Intent → Kit → WAL сохраняет эффект с одним operation_id. FIFO ждёт read/yield и свежего физического конца без user bubble; UNKNOWN не повторяется. Старые планы сохраняют выбранный plugin-v1/legacy-dom и прежнюю семантику. [Контракт](assignment-dialogue.md).

O заранее сохраняет и авторизует prepare с dispatch_when_ready=true; backend доставляет после готовности без дополнительного ready-хода. Claim/verify объединены, UI/telemetry не блокируют функциональную доставку. DOCS может запускаться при текстовом ходе O, финальный ход — до terminal E; cleanup/complete сохраняют строгие барьеры. [Тайминги, причины ожидания и границы измерений](dialogue-timing.md).

В 0.5.7 подготовка общей службы не конфликтует между исполнителями. Выбор живой сессии не отменяет bootstrap и не открывает главную вместо временного разговора; новый record после restart не воспроизводит неизвестный Send. Проекция отдельно показывает подготовку/адрес, регистрацию, действующую SDK lease и рабочее уведомление. Pending-транзакция Kit при запуске удерживает только свой проект; Continue требует свежей readiness, архив/удаление остаются доступны. Подтверждённое удаление останавливает scheduler и команды проекта, отзывает связь, затем очищает настройки, без DONE/INTEGRATED ([жизненный цикл](project-lifecycle.md)).

С 0.2.0 вся координация выполняется в [backend](backend.md). Допуск фоновой работы не требует окна, sidebar или видимой страницы: закрытие клиента, ноль зрителей и потеря lease не останавливают выполнение плана, Review и исполнителей. Явная остановка службы (draining) не даёт новых отправок, контекста и назначений, но дожидается текущего ответа, инструментов и команд Kit; отмена остановки продолжает с места ожидания.

ControlFacade создаёт coordination: она владеет разрешениями проектов, журналами отправок, восстановлением основных и назначенных сессий, адресными подписками и допуском интеграции. Модель Desktop в backend вызывает операции переключения/восстановления и получает снимки. Книги назначений, состояния очередей и Map подписок наружу не передаются; очищается только явно адресованный проект. Отображение принадлежит Desktop, состояние настроек — Control. Порт продолжения плана для текущей видимой сессии сохранён для Desktop и donor smoke. С 0.4.7 в коде нет имени AutoPlan; настройки (`projectAutoPlan`) и чекпоинты исполнителей (`autoPlanCheckpoint`) 0.4.6 и ранее при загрузке переносятся под новые имена `projectPlanContinuation` и `continuationCheckpoint`. Workflow Kit 1.9.5 не упоминает AutoPlan: агент сообщает пользователю, что запуск, пауза и продолжение — кнопка выполнения плана.

Execution предоставляет процессы, физический IO, проверку жизни процесса/загрузки ОС и файловые наблюдатели. Наблюдатели сохраняют ограниченный список входов и перевешивание при замене inode; наблюдение файлов событийное. Только текущий SDK gate допускает ограниченную read-only сверку физического конца хода, без модели и Send. Control обращается к ExecutionFacade. Kit остаётся единственным владельцем изменений плана, назначений и транзакций; его Review API и CLI используются без второй копии плана.

execution_origin_session_id выбирается из подтверждённого parallel-плана и сверяется со снимком max_workers основной сессии. recipient_session_id остаётся самостоятельным адресом Review; получатель сверяется повторно по сохранённому состоянию непосредственно перед Send. OFF, Stop, draft, неподтверждённые writer-команды и UNKNOWN сохраняют прежние блокировки. Готовый source не доказывает merge safe: диагностическое поручение, последовательная интеграция и финальная передача имеют отдельные сохранённые этапы без повторного Send.

Новые worktree и quarantine используют .workflow-pilot-worktrees и .workflow-pilot-delete-. Донорские проекты открываются по исходному формату Kit; перенос регистра локальных проектов не выполняется. Два приложения не должны исполнять один план одновременно.

packages/workflow-kit содержит Kit 1.9.5 (с 1.9.5 во время `commit --task` в журнале транзакции `<git-dir>/workflow-kit/transaction.json` лежит `verification_progress` {version 1, task_id, check_id, index, total, check_started_at_ms, run_started_at_ms}; запись атомарна и очищается при успехе, отказе и отмене; приложение читает её из git-dir того checkout, где идёт коммит — main или worktree исполнителя, — и наблюдает этот файл; старый Kit записи не ведёт); resources/workflow-kit генерируется staging, установленный runtime обновляет installer. Циклы Kit устранены разделением правил и команд; [совместимость проектов](project-compatibility.md) описывает продолжение формата 1.7.2. Временные корневые re-export удалены; scripts и tests используют текущие модули. Архитектурная проверка запрещает циклы без исключений, обход ControlFacade из Frontend, импорты корневых мостов и физическое IO из Control.

Проверки: прежние F01–F20/A01–A06, Review recipient/restart/final-send, тесты ControlFacade для отделённых снимков, сохранения UNKNOWN/origin и адресной очистки; полный unit-all, изолированный electron-smoke, kit-check, kit-assignments и architecture. Реальные службы, модельные агенты и профиль пользователя в fixtures не используются. Проверки оркестрации — `tests/orchestrated-execution.test.mjs`, `parallel-execution.test.mjs`, `execution-control.test.mjs`, `session-roles.test.mjs`.
