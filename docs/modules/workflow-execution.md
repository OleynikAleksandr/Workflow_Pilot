# Workflow execution — координация в Control

С 0.5.29 отказ Kit — это штатный выход с JSON-кодом (`kitRefusal` в SessionPlans), кроме кодов неизвестного исхода и повторяемого чтения; ParallelKit даёт статус `REFUSED`, ParallelExecution — паузу `refused` с текстом «Kit отказал в назначении …» и без повторного создания до «Продолжить»; таймауты, сигналы и неполный вывод остаются `unknown`. Пауза наступает, когда нет работающих исполнителей: назначение без сессии исполнителя и без идущего создания или открытия страницы её не держит. PlanningOwners (Control) снимает владельца при архиве сессии и передаёт его по выбору пользователя; с Kit 1.9.8 владельца занимает `plan:mode-request`, с 1.9.7 — первая ручная отправка кандидата. UserChoices (Control) — [карточки выбора пользователя](user-choice.md): причины из фактов coordination, запись нажатия, существующие действия и доставка `user-choice`; sequential-план сессии продолжается в его `execution_origin_session_id`. Review нового плана по умолчанию OFF; переключатель решает в момент публикации и заблокирован во время ревью и после публикации (Kit 1.9.6, PlanReviewClient показывает причину). При ON Kit согласует пару spec/plan через Claude CLI; успешный отзыв требует позиции автора, изменение пары — нового раунда. Execution запускает процесс, Control координирует ожидание и продолжение, Kit единственный публикует план. Неизменённое согласие не требует лишнего раунда. Ошибка/спор сохраняются для явного решения, OFF возвращает обычную публикацию.

В review:prepare получатель recipient_session_id задаётся на верхнем уровне, execution_origin_session_id находится внутри scope и обозначает происхождение снимка настроек, а не владельца плана. Выбранная строка другого чата не подменяет получателя. parallel_allowed/max_workers/strategy/reason сохраняются для плана; изменение Settings не перенастраивает текущий снимок. Подробный CLI-контракт — [Workflow Kit](../../packages/workflow-kit/docs/modules/workflow-kit-package.md#опциональный-review).

Изменение Review ON/OFF сначала долговечно сохраняется в том же state.json Kit: preference ID/revision/enabled/recipient/time и review_events. PlanReviewClient сразу ставит адресное `user-choice` с ui_event через DialogueDelivery и прежний WAL/SDK; отдельного транспорта нет. Повтор после сбоя идемпотентен и адресован захваченной при нажатии сессии. До intent устаревшая версия снимается; UNKNOWN не повторяется. Активный ответ и команда не удерживают SDK; ручной Stop, UNKNOWN и неподтверждённая identity запрещают новую отправку. Событие не даёт Start и не меняет роль; агент сверяет review:status до подготовки/публикации. [Контракт решения](user-choice.md#переключение-review).

Основная панель читает канонический Review своего workspace через viewFor при sync/wait; пропущенный watcher не закрепляет cached IDLE. ReviewActivity показывает фактический раунд и рассмотрение замечаний указанным автором. Kit сохраняет отдельные события подготовки пары, запроса запуска, положительного spawn, завершённого отзыва, записанной позиции автора, отмены/ошибки и публикации. ID/время относятся к факту; старым данным передача и дата не выдумываются. PUBLISHED и cleanup удаляют временные файлы, сохраняя review_events; legacy history даёт только известные отзывы/позиции. Второй ленты в sidebar нет.

Control содержит PlanContinuation (продолжение sequential/parallel-плана), ProjectPlanContinuation (разрешение проекта), ReviewContinuation, PlanReviewClient, ParallelExecution/Kit, исполнителей, подтверждение плана и его проекции в src/control/workflow. Алгоритмы базы 0.6.115 сохранены: sequential работает в основном checkout, parallel использует отдельные worktree. С 0.4.4 отдельного переключателя запуска нет ни в интерфейсе, ни в IPC: у любого активного плана одна кнопка `setPlanExecution` («Начать выполнение плана» / «Пауза» / «Продолжить»). У sequential/parallel-плана кнопка включает и выключает механизм продолжений (PlanContinuation/ProjectPlanContinuation) с его проверками; пауза немедленная, состояние кнопки берётся из этого механизма. Без плана, во время планирования и после выполнения кнопки нет. С 0.4.0 план оркестратора ведут ExecutionControl (кнопка запуска и паузы) и ParallelExecution с волнами, delivery-фазой, сигналами Kit и автопаузой — [оркестрованное выполнение](orchestrated-execution.md). Отложенная ротация 0.6.113/114 не включена.

ExecutionControl сохраняет техническую причину blocked/issue. Start/Continue до grant выполняют свежий preflight: dirty даёт paused/blocked и «Продолжить» без новых назначений/Send; clean одним действием продолжает scope. Активные команды завершаются на безопасной границе. Ручная пауза/Stop/UNKNOWN приоритетны. Безопасные relative paths сохраняют rename/пробелы из NUL porcelain; Finder-only untracked после installer игнорируется, tracked/реальные правки блокируют.

DialogueDelivery связывает существующую coordination с [каналом](chatgpt-plugin.md), без второго scheduler. В новых orchestrated-планах dialogue_version=1: короткий URL-bootstrap O и полный [контекст через панель](orchestrator-startup.md), минимальный bootstrap E; готовность доставки требует SDK/bind и принадлежности документа, без ожидания физического конца ответа. O сам отправляет task/context, E result, O acceptance и Kit integration. Intent → Kit → WAL сохраняет эффект с одним operation_id. После accepted следующий pending передаётся сразу, без read/yield/busy/команд. UNKNOWN не повторяется. Старые планы также используют plugin-v1, сохраняя семантику Kit и запрет повтора legacy sending. [Контракт](assignment-dialogue.md).

Новый план хранит полные авторские task_brief/prepared_task и immutable contexts до Review/публикации. После Start backend механически связывает согласованный пакет с реальным назначением и авторизует при свежем grant, без нового O-хода для сочинения. Старый brief-only план сохраняет поздний prepare(dispatch_when_ready=true). [Контракт подготовки](prepared-tasks.md). Claim/verify объединены; telemetry не блокирует доставку. DOCS/O и final/E могут перекрываться при сохранении барьеров cleanup/complete. [Тайминги](dialogue-timing.md).

Привязка собственного согласованного поручения до reservation участника возвращает participant-reservation и продолжается по готовности того же назначения. Отозванный/чужой адресат и stale/hash не скрываются. Успех той же восстановленной записи убирает только прежний RECIPIENT; другая ошибка или UNKNOWN остаётся действующей. Пользователь видит нормальное подключение исполнителей, а не вспышку ошибки.

В 0.5.7 подготовка общей службы не конфликтует между исполнителями. Выбор живой сессии не отменяет bootstrap и не открывает главную вместо временного разговора; новый record после restart не воспроизводит неизвестный Send. Проекция отдельно показывает подготовку/адрес, регистрацию, действующую SDK lease и рабочее уведомление. Pending-транзакция Kit при запуске удерживает только свой проект; Continue требует свежей readiness, архив/удаление остаются доступны. Подтверждённое удаление останавливает scheduler и команды проекта, отзывает связь, затем очищает настройки, без DONE/INTEGRATED ([жизненный цикл](project-lifecycle.md)).

С 0.2.0 вся координация выполняется в [backend](backend.md). Допуск фоновой работы не требует окна, sidebar или видимой страницы: закрытие клиента, ноль зрителей и потеря lease не останавливают выполнение плана, Review и исполнителей. Явная остановка службы (draining) не даёт новых отправок, контекста и назначений, но дожидается текущего ответа, инструментов и команд Kit; отмена остановки продолжает с места ожидания.

ControlFacade создаёт coordination: она владеет разрешениями проектов, журналами отправок, восстановлением основных и назначенных сессий, адресными подписками и допуском интеграции. Модель Desktop в backend вызывает операции переключения/восстановления и получает снимки. Книги назначений, состояния очередей и Map подписок наружу не передаются; очищается только явно адресованный проект. Отображение принадлежит Desktop, состояние настроек — Control. Порт продолжения плана для текущей видимой сессии сохранён для Desktop и donor smoke. С 0.4.7 в коде нет имени AutoPlan; настройки (`projectAutoPlan`) и чекпоинты исполнителей (`autoPlanCheckpoint`) 0.4.6 и ранее при загрузке переносятся под новые имена `projectPlanContinuation` и `continuationCheckpoint`. Workflow Kit 1.9.8 не упоминает AutoPlan: агент сообщает пользователю, что запуск, пауза и продолжение — кнопка выполнения плана.

Execution предоставляет процессы, физический IO, проверку жизни процесса/загрузки ОС и файловые наблюдатели. При подключении/rearm child command receipt watch выполняет одну сверку текущего состояния, закрывая потерю первого fs.watch события; постоянного polling нет. Наблюдатели сохраняют ограниченный список входов и перевешивание при замене inode; наблюдение файлов событийное. Отдельная обработка сообщения допускает ограниченную read-only сверку физического конца для terminal/cleanup/complete; эта сверка не задерживает следующий SDK. Control обращается к ExecutionFacade. Kit остаётся единственным владельцем изменений плана, назначений и транзакций; его Review API и CLI используются без второй копии плана.

execution_origin_session_id выбирается из подтверждённого parallel-плана и сверяется со снимком max_workers основной сессии. recipient_session_id остаётся самостоятельным адресом Review; получатель сверяется повторно по сохранённому состоянию непосредственно перед Send. OFF, Stop и UNKNOWN запрещают новую рабочую доставку. Draft и writer-команда не задерживают SDK; операции Git/интеграции сохраняют собственные ограничения. Готовый source не доказывает merge safe: диагностическое поручение, последовательная интеграция и финальная передача имеют отдельные сохранённые этапы без повторного Send.

Новые worktree и quarantine используют .workflow-pilot-worktrees и .workflow-pilot-delete-. Донорские проекты открываются по исходному формату Kit; перенос регистра локальных проектов не выполняется. Два приложения не должны исполнять один план одновременно.

packages/workflow-kit содержит Kit 1.10.3: новые согласованные подготовленные пакеты, ролевой протокол 12 и installer-правило `.DS_Store`. Runtime формируется staging, установленную копию обновляет installer. Во время commit Kit атомарно пишет verification_progress (version/task_id/check_id/index/total/check_started_at_ms/run_started_at_ms) в git-dir текущего checkout и очищает при успехе/отказе/отмене. Архитектура запрещает циклы, обход ControlFacade и физический IO из Control. [Совместимость](project-compatibility.md).

Проверки: прежние F01–F20/A01–A06, Review recipient/restart/final-send, тесты ControlFacade для отделённых снимков, сохранения UNKNOWN/origin и адресной очистки; полный unit-all, изолированный electron-smoke, kit-check, kit-assignments и architecture. Реальные службы, модельные агенты и профиль пользователя в fixtures не используются. Проверки оркестрации — `tests/orchestrated-execution.test.mjs`, `parallel-execution.test.mjs`, `execution-control.test.mjs`, `session-roles.test.mjs`.
