## A — два исполнителя, контекст и весь цикл

Задание O в новом небольшом Node-проекте: подготовить без Review спецификацию и orchestrated to-do для двух независимых модулей, затем DOCS. T001 — `normalizeLabels(values)` в `src/normalize-labels.mjs`: строки trim, внутренние пробелы схлопываются, пустые удаляются, порядок сохраняется, некорректный тип отклоняется. T002 — `summarizeNumbers(values)` в `src/summarize-numbers.mjs`: count/sum/min/max/average, правила пустого списка явно задать в spec, конечные числа, вход не меняется. Для каждой задачи отдельный `node:test` и разрешённые пути. Не начинать до кнопки пользователя.

После Start O получает уведомление о назначениях и сохраняет prepare каждого поручения с dispatch_when_ready=true одновременно с bootstrap E. После ready backend отправляет разрешённый пакет без дополнительного хода O; до подтверждённого канала нет grant/task/SDK Send. E получают через DOM только правила/identity/bootstrap, автоматически открывают панели и начинают по task O. Они делают реальные проверки/commit, затем каждый отправляет result. O проверяет diff/доказательства, принимает точный SHA и выполняет последовательные интеграции Kit. После них автоматически создаётся DOCS даже при продолжающемся текстовом ответе O; O параллельно её bootstrap готовит и авторизует актуальное поручение, затем завершает cleanup/итог.

PASS: два независимых адресата; ни одного визита/Enable/переноса ID; авторы task=O, result=E; нет рабочего DOM Send; proof/acceptance/INTEGRATED; DOCS, терминальные квитанции, cleanup и итог до complete/отключения связи. Карточка и панель показывают 3/3, активной «Паузы» нет, после повторного открытия complete сохраняется. Временная «Завершение» имеет конкретную причину. Два чистых коммита сами по себе не PASS; ускорение отдельно подтверждается временной лентой.

Внутри — `workspace`, рядом — `ORCHESTRATOR_BRIEF.md` и `REPORT.md`. Существующий каталог, симлинки, product/donor и прежний probe отклоняются. Пользователь добавляет workspace, открывает O и передаёт brief. Он содержит выбор политики только для O; не копировать его в Git/spec/context E до вопроса. T001 — нормализация, T002 — проверка возраста, T003 зависит от интеграции обеих; DOCS дополнительная.

E T002 сталкивается с настоящим отсутствующим `src/policy.mjs`, проверяет два локальных варианта и отправляет O блокирующий question с фактами. O сначала отправляет clarification о доступных пакетах, E отвечает фактами по тому же block_id, O передаёт выбранную политику и decision resume=true. E продолжает ту же задачу, проходит проверку и отправляет result существующего проверенного коммита. T001 независимо выполняется. O принимает/интегрирует, выдаёт T003 и DOCS, завершает план.

До task:start отдельно проверить context_request с недостающим правилом. Разрешённый ремонт общей среды — самостоятельная ветка: один владелец, припаркованные затронутые E, проверка и адресное resume. Самостоятельное решение E без вопроса не подтверждает B.

## C — доработка до слияния

На отдельном scope заранее предусмотреть проверяемое уточнение одного результата до интеграции. O читает E result и обоснованно отправляет revision_request с текущими result_id/source_commit. Появляется новая попытка того же назначения; старые proof и commit сохраняются, старая acceptance не действует. E получает адресное поручение новой попытки, делает исправление, проверки и новый result. O принимает только новый SHA, затем интегрирует.

Вторая задача независима; третья зависит от интеграций обеих. PASS: нет автоматического merge по READY, старого решения новой попытке, повторной реализации уже INTEGRATED; зависимая задача стартует после доказанных интеграций. Нельзя специально портить рабочий проект: только одноразовый опыт с оговорённым уточнением.

## D — пять E и восстановление

Отдельный новый план: четыре-пять непересекающихся заданий, лимит сохранён при публикации. O адресует каждого и различает встречные вопросы/результаты. Проверить занятый O: результаты ждут своей очереди, не теряются, следующее пробуждение происходит после read/yield и физического конца хода без новой пользовательской реплики.

Подопыты записываются отдельно:

- Закрыть только клиентское окно при живом backend; записать точные времена. Новое событие после закрытия и завершение ранее начатого обмена — разные доказательства.
- Restart backend/компьютера → один общий Continue, без отдельных Enable/ID/повторного bootstrap и без повторов UNKNOWN.
- Stop/пауза во время работы → новые пробуждения/назначения/интеграции запрещены; активный ход безопасно сохраняет outbox; Continue продолжает.
- UNKNOWN → отсутствие повторного SDK/DOM Send; фактическое чтение/обработка того же ID уточняет исход, фиктивных квитанций нет.
- Удаление одноразового незавершённого проекта с dirty worktree и pending intent: отмена диалога ничего не удаляет; подтверждение очищает собственные пути/ссылки без требования DONE; сосед продолжает. «Убрать из списка» проверяется отдельно и сохраняет папки. После restart поздние callbacks не возвращают проект.

Для прежнего orchestrated 0.5.7 отдельный опыт миграции: безопасная пауза → O `workflow_assignment_migrate` → обновлённые роли → Continue; READY E присылает отчёт существующего SHA по просьбе O, INTEGRATED не повторяется. Busy/UNKNOWN/dirty должны дать точный отказ, не скрытый сброс.

## Критерии и ограничения

Любое обязательное ручное открытие E/панели, перенос ID, Enable, пользовательский перенос сообщения, рабочий DOM Send после bootstrap, backend-авторство task/result или merge без приёмки O означает FAIL целевого сценария. Host confirmations фиксируются как ограничение автономности; их не обходят. Успех после ручного исправления не превращает исходный FAIL в PASS.

Accepted ≠ read ≠ handled ≠ физический конец ≠ результат ≠ acceptance ≠ INTEGRATED/DONE. SDK-уведомление может отображаться хостом как user; канал устанавливается по фактическому вызову, не по одному визуальному bubble. Сохранённая панель после перезагрузки отдельно доказывает подключение SDK, а не только восстановленные поля.

Автоматические проверки и их границы — [матрица](assignment-dialogue-reliability.md#проверки-и-граница-доказательств). Native Windows/Linux, чистая VM, Chrome recovery и iPad через реальную мобильную сеть проверяются отдельно. Разработка не меняет Test_02, живые профили и не запускает модельные команды. После отчёта пользователь принимает результат или поручает доработку; scope автоматически не архивируется.
