# Приёмка автоматического диалога

Сценарии относятся к встроенному Workflow Pilot и новым разговорам ChatGPT. Начальный статус S1–S3 — **NOT_RUN**. Автоматические fixtures не подтверждают автономность реального хоста. Chrome, сон компьютера и остановленная служба требуют отдельных опытов.

## Подготовка

Установить проверенный выпуск по [инструкции поставки](release.md). Если installer оставил pending из-за работающей службы, пользователь сначала штатно останавливает службу, завершает установку и открывает новую версию. Записать фактические версии приложения/backend, build и протокол панели, Kit и sourceCommit; название приложения само по себе версию не подтверждает.

Из исходного checkout выполнить подготовщик с абсолютным **новым** каталогом, например:

```bash
node scripts/prepare-agent-dialogue-experiment.mjs /Users/oleksandroliinyk/VSCODE/Workflow_Pilot_Dialogue_Acceptance_01
```

Подготовщик создаёт `workspace` — отдельный Git-репозиторий с установленным Kit, локальными зависимостями и тремя заданиями, а рядом — `ORCHESTRATOR_BRIEF.md` и `REPORT.md`. Он не открывает приложение, не запускает модели/службы, не меняет продуктовый checkout, donor или прежний `probe-20261018-1748`. Существующий каталог и симлинки в пути отклоняются. При частичном сбое файлы остаются для диагностики; повтор использовать с другим новым каталогом.

Пользователь добавляет полученный workspace как новый проект, разрешает два параллельных исполнителя и открывает нового оркестратора Chat либо Work. Повтор другого режима — отдельный новый опыт. Первичная общая настройка MCP и вход в ChatGPT выполнены заранее; индивидуальное подключение каждого исполнителя предварительной настройкой не считается.

Оркестратор получает обычный startup и сам открывает панель. Передать ему содержимое `ORCHESTRATOR_BRIEF.md`: оно включает продуктовый выбор для второй задачи. Этот выбор не копировать в Git, спецификацию, план или контекст исполнителя до его вопроса. Обсудить и опубликовать план по `TASKS.md`, пройти обычный Review, если он включён. Публикация не запускает выполнение. Пользователь нажимает ровно одну кнопку «Начать выполнение плана».

## S1 — два новых исполнителя

T001 реализует нормализацию строк, T002 — проверку возраста. Разные файлы позволяют независимую работу. Проверки `npm run test:normalize` и `npm run test:validate` назначить соответствующим задачам. Назначения, worktree и Chat-разговоры создаёт приложение. Агенты вызывают панель в загрузочном ходе; работа начинается после SDK, автоматической привязки и рабочего уведомления.

PASS требует двух разных действующих назначений, автоматического открытия/привязки обеих панелей и начала работ без посещения исполнителей пользователем. Любое ручное открытие панели, join, перенос ID, Enable или требуемое хостом индивидуальное подтверждение означает **FAIL автоматизации S1**. Разрешения хоста не обходить. Успех после ручного восстановления исходный FAIL не отменяет.

## S2 — настоящая блокировка и продолжение

У T002 исходно отсутствует `src/policy.mjs`; проверка падает на импорте. В репозитории доступны два локальных пакета с разными допустимыми политиками. Исполнитель проверяет ошибку и варианты, но не угадывает продуктовый выбор. Через `task:block` он сообщает факты, предпринятые попытки, состояние файлов/команд и точку продолжения, затем завершает ход без DONE.

Оркестратор получает вопрос автоматически и отвечает `assignment:message` по точному `block_id`, используя выбор из своего brief. Исполнитель получает адресное решение, продолжает ту же задачу, подключает выбранный пакет, проходит проверку и делает `commit --task`. Оркестратор проверяет последующую интеграцию. T001 не должна останавливаться из-за этого вопроса.

PASS требует всей цепочки: фактическая ошибка → вопрос → прочтение → коррелированное решение → возобновление → успешная проверка → коммит → проверенная интеграция. Пользователь не исправляет окружение и не пишет «продолжай». Самостоятельное решение без вопроса полезно, но S2 не подтверждает. Ответ «отправлено» без выполненной задачи также недостаточен.

## S3 — третья задача и итог

После интеграций T001 и T002 приложение назначает T003: итоговую функцию `record`, использующую оба результата, с общей проверкой `npm test`. Третий исполнитель автоматически подключается под разрешением того же плана. Служебная DOCS — дополнительное назначение, а не замена T003.

PASS требует соблюдения зависимостей, автоматического подключения третьего исполнителя, содержательного результата, проверки main, DOCS и cleanup, итогового ответа оркестратора до отзыва разрешения. После завершения нет новых рабочих уведомлений или бесконечных подтверждений.

## Доказательства

Заполнить созданный `REPORT.md`: PASS/FAIL/NOT_RUN отдельно для S1–S3; версии; project/scope; роли, назначения и task IDs; полный список действий пользователя; времена bootstrap/bind/уведомлений/вопроса/решения/возобновления; коммиты и доказательства интеграций. Нужен очищенный экспорт с фиксированным `through_seq`: первая страница задаёт границу, последующие продолжают `after_seq` до `complete=true`. Недоступный экспорт и gaps прямо ограничивают выводы.

Не включать приглашения, секреты или исходные host metadata. `accepted`, `read`, решение и выполненный коммит — разные факты. При закрытии интерфейса записать время: завершение ранее начатого обмена и получение нового события после закрытия различаются.

Пять исполнителей, занятый адресат/черновик, новая блокировка, замена назначения, пауза и перезагрузка с одним Continue входят в автоматическую матрицу; их живые варианты — отдельное расширение приёмки. Сохранность привязки после restart не означает сохранения разрешения.

## Автоматическая матрица

`tests/automatic-agent-dialogue.test.mjs` проходит настоящий ContextSession и кнопку Start, Control/Execution, staged HTML и SDK, Python MCP, сохранение и реальные команды Kit/Git. Симулируются только физический хост/композер и действия модели. Отдельно проверяются оркестраторы Chat/Work, Chat-исполнители, два параллельных назначения, block/decision, коммиты/интеграции, третье назначение, DOCS и финальное отключение. Нет ручного открытия исполнителей, Enable и рабочих DOM Send.

`workflow-channel`, `plugin-enrollment`, `chatgpt-plugin`, `workflow-signals`, `parallel-execution`, `execution-control` и проверки Kit покрывают один O и пять E, свежую identity, несовместимые версии, поздний SDK, исторические результаты, большой контекст, занятость, idempotency, неизвестный исход без повторов, потерю подтверждения, устаревшие решения, предел повторных блокировок, Stop/паузы/restart и legacy. Отдельный тест подготовщика проверяет изоляцию, отказ перезаписи и реальную ошибку отсутствующей политики.

Готовый выпуск означает «готово к проверке автоматического подключения и автономного продолжения». После живого отчёта пользователь принимает результат либо поручает расширение плана. Архивирование требует отдельной приёмки.
