# Desktop — отдельный клиент

## Ответственность и поведение

Identity: package workflow-pilot, product Workflow Pilot, bundle com.oleynik.WorkflowPilot. Свои userData/browser/runtime/службы обязательны. Старые профили, cookies, app-state и подпись не импортируются. Формат существующих session ID и внешние DOM-контракты сохраняются; имена каталогов/служб нового продукта — собственные.

С 0.5.1 на всех трёх ОС обычный запуск открывает [встроенное окно службы](native-window.md) — этот же клиент в режиме embedded внутри службы; ниже описан клиент как отдельный процесс («Окно через HTTP (тест)», iPad через браузер). С 0.2.0 `npm start` и открытие `.app` запускают клиент (`src/frontend/desktop/client.mjs`). Его процесс владеет только окнами: основное окно с sidebar и изображением выбранной страницы, архив, редактор цветов и окна просмотра popups. Профиль клиента — `<appData>/Workflow Pilot Client`; страницы, stores, Control и модель Desktop находятся в [backend](backend.md). Клиент находит backend по приватному descriptor или запускает его, берёт право управления и показывает состояние из потока событий. Закрытие окна, Cmd+Q и падение клиента backend не останавливают.

Sidebar, архив, Доктор, настройки, onboarding, архив/удаление и цвета используют прежний UI из `src/frontend/desktop/ui/` и прежние preload. Каждая IPC-возможность входит в фиксированный список `DESKTOP_CHANNELS`; до действия проверяются точные webContents, главный frame и URL локальной страницы. Клиент передаёт вызов как `ui.invoke` в backend, где модель Desktop проверяет вход как прежний IPC-обработчик; ответ сохраняет прежний конверт `{ok, result, error, state}`. Прямых обращений UI к Control нет, preload даёт только разрешённые клиентские OS-возможности: диалоги файлов устройства, clipboard по явному действию, ввод в изображение страницы. У страниц ChatGPT нет локального preload: клиент получает только PNG-кадры.

Без backend или при ошибке службы UI остаётся доступным: sidebar показывает полное пустое состояние с причиной (`BACKEND_UNAVAILABLE`, `BACKEND_OWNER_CONFLICT`, setup-required). Путь нового проекта выбирает диалог backend — это папка компьютера backend; локальный файловый диалог клиента его не подменяет.

Клиент держит lease управления: свободный берёт автоматически, занятый — только командой меню «Взять управление»; продление каждые 10 с. Один `clientId` на процесс окна, один acquire за раз, временные ошибки повторяются ([Backend](backend.md)). Если lease у другого окна — заголовок «наблюдение (управление у другого окна)», изменения отвечают `BACKEND_LEASE_HELD`; пока окно только получает управление — «получение управления…» и просьба повторить действие. Журнал окна — `client-events.jsonl` в профиле клиента. При обрыве связи заголовок сообщает «нет связи, данные могут быть устаревшими», изменения блокируются; клиент переподключается к новому descriptor (новый boot — новые зрители и lease, ничего не переотправляется). Поток событий восстанавливается сам: любое успешное переподключение — со снимком или продолжением по номеру события — снимает состояние «нет связи»; ошибка обработчика данных не обрывает поток и пишется в журнал (`stream-handler-failed`), нечитаемое событие заменяется новым снимком, старое соединение при ошибке закрывается, причина разрыва (`stream-lost` с кодом) пишется в журнал. Остановленную службу клиент сам не перезапускает: для этого пункт «Запустить фоновую службу». Клиент другой версии — наблюдатель с объяснением, какую службу остановить.

Меню Workflow Pilot: «Управление у этого окна» / «Взять управление», «Остановить фоновую службу…» (подтверждение, draining) или «Отменить остановку фоновой службы», «Скрыть», «Закрыть окно (работа продолжится в фоне)». Меню «Вид» → «Обновить ChatGPT» перезагружает страницу backend по явному действию. Это меню заменяет системный значок там, где tray нет.

С 0.4.0 дерево проекта показывает сессии-оркестраторы (состояние, счётчик, назначения в ожидании очистки) и чаты обсуждения; группа «Исполнители» остаётся только для legacy parallel-планов. Карточка плана описана в разделе [«Ход работ»](#ход-работ). Одна кнопка «Начать выполнение плана» / «Пауза» / «Продолжить» (`pilot:plan-execution`), других переключателей запуска нет; меню сессии «Назначить оркестратором» (`pilot:assign-orchestrator`) появляется, когда оркестратор плана не определён. Подробнее — [оркестрованное выполнение](orchestrated-execution.md).

Выбор [внешней сессии плагина](chatgpt-plugin.md) скрывает изображение браузера и показывает «Открыто в ChatGPT». Он не создаёт страницу, не пересылает контекст и не показывает кнопку выполнения плана. В меню проекта остаются «Новый Chat»; пункт экспериментального запуска через плагин и его уведомление удалены. Панель связи ChatGPT адресует сообщения по собственной подтверждённой привязке, независимо от выбранной здесь сессии.

Control владеет настройками и сериализует запись через Execution/files; неудачная запись не меняет принятые настройки. Быстрые изменения цветов объединяются в очереди, полный сброс палитры — отдельная операция. Текущий план и транзакции принадлежат только Kit. Раздел Настроек «Доступ с iPad и других устройств» и необязательный шаг мастера (`ui/remote-access.mjs`) показывают проверенные шаги Tailscale, адрес и QR-код, запросы подключения с кодом (подтвердить или отклонить) и список устройств с отключением; в веб-клиенте iPad те же элементы только информируют ([удалённый доступ](remote-access.md)). Связанные сценарии: [первый запуск](first-run-onboarding.md), [проекты и архив](project-lifecycle.md), [Control](control.md), [браузер](browser.md).

Та же кнопка плана разрешает [автоматический диалог](chatgpt-plugin.md) всем назначениям. Панель подключается из bootstrap и показывает scope/task/assignment без ручных ID/Enable; Stop прекращает отправки всего плана. Sidebar не переназначает адресата. Restart требует одного Continue. Живая проверка без посещения исполнителей — [A–D](automatic-agent-dialogue-acceptance.md).

Read результата не означает запуск проверки; неизвестная операция не называется мышлением модели. Только durable complete убирает «Паузу»; приёмка scope и архив проекта различаются, backend решает об остановке архива по свежему состоянию, не по карточке. [Тайминги и стадии](dialogue-timing.md).

## Ход работ

Sidebar управляет планом; [панель](chatgpt-plugin.md#ход-работ-в-панели) показывает динамику участников. Управляющих кнопок плана в панели нет.

**Проекция.** Backend строит на проект одну проекцию `workProgress` (`src/contracts/work-progress.mjs`, сборка в `desktop-model`): этап, «в main N из M», задачи со стадиями, режимом и временем, текущие действия всех участников (`act` — действие, `wait` — ожидание, `warn` — проблема), историю и одну проблему с действием. Источники только существующие: план Kit (для выбранного проекта — свежее чтение монитора плана), `execution.view`, `planActivity`, `assignmentStage`/`executorStatus`, сообщения WAL, `command-activity` и прогресс проверок Kit, интеграция, startup-прогресс. Служебные ready/recovery/probe/startup-context, замена (superseded), квитанции, yield и конец хода событиями не считаются. Нового scheduler или хранилища нет. Snapshot модели несёт `workProgress` выбранного проекта (native и HTTP через SSE); смена смысла проекции будит ожидания панели проекта. Ожидающий участник без новой стадии дольше 15 минут показывается как «нет новых событий N мин» и даёт проблему с кнопкой «Открыть чат».

**Дерево.** Карточка постоянной высоты: название слева, справа меню «…» над меткой Chat; одна строка даты, роли и прогресса. Новый Chat создаётся из меню проекта, первый — кнопкой подготовки проекта. Doctor использует тот же вход. Выбора режима и просмотра старых Work-сессий нет.

**Карточка плана** занимает доступную высоту и делится на три зоны: закреплённый верх (короткое название — заголовок спецификации, цель во всплывающей подсказке; этап со спиннером: «Подготовка», «Обсуждение плана», «План готов», «Запуск», «Выполнение», «Нужно внимание», «Пауза», «Завершение», «Ждёт приёмки»; полоска и «в main N из M»), прокручиваемый список задач и закреплённый низ (одна кнопка выполнения, причина удержания, блок проблемы, подсказка приёмки «Принимаю результат, закрой план», переключатель Review). Строка задачи: значок (✓ влита в main, спиннер — выполняется, «!» — внимание, ○ — не начата), ID и полное название, стадия в нынешних формулировках, для незавершённой — режим, справа время текущей стадии; Kit-проверка коммита — «Kit проверяет коммит · проверка · N из M». Начатая незавершённая задача открывает чат исполнителя; выбранная подсвечена. Список сам прокручивается к задаче с проблемой, иначе к выполняемой, не сбивая ручную прокрутку. Блок проблемы появляется только при действии пользователя или остановке: неизвестный исход команды или отправки (кнопка «Разобрать неизвестный исход»), эскалация, ошибка плана, молчание исполнителя. Удалены: «Новая сессия», `agent-time`, дубли статуса, `execution-stages`, пустой `execution-next-action`, «DOCS checks:[]».

**Роли и выбор с 0.5.30 (Kit 1.9.8).** Без плана новая сессия — «Планирование». Владельцем она становится, когда агент вызывает `plan:mode-request` (Kit, compare-and-set); остальные сессии становятся «Обсуждением», Kit отвечает им `PLANNING_OWNED`. Роль владельца следует [выбору пользователя](user-choice.md): «Выполняет план» (sequential) или «Оркестратор». Отметка «Ждёт вашего выбора» в дереве и карточка над задачами плана — тот же контракт, что в панели (`pilot:choose`). Архив сессии-владельца снимает запись; меню «Назначить оркестратором» до публикации передаёт планирование явно. С Kit 1.9.7 действует прежний захват по первой ручной отправке. Однозначный отказ Kit при назначении ставит паузу «Kit отказал в назначении T…» с «Продолжить»; назначение без открытой страницы исполнителя паузу не держит.

**Review с 0.5.28 (Kit 1.9.6).** Переключатель Review — решение пользователя, действующее в момент публикации плана: если его включили во время обсуждения, Kit отвечает `REVIEW_REQUIRED` с указанием пройти ревью (`review:prepare` → `review:run` → `review:respond` → `review:publish`), и оркестратор не просит выключить Review; выключение до публикации отменяет незавершённое ревью (`CANCELLED`), план публикуется обычным способом. Пока идёт ревью или публикация (`RUNNING`/`PUBLISHING`), переключатель заблокирован (`REVIEW_BUSY`); после публикации плана (ACTIVE/BLOCKED) — тоже (`REVIEW_LOCKED`) до закрытия плана. Запрет действует в Kit, поэтому его не обходят HTTP-клиент и iPad; кнопка в карточке плана неактивна и в подсказке называет причину.

**С 0.5.26.** Пока плана нет, «Сейчас» показывает O и чаты обсуждения по состоянию их страницы: «работает над ответом» со спиннером и временем, у O в паузе — «ждёт вашего сообщения»; этап «Подготовка» — только во время старта, затем «Обсуждение плана» (спиннер, пока O отвечает). Готовый, ещё не запущенный план (с 0.5.27) показывает ожидание «План ждёт вашей проверки и запуска: нажмите «Начать выполнение плана»» со временем — независимо от ответа агента. Отложенная очистка назначения (`cleanup PENDING`) — ожидание с причиной: «очистка ждёт конца хода исполнителя» или «…завершения команды исполнителя»; дольше 15 минут — проблема с кнопкой «Открыть чат» исполнителя (открытие чата подтверждает конец хода). «Завершение» без действий идёт без спиннера. Сессии закрытого плана не дают уведомлений и строк старта.

**Палитра.** Sidebar, панель и фон окна используют одни токены `src/contracts/palette.mjs` (значения прототипа v8, светлая и тёмная темы); sidebar вставляет их встроенным `<style>` в рамках CSP, HTTP-клиент `web/index.html` хранит те же значения (сверяет тест), окно берёт `shellBackground`. Спиннер общий, с упрощением при reduced motion.

## Контракт и зависимости

| Часть | Код | Контракт |
| --- | --- | --- |
| Клиент | `frontend/desktop/client.mjs` | Запуск/подключение backend, окна, lease, меню, relay IPC → `ui.invoke` |
| Соединение | `frontend/client/connection.mjs` | Handshake, snapshot/SSE с resync, команды с requestId, acquire/renew/release |
| Изображение страницы | `frontend/client/browser-view.mjs`, `ui/browser-view.*` | Зритель, кадры, перевод координат, ввод, clipboard, файлы |
| UI и preload | `frontend/desktop/ui/*`, `*-preload.cjs`, `ipc.mjs` | Фиксированные каналы и проверка источника |
| Модель Desktop | `backend/desktop-model.mjs` | Прежние действия pilot:*/archive:*/colors, снимки состояния |
| Smoke-стенд | `frontend/desktop/bootstrap.mjs`, `application.mjs` | In-process окно только для `npm run smoke` в разработке |

Ввод в изображение страницы. Печать идёт через скрытое поле (русская раскладка и IME), служебные клавиши и указатель передаются как есть. Вставка — только через событие `paste` скрытого поля (Cmd/Ctrl+V, «Правка → Вставить», пункт меню): текст до 60 КБ берётся из `clipboardData` и уходит в `clipboard/paste`, файлы и картинки (скриншот) — как drop в точку последнего нажатия, иначе в центр. Основной процесс буфер не читает; в Electron 44 `clipboard` асинхронный, запись — только с `await`. Правая кнопка передаётся странице и открывает меню клиента «Вырезать / Копировать / Вставить / Выделить всё»: копирование и вырезание доступны при непустом выделении, вырезание — копирование в буфер клиента и Backspace, «Выделить всё» — Cmd+A (Ctrl+A вне macOS); Cmd/Ctrl+X работает так же. Перетаскивание файлов (до 10, каждый до 32 МБ) на изображение страницы: renderer читает содержимое файлов (пути не передаются), основной процесс проверяет имена и размеры и вызывает `drop`. Ошибки вставки, меню и передачи файлов пишутся в `client-events.jsonl` и показываются кратким статусом поверх страницы.

Клиент зависит только от `src/contracts` и локального UI; Electron-процесс backend и его модули он не импортирует. Packaged-сборка игнорирует флаги `--client-*` и `--smoke`. Dependency-cruiser проверяет, что release-пути не доходят до in-process окна и Frontend не обходит API.

## Проверка

`desktop-client` проверяет клиент с fixture backend: закрытие и kill клиента без потери страницы, relay каналов, lease и наблюдателя, устаревание и reconnect, а также вставку текста, меню правой кнопки (выделить всё, вырезать), вставку картинки и перетаскивание файлов через настоящий renderer клиента; буфер fixture-клиента — в памяти, системный не затрагивается. `backend-desktop-model` — модель Desktop в backend. `desktop-boundaries` — запреты IPC, фиксированные preload-возможности, освобождение подписок, запись настроек и отсутствие секретов в DTO. Electron smoke (in-process стенд) проходит реальные IPC и Chromium в скрытых fixture-окнах без показа и фокусировки окон ОС; clipboard в памяти. Smoke также проверяет раскладку на настоящей боковой панели: в строке списка проектов название занимает свободную ширину, «В архив» — компактная кнопка справа; строка начатой задачи to-do plan (кнопка открытия сессии) переносит название по ширине панели, как обычная. Фоновая проверка проекта при переключении сессии молчит и не сдвигает карточку плана; показывается только её ошибка. Выбор проекта или сессии и загрузка её страницы ChatGPT не показывают плашку прогресса над списком и не сдвигают его; плашка прогресса появляется только у операций дольше секунды (подготовка, восстановление, архив, удаление, отправка контекста). Перенос smoke на связку клиент/backend отложен.

Живые проверки Mac — вход ChatGPT, системные разрешения, clipboard, файлы, меню, reopen и значок — выполняет пользователь по [сценарию приёмки](../acceptance/backend-independence.md).

Запуск исполнителя показывает отдельные стадии: подготовка службы/контекста, отправка bootstrap, ожидание постоянного адреса, регистрация участника, SDK/bind, завершение загрузочного хода, рабочее уведомление и прочтение. Они вычисляются из ContextSession и канала без второго хранилища состояния; ready страницы не объявляет SDK готовым. Неизвестная отправка остаётся предметной ошибкой без повтора. Обычный выбор живого исполнителя сохраняет его страницу даже без постоянного URL ([Browser](browser.md)).

Архив позволяет убрать или подтвердить удаление незавершённого проекта; предупреждение показывает точные пути и потерю незакоммиченного. Подтверждённое действие останавливает принадлежащие проекту операции и очищает ссылки, сохраняя соседние проекты. «Убрать из списка» сохраняет папки, «Удалить с диска» удаляет выбранный репозиторий и собственные worktree; облачные чаты сохраняются. Частичная очистка предлагает повтор, а не требование закончить план ([контракт](project-lifecycle.md)).

[Chat-only URL-start](chat-only-startup.md) сохраняет раздельные статусы команды, регистрации, адреса, чтения и отмены в общей проекции Desktop/HTTP/панели. API/IPC/preload создают только Chat без параметра режима. Readiness не зависит от переключателя; вход, документ, принадлежность и актуальность пакета остаются обязательными. Отмена, пауза, потеря входа и ещё не готовая страница сообщаются отдельно от устаревшего пакета.
