### I.1. Завершение чтения startup-пакета S при изменении плана

Результат: выданный и аутентифицированный `model-pull` пакет роли S
можно дочитать и однократно подтвердить, даже если **после начала
чтения** соседний O интегрировал задачу и изменил revision/HEAD.
Подтверждение означает «этот снимок получен», **не** «снимок до сих
пор актуален». Если данные изменились, отображается предупреждение,
что для следующих решений нужен свежий контекст, но подтверждение
полностью прочитанного пакета не блокируется.

Не ослаблять проверку *до первой выдачи пакета*: уже устаревший или
отменённый непрочитанный пакет запрещён. Сохранять проверку host
identity, разрешённой роли, binding, session/project identity,
`request_id`, `message_id`, SHA-256, всех `parts_read` и запрета
после supersede, удаления или отмены. Не дать S grant O/E, команду
`task:start` или чужие сообщения. Возобновление после рестарта —
того же пакета без повторного SDK Send. Старый `sdk-notification`
и его UNKNOWN сохраняют исходный контракт. Исполнитель O/E и его
инструкции не должны переходить к незащищённому подтверждению.

Проверки на настоящем файловом WAL в изолированном fixture:
стадия S rev5 → part0 → rev6/интеграция соседнего E → parts1/2 →
`startup_complete` **успешен**, ровно один `startup.complete`;
повтор complete идемпотентен; restart сохраняет receipts.
Отрицательные: stale **до** первого чтения; новая попытка/superseded,
удаление проекта, чужой conversation/E, неверный digest, часть
пропущена, повреждённый WAL, старый SDK UNKNOWN — отказ без
повторной отправки. Тесты — `tests/startup-context.test.mjs`,
`tests/plugin-communication-store.test.mjs`, при необходимости
`tests/dialogue-delivery.test.mjs`.

### I.2. Терминальные состояния startup и понятная ошибка

UI и API обязаны различать `prepared/pending`, `reading n/N`,
`complete`, `stale/cancelled/failed`; если `startup_complete=true`,
не показывать «ожидание чтения» только из-за исторического поля
`delivery=pending`. Согласовать хранимый receipt и проекцию status:
источник истины — успешное `startup.complete`, не SDK-accepted,
не конец хода и не DOM Sent. Для ошибочного/stale старта S —
**терминальное** сообщение с понятным следующим действием;
не запускать повторных ходов чтения/бесконечной анимации.
Запрет повторной неизвестной отправки остаётся.

Проверить панель MCP, desktop sidebar и HTTP/UI-контракты на
изолированных fixtures; не расширять публичные полномочия.
Сверить `desktop-model`, `progress.mjs` и `plugin/service`:
они тоже формируют startup-статус и должны участвовать в задаче.
Назначить `unit-all`, `chatgpt-plugin` и адресные checks.
Точные пути перечислены в ToDo FIX-STARTUP-UI.

### I.3. Правдивый прогресс, поручения, проверки и финал

В **клиенте Workflow Pilot**, не в статичном ответе ChatGPT:

1. Показывать одновременно `Результаты исполнителей: X/N`
   (только если есть проверяемое основание: проверенный commit/result
   соответствующего назначения) и `Интегрировано: Y/N`
   (Kit DONE в main). Если доказательство отсутствует — ожидание
   или неизвестно, не увеличивать X на основании открытого чата или
   готовой кнопки. Индивидуальная строка E различает «работает»,
   «результат получен», «SHA принят», «интегрировано», «блокировка».
   X может превышать Y; Y никогда не выводить из X. Для DOCS
   применять ту же доказуемую семантику; не менять Kit status.
2. Различать `подготовлено`, `авторизовано, ожидает канала`,
   `доставка принята транспортом`, `исполнитель действительно
   приступил`. `dispatch_when_ready:true` + `pending` **не**
   доказывают SDK-delivery или старт `task:start`. Формулировки
   сообщений O и надписей UI должны использовать ту же семантику.
3. `checks:[]` для DOCS отображать как «проверка документальной
   транзакции» и «проверки приложения не запускались Kit», а
   внешнее `node --test` — лишь при наличии отдельного evidence.
   Не заставлять DOCS автоматически запускать полную suite.
4. `ACTIVE / READY_FOR_ACCEPTANCE` + все DONE показывать пользователю
   как «Выполнение завершено; ожидается приёмка пользователя».
   Не писать «выполняется» и не архивировать без поручения.
5. Автообновление происходит через **имеющуюся** модель backend и
   SSE/события клиента, без новых каналов и polling моделью.
   Проверить переход 1/4+2 результата → 2/4 интеграции,
   затем финальные 4/4 и cleanup. Отображение должно реагировать
   на изменения, а не оставаться снимком.

Включить реальные точки ответа инструментов
`workflow-channel.mjs` и `assignment-dialogue.mjs`: O должен
получать различимые стадии и не объявлять доставку по одному
`pending`. Ролевые инструкции Kit не менять без нового upgrade.
Тесты полного набора `unit-all` дополняют узкие проверки, иначе
часть изменяемых тестов пропускается. Точные пути — FIX-PROGRESS
в ToDo. Не делать отдельную систему учёта; сохранять
совместимость sequential/parallel/legacy.
Проверить `backend-desktop-model`, `parallel-execution-ui`
и `workspace-session`; изменять проекцию сессии только
при необходимости, не ломать awaiting-acceptance.
