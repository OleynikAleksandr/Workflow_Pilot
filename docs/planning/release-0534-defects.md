## UI001 — убрать дублирующую область

Кнопку «Текущие действия» удалить полностью, без переноса в меню и без нового входа. Удаляются dialog-копия панели, открытие/закрытие/фокус, состояние её показа, временное скрытие native-страницы, соответствующие клиентские IPC/preload/HTTP-ветки и их стили. Обычный Chat не отсоединяется ради этого представления.

Явная опись элементов, которые sidebar.mjs перемещает в dialog:

- `plan-choice` и экземпляр `mountCurrentActions` sidebar удалить вместе с обработчиками выбора/отрисовки дубликата. Полная карточка выбора остаётся только в настоящей MCP-панели; общий renderer для неё сохранить.
- `session-notice` с `retry-context`, `cancel-context`, `observe-context`, `return-chat` и `conversation-recovery` с `reconnect-chat` оставить в исходных узлах index.html. Сохранить условия допустимости операций и показывать только актуальную незавершённую подготовку/проблему восстановления; подтверждённый успешный startup не возвращать постоянной карточкой.
- `plan-attention`, `plan-run-message`, `plan-continuation-message` оставить в исходных узлах карточки опубликованного плана с действующими условиями нужного действия/блокировки. Они не становятся второй лентой общего прогресса или Review. Навигация и одна кнопка Start/Пауза/Продолжить сохраняются.

Обновить проверки вложенности в dialog на отсутствие дубликата и доступность именно нужных действий при их реальных условиях. Не выдавать скрытый элемент за доступный путь. В HTTP-клиенте без MCP iframe удалённый fallback выбора больше недоступен: это явное ограничение, без нового экрана, входа или переноса выбора в sidebar.

Review остаётся на прежнем месте. Будущий отказ от Electron/sidebar, полноэкранная панель и новая боковая панель — отложенное обсуждение. Оно не входит в эту работу.

## EXEC002 — зависание результатов за прежним выбором

Подтверждённый случай: result T001 сохранён в 15:29:43.957, T002 — в 15:30:25.738 Europe/Madrid. На срезе WAL до 15:32:57 оба pending/read=false, без intent отправки. Gate O относится к user-choice от 15:16:39: SDK accepted, read в 15:16:51, reply_observed=false. У сообщения scope_id=null, нет dialogue_version=1. Grant плана running.

Старый observed требует новые turnId/userTurnId либо одновременный рост assistantRevision/userMessagesRevision. SDK не создал нового видимого user bubble: userMessagesRevision осталось 2, turnId/userTurnId пустые; assistantRevision выросло с 287 до 672, ответ завершился. Наличие deliveryGate запрещает выдачу следующего сообщения. На клоне состояния свежий idle без нового user bubble не освобождает очередь; контрольное увеличение userMessagesRevision освобождает result. Реальный чат не изменялся.

Исправление должно подтверждать конец ответа на пользовательское событие по положительным свежим фактам своего разговора без обязательного user bubble. Прочтение не приравнивается к окончанию работы. Обработанный доплановый выбор не удерживает очередь нового scope. Нельзя просто удалить gates, обнулить их при Start или вручную записать reply_observed ради продолжения.

Сохранить защиту активного ответа/команд, точный conversation/document/attempt, ручную остановку, UNKNOWN и запрет повторного Send. Установить явную семантику завершения пользовательского события отдельно от результата назначения E: выбор режима не обязан запускать task:start и не является result/yield задачи. Учитывать события до/после назначения роли, публикации, mount панели и перезапуска.

Критерии: после выбора, Review, публикации и одного Start оба result доставляются и читаются O; он может принять точные SHA, интегрировать их и продолжить зависимую задачу. Повторный callback, рестарт и поздний конец предыдущего ответа не снимают чужой gate и не создают вторую отправку. Ожидание очереди показывает фактически блокирующее сообщение, даже если оно принадлежит предыдущей доплановой стадии.

## EXEC001 — ранняя привязка до регистрации

В WAL подтверждены пять assignmentPlanBind/PLUGIN_COMMUNICATION_RECIPIENT в 15:28:13.487–15:28:20.256. Текст: «Выберите адресата своего назначения из workflow_communication_participants». Reservation T001 появилась только в 15:28:20.924, T002 — в 15:28:24.436; после неё task.plan_bound, регистрация, startup.complete и одна доставка каждому E прошли. В ledger оба уже running, но содержали прежний entry.error.

openWorker/restoreExecutionPage вызывают dialogue.start; bindPrepared вызывается до проверки готовности и ищет адресата в enrollment/member. Для ещё регистрируемого собственного E это ожидаемая стадия, а не отказ пользователя. Связывать пакет после подтверждённого адресата либо возвращать явное ожидание. Сохранять подготовку автором до Start; не возвращать дополнительный модельный ход O для сочинения поручений.

Свежий подтверждённый успех того же assignment/attempt должен завершать его прежнюю ошибку в текущем состоянии. Исторический отказ остаётся диагностическим фактом. Нельзя фильтровать все RECIPIENT или задерживать все ошибки: чужая identity, отозванный target, stale подготовка, закрытый intent и UNKNOWN остаются настоящими запретами.

Критерии: разные порядки reservation/bootstrap/bind двух E и их задержки не создают ложные оранжевые карточки, лишние назначения и повторные Send; обычная стадия — «Подключаем исполнителей». Настоящая проблема называет участника, причину и нужное действие; её возникновение и разрешение доступны после обновления экрана.

## REVIEW001 — своевременная передача решений из UI

Стартовый контекст Test_002 в 15:06:41 содержал Review OFF. Переключение в 15:14:52 сохранило enabled=true/stage=IDLE. PlanReviewClient обновляет файл и UI; ReviewContinuation рассчитан на существующий review run, поэтому уведомления об IDLE-переключении нет. Агент сообщил старое OFF. Защита публикации затем потребовала Review; рецензирование прошло. Дефект — позднее извещение, а не обход Review.

Единое правило для смыслового действия в sidebar/панели: сначала долговечная запись решения, затем немедленная постановка адресного события в существующий канал. Панель уведомляет свой подтверждённый разговор, агент читает событие, сохраняется отдельная read-квитанция. Решение не выводится из того, какой чат позднее выбран слева. Использовать существующие WAL, очередь, SDK и idempotency; не создавать второй транспорт, универсальную шину или новый журнал.

В рамках этой задачи подключить Review ON/OFF. Прочие клики не превращаются автоматически в модельные сообщения. Уже работающий выбор оркестрации сохраняется и использует совместимую семантику завершения из RESULT-DELIVERY. Общий механизм может принимать только явно перечисленные смысловые события.

«Сразу» относится к сохранению и постановке в очередь. Активный ответ/команда не прерываются, закрытая панель/неподтверждённая identity не считаются доставкой. После восстановления доставляется актуальное разрешённое событие без повтора неизвестного Send. Быстрые ON→OFF, повтор, отказ сохранения, смена выбранного проекта и поздний callback не подменяют порядок/получателя. До начала отправки устаревшую версию можно заменить по явному правилу; после intent исход не угадывается.

Событие сообщает состояние, версию и смысл: Review ON требует согласования спецификации и плана до публикации; OFF разрешает обычный путь до публикации. Оно не даёт разрешение реализации, не переключает Start и не меняет ранее опубликованный план. Агент сверяет актуальный review:status перед prepare/публикацией. Защита Kit сохраняется независимо от доставки уведомления. При ручном Stop/паузе обновление состояния не обходит действующий запрет; чтение актуального состояния остаётся возможным разрешённым способом.

При изменении текста инструкций согласовать backend, read_message, startup, канонический role-protocol, шаблоны Kit и MCP-описания. Не возвращать ручные join/ID/Enable и не повторять стартовый пакет.

## REVIEW002/REVIEW003 — текущая стадия и история

Фактический Review Test_002: первый раунд changes_requested, второй approved, затем PUBLISHED. В установленном HTML #plan-review-message безусловно display:none; изолированная CSS-проверка при hidden=false подтвердила скрытие. Backend умеет reviewActivity, но причина отсутствия активной стадии именно в основной панели ещё не установлена. Реализация должна воспроизвести полный путь state → watcher → backend → MCP sync/wait → renderer, а не объявить CSS sidebar общей причиной.

Основное место текущего статуса — настоящая Workflow Pilot панель: «Рецензирование плана · Claude · раунд N», рассмотрение замечаний оркестратором, повторный раунд, ожидание публикации, ошибка/решение. Не заменять известную стадию общим «работает над ответом». Настройка Review остаётся на прежнем месте; подробную вторую ленту в sidebar не возвращать. Номер раунда и стадия относятся к своему проекту/run.

История сейчас собирается из startup, выбора пользователя и рабочего канала, но не из review_history. После PUBLISHED reviewActivity=null; сведения о раундах исчезают. Добавить подтверждённые смысловые события: спецификация и ToDo Plan переданы на ревью; получены замечания; автор рассмотрел/доработал; передано повторно; получено согласие; план опубликован. Подготовленный пакет, запуск рецензирования, отзыв, позиция автора и публикация — разные факты.

Использовать канонические записи Kit и устойчивые ID/время, не слова модели. При необходимости добавить недостающие метки в исходники Kit с совместимым чтением уже записанного Review; старым данным не выдумывать дату/передачу. История сохраняется при публикации, закрытии панели, рестарте и штатной очистке Review. Не создавать дубли при sync/wait, повторном чтении или переключении проекта. Успех, changes_requested, ошибка и отмена различаются. Review ON сам по себе не означает запуск рецензента.

## STATUS001 — понятное состояние и фактическая блокировка

На снимке 15:30:28 показано «Сообщение ожидает доставки оркестратору» и «Сохранение сообщения не подтверждает его получение». Это fallback planActivity: progress выбирает incoming текущего scope, а старый gate вне него не объясняется пользователю.

Показывать смысл: нормальная передача, результат готов и ожидает рассмотрения, восстановление соединения, подтверждённая блокировка. Если результаты ещё не отправлены, не утверждать, что O проверяет их; если прочитаны — не называть их недоставленными. Реальная причина удержания предыдущим событием должна попадать в проекцию. Неопределённость сохраняется, но объясняется понятным следствием, а не техническим дисклеймером.

Оранжевое выделение — конкретная проблема/решение, требующие внимания пользователя. Ожидаемое подключение, занятость агента и автоматическое восстановление имеют нейтральный статус. Проблема, которую приложение не может разрешить, содержит понятное следующее действие только если оно действительно доступно. Исправление текстов не заменяет исправления EXEC002.

Технические saved/accepted/read, generation, lease и gate доступны в диагностике. Нужные инструкции полностью переносятся по ширине, таймер не обрезает текст. Завершённое/разрешённое событие переходит в историю; стабильные идентификаторы и фактическое время позволяют прочитать причину даже после быстрого изменения экрана. Не показывать несколько версий одного процесса в разных местах.

## Проверки и границы

Автоматические проверки — только временные fixtures, настоящий Kit/Git/MCP/SDK-адаптер и Electron renderer с детерминированными ответами. Реальные модельные команды, пользовательские cookies/профили/службы, donor и удалённый тестовый проект не используются. Удалённый Test_002 не восстанавливать и не создавать заново.

Связная регрессия начинается **до публикации**: bootstrap с OFF → включение Review во время ожидания/ответа → чтение события → выбор оркестрации без нового user bubble → два раунда Review → публикация → один Start → отложенная регистрация двух E → task/read/конец хода → два result → доставка/read O → acceptance точных SHA → интеграции → зависимая задача → DOCS → cleanup/complete. Предыдущий fixture с уже опубликованным планом не покрывает доплановый gate и не заменяет этот сценарий.

Отдельно проверить crash до/после записи события/intent/SDK report/read, rapid toggle, повторные callbacks, смену проекта, stale attempt/identity, отмену, ручной Stop и UNKNOWN. Не повторять успешные проверки без относящихся изменений. Итоговый набор: unit-all, electron-smoke, architecture, chatgpt-plugin, обе части kit-check/kit-assignments и kit-upgrade; при изменении MCP — executor-channel/codex-tools-live. Обе части Kit и kit-upgrade назначены также UI-EVENTS и REVIEW-VIEW. Найденный в PROOF дефект продукта оформляется отдельной задачей до DOCS; scope тестовой задачи молча не расширяется.

Renderer-проверки охватывают отсутствие дубликата native/HTTP, настоящую MCP-панель, Review до/после публикации, независимых участников, переносы на 320/480/900 px и отсутствие clipping таймером. Jsdom не заменяет проверку геометрии настоящим renderer.

Перед началом реализации исправления TODO; диагностические чтения не заменяют проверки. Живая приёмка ChatGPT/macOS, native Windows/Linux и удалённого клиента остаётся NOT_RUN до теста пользователя. RELEASE проверяет семь assets, подпись/состав/архивы; INSTALL — manifest и rollback; PUBLISH — тег на sourceCommit и size/digest всех assets. Перед production безопасно удалить Python caches. Новый выпуск не означает живую приёмку.

DOCS сверяет действующие контракты перед выпуском 0.5.35, переносит реализованное в модули; незавершённые требования сохраняются. Предыдущие DONE не переиспользуются. Установка и публикация требуют собственных подтверждений, независимо от app suite.

Прежний scope закрыт после документальной передачи требований; исправления нового плана остаются TODO. Штатный carryover Kit 1.10.0 отклонён с PLAN_EXECUTION_POLICY (не переносится execution policy); код Kit ради закрытия не менялся. История DONE остаётся в Git, без копии старого плана в recovery.
