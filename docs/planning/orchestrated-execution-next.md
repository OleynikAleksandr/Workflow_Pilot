# Оркестрованное выполнение плана

Статус: рабочая спецификация этапа 0.4.0, решения пользователя от 16.10.2026. Поведение для пользователя — здесь; контракты Kit, Control и интерфейса, совместимость и проверки — в [контрактах этапа](orchestrated-execution-contracts.md). Выпущенное поведение — [workflow execution](../modules/workflow-execution.md) и [назначения Kit](../../packages/workflow-kit/docs/modules/parallel-assignments.md).

## Результат

Пользователь открывает новую сессию проекта без активного плана, обсуждает задачу и получает спецификацию и to-do plan. Эта сессия — оркестратор: планирует, через приложение раздаёт микрозадачи отдельным исполнителям, принимает их результаты в main, затем сам выполняет delivery-хвост (сборка, установка, GitHub), очищает рабочие worktree и отвечает пользователю. Обычные задачи плана и DOCS оркестратор сам не реализует.

После готовности плана (и согласования при Review ON) рядом с названием и описанием плана появляется одна кнопка «Начать выполнение плана». Она ведёт весь план автоматически, последовательно или параллельно, до последней задачи хвоста. Повторное нажатие — пауза перед следующей задачей.

В дереве проекта видны сессии-оркестраторы и чаты обсуждения. Микрозадачи плана показаны под своим оркестратором; клик по начатой или завершённой микрозадаче открывает справа сессию её исполнителя.

## Роли сессий

| Роль | Когда | Что делает | Контекст |
| --- | --- | --- | --- |
| Оркестратор | Новая сессия проекта без активного плана | Обсуждение, спецификация, план, метки, context_pack задач, Review, приём результатов, исправление интеграции, эскалация, итоговая проверка main, delivery-хвост в main, итоговая очистка, ответ, приёмка и archive по поручению пользователя | Полный recovery проекта |
| Исполнитель | Приложение запускает обычную микрозадачу или DOCS | Одна назначенная задача в своём worktree: task:start → работа → commit --task; при невозможности — блокировка с причиной | Служебная часть Kit, задача и её context_pack |
| Чат обсуждения | Новая сессия при активном плане; прежние сессии проекта после публикации плана оркестратора | Обсуждение параллельно с выполнением; план не создаёт и не меняет | Тот же полный recovery, что у оркестратора, с правилом роли |

- Роль назначает приложение при создании сессии по состоянию Kit; модель роль не выбирает. Если без плана открыто несколько сессий, оркестратором становится та, из которой опубликован план: приложение сообщает агенту Session ID в recovery, агент указывает его в плане, Kit требует это поле, а приложение сверяет принадлежность проекту и роль. Остальные сессии становятся чатами обсуждения.
- «Активный план» — от публикации до archive, включая готовность к приёмке (все задачи DONE). Приёмку и archive ведёт оркестратор по поручению пользователя.
- Сессию оркестратора активного плана нельзя архивировать или удалить: приложение объясняет причину. Если запись оркестратора потеряна или указанный в плане Session ID не совпал ни с одной подходящей сессией, план получает состояние «Требует внимания», и пользователь явно назначает оркестратором одну из сессий проекта командой меню. Архивирование проекта целиком при активном плане отклоняется.
- Оркестратор не выполняет обычные задачи и DOCS: Kit запрещает task:start в main orchestrated-плана для всех задач, кроме delivery. Записи оркестратора в main — публикация и расширение плана, исправление интеграции внутри операции Kit, delivery-задачи после завершения всех остальных, итоговая очистка, archive и docs:commit без активного плана.
- Обсуждение без последующего плана заканчивается документом: оркестратор сохраняет итог в `docs/planning` через docs:commit как невыпущенное требование. Реализующий его план переносит содержание в контракты модулей на DOCS и удаляет временный документ по правилам Workflow Core.
- Чат обсуждения документов не создаёт. По прямой просьбе пользователя агент предупреждает, что кладёт документ во временную папку `.workflow-temp/` в корне проекта вне Git, и называет путь. Пользователь сам помнит о таком документе; папку никто автоматически не чистит.

## План: метки и волны

Оркестратор помечает каждую задачу:

- **Параллельная** (`parallel_safe: true`) — может работать одновременно с другими параллельными задачами. Нужны конкретные пути записи без glob; пересечение путей исключает одновременную выдачу.
- **Последовательная** (`parallel_safe: false`) — работает одна.

Обе выполняются отдельным исполнителем в своём Git worktree и проверенно вливаются в main; так Kit гарантирует, что оркестратор не выполняет задачи в main. Delivery-задачи меток не имеют: их выполняет оркестратор в main после всех остальных задач.

Волна — одна последовательная задача или подряд идущие параллельные:

1. Последовательная задача стартует, когда все предыдущие задачи DONE (влиты в main), нет незавершённых назначений, операция интеграции свободна и main чист. Пока она не влита, новые назначения не выдаются; её слияние не конфликтует, потому что main за это время не менялся.
2. Параллельная задача стартует, когда её зависимости DONE, есть свободный слот и её пути не пересекаются с выполняемыми задачами. Слияния в main идут по одному, по мере готовности исполнителей.
3. Лимит одновременно работающих параллельных исполнителей — настройка «Максимум одновременно работающих исполнителей». Её снимок сохраняется в плане при публикации; изменение настройки действует только на новые планы. При запрете параллельности или лимите 1 все задачи плана последовательные.
4. Номер волны вычисляется для показа из порядка и меток; отдельного поля нет.

## Контекст исполнителя

Контекст исполнителя готовит оркестратор: при составлении плана он знает содержание каждой микрозадачи и указывает в её `context_pack` нужные документы (путь, required, ревизия). Kit проверяет существование, ревизии и бюджет `budget.document_bytes` и передаёт исполнителю служебную часть (идентичность, Workflow Core, PROTOTYPE, проектная часть AGENTS), его задачу и документы её context_pack. Других документов Kit исполнителю не подбирает. Нехватка или переполнение контекста — ошибка плана; оркестратор исправляет context_pack ещё не начатой задачи.

## Обязательный хвост

- Каждый план оркестратора заканчивается задачей DOCS — актуализацией всех документов проекта, включая README и OVERVIEW. DOCS обязательна и для плана без кода и без выпуска; Kit добавляет её автоматически, в том числе при plan:extend, так что план без DOCS невозможен.
- Если оркестратор отмечает, что план меняет выпускаемое приложение, после DOCS идёт delivery-хвост из настройки проекта, задачи которого оркестратор вносит в план, а Kit проверяет их состав и порядок. Без настройки хвост — только DOCS.
- Хвост Workflow Pilot: сборка выпуска трёх ОС одной задачей (платформы упаковываются параллельно, см. [контракты](orchestrated-execution-contracts.md)) → установка в `/Applications` → GitHub Release (push, тег, Release).
- Delivery-хвост выполняет оркестратор в main обычным циклом task:start/commit: сборка, установка и публикация требуют корня проекта и `sourceCommit` main, а не worktree. Kit разрешает это только после DONE всех остальных задач, без незавершённых назначений и при свободной интеграции.
- Правило Workflow Core «без выпуска автоматическая DOCS не добавляется» для планов оркестратора заменяется обязательной DOCS; для прежних sequential/parallel-планов оно сохраняется.

## Кнопка выполнения

Одна кнопка в шапке плана рядом с названием и описанием; меняется только подпись:

| Состояние | Подпись | Нажатие |
| --- | --- | --- |
| Черновик, Review или план не согласован | кнопки нет | — |
| Опубликован, выполнение не начиналось | «Начать выполнение плана» | Запуск |
| Выполняется | «Пауза» | Новые задачи не выдаются |
| Пауза запрошена, исполнители ещё работают | «Пауза…» (недоступна) | — |
| Пауза (вручную или после эскалации) | «Продолжить» | Продолжение с первой не начатой задачи (в том числе delivery) |
| Все задачи DONE | кнопки нет, пометка «Выполнено» | — |

- Пауза останавливает только выдачу новых задач. Уже работающие исполнители получают свои обычные продолжения и доделывают задачи; готовые результаты вливаются в main. В delivery-фазе приложение передаёт оркестратору поручения задач хвоста по одной, и пауза срабатывает между ними.
- Состояние кнопки хранится в backend по проекту и плану. Закрытие окна, Cmd+Q и перезапуск backend его не меняют; после перезапуска выполнение продолжается без повторного Send. Публикация плана сама выполнение не начинает.
- Кнопка доступна с Mac и с iPad тому устройству, у которого право управления.
- Кнопка — единственное управление выполнением плана оркестратора; прежний переключатель AutoPlan и его предварительное включение до плана для планов оркестратора не применяются. Агент кнопкой не управляет.
- «Стоп» в поле ввода ChatGPT — кнопка самого чата и к приложению не относится. Защиты ручного Stop, черновика, UNKNOWN и draining службы сохраняются.

## Выполнение и исполнители

- Каждая обычная микрозадача и DOCS получают новый чат ChatGPT и отдельного исполнителя того же вида, что оркестратор (Chat или Work), и назначение Kit в worktree, как сейчас в parallel-плане.
- Одновременно работают не более `max_workers` параллельных исполнителей; последовательная волна — один исполнитель. Кроме них открыты страницы оркестратора и выбранного пользователем чата.
- Сразу после проверенного слияния задачи Kit удаляет её worktree и влитую ветку. Невлитые worktree (заблокированная задача, конфликт) не удаляются, пока сбой не разрешён. Каждый worktree с подготовленным окружением занимает сотни мегабайт, поэтому накопления до конца плана нет.
- После проверенной интеграции задачи страница её исполнителя в backend закрывается; чат остаётся в ChatGPT и открывается снова по клику на задачу. Каждый новый исполнитель — новый чат и новый старт его контекста; это осознанная стоимость изоляции.
- После последней обычной задачи и DOCS оркестратор получает итоговое поручение: завершить оставшиеся интеграции и проверить main. Затем приложение по одной передаёт ему delivery-задачи. В конце оркестратор выполняет итоговую очистку Kit: проверяет, что остался только main, убирает оставшиеся влитые worktree и ветки, перечисляет невлитое, если оно есть, и отвечает пользователю. План остаётся READY_FOR_ACCEPTANCE до приёмки и archive по поручению пользователя.
- Чат исполнителя после удаления его worktree остаётся в ChatGPT и открывается по клику на задачу для чтения истории; команд в удалённой папке он уже не выполняет.
- Во время выполнения оркестратор может расширять план (plan:extend). Менять задачи, проверки и context_pack можно только у ещё не начатых задач.
- Если план устанавливает новую версию самого приложения, установка при работающей службе остаётся ожидающей; службу останавливает и новую версию запускает пользователь.

## Сбои

1. **Исполнитель** сначала устраняет сбой сам в пределах своей задачи (проверки, ошибка команды, упавшая сборка по причине окружения).
2. Не смог — блокирует задачу командой Kit с причиной. Задача остаётся начатой, её файлы сохраняются. Приложение один раз передаёт оркестратору задачу, причину и ссылку на сессию исполнителя. Конфликт и провал проверок интеграции, как сейчас, сразу передаются оркестратору.
3. **Оркестратор** устраняет сбой: разрешает конфликт внутри операции интеграции; передаёт уточнение тому же исполнителю командой Kit (приложение доставляет его в чат исполнителя); добавляет исправляющую задачу через plan:extend. Исправляющие задачи не требуют паузы и нового Review; оркестратор пишет в своём чате, что и почему добавил. Пауза и вопрос нужны, только если исправление меняет согласованный объём или требования.
4. Не смог оркестратор — он выполняет команду эскалации Kit с причиной: выполнение автоматически встаёт на паузу, а оркестратор пишет пользователю в своём диалоге. Пользователь обсуждает проблему с оркестратором и нажимает «Продолжить».

- Исход UNKNOWN (отправка, создание назначения, слияние, команда записи) не идёт по цепочке: повторов нет, выполнение сразу встаёт на паузу с причиной в интерфейсе, сверку выполняет пользователь с оркестратором.
- Сбой delivery-задачи устраняет сам оркестратор: причину в окружении (toolchain, подпись, загрузка) исправляет и повторяет. Причина в коде не исправляется внутри задачи сборки, потому что выпуск собирается из одного `sourceCommit`: оркестратор добавляет перед хвостом исправляющую задачу и при необходимости повторную DOCS, их выполняют исполнители в worktree, затем сборка повторяется из нового коммита. Не смог — эскалация пользователю.
- Пользователь в любой момент может нажать «Пауза» и обсудить ход выполнения с оркестратором.

## Дерево проекта

```
Проект
├─ Оркестратор: <название плана>          Выполняется · 3/9
│   ├─ T001 Основа контракта              → · Выполнено
│   ├─ T002 Экран настроек                ∥ · Выполняется 04:12
│   ├─ T003 Журнал событий                ∥ · Ожидает
│   ├─ DOCS Актуализация документов       → · Ожидает
│   └─ T004 Собрать выпуск трёх ОС        → · Ожидает
├─ Обсуждение: <заголовок чата>
└─ Оркестратор: <прежний план>            Выполнено
```

- Под проектом — сессии-оркестраторы и чаты обсуждения. Для планов оркестратора группы «Исполнители» нет; для прежних parallel-планов она остаётся до их закрытия.
- Строка оркестратора: состояние (Планирование, Review, Готов к запуску, Выполняется, Пауза, Требует внимания, Выполнено) и счётчик выполненных задач.
- Строка микрозадачи: ID, название, метка (→ последовательная, ∥ параллельная), состояние и таймер работающего исполнителя.
- Клик по начатой или завершённой задаче открывает справа сессию её исполнителя (последнюю, если их было несколько). Клик по не начатой показывает справа вместо страницы карточку задачи: описание, критерии, зависимости, метку.
- Оркестратор выполненного плана остаётся в дереве с пометкой «Выполнено» и после archive; его микрозадачи читаются из плана по сохранённому коммиту закрытия. После archive сессию оркестратора можно архивировать как обычно.

## Границы

- Review проходит пара спецификация и план, а не результат каждой задачи; исправляющие задачи нового Review не требуют.
- Сам этап 0.4.0 выполняется прежним последовательным циклом Kit одним агентом в main.
- Установленный Kit проекта Workflow Pilot обновляется до 1.8.0 штатной подготовкой проекта в приложении 0.4.0 после установки; до этого следующий план проекта не может быть планом оркестратора.
- Нет автоматического возобновления UNKNOWN, публичного доступа без Tailscale, VPS и автозапуска службы при входе в ОС.
- Общая ревизия состава документов проекта и фазовое планирование — [отдельный этап](phased-plans-recovery-followup.md).
- Донорский проект и его приложение не меняются.
