# Workflow Pilot: только Chat и запуск первого сообщения без DOM

**Дата:** 24.10.2026. **Статус:** спецификация для Review и публикации плана; реализация не начата. Обязательные части: [жизненный цикл](chat-only-url-lifecycle.md), [приёмка](chat-only-url-acceptance.md).

Основание сверки: Workflow Pilot 0.5.30, GitHub `b8a910e659cf778e2219eca104c17e80e22d4d2e`. Baseline планирования `df015ce35abff912a444c967639adfff667abeda`: обновлён Kit до 1.9.8 и закрыт прежний план; исходники `src` не менялись. Ниже разделены существующие механизмы, новая работа и внешние проверки.

## 1. Решение и границы

Workflow Pilot оставляет **только сессии обычного ChatGPT Chat и упраздняет поддержку режима Work**. Это изменение продукта, а не временное исключение Work из эксперимента.

Новый Chat запускается через `webContents.loadURL('https://chatgpt.com/?q=…')`. Первое сообщение содержит команду открытия панели и действующий тикет. Полный контекст передаётся существующим протоколом панели/MCP. Сохраняются и тикет, и ID чата.

От DOM отказываемся для ввода/отправки первого сообщения и получения адреса разговора. Проверки входа, черновика и при необходимости режима страницы остаются существующими наблюдениями. Полностью без DOM весь жизненный цикл этим решением не становится. Последующий канал сообщений не заменяется.

Bootstrap выполняется при создании новой локальной сессии, в том числе первой сессии проекта. Выбор существующего проекта и открытие сохранённого чата не отправляют новую команду.

### 1.1. Упразднение Work

Обязательный объём будущей реализации:

- Удалить выбор Chat/Work из интерфейса, настройки Work и возможность создавать, подключать или автоматически восстанавливать активную Work-сессию. Все новые сессии создаются как Chat.
- Backend/API/MCP должны отклонять явный запрос `experience=work` понятной ошибкой. Удаления одного переключателя в интерфейсе недостаточно. Отсутствие режима в совместимом запросе означает Chat; явный Work не преобразуется молча.
- Удалить рабочие ветви запуска и переключения в Work. Сохранить только распознавание запрещённых адресов и чтение исторических данных, необходимые для защиты и миграции.
- Старые записи с `experience=work` сохранить как неподдерживаемую историю: без нового bootstrap, выдачи стартового контекста, автоматического возобновления и исполнения через этот разговор. Не удалять историю, назначения и журналы; не заменять Work на Chat в старой записи. Новый Chat получает собственную локальную идентичность и регистрацию.
- Спецификация должна описать миграцию хранилища, отображение таких записей и безопасную остановку автоматического восстановления связанных назначений. Нельзя потерять назначение или запустить его повторно. Переход активного назначения в новую Chat-сессию требует отдельного штатного решения, а не массовой замены поля режима.
- Записи без сохранённого режима нельзя надёжно классифицировать только по `/c/…`. Для них спецификация должна зафиксировать совместимую миграцию и обработку неоднозначности; не объявлять их доказанными Chat без основания.
- Обновить проверки, документацию, инструкции и MCP-описания; сверить их с Kit без изменения его исходников. Историческое `session_experience=work` в Kit сохраняется для чтения старых планов, но не разрешает активный Work в приложении. Не удалять `workflow`, `worktree` или префикс run ID `work:`: они не означают режим ChatGPT Work.

Миграция должна быть повторяемой, сохранять данные и поддерживать восстановление после сбоя. В рамках редактирования документа никаких сессий и данных приложения не меняем.

## 2. Идентичность и полномочия

| Значение | Когда известно | Назначение |
|---|---|---|
| Локальный ID сессии | До открытия ChatGPT | Владелец запуска внутри workspace |
| Тикет | До первого сообщения | Разрешение первоначальной регистрации конкретного назначения |
| ID чата из `/c/…` | После создания разговора | Сохранение адреса и открытие того же разговора |
| `openai/session` | Из metadata MCP-хоста | Анонимизированная идентичность разговора для регистрации |

ID чата неизвестен при формировании первого сообщения и не заменяет тикет. `openai/session` не считается равным публичному ID из URL. Связь строится через одну локальную сессию и принадлежащую ей попытку запуска; нельзя выбирать получателя по активной карточке, последнему workspace или времени поступления запроса.

Совпадение локального ID у записи URL и участника само по себе не доказывает, что это один разговор. Поэтому обязательны отсутствие повторной отправки, контроль происхождения навигации и остановка подтверждения при неоднозначности.

## 3. Последовательность запуска

1. Создать локальную Chat-сессию и сохранить идентичность попытки: `requestId`, владельца и поколение. Подключить существующий канал runtime, расширенный согласно разделу 5.
2. Если страница не является проверенной точкой входа нового Chat, открыть `CHATGPT_CHAT_ENTRYPOINT` **без `q`**. Дождаться свежего наблюдения именно этого документа: вход подтверждён, страница нового Chat, черновик пуст. Чужой разговор или неподтверждённая страница не подходят.
3. Через `prepareBootstrap` / `reserveParticipant` получить тикет. Подготовить и сохранить полный контекст через `stageStartup`. Повторно проверить актуальность наблюдения страницы и владельца перед внешним действием. Ожидание пользователя не должно незаметно израсходовать срок приглашения.
4. Долговечно сохранить начало отправки (`sendStartedAtMs`), связь попытки с приглашением и основания сроков T1/T2. Затем единожды открыть URL с `q`. Отмена поколения контроллера собственной навигацией не отменяет сохранённую попытку.
5. Независимо принимать события адреса и регистрации. Регистрация по тикету текущей попытки подтверждает `sent`; адрес учитывается отдельно. Порядок событий произвольный.
6. Проверенный постоянный адрес сохранять через `bindChat()`, сохранив проверки уникальности и запрет подмены. При утрате принадлежности навигации не соединять первый доступный адрес с первой регистрацией.
7. Агент читает все части контекста и подтверждает SHA через `workflow_startup_complete`. Готовность интерфейса панели и канала дальнейших SDK-сообщений проверяются отдельно. Получение контекста не разрешает автоматически выполнять план.

`loadURL()` завершился — это только загрузка страницы, не подтверждение отправки или регистрации.

### Первое сообщение

```text
Открой панель Workflow Pilot: один раз вызови workflow_pilot_panel с аргументами {"enrollment_ticket":"<TICKET>"}. Если вызов вернул ошибку или в ответе нет startup_context, сообщи точную причину и ничего не выдумывай; подтверждения хоста не обходи. Приглашение не публикуй и не сохраняй.
```

`<TICKET>` выдаёт backend. Если причина отсутствия контекста не сообщена, агент сообщает только факт отсутствия. Инструкции чтения `STARTUP_INSTRUCTIONS` приходят с каждой частью, но при ошибке регистрации они могут не прийти; поэтому правило ошибки есть в первом сообщении.

Запрет публикации относится к дополнительным копиям в файлах, отчётах и сообщениях другим получателям. Тикет неизбежно передаётся в URL, первом сообщении и аргументах инструмента. «Один раз» в тексте не заменяет программную защиту от повторов.

URL строится из точного текста через `encodeURIComponent`. Recovery, содержимое проекта, `model`, `hints` и `temporary-chat=true` в bootstrap не включаются.

## 5. Расширение существующего канала навигации

**Сейчас:** `did-navigate-in-page` вызывает `emit('navigated')` без адреса события и признака главного фрейма. Snapshot содержит текущий `getURL()`, но он не заменяет адрес каждого перехода. `did-navigate` и `did-redirect-navigation` отдельными событиями этого порта сейчас не передаются. Поэтому прежнее требование отслеживать любой адрес попытки без доработки порта невыполнимо.

**Новая работа:** внутри того же BrowserSessions-порта передавать события `did-navigate-in-page`, `did-navigate` и `did-redirect-navigation` с адресом из аргументов события, нормализованным `isMainFrame`, видом события и существующей идентичностью runtime/поколения. При необходимости расширить `navigation-start` теми же данными. Точную совместимую схему аргументов Electron закрепить в спецификации и fixtures. Не создавать отдельный параллельный канал привязки в control.

Control получает фактический адрес перехода, сохраняет необходимые признаки текущей попытки и только затем запускает сверку. Промежуточный серверный redirect должен быть виден, даже если следующий переход уже показывает `/c/…`. Подписки снимаются при release; поздние события не оживляют закрытую попытку. Дубли событий обрабатываются идемпотентно.

Принимать для привязки только события главного фрейма принадлежащих попытке webContents. Проверять `normalizeChatUrl`; временные `WEB:` / `local-chatgpt:` распознавать через `isPendingChatGPTConversation`, но не сохранять как постоянный chatUrl. Не вводить узкий UUID-парсер, ломающий ранее допустимые ID.

Если любой адрес главного фрейма текущего запуска классифицирован как Work (`/work…`, корень с `?surface=work|tpp`), сохранить несоответствие и остановить подтверждение привязки. Поздний `/c/…` его не отменяет. Один `/c/…` не доказывает Chat: Work тоже может иметь такой адрес. Проверить аккаунт с ранее выбранным Work; если URL недостаточно, использовать существующее наблюдение режима либо считать конфигурацию неподдерживаемой. Это защита от Work, а не его поддержка.

## 6. Подтверждение отправки и отображение

В текущем `tick` после `sendStartedAtMs` установлен `sendAttempted`, а `ownMessageSeen` проверяется только при `!sendAttempted`. Старый переход в `sent` выполняют `composer.deliver()` или обнаружение собственного сообщения. URL-путь не вызывает `deliver()`: без нового перехода остаётся `send-unknown`, а прогресс пакета, зависящий от `state === 'sent'`, скрыт.

Правило нового пути: **долговечно подтверждённая регистрация по тикету текущей неотменённой попытки → `sent`**. Сохранить время подтверждения и его основание. Это не точное время отправки на сервере ChatGPT. Связь с приглашением, `requestId`, назначением и локальной сессией должна проверяться; прежний участник не подтверждает новый запуск.

| Наблюдение | Состояние и отображение |
|---|---|
| Только завершение loadURL или временный URL | Отправка ещё не подтверждена |
| Допустимый постоянный адрес до регистрации | Адрес учтён; «Ожидаем регистрацию панели» |
| Регистрация до постоянного адреса | `sent`; прогресс контекста и отдельно «Ожидаем адрес чата» |
| Регистрация есть, startup_context отсутствует/ошибка | Отправка подтверждена; контекст не готов |
| Все части и действующее подтверждение SHA | Контекст получен; это не разрешение выполнения плана |

Не подтверждать `sent` по одному URL и не скрывать прогресс ранним выходом `tick` при временном адресе. Повторы регистрации и сверка после потери ответа не должны повторять команду.

## Миграция и допуск операций

Новая версия схемы хранилища отделяет сохранённый `experience` от допуска: `availability=active|legacy-work|mode-unverified`. Номер схемы следующий после текущего; использовать штатную атомарную запись/резервную копию, не переписывать chatUrl/identity. Явный chat становится active; work — legacy-work. Для старой схемы без режима `/work/` доказывает legacy-work, `/c/…` остаётся mode-unverified. Уже явно сохранённый chat не переклассифицировать по предположению о прошлом.

Текущая схема v6; новая — v7. Для ещё не мигрированных v3 и более старых файлов изменить этап v3→v4 так, чтобы исходная неопределённость не исчезала из-за `conversationExperience(...) ?? 'chat'`: `/work/` → legacy-work, `/c/…`, отсутствующий/неразличимый адрес и `chatUrl=null` → mode-unverified. Сведения о происхождении довести до v7 атомарно. Запись без режима и без адреса не запускается автоматически; пользователь создаёт новый Chat.

Осознанная граница: сохранённый `experience=chat` в v4–v6 принимается как chat, хотя прежняя миграция могла вывести его из URL. В этих файлах происхождение уже утрачено; не заявлять доказательство фактического прошлого режима и не переклассифицировать все старые Chat. Явный work в любой поддерживаемой схеме остаётся legacy-work. Tests покрывают оба пути и null chatUrl.

legacy-work виден как история без открытия живого runtime, регистрации, новых сообщений, контекста и автоматического восстановления. Восстановление из архива не делает его active. mode-unverified также не возобновляет работу; безопасный выход — новый Chat. Перенос активного назначения в новый Chat требует отдельного штатного решения и не входит в автоматическую миграцию.

Если execution origin или незавершённое назначение связано с недопущенной сессией, удержать соответствующий проект до открытия браузеров и выдачи сообщений: без старта E, grant и автоматических интеграций. Сохранить worktrees, task/result/receipt/acceptance и неизвестные исходы. Соседние проекты с Chat не удерживать, ручной OFF не заменять ON.

Допуск централизуется в control: первая/новая сессия, reopen/restore, connectExternal, localParticipantTarget, runtime restore и plan/assignment continuation. По умолчанию создаётся chat; явный work даёт `SESSION_EXPERIENCE_UNSUPPORTED`; историческая/неоднозначная сессия — `SESSION_MODE_UNSUPPORTED` / `SESSION_MODE_UNVERIFIED` без побочных действий. Plugin сохраняет штатный префикс ошибок и не выдаёт контекст. Это не изменение выбора sequential/orchestrated в Kit.

## Проверка через пользовательский вход

Новый Chat запускается через создание первой сессии проекта и меню «Новый Chat», не только helper. Desktop и HTTP используют один backend-контракт. Матрица и ограничения живой проверки — в [приёмке](chat-only-url-acceptance.md); долговечные поля и гонки — в [жизненном цикле](chat-only-url-lifecycle.md).
