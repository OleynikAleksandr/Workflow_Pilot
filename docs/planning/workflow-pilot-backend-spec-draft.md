# Workflow Pilot — независимый frontend и постоянно работающий backend

Дата: 15.10.2026. Статус: ЧЕРНОВИК ДЛЯ ОБСУЖДЕНИЯ.
База: Workflow Pilot 0.1.6; предыдущий план закрыт.
Предлагаемый выпуск: 0.2.0; номер подтвердить перед публикацией плана.
План: [workflow-pilot-backend-todo-draft.md](workflow-pilot-backend-todo-draft.md).

## 1. Результат

Основной обязательный сценарий — backend Mac и frontend Mac на одном Mac. Mac является полноценным компьютером выполнения. VPS для этого не нужен.

Одно открытие Workflow Pilot:
1. Находит собственный backend либо запускает его.
2. Обеспечивает браузер ChatGPT, Control, Execution, Kit, собственный MCP, мост плагина и выбранный настроенный туннель.
3. Открывает отдельный frontend с панелями проектов/сессий/плана и интерактивным представлением страницы ChatGPT.

Закрытие окна, выход из клиентского приложения и завершение процесса frontend отключают только интерфейс. Backend, браузер, команды, AutoPlan, Review, исполнители, MCP и туннель продолжают работу на этом же компьютере. Повторное открытие возвращает к тем же живым страницам и операциям без reload, второго разговора или повторного recovery.

Системный значок показывает состояние, открывает клиент и позволяет явно остановить backend. Если Linux tray недоступен, статус/остановка доступны через launcher/клиент; ограничение отражается в DOCS и платформенной приёмке.

Работа продолжается при работающей ОС. Сон, logout, выключение и падение backend не равны закрытию frontend; сохранение живой генерации после них не обещается.

## 2. Основание и решения пользователя

Исходное задание — приложенный документ «Workflow Pilot — задачи клиент-серверной архитектуры». Выпуск реализует задачу 1 и необходимое для неё интерактивное представление браузера.

Уточнения разговора имеют приоритет:
- Один рабочий диалог — один живой экземпляр страницы на backend. Все интерфейсы подключаются к его изображению и вводу.
- Продолжение того же диалога через отдельно открытый ChatGPT.com или мобильное приложение не является штатным сценарием. Это заменяет соответствующие предложения исходного задания.
- Основание — повторяемое наблюдение пользователя: без второго браузера большие планы работают устойчиво, после открытия/ввода во втором возникают сбои. Причина не установлена; это проектное ограничение, не заявление о запрете ChatGPT.
- Нужен полный интерактив: редактор, кнопки ответов, подсказки, меню, просмотр файлов, копирование и вложения.
- Новые правила конфликтов ручных действий с автоматизацией — отдельное обсуждение и план. Здесь сохраняются существующие защиты.
- Подготавливаются только черновики. Они не публикуют активный план и не запускают реализацию, сборку или выпуск.

## 3. Подтверждённая исходная база

Проверено после закрытия плана: desktop/bootstrap.mjs задаёт identity и создаёт фасады; desktop/application.mjs владеет stores/workflow/сессиями. Обработчик closed освобождает AutoPlan, Execution, Review, plugin bridge и вызывает app.quit(); window-all-closed также завершает приложение. BrowserHost держит WebContentsView; ExecutionFacade.dispose закрывает браузер/мост/команды. Отдельные login-службы могут пережить desktop. Мост уже проверяет Host/Origin и токен. Есть single-instance lock, Tray не найден.

Простое удаление app.quit() или скрытие окна не отделяет владельцев состояния и процессы.

## 4. Границы нового выпуска

Включено: самостоятельные backend/browser lifecycle; launcher и отдельный frontend; локальный сетевой API; полный интерактив браузера; запуск/закрытие/переподключение/явная остановка; системный значок; MCP/туннель/плагин; один управляющий клиент; переход с 0.1.6 и полный выпуск трёх ОС.

Не включено:
- Публичный веб-доступ, HTTPS из интернета, мобильная адаптация и приёмка iPad/iPhone.
- Развёртывание на VPS, передача проектов Mac ↔ Linux, распределённое право выполнения и Git-синхронизация узлов.
- Новая оркестрация и новые правила ручного вмешательства в автоматизацию.
- Новые возможности голоса, камеры и микрофона.
- Автоматическое возобновление UNKNOWN после падения и новый автозапуск работы при входе в ОС.

Будущие этапы исходного документа сохраняются как отложенные. Контракт пригоден для другого компьютера, но доступ этого выпуска ограничен loopback. Два независимых локальных клиента проверяют сетевую границу. Подготовка контракта не означает готовности удалённого продукта.

## 5. Процессы и владельцы

| Компонент | Ответственность |
| --- | --- |
| Launcher | Проверить/запустить локальный backend, открыть клиент |
| Backend host | Независимый процесс; Control, Execution, Kit adapters, stores, workflow |
| Browser runtime | Страницы, partition, observer и автоматизация; принадлежит backend |
| MCP / туннель | Существующие собственные службы; lifecycle координирует backend |
| Plugin bridge | Доступ существующего MCP к тому же Control без frontend |
| Frontend | Панели, изображение выбранной страницы и пользовательский ввод |
| Системный значок | Backend либо минимальный независимый системный компонент |

T003: `--backend-host` запускает отдельный Electron backend со своими Control/Execution/Kit, браузерным host и закрытым loopback-port. Один владелец userData/partition защищён Electron lock и приватным descriptor; повреждённые данные/Kit journal отвергаются. Обычный Desktop пока работает в legacy-режиме и не может владеть тем же профилем одновременно; перенос страниц/клиентского UI завершают T004–T007. Новый backend не создаёт видимое окно и не требует sidebarReady.

macOS: выбран отдельный backend helper со своей identity; в T009/T011 проверить LaunchServices/reopen, locks, profile, Dock и подпись nested helpers. Повторное открытие `.app` подключает клиент без рестарта backend.

Backend не зависит от frontend/process group. Stores, план, cookies, partition и секреты остаются у backend; frontend имеет свой профиль. `persist:workflow-pilot-chatgpt` принадлежит backend.

Kit остаётся единственным владельцем плана и транзакций. Готовность проверяется по backend identity, поколению запуска, API version и состоянию компонентов; один PID/порт её не доказывает.

## 6. Браузерное представление

ChatGPT загружается только на backend. Наши панели рисуются клиентом из данных API; область диалога показывает интерактивное изображение настоящей страницы. Рабочий стол пользователя передавать не требуется. Интерфейс ChatGPT не реконструируется из ответов или копии DOM.

Один экземпляр страницы допускает нескольких зрителей; разных страниц для сессий/исполнителей может быть много. Reconnect не создаёт страницу. Система не обещает запретить пользователю вручную открыть тот же чат вне Workflow Pilot.

Управляющий клиент задаёт viewport, scroll и выбор отображаемой сессии. Наблюдатели масштабируют изображение без изменения серверного представления. Без зрителей можно остановить передачу кадров, но не выполнение страницы, observer или ожидания.

Обязательный интерактив:
- указатель, клики, удержание/отпускание, прокрутка, клавиатура, русский и составной ввод;
- подсказки, меню ответов/разговора, вложенные меню, выделение текста;
- browserSessionId и поколение документа/представления для ввода; поздние события не попадают в другую страницу;
- сброс зажатых клавиш/кнопок при разрыве; сырой ввод не переигрывается;
- clipboard по явному действию в обе стороны;
- передача клиентского файла на backend с transferId и прикрепление после проверки завершения;
- скачивание результата на устройство клиента;
- дополнительные окна, авторизация и файловые диалоги без обязательного видимого серверного окна.

Branch/Delete/Retry передаются настоящей странице, но новая политика их взаимодействия с workflow в этот выпуск не входит. Проверки — на пассивной fixture; живые действия пользователя — в безопасной паузе по действующим правилам. Автоматический ввод не должен потерять существующие защиты draft/Stop/UNKNOWN.

### Ранний эксперимент — обязательное условие продолжения

До массового переноса проверить отдельные backend/client на локальной fixture-странице: завершить клиент, сохранить страницу/таймер/черновик/тестовую работу, подключить новый клиент.

Сравнить минимально подходящие готовые решения:
- Electron offscreen: источник кадров/текстур, не готовый сетевой продукт.
- Xpra: постоянные удалённые приложения и HTML5-клиент; seamless-сервер не универсален для Mac/Windows.
- noVNC: готовый встраиваемый клиент, которому необходимы подходящий сервер и интеграция файлов.

Предварительные результаты и рекомендуемый транспорт — [протокол T001](workflow-pilot-backend-t001-evidence.md). Требуются живая проверка ввода, меню, clipboard, файлов, читаемости и задержки и согласие пользователя. Собственный видеокодек и универсальный remote desktop не разрабатывать.

После результата T001 исполнение переводится в BLOCKED до живой проверки пользователем и записанного user_decision о транспорте, читаемости и задержке. T002 не стартует без этого решения. Эта новая граница имеет приоритет над прежним правилом переноса вопросов после релиза.

Общий контракт допускает платформенные адаптеры. Непроверенная ОС остаётся pending. Неуспех обязательного интерактива останавливает зависимые задачи до пересмотра решения; скрытое прежнее окно не считается выполнением.

Источники, проверенные 15.10.2026:
- https://www.electronjs.org/docs/latest/api/base-window
- https://www.electronjs.org/docs/latest/tutorial/offscreen-rendering
- https://www.electronjs.org/docs/latest/api/web-contents — в частности требование фокуса sendInputEvent.
- https://github.com/Xpra-org/xpra
- https://xpra-org.github.io/xpra/Usage/Seamless.html
- https://github.com/novnc/noVNC

Проверить компоненты на закреплённой версии.

## 7. Сетевой контракт

После живой приёмки T001/T001R принят Electron offscreen PNG/CDP, с автоматической плотностью клиентского дисплея. Локальный API: HTTP для команд/снимков/файлов, WebSocket для событий и ввода; конкретная реализация в T005–T006. Контракты и тесты: `src/contracts/{backend,browser-presentation}.mjs`, `src/backend/protocol.mjs`. UI не вызывает Control напрямую.

| Объект | Контракт |
| --- | --- |
| Handshake | API version, identity, boot generation, capabilities, готовность служб |
| State | Snapshot + sequence/revision событий; при пропуске/смене поколения — resync |
| Command | requestId, allowlisted operation, args, revision при необходимости, право управления |
| Result | accepted + operationId либо completed/failed/rejected |
| Operation | Серверное состояние независимо от соединения; запрос по ID |
| Browser input | Адресное, упорядоченное, без replay после disconnect |
| Error | Код и безопасное сообщение без секретов/текста чата |

Версия API = 1; identity/boot generation и lease generation обязательны. Один requestId + неизменные аргументы → прежний operationId, другие аргументы → конфликт. Атомарное долговременное acceptIfAbsent **до** эффекта; неопределённый исход → UNKNOWN, не повторный Send. Snapshot и события имеют sequence/revision и resync при пропуске; порядок даже при синхронном callback сохраняется. Очереди, размеры сообщений и файлов ограничены; медленный клиент не блокирует backend.

Loopback тоже требует bearer, точный Host и разрешённый Origin, включая WebSocket handshake. Discovery/credential-файл приватный, без симлинков; токены не в URL/логах. TransferId и имя файла валидируются; локальный путь выбирает только backend. Клиент не получает открытый CDP, JS или shell. Plugin UI-мутации требуют lease, агентский MCP независим от окна.

## 8. Право управления

На backend один управляющий интерфейс, остальные наблюдают. Право берётся/освобождается явно; каждая мутация и ввод проверяют поколение lease.

Предложение (не утверждено): lease обновляется каждые 10 секунд, истекает через 45 секунд. Старый владелец теряет право ввода; принятые операции продолжаются. Подписка не захватывает управление.

Потеря lease не выключает AutoPlan или агентские MCP-инструменты. Plugin UI-мутации подчиняются lease, получение контекста и выполнение агента не требуют открытого frontend.

Значок — проверяемый локальный вход, не обход прав. Новая координация ручного ввода и AutoPlan отложена.

## 9. Жизненный цикл

| Событие | Поведение |
| --- | --- |
| Первый запуск | Один bootstrap backend, затем клиент; этапы готовности видны |
| Нет настройки | setup-required, доступный UI мастера; не требуется готовый ChatGPT для открытия клиента |
| Два запуска | Один backend, handshake, подключение |
| Backend работает | Без нового MCP/туннеля/страницы/recovery |
| Закрытие / Cmd+Q / crash frontend | Только отключение клиента; backend продолжает |
| Разрыв связи | Устаревание показано; reconnect со свежим состоянием |
| Crash backend | Ошибка и новое boot generation после восстановления; UNKNOWN без повторов |
| Явная остановка | Draining → безопасная точка → остановка → проверенное подтверждение |

Обычная остановка прекращает новые автоматические назначения и отправки, но позволяет текущему ответу и его инструментам завершиться. UI показывает ожидаемые операции/причину задержки и позволяет отменить запрос остановки. Автоматического timeout → kill нет; принудительная остановка отдельно согласуется.

В безопасной точке сохранить данные и завершить только собственные браузер/мост/службы в порядке, не разрывающем текущие операции. Остановка подтверждается фактическим состоянием, а не исчезновением связи. Descriptor удаляется лишь при доказанном владении.

Запуск не обходит ключи, вход и системные разрешения. Запускается выбранный настроенный канал, не все альтернативные туннели. Плагин означает доступность MCP-инструментов/ресурса; панель в чужом разговоре не открывается автоматически.

## 10. Совместимость и обновление

Сохранить проекты/сессии, адресацию и cwd фоновых задач, recovery once, UNKNOWN no-retry, AutoPlan/Review/sequential/parallel, настройки, архив/удаление/Доктор и подключения. Убрать зависимость допуска workflow от window/sidebarReady/видимости и настроек клиента, сохранив предметную готовность проекта и страницы.

Профиль Workflow Pilot 0.1.6 сохраняется, донор не меняется. Старая/новая версия не открывают один профиль одновременно; миграция и откат защищают данные.

Установка пакета при живом backend не должна заменять используемые runtime-файлы. Выбрать по проверке существующего installer: закреплённый за процессом runtime версии либо отложенное безопасное переключение. Несовместимый новый клиент показывает требуемый переход, не убивает backend и не создаёт второго.

## 11. Приёмка

Автотесты используют временные profiles/workspaces и fixture-страницы. Модельные ходы, управление пользовательскими окнами/вводом и изменения реальных служб в тестах запрещены.

| ID | Результат |
| --- | --- |
| A01 | Launcher поднимает ровно один backend; конкурентный запуск безопасен |
| A02 | Закрытие/kill frontend сохраняет страницу, её состояние, тестовую работу и MCP/bridge |
| A03 | Reconnect возвращает ту же страницу/операцию; reload/recovery/Send не растут |
| A04 | Независимый API-клиент без preload получает те же разрешённые операции |
| A05 | Fixture-цепочка микрозадач продолжает переходы без frontend |
| A06 | Два клиента: общий state, один writer, позднее старое поколение отклонено |
| A07 | Пропуск событий/restart/reconnect не повторяют мутации и ввод |
| A08 | Меню, русский ввод, выделение, clipboard, upload/download работают сквозным образом |
| A09 | Popups/авторизация не требуют видимого серверного окна; ноль зрителей допустим |
| A10 | MCP-инструменты и plugin resource/list/open/connect работают без frontend |
| A11 | Stop ждёт безопасную точку, не убивает текущую работу, подтверждает остановку своих служб |
| A12 | Upgrade, занятый профиль/порт, старый descriptor, несовместимость и отказ записи не теряют данные |
| A13 | Проверены auth/Origin/Host, границы файлов, очереди и медленный клиент |
| A14 | Три пакета одного sourceCommit содержат полный backend/client и корректный запуск |

Пользовательская приёмка Mac: тестовый план → закрыть клиент → проверить значок → открыть вновь → тот же диалог и продолжившаяся работа. Отдельно меню/clipboard/файлы и явная остановка. Windows/Linux/clean — отдельные строки матрицы; fixture на Mac не заменяет их.

В T001 измерить читаемость, задержку и idle, записать факты и согласовать приемлемость без выдуманных обещаний FPS. Ухудшение обычного чтения/ввода — существенный риск.

## 12. Поставка

После интеграции и проверок — отдельная DOCS до sourceCommit/build. Каждый документ не более 28000 UTF-8 bytes; отложенные требования сохраняются.

Полный релиз: macOS arm64, Windows x64, Linux x64 из одной базы, manifest/архивы/инструкции/digests. После сборки — штатная установка готовой app в /Applications/Workflow Pilot.app и проектную копию без пересборки/переподписи. Агент не завершает и не перезапускает работающий продукт; переключение выполняет пользователь.

Затем обычный push, тег на manifest.sourceCommit, GitHub Release и сверка всех assets без force/пересборки. План остаётся READY_FOR_ACCEPTANCE; закрывается по прямому поручению.

До публикации пользователь подтверждает версию, lease 10/45 с и описанный draining; решения записываются в user_decisions. Сейчас это предложения. Транспорт и качество подтверждаются отдельно после T001; T011 применяет уже выбранную версию.
