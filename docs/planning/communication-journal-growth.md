# Рост журнала связи (0.6.5)

## Проблема

Живой прогон T_003 (0.6.4) остановился через час работы шести участников. Журнал связи одного workflow-прогона `plugin-communication/<sha256(run_id)>.jsonl` вырос до 536 578 209 байт и упёрся в предел 512 МиБ. Следующая запись отклонена, хранилище стало `broken`, и с этого момента все вызовы панелей (`call_mcp`) получали 400. Отчёт исполнителя не дошёл до оркестратора.

Причины:

1. Каждая строка WAL содержит полное состояние прогона. Состояние растёт, поэтому файл растёт квадратично: 1914 строк, последняя около 590 КБ.
2. 492 КБ состояния занимает `clientEvents`: полный текст подписи каждого события панели (1110 записей), без удаления.
3. 80% событий прогона — служебные тайминги: `kit.timing` для каждого опроса `assignment:dialogue-status` (1337 за час) и `rpc.completed` панели. При пределе `run.events.length < 20000` прогон остановился бы через 6–7 часов даже без предела файла.
4. Загрузчик читает файл целиком одной строкой. Для файла около 512 МиБ это почти предел длины строки V8.

## Требования

- **Сжатие журнала.** Если запись превысит порог `max(32 МиБ, 4 × размер последнего снимка)`, хранилище атомарно (временный файл, fsync, rename, fsync каталога) заменяет файл одной строкой-снимком. В снимке текущее состояние и все события с `seq` от 1, `previous: null`. Формат записи прежний: снимок читают текущий и выпущенные валидаторы. Рост файла линейный. Оставшийся временный файл удаляется при открытии.
- **Потоковое чтение.** Журнал читается по строкам без строки размером с файл. Правила проверки, хвоста и ошибок прежние.
- **Отпечатки событий панели.** `clientEvents` хранит SHA-256 подписи события, а не её текст. Прежние значения принимаются для сравнения. Хранятся последние 1024 записи; более ранний идентификатор проверяется прежней проверкой по журналу событий.
- **Реже тайминги Kit.** Успешный быстрый (до 1000 мс) `kit.timing` записывается не чаще раза в 30 с на операцию и назначение. Ошибки и медленные операции записываются всегда.
- **Тайминги не останавливают прогон.** С 16000 событий диагностические события (события панели, тайминги, gap, claim.deferred) не записываются. Рабочие события продолжаются до прежнего предела 20000.
- **Пауза повторов панели.** При неудаче ожидания пауза между повторами растёт до 30 с, а не до 5 с.
- **Восстановление прогона.** Прогон 0.6.4, остановленный на пределе, после запуска 0.6.5 загружается, сжимается при первой записи и продолжается без потери состояния.

## Критерии

- Тест: тысячи событий панели и таймингов не выводят файл за линейный размер; снимок читается текущим загрузчиком и валидатором 0.5.41.
- Тест: загрузка большого журнала без строки размером с файл; сжатие после загрузки; повреждённый хвост по-прежнему даёт TAIL.
- Тест: повтор события панели — duplicate; другая подпись — CONFLICT; лимит отпечатков 1024.
- Тест: диагностические события после 16000 не записываются, рабочие записываются.
- Живая проверка длинного прогона — у пользователя. Журнал T_003 удалён по решению пользователя (в Корзине), его продолжение не проверяется.
