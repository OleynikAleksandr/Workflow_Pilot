# Workflow Pilot 0.5.2: готовность работающего исполнителя

18.10.2026 пользователь поручил восстановить текущую работу и добавить исправление временной блокировки при выборе сессии. T000D следует после T000C перед T001/T002. Общая автономная оркестрация из документа на Desktop сюда не входит.

## Причина

При выборе исполнителя desktop-model устанавливает sessionRecord.ready=false и вызывает WorkspaceReadiness. Наличие operation/transaction даёт READINESS_BUSY. Catch записывает временную занятость как ошибку, вызывает controller.cancel и показывает «Повторить проверку / Доктор проекта». executorStatus отдаёт record.error приоритет перед фактической активностью.

В T000A это совпало с полной проверкой перед коммитом. После окончания команды сообщение осталось при уже отсутствующих lock/transaction. Полная suite также дала HANDOFF_CHILD_CHANGED: это отдельный результат тестов, который исправляет исполнитель. Позже зафиксирована повторная активная проверка — её нельзя прерывать по старой надписи.

## Требования

1. Занятость своего уже работающего worktree — ожидание, а не повреждение проекта. Выбор сессии не отменяет controller, не теряет наблюдение за ответом/командой и не перезагружает страницу. Прежняя готовность не разрешает новую запись при действующей блокировке.

2. Показывать подтверждённую стадию («Выполняет проверки», «Сохраняет результат») либо общее «Рабочая папка занята; проверим автоматически после завершения операции». Устаревшая ошибка не вытесняет действительную активность или новый результат тестов.

3. После освобождения операции backend сам запускает адресную повторную проверку существующей очередью/watchers. Учитываются identity проекта/назначения, readinessEpoch, смена выбранной сессии, уничтожение record и перезапуск backend. Поздний результат не применяется к другому исполнителю; одинаковые события не размножают проверки.

4. Успех снимает только временную ошибку. Не скрывать другую реальную ошибку, не повторять Send, не пересоздавать назначение. Повторная занятость сохраняет ожидание; повреждение проекта получает предметную диагностику. Не нужен новый сервис, частый бесконечный polling или автоматическое удаление locks.

5. «Доктор проекта» и ручная перепроверка остаются для настоящих ошибок подключения/установки. При обычных тестах/commit они не предлагаются как требуемое действие пользователя. Доктор не запускается автоматически для обхода живой операции. Native/HTTP и обе темы одинаковы.

6. Ручная пауза сохраняется: текущий исполнитель штатно заканчивает задачу и интеграцию, следующий не стартует. После подтверждённого завершения всей активной работы появляется «Продолжить». Провал тестов не превращается в готовность к слиянию.

## Исполнение и проверки

Отдельное последовательное назначение T000D использует интегрированные T000A/B/C и существующие WorkspaceReadiness, наблюдатели, lifecycle сессии и проекцию. Не менять параллельно worktree T000A. Не выполнять hot patch установленного приложения; build/install остаются в delivery.

Поведенческие fixtures: выбор работающей сессии во время commit; busy→ready без клика; busy→failed tests без потери результата; повторный lock; несколько событий освобождения; переключение исполнителей с поздним ответом; восстановление backend без повторного Send; настоящий damaged project; ручная пауза до окончания команды и доступное продолжение после интеграции; обе темы/native/HTTP.

Проверки unit-all и architecture. T004 проверяет взаимодействие с остальными исправлениями. DOCS переносит контракт в desktop/orchestrated-execution/workflow-execution, удаляет выполненную временную спецификацию с точным Git context. Живую приёмку выполняет пользователь.
