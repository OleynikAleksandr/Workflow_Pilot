# Оркестрованное выполнение: контракты этапа

Статус: рабочая спецификация этапа 0.4.0, часть 2. Поведение для пользователя — [основная спецификация](orchestrated-execution-next.md). Здесь — что меняется в Kit, Control и интерфейсе, совместимость и проверки.

## Workflow Kit 1.8.0

**Стратегия плана.** Новое значение `execution_strategy: "orchestrated"` рядом с `sequential` и `parallel`. Его принимают схема и валидатор плана (`plan.mjs`, `schemas/plan.schema.json`), plan:create, review:prepare/publish, plan:extend, назначения, интеграция, recovery и запрет записи основного чата (`PARALLEL_MAIN_READ_ONLY`). Для orchestrated:

- `execution_origin_session_id` обязателен: агент указывает Session ID из recovery своей сессии, Kit проверяет наличие поля, Control сверяет сессию.
- DONE обычной задачи и DOCS требует роли `integration` с operation_id и source_commit (все они выполняются в worktree); DONE delivery-задачи — роли `implementation` (схема `allOf` и `plan.mjs`).
- `parallel_safe: true` допустим только при `parallel_allowed: true` и `max_workers > 1`. Для sequential/parallel прежние правила не меняются.
- Поле плана `release: boolean` — меняет ли план выпускаемое приложение.
- `context_pack` задачи принимают plan:create (`simple-workflow.mjs`), review:prepare, plan:extend (`extend-plan.mjs`) и task:update (`task-update.mjs`, только для не начатой задачи).

**Обязательная DOCS.** Для orchestrated Kit всегда добавляет DOCS (`normalizeCompletionContract` в `actions.mjs`): без delivery она последняя задача, с delivery стоит перед ним. plan:extend сохраняет DOCS последней обычной задачей; добавленные задачи встают перед ней. Агент ID `DOCS*` не задаёт.

**Delivery-хвост.** В `.harness/workflow.json` (схема `workflow.schema.json`, `validateConfig`) поле `delivery_tail` — упорядоченный список `{verification_ids, verification_kind}`. При `release: true` Kit проверяет, что после DOCS идут delivery-задачи именно этого состава и порядка; при `release: false` delivery-задач нет. Без `delivery_tail` план с `release: true` отклоняется с объяснением. Workflow Pilot задаёт хвост через config:apply после обновления своего установленного Kit до 1.8.0: `three-platform-release` (package) → `release-installed` (installed) → `github-release` (package).

**Main только для оркестратора и delivery.** В orchestrated-плане `PARALLEL_MAIN_READ_ONLY` действует для всех обычных задач и DOCS: они выполняются только через worktree-назначения, в том числе `parallel_safe: false`. task:start в main допускается только delivery-задаче и только когда все остальные задачи DONE, нет незавершённых назначений, интеграция IDLE, main чист и нет транзакции. Отдельного назначения main и секрета нет: в этот момент законно писать в main может только оркестратор.

**Барьер последовательной задачи.** Назначение для `parallel_safe: false` выдаётся, только когда все предыдущие задачи DONE и нет незавершённых назначений; пока оно не INTEGRATED, другие назначения отклоняются.

**Окружение worktree.** Подготовка `npm ci` выполняется только когда назначенные проверки задачи её требуют (`packageDirectories`); DOCS без проверок получает worktree без npm ci.

**DOCS в worktree.** Если DOCS удаляет required-документ, закреплённый в context_pack плана или задач с ревизией `WORKTREE`, интеграция переносит закрепление точной ревизии в общий план main вместе с кандидатом плана (`task-integration.mjs`, `integration-proof.mjs`), так что recovery main не ссылается на удалённый файл.

**Delivery в main.** Коммит delivery-задачи — однородительский implementation-коммит поверх merge-коммитов; проверка HISTORY_NOT_LINEAR его не отклоняет и не меняется.

**Удаление worktree.** Control запускает интеграцию только при остановленном исполнителе без активных команд (MCP исполнителя запущен не из worktree). После подтверждённого INTEGRATED Kit в той же операции интеграции удаляет worktree назначения (`git worktree remove` без force) и влитую ветку (`git branch -d`). Отказ удаления не отменяет интеграцию: назначение помечается для итоговой очистки. Прежний запрет удаления worktree и веток заменяется этим правилом только для orchestrated-плана. `assignment:cleanup` — итоговая очистка оркестратора: удаляет оставшиеся worktree и ветки только INTEGRATED-назначений, остальные перечисляет без изменений; повтор безопасен.

**Сигналы.** Новые команды пишут запись в журнал общего git-common-dir основного checkout (`workflow-kit/signals.jsonl`, как записи назначений) без коммита, в том числе из worktree исполнителя; повтор с тем же ID не дублирует запись:

- `task:block --task ID --reason` — исполнитель не может завершить задачу. Задача остаётся IN_PROGRESS в своём worktree, файлы не трогаются; в родительской задаче сохраняется `blocked_reason`, recovery и status его показывают. Заблокированный worktree не удаляется.
- `assignment:message --id ID --text` — уточнение оркестратора исполнителю.
- `plan:escalate --reason` — оркестратор не может устранить сбой.

**Recovery по ролям.** `recover --role orchestrator|discussion|executor`:

- orchestrator и discussion — полный recovery по существующим правилам; блок роли с правилами (для discussion: план не создавать и не менять, документы только по просьбе пользователя в `.workflow-temp/` с предупреждением). При активном orchestrated-плане оба видят, какие задачи выполняются исполнителями и что обычные задачи в main не выполняются.
- executor — идентичность, Workflow Core, PROTOTYPE, проектная часть AGENTS, задача и только её context_pack; документы плана и OVERVIEW автоматически не добавляются. Задачу Kit берёт из локального плана worktree назначения.
- Без `--role` (CLI-агент, hook SessionStart) — прежний recovery без блока роли; для orchestrated-плана продолжение говорит, что план выполняет приложение, и не предлагает task:start обычных задач.

**`.workflow-temp/`** входит в управляемую секцию `.gitignore`; Kit исключает её из recovery, посторонних изменений, проверок коммита и pre-push. При ручных правках секции installer сообщает конфликт, как сейчас.

**Версия и upgrade.** Kit 1.8.0; install --update поддерживает 1.7.0–1.7.3 и прежние upgradeFrom и сохраняет активный план и назначения. Документ `workflow-kit-package.md` уже близок к лимиту, поэтому новые контракты описываются в отдельном `packages/workflow-kit/docs/modules/orchestrated-plans.md`.

## Control (backend)

**Роли сессий.** Запись сессии хранит роль (orchestrator, discussion, executor) и для оркестратора — scope_id своего плана. Новая сессия без активного плана — кандидат-оркестратор без scope_id; recovery запрашивается с ролью, кеш контекста (`src/control/context`) учитывает роль. После публикации orchestrated-плана Control сверяет `execution_origin_session_id`: кандидат с этим ID получает scope_id плана; прочие кандидаты без scope_id и сессии без роли становятся discussion; оркестраторы прежних планов со своим scope_id не меняются. Несовпадение — состояние «Требует внимания», кнопка недоступна. Команда меню «Назначить оркестратором» (канал Desktop) доступна при потерянном оркестраторе и при несовпадении; выбор пользователя записывается в хранилище как оркестратор этого scope. Архивирование и удаление оркестратора активного плана отклоняются во всех путях (`pilot:archive-session`, окно архива, удаление сессий), архивирование проекта при активном плане — тоже.

**Хранилище.** Исполнители остаются записями дочерних worktree. Запись исполнителя INTEGRATED-назначения с удалённым worktree считается завершённой: inspect и selectSession используют сохранённую проекцию без чтения диска, страница восстанавливается только по chatUrl без повторной отправки контекста, `inspectOrphan` не считает её пропавшей, и она не попадает в «Восстановление исполнителей». Сессия хранит роль; оркестратор хранит scope_id и коммит закрытия своего плана для показа после archive. Новые поля добавляются с миграцией схемы и backup по образцу существующих.

**Состояние выполнения.** Новый `execution-control.mjs` хранит по проекту и scope: not-started, running, pausing, paused, complete и причину паузы (manual, escalation, unknown). Команда кнопки — allowlisted `ui.invoke` с lease (preload/ipc клиента, модель Desktop). Публикация не запускает выполнение; complete — когда все задачи DONE. Состояние входит в очистку при удалении проекта и в восстановление фоновой работы после перезапуска backend. Для legacy-планов работает прежний ProjectAutoPlan. Для orchestrated-плана переключатель AutoPlan и ProjectAutoPlan не используются: основной чат не получает «Продолжай» прежнего AutoPlan (`auto-plan-state.mjs`, `project-session-auto-plan.mjs`); поручения delivery-фазы отправляет только `execution-control`.

**Планировщик.** ParallelExecution для orchestrated: каждая обычная задача и DOCS — worktree-назначение и новый чат исполнителя; параллельные — до `max_workers`, последовательная — одна после барьера. Пауза прекращает только новые выдачи; автоматизация «Продолжай» работающих исполнителей и интеграция готовых источников продолжаются. После INTEGRATED страница исполнителя закрывается в backend. Итоговое поручение получает оркестратор после DONE всех обычных задач и DOCS: delivery-задачи в состоянии TODO не считаются недостающими источниками (`finalSourceState`). Затем delivery-фаза: `execution-control` по одной отправляет оркестратору поручение с текстом delivery-задачи через существующий путь отправки оркестратору (`sendExecutionMessage`/`AutomationSendState`, как итоговое поручение) и учитывает паузу между задачами; после последней — поручение итоговой очистки и ответа. Строка оркестратора показывает число назначений, ожидающих очистки.

**Сигналы.** PlanMonitor наблюдает журнал сигналов; наблюдатель файлов проекта (`src/execution/files/project-input-watch.mjs`) поддерживает этот путь в git-common-dir. task:block → одно сообщение оркестратору с задачей, причиной и сессией исполнителя; assignment:message → сообщение в чат исполнителя; plan:escalate → автопауза (escalation). UNKNOWN отправки, назначения или слияния → автопауза (unknown) без повторов. Каждая доставка записывается в журнал отправок до Send и не повторяется после неизвестного исхода.

## Интерфейс

- Sidebar строит дерево: проект → оркестраторы и чаты обсуждения; микрозадачи (метка, состояние, таймер) — в to-do plan карточки плана выбранного оркестратора. Группа «Исполнители» остаётся только для legacy parallel-планов.
- Шапка плана — название, описание и одна кнопка с подписью по состоянию; переключатель AutoPlan скрыт для планов оркестратора.
- Клик по начатой или завершённой задаче в to-do plan выбирает сессию исполнителя (delivery — оркестратора); не начатая задача не кликабельна.
- Тот же интерфейс работает в веб-клиенте iPad; кнопка требует права управления.

## Сборка трёх ОС

Выпуск остаётся одной задачей и одной транзакцией из одного `sourceCommit` с одним `release-manifest.json`. В `scripts/release-all.mjs` общие ресурсы (`resources/`: Kit, observer, плагин, vendor-notices) раскладываются один раз, затем упаковка macOS, Windows и Linux идёт параллельно в отдельные выходные папки без повторной раскладки ресурсов. Ошибка любой платформы останавливает выпуск; частичный выпуск не публикуется. Длительность сборки фиксируется в отчёте задачи сборки и сравнивается с выпуском 0.3.1; manifest для этого не меняется.

## Совместимость

- Планы sequential и parallel, уже начатые или открытые из донорских проектов, доводятся по прежним правилам и с прежним переключателем AutoPlan.
- Существующие сессии без роли показываются как раньше, пока у проекта нет orchestrated-плана; после его публикации они — чаты обсуждения.
- Kit вне приложения работает с sequential-планами в main, как сейчас.
- Внешняя сессия плагина ChatGPT в роли не участвует и выполнение не запускает.
- Внешние DOM-экспорты, границы Control/Execution/Frontend и клиент/backend сохраняются.
- AGENTS.md проекта до начала реализации получает правило о том, что этап 0.4.0 вводит оркестрованное выполнение, а прежние режимы сохраняются для начатых и донорских планов.

## Проверка

Автоматически, на изолированных fixtures без модельных ходов:

- Kit: orchestrated-план с автоматической DOCS без и с delivery; проверка `delivery_tail`; context_pack задачи во всех формах; отказ task:start обычной задачи в main и допуск delivery только после остальных задач; барьер последовательной задачи; удаление worktree и ветки после INTEGRATED и отказ удаления невлитого; assignment:cleanup и его повтор; task:block, assignment:message, plan:escalate и их повтор; recovery трёх ролей и без роли; `.workflow-temp/` и конфликт секции .gitignore; upgrade 1.7.3 → 1.8.0 с активным планом; бюджет recovery проекта Workflow Pilot.
- Control: роли при создании и после публикации, несовпадение origin, запрет архивирования оркестратора; миграция хранилища и запись исполнителя с удалённым worktree; переходы кнопки и перезапуск backend; волны (последовательная → параллельные → последовательная), лимит, пауза с доработкой; delivery-фаза оркестратора с паузой между задачами и итоговая очистка; цепочка сигналов и автопаузы, UNKNOWN; очистка при удалении проекта.
- Интерфейс (jsdom и изолированный smoke): дерево, подписи кнопки, кликабельность задач to-do plan, «Выполнено», legacy-группа «Исполнители», веб-клиент.
- Сквозной сценарий `tests/orchestrated-execution.test.mjs`: план из нескольких волн проходит до конца по кнопке, с паузой, блокировкой и эскалацией.
- Поставка: параллельная упаковка на заглушках, один manifest, остановка при ошибке одной платформы.
- Существующие unit-all, kit-check, electron-smoke, architecture и migration-compatibility проходят.

Живая приёмка пользователем: план из нескольких волн проходит по одной кнопке; пауза и продолжение; клик по задачам открывает сессии исполнителей; чат обсуждения во время плана; эскалация в диалог оркестратора; кнопка с iPad; обновление Kit проекта в приложении 0.4.0.
