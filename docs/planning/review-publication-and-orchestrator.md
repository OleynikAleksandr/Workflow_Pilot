# Публикация через Review и единственный оркестратор

Выпуск 0.5.29, Workflow Kit 1.9.7. Основание — живая проверка 0.5.28 в Workflow_Pilot_Test_01 23.10.2026.

## Что произошло

1. Пользователь включил Review, оркестратор подготовил план, Claude согласовал его с первого раунда, план опубликован через `review:publish`.
2. До этого оркестратор настроил стек и проверки через `config:apply`, но профиль проекта остался `DISCOVERY`. Обычный `plan:create` при заданном стеке сам ставит `DEVELOPMENT` и проверяет каждую задачу (`taskChecks`); путь Review (`review:prepare` → `createScope`) не делает ни того, ни другого.
3. После «Начать выполнение плана» Kit создал назначение T001 (ветка и worktree, коммит «chore: назначить T001»). Чтение его состояния (`packageDirectories` → `taskChecks`) отказало `STACK_NOT_CONFIGURED`. Приложение записало назначение как `UNKNOWN` и поставило паузу с причиной «исход операции неизвестен», хотя отказ Kit однозначен.
4. Пауза ждёт, пока все исполнители остановятся. Страница исполнителя T001 ни разу не создавалась, её нельзя признать остановленной, поэтому состояние навсегда осталось «Пауза…», а кнопка — недоступной.
5. Пока план готовился, пользователь создал в том же проекте вторую сессию; она тоже получила метку «Оркестратор». Сейчас без плана каждая новая сессия — кандидат в оркестраторы, единственный определяется только при публикации по `execution_origin_session_id`. Две сессии могут готовить план одновременно, конфликт обнаружится лишь при публикации (`SCOPE_EXISTS`, `REVIEW_BUSY`).

## Результат

### 1. Kit проверяет конфигурацию при публикации через Review

- `config:apply` с непустым `stack` переводит профиль в `DEVELOPMENT`, как `plan:create`. Пустой стек оставляет прежнее поведение.
- `review:prepare` и публикация (`createScope`, `review:publish`) проверяют каждую задачу кандидата тем же `taskChecks`, что и `plan:create`. Ошибка возникает до записи, с прежним кодом (`STACK_NOT_CONFIGURED`, `NOT_CONFIGURED`, `VERIFICATION_KIND`) и указанием, что сделать: `config:apply` со стеком и проверками.
- План, который Kit опубликовал, всегда можно начать: назначение не падает на проверке конфигурации.

### 2. Отказ Kit при назначении не вешает выполнение

- **Отказ Kit** — только структурированная ошибка валидации: процесс Kit завершился штатно и вернул JSON с кодом `WorkflowError`, кроме `ASSIGNMENT_UNKNOWN`, `INTEGRATION_UNKNOWN` и незавершённой транзакции. Такой отказ при создании или чтении назначения не превращает назначение в `UNKNOWN`: план встаёт на паузу с причиной `escalation` и текстом «Kit отказал в назначении T001: <сообщение>».
- Таймауты, сигналы, ненулевой выход без JSON, сбои ввода-вывода и git, неструктурированный вывод остаются неизвестным исходом (`unknown`): эффект мог состояться, «Продолжить» не создаёт назначение повторно. `WORKFLOW_LOCKED` и ошибки чтения, которые повторяются сейчас (`PLAN_CHANGED_DURING_READ`, `MISSING_FILE`), повторяются по-прежнему.
- Назначение, у которого нет сессии исполнителя в журнале и не идёт создание или восстановление его страницы (очередь назначения свободна), не считается работающим исполнителем: запрошенная пауза становится «Пауза» с кнопкой «Продолжить» и видимой причиной. Если создание страницы уже идёт, пауза ждёт его конца.
- Существующие причины `unknown` (неизвестная доставка, слияние, команда записи) сохраняются.

### 3. Один оркестратор с момента первой задачи

- **Кандидат.** Без плана новая сессия проекта — кандидат; в sidebar она подписана «Новая сессия», а не «Оркестратор». Кандидатов может быть сколько угодно, пока пользователь ни одному не дал задачу.
- **Владелец планирования.** Когда кандидат после подтверждённого стартового контекста получает первый пользовательский ход (на странице новый пользовательский ход после старта), служба записывает в Kit `.harness/runtime/planning-owner.json`: версия, Session ID, время, поколение, а также `scope_id` (или его отсутствие) и `plan_revision` на момент записи. Запись делает служба через библиотеку Kit под его блокировкой как compare-and-set; при `WORKFLOW_LOCKED` служба повторяет её, пока ход не обработан. Запись создаётся только при установленном в проекте Kit не ниже 1.9.7. Запись недействительна, если после неё план был архивирован (новый `archived_scope_id`/revision), даже если её не удалил старый Kit. Агент запись не создаёт. Shell-исполнитель MCP общий для всех чатов и сессию не определяет, поэтому Kit сверяет Session ID, которые агент уже передаёт: `recipient_session_id` в `review:prepare` и `execution_origin_session_id` в `plan:create`/`scope:create`.
- **Пока владелец есть** (план готовится, опубликован, выполняется, ждёт приёмки):
  - новые сессии проекта получают роль «Обсуждение»;
  - остальные кандидаты становятся «Обсуждением». DOM-сообщений в их чаты нет: роль участника в WAL меняется на S, следующий ответ `workflow_pilot_panel`/`read_message` этого чата содержит `roleUpdate('discussion')` с именем владельца, recovery — тоже. Жёсткая граница — отказ Kit `PLANNING_OWNED`;
  - «Оркестратор» в sidebar — только у владельца;
  - Kit отказывает `review:prepare` и публикации orchestrated-плана с другим Session ID кодом `PLANNING_OWNED` и называет владельца. `recipient_mode: manual` освобождает только `review:prepare` от сверки `recipient_session_id`; публикация orchestrated-плана при действующей записи всегда сверяет `execution_origin_session_id`. Проекты без записи (вне Workflow Pilot) не ограничиваются;
  - текст роли обсуждения охватывает и подготовку плана: план готовит оркестратор, эта сессия план не создаёт. Версия ролевого протокола повышается до 7; startup, шаблоны Kit, MCP-описания и backend-ошибки сверяются по AGENTS.md.
- **Снятие.** Архив плана (`archive`) удаляет запись владельца. Удаление или архив сессии-владельца снимают её. Пользователь может передать роль через меню сессии «Назначить оркестратором» — теперь и до публикации плана; это явное действие пользователя, запись владельца меняется.
- Recovery оркестратора и чата обсуждения показывает владельца планирования.
- Опубликованные планы без записи владельца продолжают определять оркестратора по `execution_origin_session_id`; sequential/parallel-планы не меняются.

### 4. Выпуск

Kit 1.9.7 с неизменяемым архивом 1.9.6 для проверки обновления; панель плагина пересобирается под build `0.5.29-communication-4` (`npm run stage:chatgpt-plugin`); приложение 0.5.29 для macOS, Windows и Linux из одного sourceCommit; установка в /Applications штатным installer; GitHub Release.

## Проверка

- Fixture Kit: Review-публикация с профилем `DISCOVERY` и функциональными задачами отказывает до записи; `config:apply` со стеком ставит `DEVELOPMENT`; затем публикация и назначение проходят.
- Fixture приложения: отказ Kit при назначении → пауза `escalation` с текстом, без `UNKNOWN`; таймаут `assignment:create` остаётся `unknown` без повторного создания; запрошенная пауза при назначении без страницы исполнителя становится «Пауза», а при идущем создании страницы ждёт его; неизвестные исходы по-прежнему дают `unknown`.
- Fixture ролей: два кандидата; первый пользовательский ход в одном делает его владельцем (с повтором при `WORKFLOW_LOCKED`), второй и новая сессия — «Обсуждение», `roleUpdate('discussion')` приходит в следующем ответе панели; `PLANNING_OWNED` для чужого Session ID, в том числе при `recipient_mode: manual` на публикации; устаревшая запись после архива недействительна; удаление владельца снимает запись; передача через меню.
- Sidebar: «Новая сессия» у кандидата, «Оркестратор» у владельца, «Обсуждение» у остальных.
- Полный набор: unit-all, kit-check, kit-assignments, kit-upgrade, architecture, electron-smoke, orchestrator-startup.
- Живую проверку выполняет пользователь: Review ON в новом проекте, вторая сессия во время подготовки плана, запуск плана.

## Границы

- Донор заморожен; модельные агенты не запускаются; живые проверки — у пользователя.
- Формат существующих планов и Review не меняется; обновление Kit с 1.9.6 сохраняет план, Review и назначения.
- Код Kit — только в `packages/workflow-kit`; установленный `.harness/kit` меняет installer.
- Документы не больше 28000 байт UTF-8.
