# Постоянная доставка сообщений через SDK

## Поручение и результат

26.10.2026 пользователь поручил полностью перевести рабочий обмен Workflow Pilot на SDK для оркестратора (O), исполнителей (E) и приложения. Очерёдность обработки входящих определяет ChatGPT. Экспериментальных режимов, активирующих скриптов, выбора пары задач, лимита двух уведомлений и разных правил для параллельных/последовательных заданий больше нет. После ревью спецификации и плана выполнить реализацию, проверки, выпуск macOS/Windows/Linux, штатную установку на этот Mac и публикацию GitHub без промежуточного согласования. Живые пользовательские сценарии обсуждаются отдельно после реализации; автоматические проверки не объявляются живой приёмкой.

До панели сохраняется единственный bootstrap нового Chat: короткая URL-команда открытия панели с enrollment ticket. SDK существует только после подключения панели; рабочий контекст и сообщения не отправляются через DOM или повторный URL-запуск. Chat-only; Work не возвращается.

## Канал и ответственность

Использовать существующие WorkflowChannel, PluginCommunication, AssignmentDialogue, DialogueDelivery и панель. Не создавать второй sender, scheduler, модельную прокладку или универсальный dispatcher. Backend сохраняет адресное сообщение в имеющемся WAL, панель получает его через существующий sync/wait и вызывает закреплённый SDK `createMessage.send` / `ui/message` с `role=user`, `target=active`, `send=true`. Получатель читает содержимое через собственный MCP и подтверждает штатные квитанции.

SDK обязателен для всех видов рабочего сообщения: task, context_request/context, question/clarification, decision/revision_request/acceptance, result, assignment-start/continue, integration/finalization, ready/recovery/diagnostic и уведомлений приложения о пользовательском выборе/Review/продолжении. Реестр и авторизация различают смысл сообщений; транспорт не выбирается по роли, виду задачи или занятости.

Сохранение Git, выполнение команд, API клиента, MCP-чтение и управление процессами остаются на своих существующих границах. Требование «все запросы через SDK» относится к доставке адресных сообщений агентам; оно не переносит локальные операции в текст чата.

Уже начатые sequential/parallel и orchestrated без dialogue_version=1 тоже переходят на SDK. Их семантика Kit и старые assignment:message/task:block сохраняются, но DOM-маршрут отправки удаляется. При восстановлении старого маршрута running не наследуется без свежего разрешения; подтверждённая существующая identity и одна кнопка Continue дают обычный SDK-grant. Сохранённый legacy sending/unknown остаётся неопределённым и не переотправляется. Отсутствие доказанной привязки/совместимой панели даёт конкретную блокировку подключения, а не новый чат, скопированные ID или DOM fallback. Проверить эту миграцию отдельной fixture.

## Отправка без ожидания свободного чата

Ни pending, first, claim, admit, verify, ни вызывающие их workflow/executor/review/continuation пути не ждут busy=false, stopped=true, writable composer, canSend, lastRole, окончания ответа, read/yield прежнего сообщения или отсутствия активной команды ради нового SDK-вызова. Это включает parallel-execution: relaySignals, diagnostic, finalization и поручения delivery не ждут page.stopped/canSend/channelSettled перед queueMessage/handoff. Эти наблюдения могут использоваться для отдельной защиты интеграции/complete/удаления worktree, но не для диспетчеризации сообщения. Семантические зависимости задач и фактические proof интеграции сохраняются.

Backend сохраняет порядок своих intent. На одном адресате одновременно один незавершённый SDK-вызов; после его accepted следующий сохранённый пакет доступен немедленно, без ожидания чтения или обработки предыдущего. Это сериализация передачи в SDK, а не расписание работы ChatGPT. Разные адресаты независимы. Более двух результатов и зависимые задачи используют тот же путь.

Обязательны настоящая Chat-привязка и свежая host identity, совпадение workspace/project/scope/session/participant/assignment/attempt/generation, действующий grant для рабочих назначений, живая совместимая панель и готовый документ. Ручные Stop/Пауза, отмена/удаление, утрата identity/связи и неопределённость уже начатой отправки остаются запретами. Наличие пользовательского черновика не является основанием переписывать composer: SDK его не трогает; совместимость этого поведения проверяется отдельно, без DOM-send fallback.

До Start разрешены только существующие законные сообщения настройки/выбора и startup. Рабочее задание не получает полномочий из одного подключённого SDK. Пауза не запрещает сохранить result текущей работы, но запрещает новую доставку, требующую grant. Continue меняет разрешение, не повторяет старый неизвестный Send.

## Atomicity, UNKNOWN и квитанции

Существующие WAL intent, ключ идемпотентности и контроль одной панели остаются. SDK вызывается ровно один раз на attempt; claim/verify непосредственно перед эффектом повторно проверяют актуальность адресата/сообщения/разрешения, без busy-гейта. SDK timeout одинаков для всех сообщений — 90 секунд; соответствующее ожидание claimed не короче 120 секунд. Панель поддерживает только свой lease во время Promise штатным sync каждые 20 секунд; это не продлевает grant и не включает режим.

claimed/UNKNOWN прежней отправки не обходятся новым вызовом тому же адресату. Потерянный report, restart/remount, истечение lease и поздний Promise не превращают неизвестный исход в успех автоматически. Поздний accepted/rejected журналируется с исходными message_id/attempt/generation. Явное реальное read может доказать чтение, но не стирает историю неопределённости и не разрешает переотправку. Другие адресаты продолжают независимо.

Принятие SDK, чтение MCP, yield, конец обработки, принятие SHA, интеграция, terminal receipt, cleanup и complete остаются разными фактами. accepted не означает DONE. Вместо одного member.deliveryGate для всего потока каждое сообщение хранит собственное состояние обработки; несколько accepted/unread/обрабатываемых сообщений допускаются одновременно. Старые сохранённые deliveryGate безопасно продолжают наблюдаться как обработка, но не удерживают новые принятые SDK-пакеты. Исторические sdk_busy поля/WAL читаются без включения режима и без переписывания пользовательских журналов.

Для терминальных операций сохранить доказательство read/yield/коррелированного окончания E и отсутствие команд перед удалением worktree; финализацию O и cleanup не имитировать. Наблюдение окончания ответа не является очередью доставки. Таймеры не разрешают SDK по догадке «похоже закончил».

## Полное удаление опыта и обходных путей

Удалить runtime-профиль sdk-busy, наблюдатель его файла, настройку off/burst, выбор case/пары/слотов, hold/checkpoint/probe инструменты и bridge/API descriptors, скрипт включения и экспериментальные тесты/анализатор, которые поддерживают этот механизм. Сохранить полезную общую причинную телеметрию message_id, intent, sdk.invoked/accepted/rejected/late, read/yield и lifecycle.

Проверить весь src, Python MCP, scripts, tests и исходный Kit: никакой отправитель O/E/приложения не должен возвращаться к DOM composer.deliver, загрузке q или скрытому busy/FIFO барьеру. Внешние публичные DOM-экспорты сохраняются по AGENTS как библиотечный контракт; они не используются для рабочего обмена. При отсутствии панели честное состояние ожидания подключения, без автоматического дубля сообщения и без требования пользователю копировать ID/включать режим.

## Интерфейс

Панель показывает одну фактическую текущую стадию: «Передаём сообщение», «Сообщение принято ChatGPT», «Получатель прочитал сообщение», ошибку с конкретной причиной или отдельную задачу агента. Не писать «ждём освобождения чата», «передадим после ответа» и не объявлять обработку/очередь ChatGPT по одному accepted. Передача нескольких сообщений не скрывает более позднюю реальную ошибку; исторически принятый пакет не называется ожидающим отправки. Оранжевый используется только для требующего внимания состояния, не для обычной занятости. Не добавлять кнопки/переключатели и дубли в sidebar.

## Автоматическая проверка

Через существующие публичные API/MCP/панельный SDK и изолированные fixtures проверить оба направления, сообщения приложения, больше двух сообщений, параллельные и зависимые задачи. Busy generation/tool wait/active commands, незаконченный prior turn и accepted-unread не блокируют вызов. Реальная цепочка fixture проходит prepared tasks → Start → E result → O read/exact acceptance/integration → dependent tasks/DOCS → terminal receipt/cleanup/complete. Хост симулируется явно; это не доказательство внутренней очереди настоящего ChatGPT.

Отказы: две панели, remount/restart, потерянный report/lease, UNKNOWN, поздний Promise, Stop/Continue, смена scope/attempt/identity, stale сообщение, чтение до уведомления. Не должно быть повторов SDK или интеграции, ложных квитанций и межпроектного влияния. SDK-совместимость закреплённых зависимостей проверяется по их реальному коду; зависимости не обновляются без необходимости.

Обязательны unit-all, architecture, chatgpt-plugin, executor-channel/codex-tools-live, electron-smoke и обе части Kit: kit-check и kit-assignments, плюс kit-upgrade. Не ослаблять проверки ради нового пути; прежние ожидания busy заменить проверкой нового контракта. Python выполнять с -B/PYTHONDONTWRITEBYTECODE. Живые ChatGPT/macOS/Windows/Linux/iPad не объявлять PASS по fixtures. Найденный в PROOF продуктовый дефект оформляется корректирующей задачей plan:extend до DOCS либо расширением её области штатным task:update до исправления; не делать скрытые src-правки в тестовой задаче.
