# Стартовый контекст оркестратора через панель

## Результат и границы

Новая сессия оркестратора получает через DOM только короткое поручение открыть Workflow Pilot с адресным приглашением и закончить загрузочный ход. Полный неизменяемый пакет recovery готовит backend и передаёт через подтверждённый канал панели. Загрузка файлов в ChatGPT для этого запуска не используется. Существующие отправленные попытки не воспроизводятся, путь исполнителя и выбранные оркестратором поручения сохраняются.

Это изменение транспорта, не исправление первоначальной внешней обработки вложений: её причина пока не доказана. Обновление не запускает автоматически план или задачи. Старые вложения, retry и их диагностика остаются для совместимых путей.

## Контракт

1. ContextSession собирает и проверяет полный пакет текущего проекта (identity, роль, scope, HEAD/signature), сохраняет его по SHA вместе с уникальным requestId до короткого DOM Send. Приглашение связывает только эту локальную сессию и текущий разговор. В DOM нет recovery, вложений и поручения реализации.
2. Стартовый контекст — отдельный вид сообщения backend → O в существующем WAL и content store. Его транспортный допуск действует до создания/старта плана и не выдаёт grant выполнения. E и посторонний разговор не могут читать пакет либо подтверждать его. Общее разрешение рабочих сообщений не расширяется.
3. Доставка происходит после регистрации, актуального bind/SDK и физического конца bootstrap при свободном вводе. Используются имеющиеся intent/accepted/unknown и idempotency. UNKNOWN никогда не разрешает повтор SDK Send. Reconnect восстанавливает тот же пакет и receipts; непрочитанные части доступны без повторного bootstrap.
4. Агент получает адресное уведомление с message_id, читает metadata и все части через MCP read_context, затем подтверждает digest через отдельный startup_complete. Backend принимает подтверждение только после чтения всех частей соответствующим O. Receipt чтения означает возврат части инструментом, а не измерение скрытого рассуждения. Повтор чтения/подтверждения идемпотентен.
5. Пакет сохраняется целиком, делится по UTF-8 без повреждения символов. SHA и число частей проверяются. Отмена/удаление/замена проекта или назначения запрещает чтение/доставку устаревшего пакета; новая попытка имеет отдельный requestId. Нельзя подменить пакет уже начатой отправки. Текст контекста не выводится в диагностику.
6. Планирование становится доступным после подтверждения контекста. Завершение bootstrap, SDK accepted, чтение и подтверждение контекста — разные стадии. Sidebar и панель показывают подключение, ожидание контекста, прочитанные части, готовность или конкретную ошибку; ошибочное «контекст отправлен» только по DOM Send исключается.
7. После подтверждения стартовый транспорт закрывается, последующий Start использует штатный grant. После рестарта pending может продолжиться; неопределённая отправка не повторяется. Закрытие панели не уничтожает пакет и receipts. Полный контекст O получает от приложения; дозирование задач для E остаётся обязанностью O.

## Реализация и проверка

Один последовательный этап реализации охватывает Control/канал, bootstrap, MCP и UI, чтобы не выпускать несовместимый протокол частями. Разработка этим чатом без модельных исполнителей. Review плана выполняет разрешённый Claude через Kit. Проверки адресные: новый старт без вложений, запрет до bind/конца хода, многочастный UTF-8, ранний ack, чужой получатель, повтор/reconnect/restart, stale/удаление, UNKNOWN, отсутствие grant задач, регрессия E и старого recovery. Интеграционные fixtures используют настоящий MCP/SDK с изолированным host, без живых моделей и рабочих профилей.

После реализации согласовать версию 0.5.20 и инструкции, обновить действующие контракты (DOCS), собрать macOS/Windows/Linux из одного sourceCommit и проверить состав/manifest. Перед production-сборками очистить только сгенерированный Python cache в tools/codex-app-server-mcp. Установить готовое macOS-приложение штатным installer без пересборки и остановки работающего приложения; занятый backend означает проверенный pending и ручное переключение пользователем. GitHub publication в этот scope не входит.

Живая приёмка пользователем: несколько новых workspace/сессий без выбора карточек; только короткий bootstrap, автоматическая панель, весь recovery получен и подтверждён, план ещё не запущен. Отдельно переподключение панели. Автоматические fixtures не доказывают доступность SDK настоящего ChatGPT.

Согласование инструкций: сверить role-protocol.mjs и шаблоны Kit с новым bootstrap, MCP-описаниями и ошибками; сам Kit и полномочия ролей не меняются. Стартовый receipt описывается единым контрактом канала. Версия communication protocol повышается до 4, старые панели получают штатный отказ VERSION и предложение обновить панель. Проверки Python запускаются с -B/PYTHONDONTWRITEBYTECODE=1. STARTUP создаёт tests/startup-context.test.mjs и выполняет также startup-recovery, attachment-diagnostics, prepared-flow-cycle и executor-channel. DOCS включает README и действующие docs/modules, явно оставляет живую приёмку pending.
