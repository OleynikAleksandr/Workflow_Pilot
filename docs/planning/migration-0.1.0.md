## Архитектура и ответственность

| Кластер | Ответственность | Граница |
| --- | --- | --- |
| Control | Проекты, логические сессии, привязки к чатам, задания, AutoPlan, Review, recovery, пользовательская проекция выполнения | ControlFacade |
| Execution | Команды, файлы, процессы, службы, технические исполнители, браузер и наблюдение страниц | ExecutionFacade и узкий browser-контракт |
| Frontend | Desktop bootstrap, окна, preload/IPC, представление и ввод пользователя | Клиент ControlFacade |

Frontend вызывает Control; Control вызывает предоставленные операции Execution; Execution возвращает подтверждённые результаты/события; Control обновляет продуктовую проекцию. Конкретные объекты собирает desktop bootstrap. Control не импортирует Electron/renderer; Execution не импортирует внутренности Control; Frontend не пишет во внутренние stores. Bootstrap только собирает зависимости и жизненный цикл, не принимает продуктовые решения.

Владельцы: проекты/сессии/привязки/назначения — Control; current plan и его транзакции — Kit; процессы/stdin/доказательства завершения — Execution; страницы/observer/технический Send — Execution/browser; выбор экранов — Frontend. Один checkout имеет один current plan, чат планом не владеет. Проекция не создаёт вторую копию плана.

Публичные методы описывают конкретные действия: открытие сессии, снимок состояния, продолжение, остановка точной операции, подготовка контекста, удаление проекта. Для каждого: аргументы, результат, ошибки, допустимые состояния, порядок вызовов, правила повтора и освобождения подписки. Передаются сериализуемые снимки/ID, а не Map, изменяемые records или Electron-объекты. Успех, ошибка, отмена и UNKNOWN различаются; потеря связи не доказывает завершение. Владелец запуска/остановки компонента один.

Никаких универсального execute(action), DI-контейнера, общей шины событий, скрытого polling или фреймворка ради будущего плагина. Классы — для состояния/жизненного цикла, чистые функции — обычные модули.

Целевая раскладка:
- `src/control/{projects,sessions,workflow,context}/`, `src/control/facade.mjs`;
- `src/execution/{commands,files,browser,runtime,platform}/`, `src/execution/facade.mjs`;
- `src/frontend/desktop/` — bootstrap, окна, preload, IPC и renderer;
- `src/contracts/` — только общие сообщения/ошибки/валидация границ;
- `packages/workflow-kit/` — единственный исходный Kit, логически Control;
- `tools/codex-app-server-mcp/` — исполнитель, логически Execution;
- `resources/` — ресурсы и автономные workers; `scripts/` — разработка/поставка.

Подпапки только по необходимости. packages/tools/resources — технологические границы, не новые кластеры. contracts не становится shared/common. Python не переносить в JS-каталог ради симметрии. src не импортирует scripts; автономные workers не зависят от недоступного src.

## Карта переноса и порядок

До копирования уточнить реальные экспорты/зависимости и наличие динамических входов. Рабочая карта в этой спецификации уточняется T001; не удалять код по одному отсутствующему статическому импорту.

| Донорский блок | Целевое размещение и разделение |
| --- | --- |
| main, preload, ui, окна | bootstrap и Frontend; продуктовые решения — Control |
| workspace-session, session-plans | Control/projects, sessions, workflow; физический IO — Execution |
| context-session, context-inputs, context-cache | Control/context; чтение и attachment — Execution |
| session-runtime, conversation-recovery | Control решает привязку/recovery; Execution/browser ведёт страницу |
| auto-plan, project-auto-plan, project-session-auto-plan | Control/workflow с прежней семантикой |
| plan-review, review-continuation | Control/workflow; запуск Claude — Execution |
| parallel-execution, parallel-kit, executor-session | Назначения/интеграция — Control/Kit; страницы/процессы — Execution |
| chatgpt-dom/composer/experience, page-observer, page-state | Execution/browser; сохраняются публичные экспорты и pageScript |
| mcp-runtime, mac-runtime-switch, windows-runtime, vps-tunnel | Execution/runtime и platform |
| workspace-setup, project-doctor, deletion, state-cleanup | Сценарий Control, worker Execution, экран Frontend |
| startup-readiness, startup-platform, browser-startup, tunnel-setup | Первый запуск через те же границы, без отдельного установщика |

Сначала получить самостоятельную запускаемую копию с безопасной identity, затем переносить по блокам: контракт → реализация и её тесты → потребители → проверка сценария → удаление старого моста. Неперенесённые части временно могут оставаться в исходных путях; адаптер имеет явное условие удаления. После первого каркаса каждая задача оставляет приложение запускаемым.

В Kit исследовать циклы transaction/task-integration/validate/task-assignment и actions/plan-review/recovery. Устранить циклы смешанных обязанностей; только реально необходимый оставшийся цикл допустим с коротким обоснованием в контракте и проверкой, запрещающей расширение исключения. Не переписывать весь Kit.

Стратегия ЭТОГО плана — sequential: фасады, main, stores и контракт Kit меняются взаимозависимо, отдельные worktree сейчас увеличат объём временных мостов. Снимок разрешает до четырёх исполнителей, но не требует их. Будущий продуктовый алгоритм не является поручением делегировать текущий перенос.

## Identity, подключение и существующие проекты

Новые имя пакета `workflow-pilot`, productName `Workflow Pilot`, bundle id `com.oleynik.WorkflowPilot`, собственные userData/browser profile/runtime и имена служб. Предлагаемый постоянный macOS-путь: `<workspace>/Workflow Pilot.app`; установленная копия `/Applications/Workflow Pilot.app`. Перед записью проверять цель и симлинки; донорские пути запрещены.

Не переносить механизм автоматического захвата/остановки legacy-служб донора. Локальные порты выбирать по фактической доступности с проверкой владельца. Закрытие окна сохраняет службы как в базе; остановка адресует только свою операцию. Два приложения не пишут одновременно один план: тест продолжения старого проекта выполняется после остановки его работы в доноре.

VPS пользователя: проверено через SSH 13.10.2026 — Ubuntu 24.04.5 LTS, x86_64; описание `/Users/oleksandroliinyk/VSCODE/vps-server`. VPS сейчас обслуживает канал, а не доказывает готовность Linux desktop. В доноре есть общие `com.oleynik.vps-mcp-tunnel`, SSH alias `vps-mcp-tunnel`, удалённый loopback-порт 17842 и адрес в конфиге vps-server. Новое приложение не должно переписывать эту службу или присваивать существующий маршрут.

Сохраняются Secure MCP Tunnel и VPS с переключателем. В новом приложении конфигурация VPS задаётся явно: собственные alias/служба/локальный конфиг и отдельно выделенный loopback-маршрут, либо видимый отказ при конфликте владельца. Дефолты не перенастраивают работающий канал. Настройка нового маршрута/пользователя/SSH на живом VPS — отдельное изменение проекта vps-server по его правилам; в этом плане сервер не меняется. Пока новый маршрут не подготовлен, Workflow Pilot работает через собственный Secure MCP Tunnel, а VPS помечен «требуется настройка», не ложно готовым. Конфликт не решается отключением донора. В документации сохранить конкретную процедуру подключения; действующий секрет не печатать.

Открытие проекта, созданного в доноре: пользователь выбирает существующую папку → inspect Kit → существующий current plan и история сохранены → создаётся новая локальная сессия → recovery отправляется один раз → работа продолжается с незавершённой задачи. Чаты/профиль/список проектов из старого приложения не импортируются. При чужом активном исполнении, неподтверждённой транзакции или назначении — диагностируемый запрет, без сброса и повторного присвоения операций.

Kit переносится из 1.7.2. Изменения только в новом packages/workflow-kit. При изменении его поставляемых owned-файлов повышать собственную версию и проверять штатное обновление с базовой 1.7.2 с сохранением ACTIVE/DONE и identity проекта; не оставлять разные owned-файлы под одной версией. resources/workflow-kit генерируется, .harness/kit обновляет installer. Никакого массового обновления реальных пользовательских проектов при переносе.
