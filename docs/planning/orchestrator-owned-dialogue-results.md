# Диалог O/E: результаты, интеграция и переход

Обязательная третья часть [спецификации](orchestrator-owned-dialogue.md) и [контракта надёжности](orchestrator-owned-dialogue-reliability.md), scope `orchestrator-owned-dialogue-refactor`.

## Обязательный результат исполнителя

После успешного commit --task E обязательно отправляет result O: что изменено, фактические проверки и ограничения, полный source_commit, идентификатор доказательства Kit, отсутствие/состав excluded_changes и точные относящиеся артефакты. Если проверки не прошли или коммит не подтверждён, это вопрос/блокировка, а не успешный result. Собственный финальный текст E не заменяет канал.

Backend проверяет связь result с собственным назначением, попыткой и существующим доказательством Kit. O читает отчёт и проверяет diff/результат через инструменты; текст E не заменяет Kit/Git. O затем посылает revision_request либо acceptance, привязанные к result_id и точному source_commit. При недоступном канале E сохраняет подготовленный отчёт и честное состояние ожидания; backend не сочиняет его из факта коммита.

## Приёмка и доработка

O принимает конкретную версию, а не любое будущее состояние T001. Если worktree изменился после результата, есть команда/transaction или новый commit, интеграция не начинается по старому acceptance.

Для доработки до интеграции Kit вводит явную новую попытку того же назначения по решению O: сохраняет прошлый result/commit/checks неизменяемой историей, отзывает его приёмку и открывает разрешённую коррекцию той же задачи в том же worktree. Родительская задача ещё не DONE. Это отдельный переход, а не повтор уже выполненного task:start/коммита или ручная правка DONE. Новая попытка получает собственные проверки, коммит и result; старая acceptance больше не действует.

Revision_request открывает новую попытку только при безопасном состоянии worktree и отсутствии незавершённой интеграции. Старые сообщения, доказательства и коммиты не переписываются. Kit штатно поддерживает этот переход, включая allowlist команд E, recovery, журнал попыток и commit provenance. Исполнитель не может сам принять результат или перевести задачу main в DONE. После интеграции коррекция оформляется новой задачей через штатное расширение плана.

## Интеграция

Acceptance сохраняется в Kit с result_id/source_commit/attempt. Затем O вызывает штатную integration:start/continue. Для нового режима Kit отвергает интеграцию без актуальной приёмки; scheduler больше не запускает merge лишь по READY_FOR_INTEGRATION. При изменении source_commit требуется новая приёмка. Основной checkout сериализован существующей операцией Kit. Интеграция уже принятого результата может быть продолжена тем же operation_id после сбоя; новая acceptance для неизменной операции не требуется.

Конфликт или ошибка проверок возвращаются O с operation_id; он устраняет конфликт разрешённых путей в рамках операции либо адресно организует необходимое исправление. Сохраняются MERGE_HEAD/operation и штатный repair/continue; O получает факты, не автоматический успех. Не подменять merge принудительным ours/theirs. Correction в main ограничена текущей операцией и разрешёнными путями. Перед новым назначением, затрагивающим занятый main, сначала разрешить или безопасно завершить существующую интеграцию штатно.

Kit остаётся единственным источником факта INTEGRATED/DONE. O может проверить два независимых результата в любом порядке, но слияния в main последовательны. Следующая зависимая задача получает задание только после проверенной интеграции зависимостей. После DONE исправления не переписывают доказательства старой задачи.

## Завершение плана

После интеграции обычных задач O выдаёт исполнителю DOCS адресное задание с необходимыми итогами. После интеграции DOCS O выполняет предусмотренный delivery-хвост и cleanup через Kit, проверяет общий main, выдаёт итог пользователю. Backend завершает разрешение связи только после подтверждённого завершения всех задач, финальной обработки O и отсутствия требующих решения сообщений. Остановка канала не должна отрезать последний result/ответ. Отсутствие новых сообщений не считается выполненным планом.

Ролевой текст O/E хранится в `packages/workflow-kit/src/lib/role-protocol.mjs`. Startup, recovery, шаблоны Kit, MCP server instructions/tool descriptions, сообщения и backend validation используют согласованную версию. Обновление правил в уже открытом чате идёт с рабочим чтением без повторного task:start. Несовместимый агент/панель не получает задание по старому протоколу.

## Совместимость и переход

Новый диалог получает явную версию capability в состоянии плана/назначения, Kit, backend, панели и MCP. Новые orchestrated-планы после обновления используют новый контракт. Старые sequential/parallel и legacy эксперимент сохраняют свой маршрут и доказательства; не переключать их молча по текущему флагу UI. Сохранить внешние DOM exports и Review-процесс.

Активный orchestrated scope 0.5.7 не переотправляет recovery/assignment-start и не мигрирует автоматически в середине хода. Поддержать штатную адресную миграцию при паузе и безопасной точке: сверить все назначения/коммиты/операции, записать версию, отправить через канал обновление правил O/E без повторения работы и продолжить после общего Continue. Пока есть занятый/неопределённый ход, миграция ждёт или возвращает точную причину; штатное удаление всё равно доступно.

Для уже готового E: после безопасного подключения O получает service-факт «есть результат без отчёта», затем просит E по каналу сформировать result по существующему коммиту. Backend не выдаёт собственный текст за отчёт E и не повторяет commit. Для уже интегрированных задач новые result/acceptance не требуются. Исторические UNKNOWN не отправляются заново и не подделываются read/DONE; переход требует установленного исхода либо адресного отказа, не общего сброса журнала.

Установленный Kit обновляется только installer, источники — packages/workflow-kit. Зафиксировать совместимый следующий номер Kit и протокол; проверить upgrade текущего и предыдущего комплекта. Несовместимость должна давать предметный код до запуска или эффекта, без ручного join. Рабочий опыт Test_02 не изменять в разработке; миграция проверяется на его обезличенной форме в fixtures, живой опыт — только по поручению пользователя.
