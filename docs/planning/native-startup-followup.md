# Исследование: значки Dock и светлая вспышка при открытии окна

18.10.2026 пользователь сообщил о двух дополнительных значках Workflow Pilot в Dock и белой заливке перед появлением диалога. Поручение — выяснить причины; реализация и новый план пока не запрошены. Исследован установленный выпуск 0.5.1 без управления интерфейсом, запуска новых экземпляров или остановки службы.

## Дополнительные значки

Подтверждено чтением процессов, LaunchServices, настроек Dock и журналов:

- Работает один основной процесс Workflow Pilot — backend с аргументом `--backend-host`. Отдельного HTTP-клиента на момент проверки нет.
- Dock содержит одну запись Workflow Pilot в `persistent-apps` и две в `recent-apps`. Все три имеют один bundle ID `com.oleynik.WorkflowPilot` и путь `/Applications/Workflow Pilot.app/`.
- LaunchServices сохраняет две записи того же bundle: завершившийся launcher PID 33245 со статусом `exited-with-subordinates` и его coalition, включающей backend PID 33254; сам backend зарегистрирован отдельно как `Foreground`.
- Журнал подтверждает: запуск backend в 10:03:14, открытие встроенного окна в 10:03:17, затем успешное завершение launcher. Вторая служба из этих значков не следует.

Причина в схеме запуска: `src/frontend/desktop/client.mjs` запускает тот же executable через `spawn(..., {detached:true})`, просит `window.open` и завершает launcher. `src/backend/main.mjs` переводит backend из `accessory` в `regular`, когда открывает встроенное окно. Получаются две регистрации одного GUI bundle; в наблюдаемой системе завершившийся launcher остаётся зарегистрированным с дочерними процессами. Отделение process group само по себе здесь не исключило сохранение LaunchServices coalition и дубликатов Dock. Установленный Info.plist не задаёт LSUIElement/LSBackgroundOnly.

Окно, меню приложения и значок службы используют один backend. Пункт остановки службы в меню окна обращается к этой же службе; наличие одинаковых пунктов управления не подтверждает два backend.

Направление исправления: обеспечить одного владельца видимого представления приложения в Dock, сохранив независимость службы от закрытия окна. Выбор механизма запуска требует отдельной проверки macOS LaunchServices и холодного/повторного запуска. Простое отключение «Недавних приложений» скрывает симптом; один `detached:true` уже недостаточен. Не чистить Dock и не менять identity/backend архитектуру без выбранного решения.

## Белая заливка

В `src/frontend/desktop/client.mjs` начальная тема всегда `light`. `BaseWindow` создаётся сразу видимым (`show: !fixture`) с фоном `#f4f6f8`. После показа загружается HTML панели, устанавливается соединение с backend, приходит состояние с сохранённой темой и отдельно запрашивается/прикрепляется выбранная страница. Получение темы в начальном state обновляет переменную, но не вызывает `applyTheme`; цвет окна меняет обработчик отдельного события `ui.theme`.

У `WebContentsView` панели и настоящей страницы (`src/execution/browser/backend-host.mjs`) стартовый фон явно не задаётся. `attachNative` прикрепляет страницу без условия готовности её первого кадра. Пользовательские цвета ChatGPT применяются через CSS на `dom-ready`/`did-finish-load`, то есть позже создания поверхности. Поэтому окно и область страницы могут показать светлую пустую поверхность до готового диалога. Для отдельного HTTP-клиента существует дополнительный светлый стартовый фон в `browser-view.html`; он не использовался в наблюдаемом запуске.

Вывод: в коде подтверждён показ промежуточного светлого состояния. Без записи кадров нельзя строго разделить вклад светлого фона окна и пустой поверхности страницы в конкретную вспышку пользователя.

Направление исправления: определить тему до первого показа, задать согласованный фон окну и вложенным поверхностям, показывать готовую оболочку с фоном ожидания, а страницу — после готовности отображения. Не ждать бесконечно сетевой загрузки ChatGPT и не перезагружать уже живой диалог. Фон обновлять также из начального snapshot.

## Доказательства и ограничения

Файлы `src/frontend/desktop/client.mjs`, `src/backend/main.mjs` и `src/execution/browser/backend-host.mjs` побайтно совпадают с файлами установленного app.asar. Это исследование фактического выпуска, а не только невыпущенных исходников.

Существующие native-window fixtures проверяют API и перенос живой страницы в скрытых окнах. В fixture не меняется Dock и не проверяется визуальная последовательность первого показа, поэтому эти две проблемы могли пройти автоматические проверки. Код приложения не изменялся; тесты и сборка для исследования не запускались. Будущая приёмка: один корректный значок при холодном и повторном запуске, сохранение службы после закрытия окна, отсутствие светлой вспышки в тёмной теме при открытии и переключении сессий; живую проверку проводит пользователь.
