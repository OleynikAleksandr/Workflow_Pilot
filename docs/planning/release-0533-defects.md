## Сохранённые границы

- Только обычный Chat. Work не возвращается ни в модель, ни в UI, ни в тестовые данные совместимости. Существующие реальные Work-сессии не поддерживаются.
- Новый Chat получает короткую команду открытия панели с тикетом через уже работающий URL/официальное расширение. Контекст передаётся панелью. Не возвращать DOM-ввод или автоповтор `q`; существующие наблюдатели страницы и входа сохранить.
- Receipt регистрации по тикету, постоянный Chat ID, чтение частей, `startup.complete`, SDK accepted, read, task:start, result, acceptance, integration и complete — разные факты. Никакой подделки квитанций ради снятия ожидания.
- Backend работает независимо от открытого окна; native и HTTP имеют одинаковые состояния и действия на macOS/Windows/Linux. Control не делает IO напрямую; сохраняются ExecutionFacade, allowlist API, identity и изоляция проектов.
- Новое событие или повтор status не разрешают повтор Send с неизвестным исходом. Один ключ/idempotency effect, один фактический intent. Ручной Stop/пауза, удаление проекта и отмена сохраняют приоритет.
- Не изменять donor, рабочие cookies/профили, глобальный Git, пользовательские файлы и живой `Test_001` во время автоматических проверок.
- Не строить универсальный диспетчер или параллельный журнал. Использовать существующие Kit, WAL, content store, канал навигации, shared contracts и проекции.

## Запуск и управление результатом

Рабочий вход пользователя остаётся прежним: новое обсуждение → выбор оркестрации → подготовка и Review → опубликованный план → одна кнопка Start/Пауза/Продолжить. После выбора оркестрации роль O меняется сразу; публикации для этого ждать не надо. До публикации плана sidebar не имитирует готовый план.

Разработка по этому to-do ведётся этой сессией Codex последовательно через Kit, без модельных исполнителей: у исправлений пересекаются модель статусов, план, WAL и общие проверки. Это CLI-план разработки вне сессии Workflow Pilot, без вымышленного `execution_origin_session_id`; продуктовая оркестрация остаётся оркестрованной. Пользователь разрешил выполнение всего плана. После PROOF отдельная VERSION готовит согласованные версии, затем DOCS, RELEASE, INSTALL и PUBLISH. Выпуск 0.5.34: macOS arm64, Windows x64, Linux x64 из одного закоммиченного sourceCommit; полный комплект по действующему release-контракту. Установка готового проверенного macOS bundle через штатный installer без пересборки/переподписи, с manifest/подписью/откатом; при работающей собственной службе допускается проверенный pending без её остановки. PUBLISH проверяет собственный GitHub repo, main/tag и все assets. Незавершённая платформа запрещает публикацию; native/live pending не объявляются пройденными.

## Проверка и доказательства

Каждая задача получает проверяемый результат и свой commit через Kit. Пути — ожидаемая область изменения; уточнение по фактическому коду проводится штатной командой, без обхода ограничений. Установленные managed-файлы Kit обновляет installer; реализация Kit меняется только в `packages/workflow-kit`.

На Review проверены все три части спецификации. Для исполнения общий required context — этот основной документ и компактный OVERVIEW; тематическая часть исполнения или UI подключается к относящейся задаче. Остальные части и модульные контракты перечислены адресно как reference-only: перед изменением соответствующего механизма агент обязательно читает их из checkout, но они не дублируются целиком в каждом recovery. Для расширенного плана сохраняется обязательный 20% запас: фактический recovery ≤144000 UTF-8 байт, ≤7 частей, каждая часть ≤28000 байт. Требования не обрезаются ради бюджета; уменьшается избыточное дублирование контекста, а не смысл критериев. Проверка вариантов пакета в изолированной копии не исполняет задачи и не имитирует DONE.

Минимальный итоговый автоматический набор: `unit-all`, обе части `kit-check` и `kit-assignments`, `architecture`, `chatgpt-plugin`, `electron-smoke`. При изменении MCP — `executor-channel` и `codex-tools-live`. VIEW обязательно запускает `unit-all` для всех изменяемых UI-тестов и `electron-smoke` с renderer-проверкой layout; файлы этой проверки входят в область VIEW. STARTUP и GIT также запускают `unit-all`, чтобы их изменяемые тесты не остались вне назначенных проверок. Адресные проверки задач используют существующие реальные verification IDs; не создавать фиктивный PASS и не заменять проверку кнопки вызовом внутренней функции. Тесты выполняются после реализации, сейчас их прохождение не заявляется.

PROOF добавляет связный сценарий через существующие пользовательские API/UI-компоненты на изолированном host fixture: публикация с подготовленными T001/T002 → Start при Finder metadata → блокировка настоящим файлом → Continue → смена generation/lease O → доставка обоим E → result/acceptance/integration → зависимая T003 → DOCS → cleanup/complete. Проверить отдельные этапы и одну непротиворечивую историю. Bootstrap — не task:start; модельные ответы в fixture детерминированы, реальные модельные команды не запускаются.

Fault injection: разрыв до/после WAL, потеря ответа prepare/sync/SDK, stale attempt, отмена, повторный Continue, restart до/после authorisation. Проверять отсутствие лишних назначений, интеграций и Send; сохранение manual pause; отсутствие влияния на соседний scope/project. Ранее существующие безопасные UNKNOWN-барьеры должны продолжить проходить.

UI проверяется native и HTTP: обсуждение, Review, выбор до/после сохранения/read, startup, готовый план, blocked и Continue, одновременно активные E. Ширины 320/480/900 CSS px, темы light/dark, 100/200% текста; на меньшей ширине — безопасное сложение колонок. Семантические DOM-тесты проверяют содержание/действие/отсутствие дубликатов, проверка layout — реальным renderer fixture и снимками; jsdom не считается доказательством переносов. Живые ChatGPT, клавиатура/assistive technology, native Windows/Linux и фактические macOS-окна остаются отдельной пользовательской приёмкой с честным NOT_RUN до её проведения.

## Приёмка

1. Все строки таблицы D001–D011 имеют отдельное проверяемое доказательство или явно описанное pending, без исчезнувших критериев.
2. Запуск двух E не требует ремонта `.gitignore`, повторной паузы, ручного открытия чужого чата или Enable.
3. До Start есть согласованное авторское содержание; после Start доставка не зависит от обязательного нового хода O для его сочинения.
4. Одна актуальная область внимания объясняет участника, стадию, адресата, причину и следующее действие; законченные события не занимают sidebar.
5. Потеря или обновление клиента не меняют identity и не повторяют действия. Реальные конфликты/неопределённость остаются видимыми.
6. Все назначенные проверки завершены, ограничения и pending-приёмка сохранены. DOCS не выдаётся за запуск suite; DONE не означает пользовательскую приёмку. Закрытие этого scope требует отдельного прямого поручения.

Связный сценарий `D001-D011 cycle` публикует готовые авторские пакеты, оставляет root/nested Finder metadata и добавляет настоящий пользовательский файл. Start и повторный Continue дают MAIN_DIRTY без E/SDK-эффектов. После удаления только тестового пользовательского файла один Continue запускает две независимые задачи; во время их работы протухает lease O. Далее проверяются восстановление sync, вопросы/решения, revision/result/acceptance/integration, зависимая T003, DOCS, cleanup и complete. Finder metadata не удаляется. Физический ChatGPT и ответы модели подставлены; API/MCP/SDK-адаптер, stores, scheduler, Kit и Git настоящие.

Обнаруженная при проверке стадий поправка: ожидание чтения после SDK accepted начинается по `send.report`, обработка — по `message.read` WAL, ожидание физического конца — по сохранённому yield; `created_at` относится к очереди доставки. Хост принял сообщение для O — отдельное нейтральное ожидание чтения, даже при последующей потере lease; оно не называется недоставленным запросом подготовки. Если квитанции времени нет, используется наблюдаемое время backend, без присвоения длительности очереди обработке.

До новой пользовательской проверки остаются **NOT_RUN**: настоящие ChatGPT/расширение/SDK в рабочем аккаунте, реальные macOS-окна и assistive technology, native Windows/Linux, iPad/Tailscale и фактические живые тайминги. Поставка трёх архивов, установка и GitHub публикация подтверждаются только последующими RELEASE/INSTALL/PUBLISH; PASS fixture их не означает.
