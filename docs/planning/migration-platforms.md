# Workflow Pilot 0.1.0 — платформы, проверки и поставка

Обязательная часть [спецификации переноса](migration-0.1.0.md). Все требования относятся к тому же первому выпуску.

## Платформы и первый запуск

| Платформа 0.1.0 | Пакет и проверка |
| --- | --- |
| macOS arm64 | .app и ZIP; первая живая проверка пользователем на его Mac |
| Windows x64 | Portable ZIP и нужные компоненты; затем UTM, с явной отметкой эмуляции на ARM |
| Ubuntu 24.04 LTS x64, X11 | Архив tar.gz с приложением и инструкцией; затем пользовательская Linux VM |

Linux ARM64, другие дистрибутивы и полноценный Wayland в 0.1.0 не заявляются. Для выбранной x64-матрицы VM в UTM на Apple Silicon должна запускать x64 через эмуляцию; ARM64 VM не является проверкой x64-пакета. На Wayland не выдавать захват XWayland за полный доступ к окнам/экрану; неподдерживаемая возможность явно видна. Начальная цель X11 фиксируется как техническое ограничение первой версии.

T001 до массового переноса проверяет официальные артефакты Electron/Node/Codex App Server/Python/uv/ripgrep/Git/tunnel-client для Linux x64 и условия поставки. Недоступная обязательная зависимость — blocker с конкретным решением, а не заглушка. Изменение закреплённой версии ради Linux отдельно обосновывается в спецификации.

Источник Windows-компонентов для первого выпуска: https://github.com/OleynikAleksandr/Project-Web-Pilot/releases/download/v0.6.115/Windows-Codex-Local-2026-09-10.zip, SHA-256 1f041488ad97d8abf1984fd3521afb8abe15f50b8df3d3e11f1cc4248e019d98 (из закреплённого src/windows-runtime.mjs донора). T001 проверяет наличие именно этого asset и digest; если не совпали — остановка, не fallback на latest. Загружать в собственный build-cache; из архива использовать только uv/tunnel-client/rg/MinGit, старый сервер не возвращать. Исходный архив с тем же digest публиковать отдельным asset 0.1.0, сохраняя его историческое имя. Новый репозиторий до первой публикации источником самого себя не является. Локальный runtime донора не копировать. Все автоматические ссылки на releases/latest донора запрещены; собственные env/marker/install имена используют WORKFLOW_PILOT_* и .workflow-pilot-*, кроме явно сохранённого имени vendor-архива.

Linux требует собственного runtime: control.py сейчас явно ограничивает платформы, startupSupported допускает только darwin/win32. Реализовать XDG-пути/права, user-службы при входе, группы процессов/stdin/terminal evidence, установку компонентов и оба канала, загрузку Chromium/preload/observer. Без root-запуска Electron и отключения sandbox ради обхода ошибок. Наблюдение окон/снимки в X11 проверять реально; управление мышью, клавиатурой и окнами не добавляется. API исполнителя сохраняет каталог базы, его параметры и ошибки.

Мастер первого запуска сохраняет вход/регистрацию ChatGPT, подготовку компонентов, туннель и ID, подключение коннектора, выбор проекта и диагностику. Он различает готовность страницы, служб, туннеля, подключения в аккаунте и первого действия агента с файлом. Перенести существующие инструкции определения адреса/IP и подключения там, где они действительно реализованы; не обещать автоматическое создание VPS-аккаунта или доступность функций OpenAI.

Пользователь выполняет вход, системные подтверждения и живые проверки. Агент не запускает/не переключает VM, не управляет интерфейсом. Тестовые fixtures не ставят реальные службы. На каждой ОС проверяются пробелы/Unicode в путях, executable bits, регистр имён, освобождение подписок и восстановление после перезапуска.

### Linux X11 и реальные ограничения

Выбраны обычные Python-библиотеки: mss 10.1.0 для экрана, python-xlib 0.33 для X11-дерева/EWMH и drawable GetImage, Pillow 11.3.0 для кодирования. [Исходник python-xlib 0.33](https://github.com/python-xlib/python-xlib/blob/0.33/Xlib/xobject/drawable.py) действительно реализует query_tree/get_image; старые справочные страницы с пометкой «not implemented» не использовать как контракт. Нет управления вводом/фокусом. Оконный capture должен читать drawable, а не выдавать прямоугольник экрана за независимый снимок окна. BadMatch/BadWindow, недоступное/свёрнутое окно и несовместимый формат возвращают явную ошибку; ограничения перекрытых областей фиксируются в приёмке, скрытого обещания полного захвата нет.

На [PyPI](https://pypi.org/) проверены: mcp 1.28.1 (MIT, Python >=3.10), mss 10.1.0 (MIT, >=3.9), python-xlib 0.33 (LGPLv2+), Pillow 11.3.0 (MIT-CMU, >=3.9). Есть portable wheels первых трёх и cp313 manylinux x86_64 для Pillow; Linux не требует компиляции этих прямых зависимостей на машине пользователя. T009 закрепляет транзитивные зависимости и hashes отдельным Linux lock; python-xlib поставляется отдельным заменяемым модулем с лицензией и соответствующим исходным архивом. Донорский marker Pillow только win32 расширяется на Linux; Windows psutil 7.2.2 остаётся платформенным, Linux использует штатные process API.

Ubuntu: live VPS подтвердил glibc 2.39, Git 2.43.0, наличие apt-пакетов libx11-6, libxext6, libxcb1, libnss3, libgtk-3-0t64, libgbm1, libasound2t64. Это минимальные известные системные зависимости, полноту проверяют loader/startup T009/T012 на desktop VM. На VPS Xorg/Xwayland не найдены; пакеты/службы не устанавливались. Для capture нужны X11 session, DISPLAY и разрешённый XAUTHORITY; отсутствие доступа и Wayland — диагностируемые unsupported, не пустой успешный снимок. Запуск пользовательской службы после login должен получать графическое окружение; не запускать GUI runtime как root.

UTM x64 VM ещё не создана/не проверена пользователем. Официальные базовые Linux assets доступны; инфраструктурного blocker по их наличию нет. Остаются обязательные работы T009: Linux setup/control/startup, собственные XDG/service paths, скачивание и проверка native payload, screen/window adapter; T010/T012: упаковка и notices. Техническая работоспособность Linux не объявляется доказанной до этих работ и живой проверки.

## Проверки и приёмка

Существующие проверки переносить вместе с поведением: unit-all (npm test), electron-smoke (npm run smoke), kit-check, executor-channel, codex-tools-live. Smoke моделирует ChatGPT, не вызывает модели. Точечные проверки назначать по блоку; полный набор — на базовом переносе и общей интеграции, без повторов успешных прогонов без причины.

Новые проверки должны покрывать реальные границы/отказы: identity и сосуществование, фасады и импорты, продолжение донорского проекта, Linux runtime, упаковку трёх ОС. Для зависимостей сначала рассмотреть dependency-cruiser/Knip; не писать свой анализатор. Отчёт лишних файлов не разрешает удалять динамические входы, IPC, pageScript, workers, HTML, preload, внешние экспорты и ресурсы упаковки. Чужой Web Pilot Sidebar не менять.

## Поставка

Все подготовительные изменения сборки/проверок делаются до DOCS. Общая команда npm run build собирает ОБЯЗАТЕЛЬНО три платформы; первая ошибка оставляет выпуск незавершённым. Форматы выше — исходная матрица; один номер 0.1.0, одни lock-файлы и sourceCommit. Разные хосты разрешены, произвольная отдельная сборка не считается полным выпуском.

macOS: собственная identity, для первоначального локального прототипа допускается техническая ad hoc подпись с явной отметкой о разрешениях; сертификат пользователя автоматически не выбирать/не копировать. Если до поставки пользователь явно выберет существующий сертификат, закрепить это в локальном конфиге нового продукта и проверках. Подпись донора не менять, ключи не создавать/не экспортировать, notarization сейчас не требуется.

Manifest включает ОС/архитектуру, version/sourceCommit, имена/размеры/SHA-256 всех assets, соответствие исходникам, зависимости/Kit, подпись и фактический статус native/VM/clean проверок. Шесть assets донора не являются новым нормативом. Linux-пакет содержит реальную реализацию, не только переупакованный Electron.

Корневой release-manifest.json — отслеживаемая побайтовая копия manifest готового комплекта, создаётся T012 после сборки, исключён из исходного снимка упаковки и не хеширует сам себя. Staging, Downloads, корневая копия и GitHub asset должны иметь одинаковый digest. T013/T014 его не дописывают: результаты установки/публикации хранятся в evidence Kit, а поздняя пользовательская приёмка не переписывает исторический manifest выпущенного комплекта. Корневой manifest может быть единственным функциональным путём delivery-задачи без обязательной правки его байтов.

После DOCS отдельные delivery-задачи: общий build через проверку Kit → установка готовой macOS-копии в два новых пути без пересборки → GitHub Release и проверка полного комплекта. Поставка `~/Downloads/WorkflowPilot-0.1.0/`, staging `.harness/runtime/releases/0.1.0/`. Перед записью проверять назначения/симлинки и состав. Каждый пользовательский архив содержит только необходимое для работы; корневой app и материалы разработки не вкладывать рекурсивно.

Публикация в новом репозитории: обычный fast-forward, тег v0.1.0 на manifest.sourceCommit, draft до сверки всех assets, затем публикация полного комплекта. Не переносить донорское разовое force-with-lease. Итоговый main может включать служебные коммиты delivery; тег указывает на исходный коммит сборки. После финального push ещё раз сверить main/tag/assets. При изменении исходников собрать заново весь комплект из новой базы, не смешивать платформы.

До явной приёмки пользователя план остаётся READY_FOR_ACCEPTANCE. Native Windows/Linux и чистая установка могут быть pending при первой публикации полного комплекта для пользователя; это отражается в manifest и Release, а не объявляется проверенной поддержкой. Отсутствующий пакет любой ОС запрещает полный выпуск.
