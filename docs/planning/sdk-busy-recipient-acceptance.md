# Измерение полного SDK-цикла с занятым получателем

Основной контракт — [sdk-busy-recipient](sdk-busy-recipient.md), выпуск и возврат — [поставка](sdk-busy-recipient-delivery.md). Живые проверки здесь NOT_RUN; данный план только готовится. Fixtures не доказывают поведение ChatGPT.

## Подготовка и контроль

Сохраняются независимые успешные исправления 0.5.36. Для нового комплекта записать фактические backend/app/Kit/role, panel build/protocol/resource URI, SDK version и модель/режим ChatGPT. Matching HTML на диске не подтверждает свежий iframe. Пользователь переключает службу/приложение в безопасной точке и обновляет подключение/панель; разработчик не управляет окнами/службой. Старый snapshot/capability — BLOCKED с точной причиной.

Сначала выполнить один полный mode=off контроль: раннее имя, Review ON по выбору пользователя, полные prepared_task всех задач до Review/публикации, один Start, два E, T003/DOCS, terminal acceptance, cleanup/complete. Сравнение — с пользовательским отчётом 0.5.36, не с выдуманной измеренной скоростью. Новый контроль снимает недостающие квитанции и подтверждает, что default off не изменил штатный канал. Review не переключать от имени агента.

Тестовые проекты новые и отдельные от Workflow_Pilot/донора/старых Test_*. Пользователь создаёт/выбирает их штатно. QA-файлы — `.harness/runtime/experiments/<experiment_id>/`, а не неучтённый Markdown в main. Существующие данные не чистятся ради повторения.

## Настоящий контрольный план

Во всех busy-прогонах одинаковый небольшой план, Node ES modules/node:test без внешних зависимостей, release=false:

| Задача | Результат | Зависимости |
| --- | --- | --- |
| T001 | normalizeLabels(values), отдельные исходник/тест | Нет, parallel_safe=true |
| T002 | summarizeNumbers(values), отдельные исходник/тест | Нет, parallel_safe=true |
| T003 | JSON CLI и интеграционные проверки | Проверенные интеграции T001+T002 |
| DOCS | README с запуском/примерами/ограничениями | T001+T002+T003 |

normalizeLabels: массив строк, trim и схлопывание пробелов Unicode, исключить пустые, сохранить регистр/порядок/повторы, не менять вход; неверный массив/элемент — TypeError. summarizeNumbers: массив конечных чисел, count/sum/min/max/average; пустой → count=0,sum=0,min/max/average=null; неверный вход/NaN/Infinity — TypeError, без мутации. CLI связывает функции; точный формат входа/JSON закрепить в подготовленном поручении до Review. Каждая задача, включая DOCS, запускает назначенный node --test; исполнитель проверяет source SHA. Документационный commit без tests не объявляется их PASS.

Полные task_brief/prepared_task и исходные context bytes готовы до Review/публикации. Роль O сама принимает точные SHA и интегрирует последовательно; backend не принимает/мержит автоматически по SDK accepted или READY. E задают вопросы и отправляют результаты штатным dialogue_version=1. После Start O не сочиняет задания заново.

## Case и инструментальный интервал

Подготовительный локальный скрипт до Start фиксирует exact case и task IDs T001/T002 своего опубликованного scope. После создания назначений и двух проверенных result backend однократно привязывает реальные assignment/attempt/message_id/SHA. Уведомления только этих двух result можно временно удержать до начала измерения; запись/проверка E-коммита и публикация WAL не блокируются. Удержание помечено experiment.fixture_hold и не маскируется обычным gate. Доработка E/новый attempt аннулирует выбранную пару. Новый case — новые реальные result; не сбрасывать read/intent старых.

Read/model-pull любого выбранного result до его sdk.invoked (в том числе до hold_started через status/journal) аннулирует пару: INCONCLUSIVE, без запрета штатного чтения и без повтора уведомления. Уже отправленный intent сохраняется, неотправленная часть пары больше не посылается экспериментально. В анализе указать раннее чтение как причину, а не выдавать обычную обработку за успешный burst.

Действующий Start один на каждый новый тестовый план. Для постановки контрольного опыта разрешён один заранее описанный запрос пользователя O с case_id; это экспериментальный стимул, а не ручное размораживание результатов. Если понадобятся повторный Start/«Продолжай»/повтор SDK для доставки, случай провален. Инструкцию и число вмешательств записать.

Узкие MCP-инструменты при вооружённом своём case:
- workflow_delivery_experiment_hold(case_id,duration_ms=15000): только O, максимум 30000; сервер сохраняет hold_started/hold_finished, возвращает nonce. Повтор idempotent: тот же case не создаёт второй интервал и вторую отправку.
- workflow_delivery_experiment_checkpoint(case_id,marker,nonce): только свой O и разрешённые marker begin/resume/final. Для generation первый begin без nonce создаёт серверный nonce и возвращает его; повтор begin возвращает тот же nonce, не запускает второй случай. Для resume/final nonce обязателен и сверяется с case/поколением; tool-wait получает его из hold. Никакого принятия result или управления режимом.

Ожидание hold выполняется асинхронно ВНЕ общей очереди мутаций/WAL и не удерживает запись других участников. Серверные события/изменения состояния остаются атомарными. Проверить Python HTTP timeout/bridge/runtime, одновременные wait/telemetry/E-send; ограниченные schema/error/read-onlyHint должны соответствовать реальному эффекту. Hold не является доказательством завершения ответа.

tool-wait: оба result уже готовы; пользователь даёт O инструкцию один раз вызвать hold со своим case_id, после возврата checkpoint(resume,nonce), закончить прежнюю контрольную работу и финальную строку с nonce. hold_started снимает подготовительное удержание; панель делает два последовательных SDK-вызова внутри интервала. Не просить O игнорировать поступившее сообщение.

generation: отдельный новый план/пара result. Пользователь заранее задаёт конечную текстовую работу с маркером завершения; O делает checkpoint(begin) и продолжает ответ без shell/нового hold. Case отпускает результаты только после свежего фактического busy/streaming наблюдения того же документа вне активного диагностического tool. Для положительного измерения нужна наблюдаемая незавершённая генерация и сохранённый конец исходного ответа/turn. Если в журнале нельзя отличить генерацию от ожидания tool либо уведомление оказалось вне неё, это INCONCLUSIVE, а не второй tool-wait PASS.

Для воспроизводимости произвольные «подумай 15 секунд», счёт символов или оценка скрытого reasoning не используются. Capture реальной границы ответа/turnId и контрольной работы; при необходимости пользователь сохраняет относящийся фрагмент транскрипта. Не экспортировать сырой разговор в диагностические события; транскрипт хранить отдельно по явному действию пользователя, в анализе — ссылка/digest.

read-only-command: после успешных основных случаев один новый полный план с точным безопасным probe из основного контракта. Command-activity отдаёт command_hash и все активные процессы, включая verified read-only/services; только единственная точная probe допускает отправку. Для tool-wait/generation даже чужая read-only команда блокирует опыт. Исполнение probe — собственный поставляемый Python -B -c с фиксированным кодом/аргументами, без чтения скрипта из app.asar системным node. Command-activity доказывает, что SDK вызван в его интервале. Прежний процесс/вывод завершаются; любые write/Kit/дополнительные команды запрещают обход. Этап не расширяется автоматически на реальную разработку во время команды.

## Последовательность полного живого опыта

1. Два E автоматически создаются/подключаются и получают задания. Не открывать их карточки для «помощи» readiness. Ручные join/ID/Enable исключены.
2. Дождаться обоих проверенных WAL result, подготовительно удержанных только своим case. Зафиксировать оба source SHA, idempotency keys, assignment/attempt, причину и время удержания.
3. Запустить согласованный контроль занятости. Отправить result1, затем result2; при быстром accepted целевой интервал до 1 секунды. Фактическую длительность сохранить. Если первый Promise не освобождается до конца занятости, burst не состоялся: SDK_DEFERRED/INCONCLUSIVE по данным. Не переходить к параллельным вызовам.
4. Доказать пересечение двух sdk.invoked с занятостью. SDK accepted, read и yield связать со своими attempt. Проверить текущую работу O и судьбу каждого result. Возвращение прежнего nonce/итогового маркера подтверждает продолжение, но без конца прежнего хода не доказывает отдельную очередь.
5. O проверяет и принимает оба точных SHA; каждую интеграцию подтвердить Git/Kit. Независимые результаты можно обработать в другом порядке, зависимые задачи запускаются только после обеих интеграций. Одна интеграция на source result.
6. Довести T003 и DOCS. Для четырёх acceptance отдельно получить saved, SDK result, read, yield/handled, physical close и Kit transport receipt. Проверить отсутствие pending/unread/UNKNOWN, cleanup DONE, удаление 4 worktree, only_main и чистый Git; complete backend и его отображение в панели подтвердить независимо.
7. Автоматическое завершение канала/клиентского ожидания и READY_FOR_ACCEPTANCE отличаются от закрытия плана. Архив — только по отдельной прямой приёмке пользователя.
8. Экспортировать полный JSONL/анализ и сохранить точный комплект. При первой потере/UNKNOWN/чужом адресате/дублировании остановить новые отправки, сохранить доказательства, не «добивать PASS» повтором.

Повторы: три валидных полных прогона, минимум один tool-wait, один generation. Третий — повтор одного из них без посещения карточек E и с закрытым пользовательским окном при живом backend; реальный O-case стартует до закрытия окна. Дополнительный read-only-command прогон — после положительного предварительного итога этих трёх. Отдельного single нет. Idle/off контроль не засчитывается в три. Один удачный случай не даёт общего PASS; будущие версии хоста этим не гарантируются.

## Журнал и классификация

Использовать существующие WAL/event_id/server_seq/client_sequence/export JSONL; новые серверные experiment.* события не принимаются из клиентской telemetry. Полный экспорт с пагинацией. Python CommunicationEvent(extra=forbid), JS allowlist и store согласованы. Перед SDK реальные параметры/корреляция фиксируются непосредственно рядом с вызовом, а не при получении wait.

Обязательны experiment/case/mode/busy_kind, BASE_COMMIT и build/sourceCommit/SDK; project/scope/run/O/panel/backend/generation/document; message/attempt/assignment/task/source_commit; прежний gate; busy/commands/draft/manual-stop/connection/identity/snapshot freshness. SHA backend получает по message_id, не из повторённого клиентом значения. Все переходы — message.persisted, claim, send.intent, sdk.invoked/accepted/rejected/timeout/error, send.report, read/yield, прежняя работа/checkpoint/end, result acceptance/integration, final close.

Передавать delivery_attempt_id/case_id во все SDK события, поздний Promise отдельно. Не писать токены, cookies, enrollment ticket, private URL и полный текст общения. Для результата — обычный content_ref; для identity — безопасный digest. Длительности только внутри одной монотонной clock_domain. Батч telemetry может прийти позже read: серверный порядок получения не равен времени SDK. Сопоставлять причинные связи и клиентскую последовательность; не вычитать performance.now разных процессов.

Анализатор scripts/analyze-sdk-busy-experiment.mjs принимает папку с экспортом, ничего не меняет в приложении. Вывод JSON + Markdown: таймлайн обоих result, доказательства занятости, принятия, сохранения прежней работы, чтения/обработки, точных SHA/интеграций и полного завершения. Считает read calls отдельно от долговечной read-квитанции, повторные чтения не выдаёт за повтор исполнения. Для каждого вывода — event refs, пропуски, фактические ограничения.

| Класс | Что установлено |
| --- | --- |
| QUEUED_OBSERVED | Оба приняты во время занятости, прежняя работа завершена, read в следующем наблюдаемом ходе, каждый эффект один |
| MID_TURN | Хотя бы один обработан внутри прежнего хода; отдельно сохранена ли прежняя работа |
| SDK_DEFERRED | Promise первого/второго разрешился после занятости; быстрый burst не доказан |
| REJECTED | Явный отказ хоста с кодом/временем |
| UNKNOWN | Исход неизвестен; повтора нет, поздние факты отдельно |
| ACCEPTED_UNREAD | Принято, но за 120 секунд не прочитано; о последующем времени выводов нет |
| INCONCLUSIVE | Нет границы хода/пересечения busy, логи неполны, сменился документ или вмешательство исказило измерение |

Фиксировать отдельно каждое сообщение и общий burst: разные классы нельзя сворачивать в QUEUED_OBSERVED. Успешный read до конца прежнего хода даёт MID_TURN даже при правильной интеграции. SDK accepted не является proof очереди. Внутренняя очередь ChatGPT недоступна; QUEUED_OBSERVED описывает только внешнее поведение.

Потерянная пагинация, frontend.gap, несвязанные часы/attempt, отсутствие финального транскрипта/turn boundary для строгой классификации — INCONCLUSIVE. Итог работы может быть PASS при неизвестной очереди, но разрешение публикации требует полный GO ниже.

GO: off-контроль без регрессии, все три основных валидных burst и read-only-command дали QUEUED_OBSERVED, прежняя работа сохранена, один эффект каждого result, полный цикл/квитанции/cleanup/complete, полные логи. MID_TURN/SDK_DEFERRED с сохранением работы — полезный иной результат, требует отдельного решения пользователя по дизайну; автоматически GO не становится. FAIL/UNKNOWN/потеря/дубли/чужая identity — NO-GO. INCONCLUSIVE устраняется улучшением измерения без переотправки старых result.

## Автоматические проверки до delivery

POLICY/DISPATCH: mode off без изменений, точная identity/scope/case/grant, два слота, неизвестные поля/симлинки/отказ записи; все допуски включая first/_verify(true)/admit/reserved. Прежний read gate остаётся, непринадлежащие/unread/UNKNOWN блокируют, два selected result разрешены в заданном порядке. Два клиента не вызывают двойной SDK. Stop/draft/commands/login/unavailable остаются отказами.

PROBE: настоящий Python MCP → bridge → backend → WAL → export; hold не держит мутационную очередь, старый ресурс/identity не может управлять case. Таймаут 90 при lease 60, успешное штатное обновление, отказ/expiry/Stop/remount и late Promise. Нельзя отложенный lease error выдать за отказ ChatGPT. Анализатор различает все классы, раннее read/model-pull, порядок telemetry, пробелы, read-vs-effects, физические границы, срок120 и продолжение плана после него. Отдельные fixtures подтверждают раннее чтение до hold/до SDK второго сообщения, отсутствие повторного Send и блокировку любых дополнительных команд, включая verified read-only.

PROOF: полный существующий API/MCP/SDK/Kit/Git/Electron fixture: раннее имя, Review OFF→ON/read, выбор/два Review/публикация, один Start, 2E, 2 result во время busy, exact acceptance/2merge, T003/DOCS, terminal receipts, cleanup/complete; без прямой подделки observed/read/acceptance. Late events, длинный busy, restart без повтора, скрытые карточки, соседний проект, SDK loss, error/UNKNOWN/отмена и rearm. Управляемые часы без реального sleep.

Проверки Kit назначаются ОБЕ: kit-check и kit-assignments; также kit-upgrade, executor-channel/codex-tools-live, unit-all, electron-smoke, chatgpt-plugin, architecture. Перед production-частями Kit удалить только проверенные Python caches по AGENTS, Python -B. Старые публичные DOM exports и строгий состав пакетов не ослаблять.

Native Windows/Linux/iPad/clean-install остаются NOT_RUN без настоящей среды. Успех macOS ChatGPT не повышает эти статусы. Общая приёмка всех функций приложения не объявляется завершённой данным экспериментом.
