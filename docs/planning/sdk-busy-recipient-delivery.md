## Последовательность задач

Разработка последовательная: общий транспорт/состояние/мост требуют согласованности, модельное делегирование не разрешено. parallel_allowed=false, max_workers=1, execution_strategy=sequential. Два E в испытании не меняют эту политику разработки.

| ID | Проверяемый результат | Зависимость |
| --- | --- | --- |
| POLICY | Узкий профиль/допуск и сохранённый базис, default off | — |
| DISPATCH | Два result busy-O, gates/слоты/lease/идемпотентность | POLICY |
| PROBE | hold/checkpoint, журнал и read-only анализатор | DISPATCH |
| PROOF | Связный полный fixture, fault injection и все checks | POLICY, DISPATCH, PROBE |
| VERSION | Следующий свободный номер и согласованный build | PROOF |
| DOCS | Актуализация всех документов проекта | Все предыдущие |
| RELEASE | Полный проверочный комплект трёх ОС | DOCS |
| INSTALL | Штатная установка и живой полный опыт до GO | RELEASE, DOCS |
| PUBLISH | GitHub только при подтверждённом GO | INSTALL, DOCS |

Task briefs/контекст готовы до Review. Внешняя Codex-сессия не получает выдуманный Session ID и не вызывает mode-request как сессия продукта. Review recipient_mode=manual; его положение принадлежит пользователю.

INSTALL намеренно содержит два раздельных результата: installed/verified pending по штатной проверке и фактический пользовательский live GO по журналам. Проверка release-installed подтверждает лишь установку. INSTALL нельзя завершить по одному installer receipt, пока нет живой приёмки. При pending пользователь сам в безопасной точке останавливает службу, повторяет installer и запускает новую; до подтверждения работающего backend/панели испытание NOT_RUN. Это необходимая пользовательская стадия, не повод тайно останавливать службу или подменять live fixtures. Исходники после RELEASE во время испытания не меняются; runtime-логи не загрязняют main.

В INSTALL сохранить immutable папку evidence: baseline/experiment-info, полные communication JSONL, analysis JSON/Markdown, Git/Kit receipts, фактические версии, источник/manifest, пользовательские подтверждения. Digest итогового набора и GO привязать к точному sourceCommit/build, версиям/ресурсу панели, case IDs и результатам. Сохранённый acceptance не объявлять прочитанным. Kit-коммит INSTALL фиксирует проверенные критерии, не превращает успешный release-installed в автоматический live PASS.

Если GO отсутствует, PUBLISH не начинать и не помечать DONE. INCONCLUSIVE означает завершённый сбор данных с недостаточным доказательством; старые result повторно не отправлять, для повторения новые scope/case. Пользователь заранее выбрал возврат к поведению 0.5.36 при неудаче. Закрывать незавершённый план как выполненный нельзя: дальнейшая ветка возврата оформляется через plan:extend/согласованный carryover с собственными DOCS/delivery, исходные DONE сохраняются.

## Версия, DOCS и проверочная сборка

Номер выбрать по актуальным package/manifest/локальным комплектам/GitHub перед VERSION; выше 0.5.36, не занимать номер по предположению. Статус до live — проверочная локальная сборка, не stable/latest. App/lock/backend/build/staged panel согласованы; protocol изменяется только при действительной несовместимости. Kit 1.10.2/role11 сохраняются, если продуктовый протокол не меняется.

DOCS до production: README/OVERVIEW, plugin/dialogue/timing/current-actions/совместимость/release сверяются с итогом. Новые самодостаточные контракты — docs/modules/sdk-busy-delivery.md и docs/acceptance/sdk-busy-recipient.md. До выпуска обычные модули явно обозначают проверочный статус/ограничения; пользовательская запись последующего GO — release evidence, не переписывание пакета. Реализованное перенести из временных specs в контракты; удалить только полностью отработанные planning-файлы без архивных копий, pending требования сохранить. Required-ссылки удалённого документа — на существующий exact Git blob. Каждый .md ≤28000 байт UTF-8 кроме текущего плана. DOCS checks:[] не означает тесты приложения.

Перед каждой production-командой, в том числе Kit package-check, проверить точные пути tools/codex-app-server-mcp без симлинков; удалить только сгенерированные __pycache__/.pyc/.pyo. Python -B. Строгий состав пакета не ослаблять.

RELEASE: штатный npm run build, три ОС macOS arm64/Windows x64/Linux x64 из одного sourceCommit после DOCS. Семь assets, архивы/staging/Downloads, locks/source snapshot/SHA/macOS signature проверяются действующим release-tooling. Все исходники/script изменения коммитятся до сборки. Комплект 0.5.36 сохраняется; одинаковая версия с другим содержимым запрещена даже для локального опыта. Изменение кода после прогона требует нового номера/сборки/установки/повторного live, а не повышения прежнего evidence.

INSTALL: node scripts/check-installed-release.mjs --install, готовый bundle в собственные проектную копию и /Applications/Workflow Pilot.app. Никакой сборки/переподписи или управления пользовательским окном/службой. Проверка release-installed --delivery допускает только verified pending с неизменным старым bundle. Запуск новой версии подтверждает пользователь. Донор не затрагивается.

PUBLISH: после GO тот же проверенный комплект, без пересборки/изменения manifest; собственный GitHub, tag v<version> на manifest.sourceCommit, семь assets size/SHA, draft/prerelease=false только после проверки черновика. Зависимая публикация не выполняется, если проверка draft не прошла. Remote main после последнего push равен итоговому HEAD. Явно описать ограниченную область: обычный mode off сохранён, busy допуск только для подготовленного test scope, успех не включает глобальное переключение или удаление observer. Native Windows/Linux/iPad/clean-install остаются NOT_RUN. Release-installed/github-release и live — отдельные доказательства.

Если испытания обнаружат полезный MID_TURN/SDK_DEFERRED вместо строгого queued-поведения, публикация требует отдельного решения пользователя; автоматически менять критерий GO нельзя. Этот план не распространяет обход на все рабочие result: широкое применение обсуждается по фактическому поведению хоста. Успешный выпуск с узким явно включаемым режимом сохраняет штатный default off.

## Возврат при NO-GO

1. Отключить новые экспериментальные отправки, экспортировать данные. UNKNOWN не становится pending. Не продолжать эксперимент старым кодом, не удалять worktree/журналы незаконченных E ради чистоты. Пользователь останавливает свою службу в безопасной точке.
2. Сохранить case, все экспериментальные коммиты, проверенный комплект и ограничения совместимости данных. Профиль/новые поля не должны менять существующие schema/session identity, grants или имена. Изолированный тест должен подтвердить чтение обычных записей/новых необязательных данных кодом 0.5.36 без записи в профиль. Старая версия не продолжает активный опыт и не повторяет intent.
3. Готовый комплект 0.5.36 — основа восстановления. Production-сборка требует роста версии. Сам installMacBundle общего запрета старого номера не содержит, но верхний check-installed-release связан с текущими package.version, canonical manifest, staging и source snapshot; после новых исходников нельзя просто передать ему старый Downloads. Быстрый off возвращает обычный допуск, но не заменяет бинарник. Прямое восстановление сохранённого 0.5.36 возможно только через отдельно проверенную штатную доставку готового bundle и совместимых данных; не подменять manifest/package ради обхода проверки. Точный путь прямой доставки этим планом не обещается.
4. Штатный путь восстановления: git revert только записанных функциональных/тестовых коммитов эксперимента, от новых к старым, сохраняя все независимые 0.5.36. Не reset --hard/force-push/git clean/массовый checkout и не откат всего HEAD. Учитывать пересечения и удалённые спецификации, не возвращать историю в текущие модули. Временные измерительные данные сохранить отдельно.
5. Через Kit подготовить новую ветку задач возврата, DOCS нового раунда, возрастающую версию с поведением 0.5.36, обе части Kit/регрессии, три ОС, штатную установку и контрольный mode off. При необходимости публикации восстановленной версии — отдельная delivery-задача; провалившийся опыт не публикуется stable. Эта условная работа не выполняется заранее и не помечается DONE на успешной ветке.
6. Возврат завершён после фактического запуска пользователем, проверки версии/источника/панели и нового контрольного прогона. Git revert/выключенный flag/installer pending по отдельности его не доказывают. BASE пакеты/tags/manifests не переписываются. Любая невозможность безопасного перехода данных — явная блокировка, не молчаливый reset.

Успешная ветка после PUBLISH остаётся READY_FOR_ACCEPTANCE. Приёмка и archive плана — только по прямому поручению пользователя.
