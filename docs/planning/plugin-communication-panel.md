## 1. Цель и приёмка

Подготовить канал между двумя агентами в отдельных веб-разговорах ChatGPT: отправитель сохраняет сообщение через MCP и заканчивает ход; ожидающая панель получателя получает событие, официальным SDK запрашивает новый ход текущего разговора; агент читает сообщение через MCP и отвечает через тот же канал.

Сохранение сообщения, принятие запроса хостом и чтение агентом — разные факты. Возможность пробуждения завершившего ход агента реальным ChatGPT ещё не доказана. Автоматический test host не заменяет этого доказательства.

## 3. Участники и привязка

Один запуск run_id, два участника O/E; каждый имеет participant_id, разговор conversation_key, панель panel_instance_id. Роль и выбор проекта/чата в сайдбаре не являются адресацией.

conversation_key получают только из доверенных metadata хоста. Проверить метаданные model-visible и app-only MCP вызовов раздельно. Сохранять хеш, не исходные openai/session, subject, organization. Присланный participant_id не является авторизацией. Отсутствие достаточных метаданных даёт понятный отказ без Send.

Привязка панели и модельного вызова подтверждается сопоставлением metadata; при необходимости одноразовым кодом join. Код доказывает только момент связывания. Нельзя объявлять его доказательством неизменности разговора после навигации. T001 фиксирует доступные сигналы и проверяемый алгоритм повторной проверки перед Send; если текущий адресат не доказуем, отправка запрещена. Поддержку этих сигналов настоящим ChatGPT устанавливает внешнее исследование.

После нового экземпляра панели/restart привязку проверять заново и требовать ручное включение. Никаких автоматических включений из сохранённого разрешения. Две панели одного участника конкурируют за одну доставку; разные участники ждут независимо.

## 4. Операции и сообщения

Точные schemas и имена закрепляет T001 в контракте docs/modules/chatgpt-plugin.md. Предпочтительный префикс новых операций workflow_communication_.

| Операция | Доступ | Результат |
| --- | --- | --- |
| workflow_pilot_panel | Модель/меню | Открывает прежний UI resource с новым интерфейсом |
| join | Модель | Подтверждает участника и разговор |
| send_message | Модель | Сохраняет question/answer/result |
| read_message | Модель | Возвращает адресованное сообщение и фиксирует чтение |
| probe | Модель | Одно отложенное контрольное сообщение самому себе |
| status/journal | По необходимости модель/панель | Диагностика без запуска модели |
| enable/stop | Только панель | Ограниченное пользовательское разрешение |
| wait/claim/report/telemetry | Только панель | Доставка уведомления и наблюдаемые события |

send/read/status не возвращают UI resource, чтобы не пересоздавать панель. read_message, wait, claim и другие меняющие состояние операции не помечаются readOnly. Проверять фактический MCP-каталог, visibility и annotations; сохранить общие инструменты исполнителя.

Сообщение: run_id, message_id, sender_id, recipient_id, kind, body, created_at, in_reply_to, idempotency_key. Ответ/результат связан с правильным исходным сообщением и участниками. Общий run_id не разрешает чужое чтение или отправку от чужого имени.

Один ключ + то же содержимое возвращает прежнее сообщение; другое содержимое с тем же ключом даёт конфликт. Ограничить размеры входов и очищенных ошибок явной ошибкой без молчаливого усечения сообщения.

Probe: одноразовая постановка на видимое время, отмена Stop, запись постановки и срабатывания. Без общего планировщика. Restart не воспроизводит просроченную или ранее назначенную probe автоматически; пользователь ставит новую. Никакого ожидания активной моделью внутри wait вместо пробуждения.

## 5. Ожидание, отправка и Stop

На экземпляр один long-poll; обычный timeout повторяет ожидание. Ошибка связи — ограниченная увеличивающаяся задержка до потолка. Dispose/pagehide отменяют ожидание, когда событие наблюдаемо. Журнал и очередь обновляются тем же каналом с seq-курсором, без второй частой polling-петли.

Доставка отделена от сообщения: pending → claimed → accepted/rejected/unknown. Claim одноразовый; перед SDK Send проверяются адресат, срок и поколение разрешения. После сбоя claimed считается потенциально отправленным и не возвращается автоматически в pending. Accepted и unknown не повторяются; rejected тоже требует отдельного разрешённого действия. Read — отдельная квитанция, поздний report её не отменяет. Повтор read не создаёт новое уведомление.

Enable по умолчанию на 10 минут, видимый expires_at и generation. Stop сохраняется на backend, отзывает разрешения и probe, прекращает новые отправки. Новый экземпляр/restart не снимает Stop. Если сеть потеряна, локальное прекращение и неподтверждённый сервером Stop различаются в UI.

Проверка разрешения и внешний Send не атомарны: Stop до передачи и уже начатая отправка различаются. Нельзя обещать отмену запроса, уже переданного хосту.

Перед Send сохраняется намерение. Если критическую запись сохранить нельзя — Send не начинается. Тайм-аут/разрыв после начала означает unknown, без автоматического повтора. Тайм-аут wait не означает unknown отправку. Отсутствие read не доказывает зависание модели.

Не предполагать API определения busy/черновика/постоянного conversation id без фактического подтверждения. Эти ограничения видны пользователю и проверяются отдельно в исследовательском workspace.

## 6. Хранение и сквозной журнал

Отдельный каталог экспериментальных данных собственного профиля; существующие проекты/планы/stores не переиспользовать для сообщений. Применить имеющиеся файловые средства, последовательную запись и восстановление без новой БД. T002 закрепляет источник истины и порядок записи, исключая подтверждение несохранённого сообщения.

Append-only JSONL по run_id, единый seq и server_time UTC, backend_instance_id при restart. Состояние Stop, очередь, квитанции и исход доставки переживают restart. Незавершённый хвост/повреждение обнаруживаются и явно отражаются; подтверждённые записи не теряются молча.

Общие поля: schema_version, event_id, seq, run_id, component, event_type, severity, server_time, backend_instance_id; по применимости panel_instance_id, participant_id, хеш conversation_key, message_id, delivery_attempt_id, in_reply_to, permission_generation, outcome, error_code, sanitized_error.
Frontend добавляет client_time, client_sequence, duration_ms по монотонным часам; backend — server_received_at. Повтор event_id не дублирует событие. Разные часы сами по себе не задают порядок.

Обязательно фиксировать:
- backend start/restart, build_id, SDK versions, handshake, capabilities;
- join/отказ, привязку/её проверку/наблюдаемую смену или потерю;
- enable, локальный Stop и серверное подтверждение, истечение срока;
- wait start/event/timeout/cancel/error, восстановление связи;
- persisted/duplicate/conflict, постановку/отмену/срабатывание probe;
- claim granted/denied, проверки адресата/разрешения;
- сохранённое намерение, наблюдаемый SDK invocation, accepted/rejected/error/timeout;
- report received/failed, unknown;
- read requested/returned/receipt, сохранённый answer/result;
- наблюдаемые visibilitychange/pagehide/dispose;
- ошибки диска, восстановления и экспорта, пробелы frontend sequence.

Намерение не доказывает SDK invocation; SDK accepted не доказывает read. Ограниченный буфер frontend допустим, но уничтоженный iframe может потерять события. Пробелы и ненаблюдаемые этапы обозначать, причины не выдумывать.

Хранить контрольный текст опыта; не сохранять cookies, токены, исходные session metadata, bridge descriptor, произвольные host payload или неочищенные stack traces. Без внешней аналитики и общего сбора чатов.

Экспорт выбранного run: полный UTF-8 JSONL и краткий отчёт с количеством событий, версиями и пробелами. Параметр MCP не разрешает произвольный путь записи. Экспорт не открывает чужие run. При ошибке журнал остаётся, ошибка видна.

## 7. Панель

Русский интерфейс, светлая/тёмная темы, узкая/широкая панель:
- run, роль, подтверждённый участник и привязка, build_id;
- «Включить связь», срок, «Остановить связь»;
- не привязана / остановлена / ожидает / отправляет / unknown / ошибка / срок истёк;
- непрочитанные и последнее сообщение;
- живая лента с фильтрами сообщения/участника/ошибок и выгрузка журнала;
- доступные возможности и причины отказа в диагностике.

Старые функции не прятать за переключателем. Устаревший HTML/протокол явно отклоняется; несовместимую старую панель нельзя принимать как нового участника. Выбор чата в сайдбаре не меняет адресата. Не обещать работу закрытого/уничтоженного iframe.

## 10. Передача и действия пользователя

После поставки сообщить:
1. Версию готового комплекта, путь и фактические тесты.
2. Дождаться безопасной точки и вручную выбрать «Остановить фоновую службу…» (закрытие окна недостаточно).
3. Если installer оставил pending: выполнить в Workflow_Pilot команду node scripts/check-installed-release.mjs --install, затем node scripts/check-installed-release.mjs для проверки готового комплекта; передать ошибки сюда, не обходить проверки.
4. Открыть /Applications/Workflow Pilot.app и проверить фактическую версию службы/MCP.
5. Переоткрыть прежнюю панель Workflow Pilot в ChatGPT, сверить build_id и новый каталог. Если хост держит старый каталог, обновить существующее подключение штатным действием хоста; точные доступные действия уточнить по фактическому результату, не создавать второе подключение.
6. Передать исследовательскому агенту путь handoff и версию; там по его инструкции привязать участников и включить связь.
7. Вернуть сюда результаты и журнал. После успешных опытов пользователь принимает/закрывает план; при проблемах поручает исправления.
