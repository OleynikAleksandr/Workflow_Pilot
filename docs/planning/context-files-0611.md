# Контекст агентам файлами на диске — Workflow Pilot 0.6.11

## Результат

Большой Markdown-контекст (стартовый recovery сессии и рабочее поручение O → E) доходит до агента обычного ChatGPT Chat без запроса хоста «Разрешить скачивание файлов?» и без цепочки чтения частей. Backend нарезает текст на файлы `context-NN-of-MM.md`, каждый не больше 24000 байт UTF-8, и до сигнала записывает их на диск в рабочую копию получателя. Ответ панели или `workflow_communication_read_message` содержит только список файлов с путями и размерами. Агент читает каждый файл одним вызовом `exec_command` (`read_only: true`), строго по одному и по порядку, затем подтверждает комплект конечными метками.

Причина изменения:
- A002 (0.6.10): из-за выдачи файлов как `EmbeddedResource` / `TextResourceContents` (`tools/codex-app-server-mcp/plugin.py`, `result()`) хост требует подтверждения скачивания в сессиях O и каждого E. Автономный старт исполнителей невозможен.
- A001 (0.6.9): `message_id`/`context_ref` лежали внутри файла, агент их не нашёл и не смог подтвердить старт.
- Предел одного чтения агентом — около 28000 байт. Последовательная выдача частей через `workflow_communication_read_context` провалилась в T002: исполнитель не пошёл за второй частью.

Живые измерения на 0.6.10 (01.11.2026, тот же текст 71 КБ, 329 требований, кодовые слова в середине и в конце):

| Способ | Вызовы `exec_command` | Обрезка | Ответы |
|---|---|---|---|
| 3 файла по ≤24000 байт, по одному последовательно | 3 | нет | все верны |
| 1 файл 71 КБ | 6 | да, перечитывание, ~3× дольше | все верны |
| 3 файла параллельно в одном шаге | 9 | объединённый вывод обрезан, ошибка обработки, повторы | все верны |

Отвергнуто: HTTP-доставка через внутренний веб-API ChatGPT (метод требует самостоятельно вычислять proof-of-work Sentinel — это обход антибот-защиты; вложений нет; лицензии у примера нет). Также отвергнуты прикрепление файлов через поле ввода и `EmbeddedResource`. SDK панели отправляет только текст.

## Поведение

### Нарезка

- Один канонический генератор для старта и поручения в `src/control/plugin/context-files.mjs`. Предел — 24000 байт UTF-8 на файл вместе со служебной шапкой и конечной меткой. Число файлов не ограничено искусственно: сколько нужно по объёму, но в пределах действующих бюджетов (старт 220000 байт, поручение — бюджет проекта и 1 MiB; превышение отклоняется без обрезки, с числом байт и файлов).
- Граница — последний `\n\n` (абзац или заголовок) перед пределом, затем последний `\n`, и только без них — граница символа Unicode. Символы UTF-8, кириллица и emoji не разрываются.
- Детерминизм: одинаковые `message_id` и текст дают те же файлы и метки. Метка каждого файла — первые 12 hex SHA-256 от `[message_id, context_hash, index, part]`, как сейчас. Манифест, ответ MCP и журнал меток не раскрывают.
- У каждой нарезки есть версия. Сообщения, комплект которых уже выдан 0.6.9–0.6.10 (`file_receipt` без новой версии), подтверждаются прежним посимвольным генератором, чтобы метки совпадали. Новые сообщения используют новую версию.

### Размещение на диске

- Каталог: `<рабочая копия получателя>/.harness/runtime/inbox/<message_id>/`. Для E — его worktree, для O и S — checkout проекта. `.harness/runtime/` исключён управляемой секцией Kit `.gitignore` и в коммиты не попадает.
- Путь рабочей копии определяет backend по зарегистрированной сессии, а не по данным модели: `PluginProjects` в `src/control/plugin/service.mjs` находит сессию в `projects.snapshot()` (как `terminalTarget`) и берёт `project.workspace` её проекта. Для E это дочерний worktree, для O и S — checkout проекта. `localParticipantTarget` не меняется.
- Запись выполняет Execution через узкий порт `ExecutionFacade`; Control не импортирует `fs`. Перед записью проверяется конечный путь: каталог внутри рабочей копии, без символических ссылок в цепочке `.harness/runtime/inbox/...`. Каждый файл пишется атомарно (временный файл → rename) и сверяется по SHA-256 после записи.
- Файлы неизменяемы. Уже существующий файл с тем же hash переиспользуется, с другим — ошибка `CONTEXT_FILES_CONFLICT` без перезаписи. Повторная доставка того же `message_id` не меняет байты.
- Файлы записываются до сигнала: для старта — при подготовке стартового пакета (`StartupContext.staged`) или, не позже, при первом `open`; для поручения — при фиксации сообщения `task` (`AssignmentDialogue.publish`). Ошибка записи блокирует отправку этого сообщения с понятной причиной и не запускает ход.
- Ленивая запись для сообщений, у которых комплект ещё не записан (опубликованы до обновления или запись прервана): первый `open` старта и первый `read_message` поручения записывают комплект и возвращают `context_files`. Уже выданные 0.6.9–0.6.10 комплекты (`file_receipt` без новой версии) записываются прежним генератором с теми же метками, остальные — новым.
- Очистка: каталог удаляется вместе с worktree при штатной очистке. В checkout O и S backend удаляет каталоги подтверждённых, отменённых и заменённых сообщений при отзыве/закрытии плана (событие плана в `workflow-channel.mjs`) и при старте службы (`desktop-model.mjs`). Неподтверждённые актуальные каталоги не удаляются. Удаляются только каталоги `inbox/<message_id>` с UUID-именем внутри проверенной рабочей копии, без перехода по символическим ссылкам.

### Ответ MCP

- `workflow_pilot_panel` (старт) и `workflow_communication_read_message` (поручение) больше не возвращают `markdown_files` и `EmbeddedResource`. Возвращается компактный объект `context_files`: `message_id`, `context_ref`, `workdir` (абсолютный путь рабочей копии), `files:[{index, name, path, bytes}]` (абсолютные пути в формате текущей ОС), `count`, `total_bytes`.
- Инструкция в ответе: «Прочитай каждый файл целиком одной командой, строго по одному и по порядку; не читай файлы параллельно и не объединяй несколько файлов в одну команду. Затем подтверди все конечные метки одним вызовом». Конкретную команду не называть: на Windows агент сам выберет подходящую (`Get-Content -Raw` и т. п.).
- `message_id` и `context_ref` есть в самом ответе. Служебная шапка файла их повторяет, но агенту не нужно искать их внутри файла.
- `result()` в `plugin.py` перестаёт создавать `EmbeddedResource` для контекста; общую поддержку ресурсов не удалять, если она нужна другим операциям. Описания инструментов `workflow_pilot_panel`, `workflow_communication_read_message`, `workflow_startup_complete`, `workflow_communication_read_context` обновить согласованно.

### Подтверждение

- Старт: `workflow_startup_complete` с `message_id`, `context_sha256=context_ref` и `file_receipts` всех файлов по порядку. Неполный или чужой набор отклоняется, ошибка называет число ожидаемых файлов и путь каталога.
- Поручение: `workflow_communication_read_message` с `file_receipts`. Действующие запреты сохраняются: без `files_confirmed` нельзя отправить `result` и подтвердить yield.
- Stale, superseded, cancelled, identity, generation и attempt проверяются как сейчас.

### Совместимость

- `workflow_communication_read_context` больше не используется для старта и поручения (`task`): новых стартов и поручений с частями не создаётся, правила их чтения его не упоминают. Он остаётся для старых стартов и поручений с частями и для остальных сообщений (result, question, decision, review, служебные) больше inline-порога 12000 байт и их `contexts[]`, как сейчас. Перевод этих сообщений на файлы — вне scope 0.6.11.
- Незавершённый старт 0.6.10 с выданными ресурсами после обновления продолжается: новый `open` записывает тот же комплект на диск прежним генератором и возвращает список файлов. Прежние метки принимаются.
- WAL, адресация, квитанции, `prepared_task` (неизменяемые копии выбранных документов), Review и периодическое открытие панели не меняются.
- Стартовая команда (`startupCommand`, CDP-ввод) просит открыть панель и прочитать файлы из `context_files` по одному. Приглашение не публикуется.
- Распознавание восстановленной стартовой команды в новом Chat (`ChatGPTComposer`, `clear-new-draft`) принимает список шаблонов: текущий, текст 0.6.10 (с приложенными Markdown-файлами) и вариант без файлов. Прежние тексты хранятся неизменными в `src/contracts/context.mjs`; черновик 0.6.10 после обновления очищается, а не получает `DRAFT_NOT_STARTUP`.

### Роли и Kit

- `role-protocol.mjs`: правила O/E/S о чтении комплекта переписать под файлы на диске и последовательное чтение; убрать «приложенные .md» и ссылки на `read_context` для новых ответов. Правила чтения Git и периодического открытия панели сохранить. Повысить `ROLE_PROTOCOL_VERSION`.
- `PLAN.md` и `plan:create --help`: оркестратор по-прежнему пишет один цельный `task_brief`, нарезку выполняет Pilot. Бюджеты не меняются.
- Версии: Workflow Pilot 0.6.11, Workflow Kit 1.10.10. Сохранить реальный архив выпущенного Kit 1.10.9 для теста обновления.

## Проверка

Автоматическая, на изолированных fixtures, без моделей и рабочих профилей:
- нарезка: 23999/24000/24001 байт, кириллица и emoji на границе, границы абзацев и строк, длинная строка без переводов, детерминизм, совпадение меток прежней версии;
- запись: создание, переиспользование при том же hash, конфликт при другом, отказ на символической ссылке и пути вне рабочей копии, атомарность, ошибка записи не запускает сигнал;
- настоящий MCP: в ответах панели и `read_message` нет `EmbeddedResource` и текста файлов, есть `context_files` с путями, размерами и `workdir`; метки не раскрыты;
- подтверждение старта и поручения: полный набор принимается, неполный и чужой отклоняются, `result` и yield без `files_confirmed` запрещены;
- большой result (> 12000 байт) для O по-прежнему читается через `read_context`; `task`, опубликованный до обновления, после рестарта читается через ленивую запись и подтверждается;
- путь: E получает свой worktree, O и S — checkout проекта;
- восстановленная стартовая команда 0.6.10 распознаётся и очищается;
- поручение 5×24 КБ и старт около 200 КБ проходят полным циклом; повторное чтение и рестарт службы не меняют файлы;
- совместимость: незавершённый старт 0.6.10 с выданными ресурсами подтверждается прежними метками; обновление с Kit 1.10.9;
- очистка каталога в checkout O/S и сохранение актуальных неподтверждённых.

Живая приёмка (выполняет пользователь после установки, до неё NOT_RUN): новый orchestrated-план с исполнителем, у которого поручение больше 24000 байт в нескольких файлах, с требованиями в середине и в конце. Нет запроса «Разрешить скачивание файлов?» ни у O, ни у E. Число вызовов чтения равно числу файлов, подтверждение проходит с первого раза, работа идёт без ручного «прочитай».

## Границы

- Транспорт пробуждения не меняется: панель, `openai/message`, периодическое открытие раз в 4 хода (`PANEL_CHECK_RULE`, `_panelCadence`) остаются.
- Не использовать внутренний веб-API ChatGPT, поле ввода для вложений и обход подтверждений хоста.
- Выпуски macOS, Windows и Linux одинаковы. Пути и инструкции работают на трёх ОС.
- Delivery: DOCS, сборка трёх ОС из одного `sourceCommit`, установка в `/Applications` (pending при работающей службе), затем публикация GitHub Release `v0.6.11`: fast-forward `origin/main` до проверенного HEAD, тег на `sourceCommit`, полный набор assets.
