# Интерфейс: одно место внимания и достоверные статусы

Часть [спецификации D001–D011](release-0533-defects.md). Описывает будущий результат; не является отчётом об исправлении.

## Распределение информации D002–D007

| Место | Что остаётся | Что убирается |
| --- | --- | --- |
| Sidebar | Проекты/сессии; имя, роль, компактный нейтральный индикатор агента; после публикации — настоящий план, его прогресс и одна кнопка Start/Пауза/Продолжить | Полная карточка выбора, оранжевая строка выбора в сессии, стадии/раунды/таймеры текущего процесса, доплановая пустая карточка, постоянная карточка startup |
| Основная панель Workflow Pilot | Актуальный этап, конкретная причина внимания и действие; независимые активные участники; история, свёрнутая диагностика | Несколько объяснений одной причины, исторический успех в качестве текущего события, общая «работа над ответом» поверх известной операции |
| Chat | Обсуждение, объяснения, содержательные решения агента | Продукт не обязан удалять сообщения агента; их наличие не повод дублировать управляющую карточку ещё и в sidebar |

Карточка опубликованного плана остаётся слева после всех требуемых обсуждений/Review. Её статус и progress описывают сам план; строки текущего этапа/Review, таймеров и запросов решения отдельно слева не повторяются. Единственная кнопка исполнения остаётся в карточке плана; панель ссылается на неё понятным полным текстом и не создаёт вторую кнопку запуска. Переключатель Review сохраняется штатным; значение и текущий раунд — разные сведения. Не возвращать отработанный успешный раунд как постоянное уведомление.

### Доступ при закрытой панели

Нельзя устранить дубль простым удалением единственного доступного пользователю выбора в HTTP или при недоступном iframe. Использовать тот же общий компонент и backend-решение в клиентской области текущих действий, открываемой из нейтрального перехода «Текущие действия»/«Открыть запрос» у выбранной сессии. Этот переход не повторяет вопрос, варианты, оранжевую карточку или отдельную команду исполнения в sidebar.

Встроенный клиент показывает обычную MCP-панель, когда она доступна; при явном открытии клиентской области действий основное содержимое с iframe скрывается штатным механизмом клиента. HTTP использует клиентскую область и тот же API. Область VIEW включает HTTP `src/frontend/web/app.mjs` с существующими overlays, native `src/frontend/desktop/browser-host.mjs` и адаптер viewer, а также `tests/fixtures/web-client-browser.mjs` и `tests/electron-smoke.mjs` для настоящего renderer. Одновременно в одном окне пользователь видит одну полную интерактивную карточку. Наличие SDK/lease не считается доказательством фактической видимости iframe. Не вызывать модель для обычного просмотра/ответа и не открывать новую ChatGPT-сессию. Проверять текущие session/project/choice generation по backend перед сохранением; отдельного состояния решения у fallback нет. Разные окна/клиенты могут видеть одно решение, но CAS позволяет сохранить его один раз.

## Имя участника D002

Имя обозначает лицо, стадия — действие. До назначения специальной роли использовать **«Агент»**. После выбора orchestrated — **«Оркестратор»** сразу, даже до публикации плана. Исполнитель — **«Исполнитель»** с понятным task ID/именем. При явно назначенной функции планирования допустим **«Планировщик»**, проверки — **«Рецензент»**, собеседника — **«Собеседник»**; не назначать такие роли по наличию одной реплики.

Нормативно запрещены имена «Планирование» и «Обсуждение» как субъект фразы «работает/ждёт». Существующие внутренние S/P/O/E, полномочия и выбор пользователя не меняются ради текста. Согласовать общий `participantName`, session roles, startup-тексты, историю и подписи sidebar; не поддерживать расходящиеся словари в двух UI.

## Стадия и приоритет D004/D011

Расширить текущую backend-проекцию workProgress/planActivity, а не вычислять независимую эвристику в каждом renderer. Проекция несёт семантические actor, stage, recipient при доставке, reason, требуемое действие, время начала наблюдаемого этапа и устойчивый event/choice ID. Сырой текст пакета и секреты в preview не передаются.

Приоритет для одной причины: блокирующая ошибка → необходимое решение пользователя → известная выполняемая операция → обычное ожидание. При нескольких независимых участниках главная причина внимания выделена одна, а реально продолжающаяся работа других участников видна компактно в том же разделе. Не объявлять весь план остановленным из-за одного вопроса E. Сам запрос и его суммарная строка не должны дважды требовать одно действие.

| Подтверждённый факт | Основное сообщение |
| --- | --- |
| Обычное обсуждение, конкретная операция неизвестна | «Агент работает над ответом» |
| O готовит план | «Оркестратор готовит план» |
| Review действительно запущен | «Рецензирование плана · Claude · раунд N» |
| Review только поставлен в очередь | «Ожидаем начала рецензирования»; не показывать его как начавшееся |
| Пользователь должен выбрать | Одна карточка с точным вопросом, варианты и рекомендуемый первым |
| Выбор уже сохранён | «Выбрана оркестрация · передаём решение агенту», нейтрально |
| План опубликован, не запущен | «План ждёт вашей проверки и запуска. Нажмите „Начать выполнение плана“ слева» |
| Backend просит O подготовить T001 | «Запрос подготовки T001 ожидает доставки оркестратору» |
| SDK/lease O не восстановлен | «Канал оркестратора восстанавливается; запрос T001 ещё не доставлен» |
| Поручение E действительно сохранено | «Поручение T001 сохранено; ожидаем канал исполнителя» |
| SDK принял | «Хост принял сообщение для [получатель]; чтение ещё не подтверждено» |
| E не получил task | «Исполнитель T001 ожидает поручение оркестратора» |
| MAIN_DIRTY | Конкретные мешающие пути, причина блокировки, одно доступное Continue |

Фразы формируются из фактов; метка task ID сама по себе не делает E получателем сообщения O. Не выводить generic busy вместо начавшегося Review. Таймер относится к текущей наблюдаемой стадии; не выдавать его за время рассуждения, uptime или время уже законченного этапа. При переключении/refresh время не начинает новую историю для того же события. Для пропуска измерения показывать отсутствие данных, а не выдуманный ноль.

## Жизненный цикл выбора D003/D005

1. `offered`: один вопрос с кнопками, оранжевый акцент и текст о необходимом действии. Клавиатура, доступные имена и видимый focus обязательны.
2. Запрос сохранения в пути: защита от второго нажатия; пока backend не подтвердил долговечное решение, не объявлять его сохранённым. Отказ сохранения оставляет возможность выбрать с точной причиной.
3. `chosen` после подтверждённой записи: сразу компактное нейтральное подтверждение, без большой рамки/фона/прежнего вопроса и повторных вариантов. Нормальное ожидание доставки не требует внимания пользователя.
4. SDK accepted отличается от read. После подтверждённого получения агентом выбор уходит в историю с вариантом и квитанцией; текущая область показывает следующую операцию.
5. Если требуется новое действие пользователя, оранжевый акцент возвращается только для конкретной новой причины с доступным шагом. UNKNOWN не предлагает повторить уже сохранённое решение/Send.

Повторное открытие, другой клиент, replay SSE и restart восстанавливают состояние по ID/generation из backend. История не размножает одно событие. Изменение оформления не меняет payload, идемпотентность и права; delivered/read не создаются CSS-переходом.

## Startup и адрес D001/D007

В общей проекции стартовой попытки учитывать текущую сохранённую сессионную привязку. Публичному UI достаточно проверяемых состояний без полного chatUrl/тикета. Если у собственной сессии есть нормализованный постоянный URL с действительной identity/binding и соответствующим актуальным наблюдением/сохранённым доказательством, старый `attempt.addressStatus=lost` не создаёт сообщение «Адрес чата утрачен». Сохранённый URL сам по себе не разрешает признать чужую текущую страницу своей. Реальные конфликт identity, отмена, отсутствие достоверного адреса и неподтверждённая навигация не скрываются.

Исправить место формирования `startupLaunch`/startup progress и потребителей Desktop/HTTP/plugin, а не только убрать одну строку. Разделить исторический запуск и текущее состояние адреса; повторная загрузка старой записи не переписывает identity и не выбирает последний `/c/...` в браузере. Проверить причину появления lost в controller, сохранив обоснованные lost/conflict для незавершённой попытки.

Подготовка → передача → чтение N/M → подтверждённый startup.complete показываются в текущей области панели. Завершённое событие «Контекст получен и подтверждён» сохраняется в истории, без постоянно закреплённой карточки sidebar; затем текущий статус определяется следующей реальной работой. История устойчиво идентифицирует попытку/контекст и не возвращает старый успех как новое уведомление после refresh. Квитанции и hash доступны в диагностике.

Snapshot stale сохраняется отдельным корректным фактом: агенту перед следующим решением нужен актуальный контекст. Это не потеря адреса и не автоматическая причина повторять q/открывать новый чат. Реальная ошибка или незавершённая передача остаётся в едином блоке внимания с конкретной причиной и действием. Не объявлять все startup-уведомления ошибочными по одному случаю D001.

**Критерии STARTUP:** сохранённый собственный URL + старый lost; URL действительно отсутствует; конфликт с другой страницей; отмена; renderer crash; повторное открытие и backend restart; snapshot stale после полученного part 0. Все сценарии сохраняют запрет повторной первой команды и не выдают полный URL в preview.

## Перенос текста D006 и доступность

Убрать `nowrap/ellipsis/overflow:hidden` для актуальной инструкции `.wp-what` и связанных статусов/карточек. Grid/flex должен иметь ограниченную колонку текста (`min-width:0`), перенос длинных непрерывных идентификаторов и автоматическую высоту; значок и таймер не накладываются. При узкой ширине таймер может занимать отдельную строку. Действие видно полностью без tooltip/hover, горизонтальной прокрутки и ручного расширения панели. Не фиксировать высоту по одной строке и не обрезать последнюю строку.

Проверить 320/480/900 CSS px, 100/200% текста, обе темы, русский длинный текст, длинный ID и доступные подписи. Оранжевый используется только для действия пользователя; смысл дополняется текстом/значком и достаточным контрастом. Нейтральное выполнение имеет индикатор фактической активности, а не бесконечный spinner для terminal. Изменения live-region объявляют переход состояния, не каждую секунду таймера; фокус не прыгает после SSE.

**Критерии STATUS/VIEW:** общий семантический fixture проверяет все строки таблицы; один и тот же backend snapshot даёт согласованные native/HTTP/plugin представления. Настоящий renderer проверяет перенос и отсутствие пересечений; DOM-тест — отсутствие второй карточки и корректное действие. Отдельно закрытая/ещё не подключённая MCP-панель, HTTP без iframe, переключение сессий и pending выбор другого проекта. Не терять доступ к решению при устранении дублей. Живая пользовательская проверка остаётся pending до её проведения.
