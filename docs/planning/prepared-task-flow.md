# Заранее подготовленные поручения и короткое завершение

## Результат

Один Start запускает прежний адресный O/E workflow, но O заранее сохраняет основу поручений при планировании, обрабатывает доступные назначения одним ходом и завершает план коротким итогом. После complete панель прекращает ожидание рабочих сообщений без ложной сетевой ошибки. Разработка одним агентом, Review ON, поставка трёх ОС и установка готового macOS bundle.

Контрольный Test03: prepare → публикация около 0,5 с; второй prepare произошёл отдельным ходом; DOCS bootstrap уже перекрывался с ответом O. DOCS merge → complete около шести минут, включая явно заказанный подробный отчёт. Это не измерение скрытого рассуждения. Не обещаем скорость модели или обязательное prepare до ready.

## Подготовка до Start

Добавить необязательный task_brief в задачу Kit: непустой текст O до 12000 байт UTF-8. Это сохранённая основа поручения (цель, границы, критерии, проверки, выбранный контекст и недостающие факты), не разрешение исполнения и не автоматический task. Входит в опубликованный план, Review digest и контракт назначения. Старые планы без поля работают прежним путём. Simple plan:create и обычный review/plan:apply сохраняют поле; validation отвергает неправильный тип/размер.

Ролевые инструкции и форма планирования рекомендуют O написать task_brief для каждой обычной задачи и DOCS до публикации. DOCS заранее содержит только стабильные требования, перечень документов и места для фактов интеграции. SHA, результаты и актуальная база добавляются O после подтверждённых зависимостей. Backend не сочиняет и не отправляет эту заготовку исполнителю. Статус назначения возвращает task_brief только O; bootstrap E не получает его как рабочее поручение. После Start O сверяет актуальное назначение/attempt/contract и авторизует свой окончательный текст через prepare(dispatch_when_ready=true). Прежние Stop/restart/generation/UNKNOWN проверки сохраняются; изменение brief меняет digest.

Simple plan:create принимает task_brief у явно указанной tasks[].id=DOCS и сохраняет его при автоматической нормализации DOCS; без него сохраняется прежнее поведение. JSON schema описывает поле, runtime дополнительно проверяет именно байты UTF-8. В локальном плане E brief остаётся частью неизменяемого контракта: не вырезать его только из child и не ломать integration-proof. Recovery/bootstrap/status E не выводят этот текст. Backend получает O-статус из родительского Kit с target O и возвращает поле только member.role=O; нельзя пытаться получить O-only поле запросом с target E. Проверить успешную интеграцию неизменённого brief и отказ при изменившемся контракте. Версия role-protocol повышается вместе с текстом в T001.

## Несколько назначений в одном ходе

Ответ read_message на служебное уведомление подготовки O содержит ограниченный список preparation_queue (до 8): message_id, task_id, assignment_id, recipient_ref, attempt, только того же scope/получателя и ещё не прочитанные подготовительные уведомления. Это список для явного read_message, не автоматическая квитанция и не обход контроля адресата. SDK intent/UNKNOWN не гасятся и не повторяются. Проверка stale остаётся в read/prepare. O в текущем ходе читает перечисленные уведомления и готовит все доступные независимые поручения, затем одним yield подтверждает обработанные входящие. Не завершает отдельный ход лишь ради статуса одного task. Никакого ожидания накопления полной волны, polling модели или задержки быстрого назначения ради медленного. Появившиеся позже назначения получают обычное уведомление.

Служебное чтение подготовки возвращает O актуальный task_brief и contract digest из Kit, а не весь recovery E. Текст ограничен и не попадает в диагностические события. Ролевой текст, MCP descriptions, startup и Kit help должны совпадать.

## Итог и наблюдаемая стадия

Итоговое поручение по умолчанию требует короткий ответ: что интегрировано, проверки/ограничения, оставшаяся очистка либо ожидание приёмки. Не требует заново читать WAL, строить таблицу таймингов или повторять проверки неизменившегося SHA. Явный запрос пользователя подробного отчёта сохраняет приоритет; это отдельная аналитическая работа, а не обязательный шаг каждого плана. Никакого преждевременного complete: нужны прежние terminal receipts, cleanup DONE, чистый main, отсутствие команд и физический конец итогового O. Sidebar явно показывает подготовку итогового ответа, когда это подтверждено текущим входящим finalization/read, и конкретный оставшийся барьер вместо общего сообщения об очистке.

## Ожидание после complete

Нормализовать ошибки MCP/SDK: структурированный код сохраняется и при отклонённом Promise, и при isError. Не определять завершение только по произвольному тексту ошибки. STOPPED требует свежего read-only статуса: complete прекращает wait и автоматический sync текущей привязки; pause оставляет механизм Continue. При недоступном статусе не выдавать complete и не повторять отправку. После complete кнопка восстановления/новая привязка может получить новый scope; старая авторизация не возобновляется. Проверить завершение во время wait, sync и обновления статуса, поздний ответ после rebind/dispose, network failure отдельно. Пользовательский Stop не посылать автоматически для already complete.

## Проверки и поставка

Fixtures: task_brief roundtrip plan/review/assignment, ограничения размера и старый план; O-only доступ, изменение digest; два подготовительных уведомления прочитаны одним ходом и два авторских task без нового SDK хода; адресные/устаревшие/UNKNOWN границы; короткое итоговое поручение; UI report phase; реальный HTML SDK fixture: STOPPED через rejection/isError, complete без повторных wait/sync, pause→Continue, network recovery, восстановление новой привязки. Полный 2E→DOCS→cleanup→complete fixture без настоящих моделей, проверка действующих regression suites.

T001 запускает свои новые fixtures через unit-all и обе части Kit (kit-check, kit-assignments); T002 — unit-all и реальную SDK-проверку. В DOCS сверяются также orchestrated-execution, assignment-dialogue-reliability, chatgpt-plugin-acceptance, acceptance/orchestrated-execution, plugin-communication-handoff и workflow-execution, чтобы действующие документы не сохраняли прежние версии и инструкции.

Версии app/Kit/role обновляются совместно; immutable panel URI. По уточнению пользователя повторные полные прогоны не нужны без относящихся изменений: T001 уже прошла unit-all, kit-check, kit-assignments, executor-channel и architecture; T002 — unit-all, chatgpt-plugin и architecture. T003 проверяет обновлённый полный 2E/DOCS цикл, SDK, upgrade и архитектуру. DOCS переносит контракт в модули и удаляет эту временную спецификацию с точной Git blob ссылкой. Затем сборка, проверка фактических комплектов, установка и GitHub Release отдельными задачами. Python-кэши перед сборкой удаляются адресно согласно AGENTS. Рабочие проекты и службы не трогаются. Живые задержки и интерфейс подтверждаются следующим пользовательским опытом.
