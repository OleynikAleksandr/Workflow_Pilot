# Опыт: панель плана и отдельная переписка PiP

## Вопрос и граница доказательств

Можно ли в настоящем клиенте ChatGPT одновременно держать панель плана и отдельный PiP, не прерывая основной канал при закрытии PiP? Пока НЕ ПОДТВЕРЖДЕНО. SDK поддерживает запрос pip, но хост может вернуть другой режим. Успех синтетического хоста не доказывает расположение окон ChatGPT.

Официальные источники:
- https://developers.openai.com/plugins/reference#request-another-presentation-mode
- https://developers.openai.com/plugins/concepts/ui-guidelines#picture-in-picture-pip

## Изолированный пробник

`tools/experiments/pip-probe/server.mjs` — самостоятельный MCP stdio server, использующий зависимости этого репозитория. Не включён в production, не регистрируется в рабочей службе, не читает рабочие профили, не запускает моделей и не подключается к backend проекта.

Запуск клиентом MCP: Node.js, аргумент — абсолютный путь к server.mjs. Для ChatGPT Web нужен поддерживаемый HTTPS MCP transport либо включение этих инструментов в экспериментальную сборку существующего подключения. Этот stdio-процесс сам по себе не является доступным ChatGPT Web подключением. Не менять действующий туннель или службы ради опыта.

Инструменты:
- pip_probe_open_plan — отдельный UI resource с thread entrypoint, тестовый план и счётчик обновлений.
- pip_probe_open_dialogue — другой resource, автоматически запрашивает pip и показывает фактический ответ хоста. Кнопка позволяет повторить запрос, если автоматический запрос отклонён.
- pip_probe_status — только синтетическое время и счётчик сервера; app-only, не пользовательские данные.

URI включает SHA-256 HTML. Окно переписки не содержит OpenAI message extension, вызовов Stop, регистрации участника или изменения разрешений. Teardown/pagehide прекращают только собственный таймер; поздний ответ не возобновляет его. Здесь нет тайного повторного подключения к рабочему каналу.

## Пользовательская проверка в целевом клиенте

После подключения пробника попросить агента вызвать сначала pip_probe_open_plan, затем pip_probe_open_dialogue, оставив первое представление открытым. Не переключать режим первого компонента ради имитации второго.

1. Записать фактически предоставленный режим второго ресурса и видимость обоих представлений. Если PiP не предоставлен или основная панель заменена, совместное отображение не прошло.
2. Проверить увеличение счётчиков обоих окон, затем закрыть только PiP. Основная панель должна оставаться видимой и обновляться.
3. Повторно открыть PiP; не должно быть повторного запуска основной панели или действий плана.
4. Только после проверки синтетических окон проверить рядом с рабочей Workflow Pilot панелью в отдельном контрольном проекте: получен новый адресный ответ после закрытия PiP, grant остался активным, нет Stop, повторного bind, дублирующих Send или потери основной панели. Не переносить успех шага 2 на работу настоящих агентов.
5. Проверить закрытие/повторное открытие разговора отдельно. Закрытие наблюдателя не обязано сохранять его UI, но не должно отзывать разрешение плана.

Проверку окон выполняет пользователь: AGENTS запрещает агенту управление окнами, мышью и клавиатурой. Без фактического опыта не переносить план из sidebar и не обещать PiP на других клиентах.

## Автоматически проверено

`node --test tests/pip-probe.test.mjs`: четыре успешных адресных теста. Закрытие пассивного PiP не затрагивает независимый основной viewer; отклонение/смена режима обозначаются; поздний ответ после pagehide не запускает polling; настоящий MCP stdio transport отдаёт два разных immutable ресурса и только разрешённые синтетические поля. Проверка lifecycle использует mock хоста, а не настоящий ChatGPT. Production приложение и рабочий тест не изменены.

## Последующая интеграция при успешном живом опыте

Основная панель отображает план. PiP — пассивная лента сохранённых сообщений с автором, адресатом, временем и квитанциями; Review получает свой адаптер источника. Второй UI не становится вторым владельцем доставки или разрешения плана. Чтение человеком не ставит квитанцию чтения агентом. Если ChatGPT не допускает два представления, зафиксировать отказ и выбрать иной интерфейс отдельно, без скрытой подмены эксперимента.
