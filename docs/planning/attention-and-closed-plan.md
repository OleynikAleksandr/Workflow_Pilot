## Контракт внимания

У обычного состояния должны различаться: фактическая стадия работы, кто способен продолжить процесс (система/агент/пользователь), и доступное действие. Использовать существующие проекции/контракты и действия; минимальное расширение данных допустимо, универсальный новый диспетчер/система инцидентов не нужны.

Оранжевая карточка допустима только при подтверждённой необходимости решения или действия именно пользователя. Она содержит понятную причину, почему автоматическое продолжение сейчас невозможно, и конкретную кнопку либо выполнимую инструкцию. Pending выбор пользователя — такой случай, даже если ошибки нет. После сохранения выбора он перестаёт быть оранжевым; получение агентом остаётся отдельным фактом.

Нейтральные состояния: выполняющаяся операция/транзакция, проверка готовности, ожидаемый конфликт параллельных чтений, автоматическое восстановление SDK в пределах бюджета, получение результата, проверка/решение оркестратора, ожидание terminal receipt/cleanup. Нельзя переводить их в пользовательскую тревогу только по длительности, наличию error/blocked в техническом объекте или по тому, что агент не прислал новых событий. По истечении времени можно правдиво сообщить о задержке нейтрально, без выдуманного прогресса; подробности — в диагностике.

READINESS_BUSY не считается повреждением проекта: фактическая блокировка остаётся в Control/Kit, а UI сообщает «Ожидаем завершения операции проекта». Ожидание решения O показывается «T001 ожидает проверки оркестратором» только при подтверждённом результате/стадии. Если причина неизвестна, нельзя подставлять этот текст по догадке.

В область исправления входит источник `phase:attention` в src/control/workflow/parallel-execution.mjs (reconcile, подготовка/открытие E), его безопасная классификация и tests/parallel-execution.test.mjs / tests/parallel-execution-ui.test.mjs. Проверить всю цепочку до desktop-model, не ограничиваться перекраской готового warning. Разметка и CSS src/frontend/desktop/ui/index.html также входят в область: устранить дублирующий plan-attention/role=alert при сохранении доступных управляющих элементов.

Настоящий отказ не скрывать и не выдавать за восстановление. MAIN_DIRTY с известными мешающими файлами, отсутствие входа/необходимое подтверждение пользователя, потеря разрешения и исчерпанная доставка с доступным безопасным действием сохраняют адресный понятный сценарий. Если исполняемого действия для пользователя нет, показать нейтральное «Работа остановлена: <понятная причина>», а технические сведения в диагностике; не обещать автоматическое восстановление. Не автоматизировать опасные repair/retry, не изменять Stop/grant/identity или неизвестный эффект ради снятия тревоги. Ручная пауза сама по себе — нейтральное сохранённое состояние с действием «Продолжить».

«Открыть чат» не является универсальным устранением ошибки. Переход допустим лишь при конкретном требуемом действии в целевом чате, указанном в инструкции. Не заставлять пользователя координировать E, копировать ID или повторять уже сохранённый выбор.

## Единое место и жизненный цикл UI

Основная Workflow Pilot панель показывает одну оранжевую карточку текущего пользовательского действия. Та же причина не повторяется оранжевой строкой в now и карточкой в sidebar. В sidebar остаются план, нейтральные статусы задач и штатная кнопка Start/Пауза/Продолжить; необходимые управляющие кнопки не удаляются. Review остаётся на согласованном месте. Не возвращать «Текущие действия», dialog-копию, новую панель или переключатель режима.

Существующие самостоятельные ошибки настройки/старта вне контекста плана не нужно глобально скрывать. Для планового внимания native/HTTP/sidebar используют одинаковую семантику; если основная панель недоступна, допустима нейтральная навигационная подсказка к ней, без второй карточки выбора/тревоги и без нового UI-контейнера. Не считать SDK lease доказательством видимости панели.

SSE/reconnect/переключение сессии не возвращают завершённое предупреждение. После устранения причины карточка исчезает, подтверждённый факт может оставаться в истории. Отдельная реально работающая задача не превращается в заблокированную из-за соседа. Перенос текста, фокус кнопок, доступные имена и светлая/тёмная темы сохраняются. Это исправление проекции, а не новая транспортная очередь или политика восстановления.

## Закрытый план

Читать целый JSON-блок внутри однозначных workflow-state:begin/end и внешнего fenced-блока. Внутренние Markdown fences, кавычки, обратные слеши, кириллица и строковые примеры JSON не являются концом документа. Сохранять проверку структуры, единственности/корректности маркеров и настоящего JSON; повреждённые данные не принимать за DONE.

Предпочесть имеющийся канонический разбор Kit или небольшой общий чистый helper в разрешённом слое. Не импортировать Kit/fs в Frontend/Control в обход ExecutionFacade, не копировать пакетную бизнес-валидацию целиком. Проверить все места разбора plan Markdown: closedPlan, loadContext legacy, workspace-session, plan-continuation-state, workspace-deletion; installer и канонический Kit проверить на совместимость, менять только при обнаруженном дефекте с адресными тестами. Managed Kit меняет только installer. Устранить преждевременное завершение во всех подтверждённых уязвимых потребителях.

Ещё один подтверждённый уязвимый потребитель — resources/workspace-setup-worker.mjs, fallback SESSION_REQUIRED в recoverCurrentPlan. Включить его исправление и регрессию tests/workspace-setup.test.mjs с fences внутри поручения. Поставляемый worker использует ./workflow-kit/lib: опираться на канонический поставляемый разбор или границы end-маркера, не импортировать src. Уже привязанные к end-маркеру workspace-session/plan-continuation-state/installer не переписывать без обнаруженного дефекта.

Закрытый план извлекается из родителя точного коммита закрытия. Проверять его принадлежность ожидаемым projectId/scopeId/session-владению; ключ кэша учитывает устойчивые ID рабочей копии/проекта, scope и commit. Имя/путь — только IO, не доказательство владения. Поздний асинхронный ответ удалённого/заменённого workspace не публикует чужую карточку. Не помечать все задачи DONE без фактов исходного плана.

После успешного закрытия: карточка «План закрыт», корректные название и завершённые задачи, без активных предупреждений прежнего scope. Новый план той же сессии не подхватывает старую карточку. Закрытие плана, архивирование проекта и новая сессия различаются.

При недоступном Git-объекте или действительно повреждённом историческом блоке факт подтверждённого закрытия сохраняется. Отдельный нейтральный текст «План закрыт. Подробности завершённого плана сейчас недоступны» вместо сырого exception/ложной тревоги. Не показывать вымышленные задачи, количество или успех чтения. Безопасный код и диагностические сведения — в диагностике, без контекстов, секретов и сырого содержимого задач. Ошибка кэша не вечна: штатное обновление/повторное открытие допускает ограниченную повторную загрузку, а не бесконечный polling.

## Проверки и критерии приёмки

- Через backend → workProgress → настоящие render-функции панели/sidebar: READINESS_BUSY при параллельных E, автоматическое исчезновение после завершения операции; пользователь ничего не нажимает, другой E продолжает отображаться работающим.
- Result saved/SDK accepted/read/acceptance не смешиваются. Ожидание O и долгий cleanup нейтральны, таймер сам не создаёт тревогу. Pending выбор — одна оранжевая карточка; выбранный — нейтральный; настоящий MAIN_DIRTY или требуемый вход — конкретное безопасное действие. Не маскировать постоянные отказы.
- Один и тот же инцидент не дублируется панелью/now/sidebar; повторный SSE, restart проекции, смена сессии и отсутствие видимого iframe не создают дополнительную карточку.
- Изолированный Git fixture: публикация плана с многострочными примерами кода внутри task_brief/prepared_task → все DONE → штатное archive → backend closedPlan → sidebar. Проверить название, четыре задачи/фактические статусы, отсутствие JSON exception и действий прежнего scope. Без реальных моделей и пользовательского workspace.
- Отрицательные случаи: неполный JSON, отсутствующий/повторный маркер, неверная схема, нет Git-объекта; закрытие не отменяется ошибкой отображения, ложный DONE не создаётся. Повторная загрузка после восстановления доступности, restart, новый план, удаление/создание workspace с тем же путём и иным ID, поздний ответ старого запроса.
- Полные unit-all, architecture и electron-smoke; полный Kit состоит из kit-check И kit-assignments. Если меняется Kit/installer, добавить kit-upgrade и согласовать версию Kit/role по изменённому контракту. Нужные проверки задаются до правок через task:update, не обходятся.
- Новая версия приложения и immutable panel build; протокол панели повышается при несовместимом изменении DTO. Доставка сообщений SDK, очередность ChatGPT, permissions и lifecycle остаются прежними. Старый HTML не считается новым от переустановки bundle.
- Перед production build DOCS переносит эти требования в действующие модули и удаляет временную spec с точной Git blob ссылкой в recovery. README сохранить в бюджете 28000 UTF-8, при необходимости сократить повторяющиеся абзацы без потери подтверждённой живой приёмки 0.5.39.
- DOCS сверяет также docs/modules/orchestrated-execution.md, user-choice.md и sdk-messaging.md: несогласованная роль, выбор и ошибка доставки не могут безусловно означать пользовательскую тревогу. Сохраняются реальные полномочия, обязательные выборы и безопасные действия.

## Поставка и границы

Три ОС из одного sourceCommit: macOS arm64, Windows x64, Linux x64. Перед каждой production/package-сборкой проверить точные пути tools/codex-app-server-mcp, удалить только сгенерированные __pycache__/.pyc/.pyo без следования симлинкам; Python проверки -B. Manifest, полный комплект семи assets, SHA/size/composition и подпись macOS обязательны.

INSTALL отдельно после DOCS/RELEASE: готовое подписанное приложение в /Applications/Workflow Pilot.app и собственный checkout штатным installer, проверка версии/manifest/подписи и rollback. Не пересобирать, не переподписывать, не останавливать и не перезапускать работающую службу: при BACKEND_RUNNING сохранить verified pending, пользователь переключит версию.

PUBLISH отдельно: GitHub tag на sourceCommit, полный набор assets, проверка удалённого main и публичного release. Native Windows/Linux и новая живая ChatGPT-приёмка отмечаются NOT_RUN до фактической проверки. Donor, тестовый workspace и рабочий профиль не изменять. Не расширять scope переносом с Electron, перестройкой SDK, сменой Review, массовым скрытием ошибок или новыми фоновыми наблюдателями. Разработка последовательная в текущем checkout; модельное делегирование запрещено, кроме разрешённого Claude Review.
