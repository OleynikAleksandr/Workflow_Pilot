# Исполнение: восстановление, блокировки и ранние поручения

Часть [спецификации D001–D011](release-0533-defects.md). Нормативные требования будущей реализации; исходное поведение 0.5.33 не объявляется исправленным.

## D011: восстановление канала O и E

Разрешение плана долговечно. Lease панели короткая (сейчас 60 секунд) и подтверждает доступность конкретного SDK-экземпляра; она не заменяет разрешение плана. `host.handshake` — исторический факт. Готовность для отправки требует одновременно identity/run/member, актуальных generation участника/панели/запроса, живой lease и реального `message_supported=true`.

Изменение поколения в `_grant` сохранить. Исправить согласование `allowed`, `status`, `sync`, проекции `progress` и клиентского `listen` в существующем канале:

1. При смене generation/истечении lease wait больше не повторяется с прежним binding бесконечно. Единственный recovery-проход панели читает текущее состояние и выполняет `sync` с собственной подтверждённой identity; результат атомарно заменяет локальные generation/expiry до следующего wait.
2. Recovery использует существующие `epoch`, abort, single-flight и backoff. Поздний ответ старого поколения не перезаписывает новое; одновременно не работают два listen/sync/deliver одной панели.
3. Структурированные `STOPPED`/BINDING/VERSION/ASSIGNMENT_CHANGED/STORE/PROJECT_REMOVED различаются. При потере структурированного кода на стороне хоста успешный read-only status проверяет также пригодность lease/generation конкретной панели: running само по себе не означает готовый транспорт. Непонятная ошибка не объявляется сетевой без основания.
4. `sync` продлевает присутствие при разрешённой identity, но не включает paused/complete план, не снимает ручной Stop и не расширяет scope. Для manual/restart паузы остаётся одно штатное Continue. Отсоединённый экземпляр не возрождается поздним callback; актуальный mount восстанавливается обычным bind/sync.
5. Неисправность binding/version/storage останавливает отправку с конкретной причиной; transient network повторяет безопасные чтения с backoff. Повторный Send или grant по status запрещены. Исход ранее записанного intent разрешается существующим reconciliation; sync его не стирает.
6. Один и тот же предикат живой панели применяется к status/channel_ready и progress/admission. Добавить безопасные причины `generation-mismatch`, `lease-expired`, `sdk-unavailable`, `plan-paused` в соответствующее существующее диагностическое событие и проекцию без токена, ticket, q и текста сообщений. Код ошибки проходит Python MCP/bridge/iframe без подмены произвольным NETWORK_ERROR.
7. После recovery очередь O читается с прежнего устойчивого курсора. Сохранённые recovery/ready не теряются и не дублируются; если задача уже авторизована, прежний запрос подготовки штатно superseded. Одно событие с T001 не выдаётся за готовое поручение E.

**Критерии CHANNEL:** воспроизводящий fixture меняет generation во время живого wait, отдельно истекает lease, отдельно лишает ответ структурированного кода. В каждом случае разрешённая связь восстанавливается штатно либо сообщает точную терминальную причину; нет бесконечного прежнего wait и лишнего SDK intent. Проверить O и два E, manual pause, Stop, pagehide/dispose, новый iframe, backend restart и соседний проект. Связать события generation→sync→wait→intent→read. Не требовать одинаковой длительности ответа модели.

## D008: системные файлы Finder и Git

Добавить точное правило `.DS_Store` (без ведущего `/`, чтобы охватывать вложенные папки) в управляемую секцию `.gitignore`, которую создаёт/обновляет **installer Kit**. Изменять исходники `packages/workflow-kit/src/lib/installation-files.mjs`/installer, а не вручную установленную `.harness/kit`.

Применить при штатной подготовке новых workspace и безопасном обновлении существующих, включая связанные worktree. Это штатная операция подготовки, отдельная от execution guard: контроллер исполнения не скрывает файлы прямо перед mainClean и не коммитит пользовательские изменения. Обновление учитывает существующую dirty-защиту и доверие installer. Если правило можно доставить только в отдельной безопасной транзакции, UI предлагает штатное обновление до Start; реальные изменения не обходятся. За это предложение и его API-причину отвечает BLOCK через существующие kit-update/project-doctor; VIEW отображает результат общей проекции. GIT проверяет сам installer. В BLOCK проверить новый проект и workspace с прежним Kit, где есть только неотслеживаемый `.DS_Store`, а также отказ обновления при реальных пользовательских правках.

Правило идемпотентно, сохраняет пользовательские секции, пользовательские исключения и manifest managed-секции. Наличие `.DS_Store` в отслеживаемых файлах не исправляется удалением из Git: такой tracked change блокирует запуск с понятной причиной. Не удалять Finder-файл, не менять глобальный gitignore и не добавлять маски для произвольных файлов.

**Критерии GIT:** новый проект и upgrade неизменённого старого Kit; root/nested `.DS_Store`; отдельные Git worktree; повтор installer. Проверить `git check-ignore` и реальный Git status, пользовательские правила/файлы/manifest, неизменность tracked данных. Настоящий новый `.txt` и изменённый исходник остаются MAIN_DIRTY. Выполнить обе части Kit-check и consumer upgrade fixtures; изолированные каталоги, не Test_001.

## D009: техническая блокировка и Continue

Использовать существующие `ExecutionControl` и журнал, расширив причину технической паузы (например `blocked`) и структурированную issue. Не создавать второй источник истинного состояния.

| Условие | Наблюдаемое состояние и действие |
| --- | --- |
| План опубликован, не начат | not-started; «Начать выполнение плана» |
| Допустимое исполнение | running; «Пауза» |
| Пользователь просит паузу, есть активная работа | pausing/manual; видна безопасная граница, повторная пауза недоступна |
| Безопасная ручная пауза | paused/manual; «Продолжить» |
| Продвижение невозможно из-за устранимой ошибки | pausing/blocked до безопасной границы, затем paused/blocked; «Продолжить» после достижения границы |
| Работа полностью завершена | complete; запуск недоступен, ожидается приёмка |

MAIN_DIRTY до первого назначения сразу даёт paused/blocked и «Продолжить». Ошибка содержит безопасный список мешающих относительных путей и конкретный шаг: проверить/сохранить/зафиксировать свои изменения. Служебное `.DS_Store` не предлагается коммитить. Длинный список сокращается только с доступным полным перечнем в диагностике; не терять причину.

Техническая пауза отзывает допуск новых назначений и уведомлений в согласованном переходе существующего backend. Активная команда не убивается, её результат/outbox может быть сохранён на действующей безопасной границе. По мере окончания допускается settle в paused. Обычный занятой E, зависимость или ожидание квитанции не становятся технической паузой автоматически. Устранимое восстановление канала D011 идёт в пределах разрешения; неисправность, требующая действия пользователя, получает blocked.

Continue выполняет свежие readiness/Git/identity/transaction/UNKNOWN-проверки и возобновляет тот же scope. Если причина не устранена, остаётся blocked без новых назначений/Send; если устранена — одно нажатие приводит к реальному продвижению. Не публиковать успешный running/grant до принятия preflight или обеспечить атомарный запрет эффектов до его завершения. Повтор нажатия — одна операция. Restart сохраняет причину/issue, manual имеет приоритет; никакого автоматического снятия ручной паузы по изменению файлов. Миграция существующей book понимает новую причину и не теряет записи старых Chat-планов.

**Критерии BLOCK:** API и настоящая кнопка компонента дают одинаковый результат: Start с dirty → blocked/Продолжить → повтор с dirty без эффектов → устранение → одно Continue и ровно два назначения. Проверить блокировку при уже активном соседнем E, паузу пользователя в это время, restart и утрату ответа. UNKNOWN не снимается Continue автоматически.

В область BLOCK входят существующие `src/control/projects/project-doctor.mjs` и `src/frontend/desktop/ui/workspace-setup.mjs`: проверить доступность upgrade до Start; изменять только если существующая проверка версии/готовности не покрывает новый managed-случай. Это не разрешает автоматически устранять реальные пользовательские правки.

## D010: авторский пакет до Start

### Сохранение до публикации

Ранний `task_brief` в 0.5.33 полезен, но не является подготовленным и разрешённым поручением. Расширить текущий контракт задач Kit, не заводя отдельную очередь планов: автор явно сохраняет **подготовленное содержание** каждой обычной задачи и DOCS вместе с планом, до окончательного Review. Текст находится в `task_brief`, а явная метаинформация `prepared_task` отличает готовую основу от старого краткого brief.

Минимальная семантика `prepared_task`: версия формата; project ID и scope ID; автор и подтверждённые полномочия владельца планирования; hash полного авторского текста; манифест выбранного контекста с путём/устойчивой ссылкой, SHA-256 и числом UTF-8 байт каждой части; явно отложенные входы по dependency task IDs; digest семантического контракта задачи. Этот digest охватывает версию, project/scope/task ID, авторство, цель, область файлов, проверки, acceptance, зависимости, содержание и выбранный контекст, но исключает runtime-статусы, commit_ref, текущий счётчик plan_revision и сам digest. Детерминированная канонизация и доменное разделение хеша обязательны. Только готовые данные автора помечаются подготовленными; hash не заменяет проверку прав автора и явного принятия пары Review/publication.

Каждый текстовый документ/часть вместе с оформлением ≤28000 UTF-8 байт; `task_brief` сохраняет существующий предел 12000. Общий бюджет context pack проверяется существующим механизмом. Ничего не обрезать. Подготовка не включает тикеты, bearer, cookies, chatUrl/identity чужого разговора. Авторский выбор контекста не расширяет утверждённые пути/полномочия.

Полный выбранный контекст должен быть доступен как неизменяемое содержание в штатном локальном хранилище/content store либо как существующий Git blob с точным SHA и безопасным путём. Один hash без проверяемых байтов недостаточен. Если до Start источник изменился, пакет не молча перечитывается из новых файлов: используется точный согласованный snapshot либо требуется авторская актуализация с новым digest/Review при существенном изменении. Сохранение content и метаданных идёт через существующий атомарный механизм: после сбоя виден целый пакет либо явная неполная подготовка, которая не допускается к отправке.

Review и plan publication включают `prepared_task` и все обязательные части. Для новых orchestrated-планов отсутствие подготовленной основы задачи или DOCS не допускает публикацию. CLI/fixture предоставляет диагностируемую ошибку с task ID. Для sequential-планов, не выдающих назначения E, это требование не навязывается. В этом CLI-плане разработки есть task_brief для будущего продолжения, но нет выдачи E.

### Привязка после Start

1. Start разрешает выполнение плана. Backend создаёт настоящее назначение и заново проверяет scope/project identity, семантический digest, зависимости, актуальность согласованной подготовки и grant generation.
2. Из сохранённого авторского текста/контекста и механических полей фактического назначения (recipient, assignment ID, attempt, contract digest) формируется текущий draft в существующем assignment/WAL. Это перенос уже авторизуемого содержания, а не сочинение поручения backend.
3. Явно согласованная подготовка позволяет после Start авторизовать этот draft для точного актуального назначения без обязательного дополнительного хода O. События prepared/bound/authorized/published остаются раздельными. Перед авторизацией и перед effect публикации повторно проверяются identity/digest/grant, отмена и pause.
4. Назначение не считается подготовленным только потому, что его worktree создан. До bind никакого SDK сообщения E; после bind доставка по прежнему admission при готовности конкретного E, независимо от остальных. Авторизация не означает SDK accepted или read.
5. Crash между созданием назначения, записью draft, авторизацией, публикацией и receipt восстанавливается из intent→Kit→WAL. Использовать устойчивый operation/idempotency key из project/scope/task/preparation digest/assignment/attempt. Retry не создаёт второй пакет, новую попытку или повтор Send.

Внести контракт в Kit validation/schema/Review digest/assignment contract, Control assignment prepare, MCP descriptions и единый `role-protocol.mjs`. Recovery, startup, адресные сообщения и документация должны одинаково требовать раннюю подготовку. Старый текст «после Start сначала сочините поручение» для нового готового плана убрать. PREPARE явно охватывает `simple-workflow.mjs` (сохранение поля при plan:create и нормализации DOCS), `recovery.mjs` (различение согласованной подготовки и старого brief), validation и при необходимости существующую `dialogue-migration.mjs`; ни один пользовательский путь создания/чтения не теряет prepared_task.

### Зависимые задачи и существующие планы

T003/DOCS получают до Start полные стабильные инструкции и перечень будущих проверенных результатов зависимостей. При выдаче backend добавляет только проверяемые механические факты (принятый SHA, integration proof, действительное состояние), обозначенные в манифесте. Непредусмотренное содержательное решение, изменение области или противоречие результатов требует одного адресного уточнения O; пакет не сочиняется backend. Готовность независимых T001/T002 не блокируется ожиданием содержательной доработки другой задачи.

Старый Chat-план с одним brief не становится автоматически авторизованным новым пакетом. Сохранить его текущий контракт поздней подготовки через рабочий канал и показывать реальную стадию; при невозможности продолжения — адресная диагностика/безопасная пауза, без присвоения ready задним числом. Чтение старого плана не переписывает schema/digest. Переход к новой схеме — явная штатная актуализация, без сброса DONE и активных попыток.

**Критерии PREPARE:** два независимых задания и DOCS подготовлены и рецензированы до Start. После Start нет обязательного нового вызова модели O для подготовки T001/T002; каждый E получает ровно точный согласованный текст и нужные байты. Проверить изменение контекста/digest после Review, потерю snapshot, подмену author/scope, pause/revoke, смену attempt и restart в каждом промежутке. Для зависимых задач проверенные результаты добавляются только после acceptance/integration. Для старого brief-only плана не возникает скрытой авторизации. Реальное исполнение по-прежнему начинается только через кнопку пользователя.
