# Один разговор с любого клиента: серверная доставка (Mac)

Невыпущенное требование для выпуска 0.6.0. Основа — HEAD `9b3b341` (код 0.5.41, Kit 1.10.5, панель `0.5.41-communication-8`, протокол 8). Продолжение: [свежесть, откат и проверка](shared-conversation-mac-freshness.md); отложенная мобильная часть — [followup](shared-backend-mobile-followup.md).

Решения пользователя 29.10.2026: реализовать сразу в продукте и выпустить новую версию без отдельного стенда и пробных приложений; сначала всё для Mac; телефоны/iPad проверяются через ChatGPT Web в браузере и адаптируются позже; при принципиальной неработоспособности — откат на 0.5.41, при ошибках — исправления.

## Результат

Пользователь продолжает тот же разговор O или E Workflow Pilot из любого клиента ChatGPT своего аккаунта: встроенное окно Workflow Pilot, Safari/Chrome на Mac, ChatGPT Desktop, ChatGPT Web на iPad или телефоне. Автоматическую доставку сообщений Workflow Pilot (поручения, вопросы, result, acceptance, выбор, Review, служебные) выполняет **только** серверная страница этого участника в backend. Панель Workflow Pilot, смонтированная в разговоре на любом другом клиенте, — наблюдатель: показывает ход работ и принимает явные действия человека, но не отправляет SDK-уведомлений. После хода, сделанного на другом клиенте, служба продолжает разговор в его актуальном состоянии, без новой ветви, потери входов и двойных эффектов. Закрытие всех окон и вкладок не останавливает обмен.

Исполнители остаются обычными ChatGPT Chat. Старт Chat (q + ticket, ChatGPT search extension), Kit, Review, одна кнопка плана, роли, бюджет уведомлений и UNKNOWN сохраняются.

## Границы

- Выпуск собирается одинаково для macOS, Windows и Linux; живая проверка выполняется на Mac, нативная Windows/Linux остаётся pending.
- Не входит: мобильные приложения, API v2 и независимый выбор сессий на клиентах, автозапуск службы, Linux-сервер, публичный адрес — [followup](shared-backend-mobile-followup.md).
- Не входит: замена наблюдателей DOM на CDP. Действующие наблюдатели страницы, композитор и публичные DOM-экспорты не меняются; новые наблюдаемые поля добавляются в существующий observer. Другие «замены DOM на CDP» не определены и требуют отдельного поручения.
- Не вводятся новые кнопки, режимы, переключатели запуска, DOM/клавиатурный Send, приватные endpoints ChatGPT, подмена User-Agent, внедрение панелей в DOM ChatGPT, кадры как основной путь.
- Существующий HTTP/iPad-клиент кадров сохраняется без изменений.

## Факты исходников, на которых строится решение

1. **Идентичность участника не различает клиентов.** `communicationIdentity` хеширует `openai/organization`, `openai/subject`, `openai/session` (`src/control/plugin/communication.mjs:15`); `host_metadata` в `tools/codex-app-server-mcp/plugin.py:87` сохраняет только эти ключи. `recover()` отдаёт участника любому экземпляру панели с той же identity; `_bind` (`communication.mjs:398`) регистрирует экземпляр с текущим поколением, не отзывая другие; `livePanel` (`src/control/plugin/workflow-channel.mjs:79`) истинно при любом живом экземпляре; цикл wait → `claim_ready` → `ui/message` запускает каждый смонтированный экземпляр (`src/frontend/plugin/launch.mjs:240–300`, `deliver()` — `:176`). Следовательно, панель на втором клиенте сейчас может стать отправителем.
2. **Допуск проверяет серверную страницу, а не отправителя.** `DialogueDelivery.admit` и `executorPageState().sdkDocumentReady` (`src/control/workflow/dialogue-delivery.mjs`, `src/control/workflow/executor-session.mjs:7–30`) смотрят на страницу backend.
3. **Серверная страница видит только свой документ.** Observer (`src/execution/browser/chatgpt-page-observer.mjs`) считает `busy`, `turnId`, `userTurnId`, `lastMessageRole`, ревизии; отпечатки ходов строятся из нативных `data-message-id` и стабильны между документами. О ходе на другом клиенте она узнаёт только если ChatGPT Web обновит открытый документ сам (не проверено) или после перезагрузки.
4. **Подтверждение конца хода привязано к documentId.** Для dialogue_version=1 `reply_observed` выставляет `observeDialogue` только при совпадении `page.documentId` с базовой линией `handlingGate`/`yielded.page`; другой документ принимается лишь после restart backend (`workflow-channel.mjs:303–308`, `:320–325`, `:365–378`; `src/control/plugin/assignment-dialogue.mjs:350–365`). От `reply_observed` зависят закрытие acceptance, финализация и cleanup.
5. **Report попытки не проверяет поколение.** `_report` (`communication.mjs:641`) принимает исход по `panel_instance_id` и `delivery_attempt_id`; поздний исход старой попытки пишется как `late_outcome`.
6. **Экземпляры панелей живут в памяти.** `this.panels` не входит в WAL; после restart участники `stopped`, поколение растёт (`communication.mjs:52–58`).
7. **Восстановление renderer** перезагружает тот же адрес (`src/execution/browser/session-runtime.mjs:188–200`), не более 3 раз за 10 минут; подтверждения хода при этом, по факту 4, не переносятся.
8. Документированное ограничение «второй браузер того же разговора — не штатный сценарий, причина не установлена» (`docs/modules/backend.md`, OVERVIEW) заменяется этим контрактом только после живой проверки; кандидаты причины — факт 1 (перехват доставки вторым клиентом), отправка из устаревшего документа, различие `openai/session` между клиентами.

## Владелец доставки

**Контракт.**
- Для каждого участника backend признаёт владельцем доставки только экземпляр панели, **аттестованный** Execution как смонтированный в серверной странице этого участника: тот же `browserSessionId`, текущие `incarnation` и `documentId`. Заявления клиента (роль, UA, порядок подключения) не учитываются.
- `bind`/`sync`/`wait`/`status` возвращают `delivery_role: "owner" | "observer"` и `delivery_owner_generation`. Наблюдатель получает состояние без `message_id` к доставке; `claim`/`claim_ready`/`verify` наблюдателя отвечают `PLUGIN_COMMUNICATION_DELIVERY_OBSERVER` без записи попытки и без события сбоя, расходующего бюджет.
- Наблюдатель не создаёт и не подтверждает инциденты восстановления уведомлений (`sync` с `recover_notifications`/`recovery_id`, `workflow-channel.mjs:159–187`), не продлевает аренду доставки, не вызывает `connectionWaited`.
- Наблюдатель может: показывать ход работ, историю, диагностику; нажимать карточку выбора (`workflow_communication_choose`, существующий CAS); выполнять явный Stop плана (`scope=participant`). `scope=panel` наблюдателя отсоединяет только его экземпляр.
- Поколение владельца растёт при смене аттестованного **кадра** или документа (новый `panel_instance_id` того же кадра поколение не меняет) и влияет **только на новые claim**. Попытка в полёте закрывается своим `report` как сейчас (факт 5); перемонтирование виджета хостом во время SDK не превращает доставку в UNKNOWN и не расходует бюджет. Неполученный исход — UNKNOWN по существующим правилам; бюджет notification_version=1 (3 + один цикл до 3 по проверенному восстановлению, максимум 6) и запрет повтора legacy UNKNOWN не меняются.
- Несколько аттестованных экземпляров в одном документе (виджеты прежних вызовов `workflow_pilot_panel` в истории): владелец — последний смонтированный в текущем документе; прежний становится наблюдателем после завершения своей попытки в полёте.
- Нет аттестованного владельца — доставка участнику ждёт с нейтральной причиной `owner-unavailable` (UI: «Ждём подключения панели службы»); оранжевым это становится только если требуется действие пользователя (например, серверная страница вышла из аккаунта). Это не отказ и не UNKNOWN.

**Аттестация (Execution).** Новый `src/execution/browser/panel-frame-attestation.mjs`. Панель при mount создаёт неизменяемый на всё время жизни кадра `frame_instance_id` (UUID) и публикует в своём кадре `globalThis.__workflowPilotPanel = {frame_instance_id, build_id, protocol_version}`. `panel_instance_id` меняется при повторном recover в том же кадре (`src/frontend/plugin/launch.mjs:328`), поэтому аттестуется кадр, а не экземпляр: `bind` передаёт оба значения, Control связывает текущий `panel_instance_id` с аттестованным `frame_instance_id`, и повторный recover в том же кадре сохраняет владельца без нового поколения. По запросу Control Execution перечисляет подкадры **собственного** webContents серверной страницы (`webContents.mainFrame.framesInSubtree`), исключая главный кадр `chatgpt.com`, и в каждом выполняет постоянный read-only скрипт `WebFrameMain.executeJavaScript` чтения этого одного значения. Результат валидируется (UUID, build, протокол) и связывается с `browserSessionId/incarnation/documentId`. DOM ChatGPT не читается и не меняется; в страницу ChatGPT ничего не добавляется; кадры чужих webContents и устаревших документов не учитываются. Перечисление выполняется при bind экземпляра, после навигации/перезагрузки и перед `verify` (дешёвая повторная проверка того же экземпляра). Если в реальном ChatGPT кадр панели недостижим этим способом, функция принципиально не работает → откат (решение пользователя); запасной вариант с preload в подкадрах (требует `nodeIntegrationInSubFrames`) в этот выпуск не входит.

**Изменяемые модули:** `src/contracts/backend.mjs` (протокол 9, `COMMUNICATION_APP_VERSION`/`COMMUNICATION_BUILD` 0.6.0), `src/contracts/plugin-communication.mjs`, `tools/codex-app-server-mcp/plugin.py` (поля ответа, код ошибки), новый `src/control/plugin/delivery-ownership.mjs`, `src/control/plugin/communication.mjs` (`_bind`, `allowed`, `_claim`, `_verify`, `_status`, `wait`), `src/control/plugin/workflow-channel.mjs` (`panelIssue`, `livePanel`, `sync`), `src/control/workflow/dialogue-delivery.mjs` (`admit`), `src/execution/facade.mjs` (порт), `src/execution/browser/backend-host.mjs`/`session-runtime.mjs` (доступ к кадрам своей страницы), `src/frontend/plugin/launch.mjs` (observer без цикла доставки), `src/frontend/plugin/panel.mjs`. Протокол панели 9: старый iframe получает существующий отказ версии с обеими версиями.

## Диагностика identity

Чтобы живая проверка различала кандидатов причины факта 8:
- MCP-адаптер журналирует для каждого вызова панели и модели только **имена** ключей `_meta` хоста (без значений) и префикс 8 символов `identityHash`; поля: источник (`panel-recover`, `panel-bind`, `model-read`, `model-yield`), `panel_instance_id`, `delivery_role`.
- Отказ `PLUGIN_COMMUNICATION_BINDING` в инструменте модели (identity не совпала ни с одним участником) пишется в диагностический журнал backend (`backend-events.jsonl`, без WAL, так как run не определён) событием `identity.unmatched` с префиксом хеша и именами ключей `_meta`. Это диагностика, не новое правило допуска.
- Экспорт `workflow_communication_export` O дополнительно включает записи `identity.*` из `backend-events.jsonl` текущего boot за интервал времени своего run (только префиксы хеша, имена ключей, источник, время) — иначе случай «ход с другого клиента пришёл с другой identity» не виден в экспорте (`communication.mjs:797–806` сейчас выдаёт только события run). Секреты, raw metadata, тексты и q/ticket исключены.

Ход проверки и критерии приёмки — в [продолжении](shared-conversation-mac-freshness.md#проверка). Ограничение «второй браузер того же разговора — не штатный сценарий» остаётся действующим в контрактах модулей до PASS шагов 1–4 живой проверки; DOCS выпуска описывает новый контракт рядом с ним с пометкой NOT_RUN и не удаляет ограничение раньше.
