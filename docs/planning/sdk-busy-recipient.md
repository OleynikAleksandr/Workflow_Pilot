## Переиспользуемый путь

E делает проверенный commit --task и workflow_assignment_send(kind=result, source_commit, attempt, idempotency_key). Kit проверяет назначение/SHA/proof, WAL хранит результат. Панель O получает message_id через wait, выполняет claim_ready и extensions.message.send: ui/message, role=user, target=active, send=true. Уведомление требует workflow_communication_read_message; содержимое result читается через MCP. O принимает точный SHA и интегрирует. read, yield, SDK acceptance, конец ответа, интеграция и complete остаются разными фактами.

Окончания текста E для публикации result уже не требуется. Новый Git hook и считывание заключительного ответа E не нужны. Существующий gate перед отправкой O находится в WorkflowChannel.pending/first/gatePending/claimBlockReason/physicalBlock, PluginCommunication._claim/_claimReady/_verify (обе ветви), DialogueDelivery.admit и агрегированном executorPageState.canSend. Эти места сверены с 0.5.36. Снять только одну проверку недостаточно.

## Профиль полного опыта

Один узкий профиль: mode=off|sdk-busy-burst, experiment_id, точные project_id/workspace/scope_id/O, ожидаемый build, cases. По умолчанию off; без действительного профиля полностью прежнее поведение. Глобального включения для всех проектов после успеха нет: это отдельное решение по результатам опыта, не скрытый побочный эффект публикации.

Локальный scripts/prepare-sdk-busy-experiment.mjs создаёт `<test_workspace>/.harness/runtime/experiments/sdk-busy.json` только по явно переданным workspace/scope/mode и проверенной собственной identity выделенного тестового проекта. Последний выбранный проект не подставляется. Проверить конечные пути, симлинки, размер, версию и схему; атомарная запись. Произвольный файл внутри проекта сам по себе не даёт полномочий: профиль сопоставляется с действующим собственным project/scope/grant и намеренно подготовленным экспериментом.

Execution читает профиль, Control получает проверенные данные через существующие facade/coordination; Control не читает fs. Новый IO-адаптер — src/execution/plugin/sdk-busy-experiment.mjs. Профиль фиксируется при обычном Start. В case заранее задаются case_id, busy_kind=tool-wait|generation|read-only-command, максимум ДВА новых уведомления, допустимые result/assignment refs. Лимит относится к case, не scope: последующее независимое case требует новой явной локальной подготовки, но не повторяет разрешение выполнения плана. Нельзя повторно вооружить завершённый case или заменить его результат.

До Start выбираются task IDs T001/T002 своего опубликованного scope; фактические assignment/attempt/message_id/SHA backend однократно связывает после штатного создания E и проверки result. Эта механическая привязка не меняет согласованную политику и не требует ручных ID. До обоих валидных result измерение не начинается.

Политика при Start не повышается из панели/модельного tool. Локальная подготовка следующего case допускает только заранее согласованные типы и тот же предел 2. Можно отключить новые отправки. Restart требует нового явного локального вооружения; прежние claimed/accepted/unknown не обнуляются и не посылаются повторно. Счётчик резервируется долговечно до send.intent, повтор одной attempt новый слот не расходует. Две вкладки/панели не получают третий слот.

Проверяемый режим и case видны в существующей диагностике. Новых рабочих кнопок и дублирующих карточек sidebar нет. Пользователь включает профиль локальным скриптом, не копирует conversation/participant ID и не редактирует WAL. Известный scope может быть прочитан скриптом из явно указанного тестового workspace; неоднозначность — ошибка без эффекта.

## Единая политика допуска

Для очередного result разрешить пропуск ожидания busy/idle, stopped как физического конца, lastMessageRole=assistant, writable/editor и кнопки Send, когда их отсутствие вызвано текущим ответом O. Не присваивать глобально canSend=true. Нужны раздельные факты: собственный живой документ/URL/login, binding, connectionError, panel/lease, локальные commands и пользовательский draft/manual Stop.

Сохранить current project/session/O, собственный Chat URL/документ и актуальную host identity; grant.scope/generation/boot, attempt/assignment/SHA/proof, свежий снимок, отсутствие отмены/архива/удаления, ручного Stop/Паузы, черновика и ошибки соединения. Неизвестное состояние нельзя принять за разрешённое. Last-minute проверка перед SDK проверяет ту же политику и принадлежность; она не возвращает спрятанный canSend и не разрешает устаревший scope.

Предыдущее сообщение можно пропустить только когда оно уже достоверно read (или штатно superseded_read), принадлежит этому O и мешает лишь незавершённым физическим ходом. Startup, непрочитанный старый вход, claimed/UNKNOWN, чужая generation и обязательный нерешённый вопрос остаются барьерами. Для двух заранее выбранных независимых result одного case разрешено второе последовательное SDK-уведомление без read/yield/idle первого. Это узкое исключение FIFO только для этих двух result; более ранние непрочитанные сообщения другого вида или вне case не пропускаются. Выбирать эти два result по порядку сохранения. Порядок обработки O фиксируется отдельно; причинно зависимые сообщения исключением не охвачены.

Передать одну проверенную политику через pending/first/claim/verify/admit; проверить также reservation, incoming/progress, reserved/settled/channelSettled и _verify(alreadyChecked=true). Reservation, созданная собственным первым result, не должна скрыто возвращать canSend=false для второго. Она остаётся обязательным барьером там, где защищает выполнение, интеграцию и complete. Допуск уведомления не выдаёт разрешение на изменения исходников/Kit.

tool-wait/generation сохраняют commandsIdle. Дополнительный read-only-command case разрешается только после предварительного GO двух основных видов: один заранее закреплённый безопасный измерительный процесс, свой nonce/command-id, проверенные argv/digest и время жизни. Единственный допускаемый процесс читает входные данные/ждёт/возвращает маркер, ничего не пишет в workspace и не вызывает Kit. Нужен отказ для любой другой/дополнительной команды; строка «read-only» от модели не авторизует обход. Использовать существующий command-activity watcher; не вводить универсальную классификацию shell и не выполнять присланный код. argv и определение конкретного probe фиксируются в PROBE, проверяются fixtures и попадают в пакет/manifest. Если среда не различает этот процесс, отправка запрещена, случай NOT_RUN; общий GO отсутствует.

Для этого readCommandActivity в src/control/workflow/command-activity.mjs должен отдавать command_hash и все активные процессы, включая read_only_verified/services, которые сейчас не повышают commandActive/blocksIntegration. В экспериментальном допуске tool-wait/generation блокируются ЛЮБОЙ активной командой; read-only-command допускает только единственную свою точную probe с совпавшими command_hash/nonce/command-id и текущей жизнью процесса. Обычные commandActive/blocksIntegration mode off не меняются. Проверки — tests/command-activity.test.mjs плюс channel/admit fixtures.

src/execution/plugin/sdk-busy-probe.mjs хранит определение/генератор, а не исполняемый shell-файл внутри ASAR. Исполнение — поставляемый собственный Python с -B и фиксированным inline-кодом через -c, известные nonce/duration только как позиционные аргументы; никакого eval пользовательского кода. Литерал кода, точный interpreter/argv, command_hash и связь маркера фиксируются перед Start. Скрипт лишь выводит маркеры, асинхронно/ограниченно ждёт и выходит; shell quoting генерируется штатным безопасным способом. Использование системного node для чтения пути app.asar запрещено. Если вместо inline понадобится extra-resource helper — сначала добавить точный путь и строгую проверку состава в scope, затем согласовать изменение.

## Несколько сообщений без потери прежнего хода

Единственный member.deliveryGate прежнего O не перезаписывается. Для обоих экспериментальных message_id — собственные необязательные message.handlingGate с experiment/case и исходной страницей. Существующее поле переиспользовать, не создавать второй WAL.

Наблюдать отдельно accepted+read+yielded экспериментальные сообщения: directlyHandled сейчас выбирает pending без intent и не охватывает их. Включить нужные сообщения в существующие observed/syncProbes, восстановление, timeout, progress и settled. Эксперимент не меняет правила физического завершения обычных назначений и не снимает их 120-probe предел глобально. Сохранить отдельный gate предыдущей работы, read/yield и фактический конец каждого принятого результата. Один общий конец хода может доказать завершение нескольких обработанных сообщений только при их собственных read/yield и свежем допустимом наблюдении. Не выдумывать reply_observed и не закрывать чужие gates. Если доставка прошла, а старый completion-контракт завис, отчёт различает эти факты; полный GO всё равно требует complete.

SDK-вызовы последовательны через действующий цикл панели. После быстрого ответа первого Promise второй вызывается без ожидания чтения/конца первого. Параллельный вызов ради красивого результата запрещён. При медленном Promise, rejected или UNKNOWN burst прекращается и фиксируется фактический исход. Оба result остаются долговечно сохранёнными.

Read/model-pull любого выбранного result до его настоящего sdk.invoked делает пару INCONCLUSIVE: O мог узнать message_id через status/journal. Не запрещать штатное чтение, не сбрасывать read/intent и не посылать уже прочитанное уведомление ради измерения. Для ещё не отправленных выбранных сообщений снять экспериментальное вооружение пары; уже отправленный intent сохранить. Новый случай требует новой реальной пары/плана, старые результаты продолжают обычную обработку без повторного SDK.

send.intent и attempt_id предшествуют настоящему SDK. На каждый result ровно один вызов; lost report/remount/restart/late callback не создаёт попытку. UNKNOWN сохраняет запрет повтора; положительный read может разрешить исход только штатным согласованием. Поздний Promise — отдельное событие, не перезапись терминальной записи.

## Таймауты и lease

Обычные 10 секунд SDK и 60 секунд panel lease не менять глобально. Для выбранной отправки timeout=90000 мс, окно наблюдения case=120000 мс от первого sdk.invoked; это бюджет наблюдения доставки, не выполнения всего плана. Многоминутная работа T003/DOCS в него не входит.

Поскольку listen сейчас ждёт SDK и не выполняет следующий wait, 90 секунд перекрывают lease 60 секунд. В PROBE/DISPATCH обеспечить штатный адресный sync действующей панели на время ожидания, без продления grant, смены поколения, повторного SDK или нового scheduler. Проверить закрытие/remount, Пауза/Stop и expiry; при невозможности подтвердить lease новые отправки запрещены. Старый отправленный intent не исчезает; report допустим по его attempt и после истечения lease в существующем контракте. Не объявлять SDK_DEFERRED, когда реально отказала аренда.

Таймаут измерений — UNKNOWN/INCONCLUSIVE/ACCEPTED_UNREAD с доказательствами, не разрешение повторить и не обещание отсутствия будущей обработки. Закрытие окна не закрывает backend-панель. Физическое закрытие iframe — отдельная проверка/ограничение.

## Реализация по существующим границам

- Backend desktop-model → control.createPlugin/service → PluginCommunication и coordination/DialogueDelivery получают конфигурацию через ExecutionFacade. Bridge передаёт только типизированные существующие/узкие действия, не произвольную команду.
- WorkflowChannel/PluginCommunication: единый допуск, два слота, прежний gate и отдельные handlingGate; communication-store сохраняет новые поля только при необходимости и совместимо.
- frontend/plugin/launch: прежний ui/message, таймаут, живой lease, действительный SDK-вызов и корреляция. panel: только диагностика/фактические стадии.
- plugin.py и bridge/контракты: строго типизированные диагностические case hold/checkpoint с host identity; telemetry extra=forbid и JS allowlist расширяются согласованно. Модель не включает профиль.
- scripts/analyze-sdk-busy-experiment.mjs: read-only анализ экспорта, без SDK/мутаций состояния.

Новых runtime-зависимостей и изменений Kit ради опыта не требуется. Если понадобится изменить иной публичный контракт — отдельное уточнение scope/проверок через Kit до правки. Нельзя ослабить package composition или scope guards ради теста. Семантически существенные отклонения от этой спецификации вновь проходят Review.

Официальный источник: [Plugin Extensions](https://developers.openai.com/plugins/build/extensions) и указанная там спецификация ui/message/target/send. Закреплённый в проекте @openai/mcp-extensions 0.2.0 и его lock/реальные определения сверяются до реализации; источник спецификации закрепить exact commit в runtime evidence.
