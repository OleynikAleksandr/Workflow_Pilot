## Подготовка и разрешённая отправка

Backend создаёт допустимое назначение и уведомляет O до ожидания bootstrap. O заранее выбирает задачу/контекст и сохраняет неизменяемый draft. Подготовка не зависит от регистрации страницы E: resolver обязан позволять адресовать созданное актуальное назначение до enrollment, но не давать ранний task grant. Сохранённый пакет связан с project/scope/task/assignment/attempt/contract digest; доступ по собственной identity O. Никакого копирования всего recovery E.

Добавить явное действие O: dispatch сохранённого draft с разрешением отложенной отправки при готовности. Разрешение не даёт backend сочинять или менять текст. Если E уже готов, публикация происходит сразу; иначе долговечный intent ждёт событие readiness, не нового хода O. Legacy dispatch без этого разрешения сохраняет fail-closed NOT_READY. Ответ prepare показывает доступные сведения о готовности и следующий допустимый шаг, а не требует обязательно ждать нового ready. Инструкции O: prepare → разрешить dispatch в том же ходе; ждать только реального результата/вопроса.

Основной быстрый вариант — явный параметр авторизации в prepare: O одним вызовом сохраняет собственный текст и разрешает отправку при готовности. Без параметра prepare остаётся только черновиком; отдельный dispatch сохранён для восстановления и изменения решения. Разрешение имеет отдельное состояние и не наследует автоматическое возобновление старых prepared/deferred. После смены поколения/boot нужна новая авторизация O того же неизменяемого пакета.

Служебное уведомление подготовки содержит непрозрачный recipient_ref актуального назначения, который повторно проверяется при prepare. Небольшой служебный текст возвращается целиком в read_message с digest и явным признаком полноты, без дополнительного read_context. Большой текст и выбранные контексты сохраняют части и обязательное полное чтение. После авторизации ненужные ready/prepare-recovery той же пары assignment/attempt не создают новый ход: ещё не начатые уведомления получают superseded; прочитанные входят в yield, а уже начатый SDK/UNKNOWN сохраняет прежние доказательства завершения. Новая попытка не гасится старым разрешением.

Перед эффектом всегда повторно проверяются running grant, generation, identity, attempt, digest, binding/SDK, физическое завершение bootstrap и отсутствие команд. Пауза запрещает отправку; отложенная авторизация старого поколения не возобновляется молча после Continue/restart: O получает recovery и должен подтвердить заново. Удаление/смена scope/attempt/digest отменяют старое разрешение. UNKNOWN не повторяется. Идемпотентность исключает двойной grant/message. Ready для уже авторизованного пакета не должен вызывать лишний ход O; если ready уже в очереди, его обработка не повторяет отправку.

DOCS готовится только после проверенных интеграций, одновременно с собственным bootstrap. Гарантируется независимость конвейеров и отсутствие лишнего обязательного хода, но не обещается, что модель всегда успеет до ready. Будущие задания с неизвестными результатами зависимостей заранее не публикуются.

Создание зависимого назначения в dialogue v1 не требует физического конца текстового ответа O. Оно требует разрешённого issuing, подтверждённых зависимостей, чистого main, отсутствия активных команд, незавершённой интеграции/транзакции; Kit под блокировкой повторно проверяет scope/revision/base и сохраняет тот же ID при восстановлении. Рабочее уведомление O по-прежнему ждёт свободного канала. Legacy, передача начатой задачи из main и delivery сохраняют свои ограничения. Fixture должен доказать bootstrap DOCS при ещё активном ответе O и запрет при активной записи в main.

## Быстрый путь доставки

Проследить сохранение → доступность → получение панелью → claim/verify → SDK → report/read. Обновление списка/журнала и диагностический flush не должны быть барьером между двумя доставками. Долговечная запись, адресная проверка, grant и UNKNOWN остаются обязательными. Не удалять подтверждение свежего idle, не подменять SDK DOM и не пробуждать модель опросом. Независимые E не блокируют друг друга из-за фонового обновления UI. Ограниченный фоновой refresh объединяет повторные запросы; нет бесконечной очереди и гонок после dispose/rebind/Stop. Повторные готовые события не создают дубликаты поручений.

Новый путь панели объединяет claim и verify в одну долговечную операцию с прежними проверками и событиями; старые два API сохраняются. Вызов SDK следует после её подтверждения без промежуточного refresh/telemetry. Отмена до SDK после сохранённого intent не разрешает повтор. Wait продлевает ещё действующую SDK lease при том же поколении/привязке; первоначальный sync и восстановление после общей паузы остаются. Истёкшая lease, новый boot или поколение не возобновляются этим продлением.

Диагностические события не будят доставку и всех участников планировщика. Функциональное пробуждение адресное; изменение разрешения/удаление/ошибка журнала будит затронутых участников обязательно. UI журнал обновляется отдельно с ограниченной частотой. Его обычное обновление не запускает полный Kit roster каждого E. Глобальная очередь мутаций измеряется; медленные чтения и observer не должны удерживать её там, где возможен проверенный снимок с повторной проверкой актуальности перед эффектом. Кэш по времени не заменяет свежую проверку разрешения. Если безопасное разделение конкретной проверки не доказано, она остаётся последовательной и её длительность видна.

Итоговая проверка использует уже подтверждённые доказательства конкретных SHA, не требует повторять неизменившиеся проверки без причины. Перед удалением worktree остаётся полный terminal receipt; завершение после всех delivery/cleanup и физического конца итогового O.

Подготовку итогового ответа можно начать после всех обязательных интеграций и delivery, пока E обрабатывает acceptance. Итоговое поручение содержит проверенные факты о SHA, проверках и cleanup, без повторного полного recovery. Оно не объявляет очистку законченной. O выполняет cleanup, если у любого назначения нет явного DONE; ранняя операция сохраняет PENDING, backend продолжает её после терминальной квитанции. transport_closed сам по себе не означает cleanup DONE: Kit может вернуть cleanup=null. При уже подтверждённом DONE команда очистки не повторяется. Complete требует channelSettled, всех cleanup DONE, чистого подтверждённого main, отсутствия активных команд и физического конца итогового O. Новая работа, ошибка cleanup, Pause/restart и UNKNOWN не обходят эти барьеры. Пока финальный текст опережает очистку, он честно сообщает об оставшейся стадии; sidebar затем показывает её фактический итог. Delivery с побочными эффектами не получает ослабленного разрешения.

## Тайминги и экспорт

Использовать существующий WAL/экспорт, не второй журнал истины. Корреляция: message/assignment/task/attempt, направление и тип операции, безопасный panel instance, последовательность событий. Метки backend имеют server_time; длительности внутри панели измеряются performance.now, обозначены источником и именем операции. Сравнение разных часов не выдаётся за точную длительность; client_time — вспомогательный wall clock. События: получение сообщения панелью, начало/конец или ошибка claim/verify/report/sync/wait/status, SDK invocation/outcome, наблюдаемая активность/конец агента, read/yield/result и финализация. Дополнять существующие метки без дублей. Ожидание хоста до первого наблюдаемого действия остаётся unknown/host, а не model thinking. Активность observer не доказывает генерацию токенов.

Телеметрия ограничена по размеру/числу и отправляется пакетно отдельно от доставки. Allowlist параметров: без body/контекста, tickets, identity, raw host metadata, аргументов инструментов и секретов. Отказы диагностики не повторяют SDK; переполнение/потеря/отсутствие этапа видны в экспорте. API старой одиночной telemetry сохраняется. Приоритет функциональных квитанций над необязательной диагностикой. Для повторов отдельные span IDs; после rebind старые spans не приписываются новому экземпляру.

Отдельно измеряются очередь мутаций, обработчик, Kit-проверка, подготовка окружения и observer. Отложенный claim имеет конкретную причину (FIFO, текущий ход, команды, черновик/ручная остановка, неподтверждённая привязка), запись только при смене причины. Прежнее duration_ms обозначается как время от mount; новая длительность операции — отдельное поле, не переименование старого смысла. Сравнение invoked/accepted по монотонному таймеру одной панели допустимо, но не измеряет запуск модели. В опыте оно составило около 67–291 мс; точные 1–3 с «стоимости обращения к хосту» из смешанных часов не доказаны.

## Решения независимого анализа

Рецензент исследовал код и очищенные seq1–255 опыта; основной агент проверил рекомендации. Во всех трёх стартах ready предшествовал prepare: узким местом запуска было не окончание bootstrap E. Работа самого E остаётся частью критического пути. Prepare→публикация заняли 26,7/49,5/44,6 с; это основание убрать лишние шаги O, не обещание такого же выигрыша в каждом запуске. После seq254 complete позднее seq255 project.removed не считается провалом завершения.

Ограниченная параллельная установка окружений пока не включается: текущий Kit держит parent operation.lock всё время npm ci. Простое Promise.all нарушит этот контракт; в опыте установка не определяла задержку запуска задания. Её время измеряется, но перенос длительной установки под отдельные child locks с восстановлением, удалением и остановкой — отдельная последующая работа при подтверждённом вкладе.

Повтор roleUpdate подтверждён, но автоматическое «один раз на participant» не принимается: backend не знает об утрате контекста при compaction. Полный ролевой fallback сохраняется. Сначала сокращаются лишние ходы/служебные чтения; отдельное сокращение инструкций возможно лишь с явным подтверждением актуальной версии агентом и гарантированным recovery, без потери обязательных правил.

## Интерфейс

Состояние задач и завершение плана — разные показатели. Галочки обозначают проверенные интеграции. При 3/3 и активном выполнении: «Задачи интегрированы: 3/3» и «План завершается», а не общее «Всё выполнено». «План выполнен» появляется только при complete; приёмка scope пользователем остаётся отдельно. Кнопка Пауза — управление, не единственный индикатор активности.

После complete при незакрытом scope явно показывать «Выполнение завершено — ожидается ваша приёмка» и инструкцию: сообщите оркестратору «Принимаю результат, закрой план». Только прямое решение пользователя разрешает Kit archive scope. Не подменять приёмку автоматическим закрытием или архивированием проекта в sidebar. Архивирование проекта с complete не должно утверждать, что выполнение продолжается или будет остановлено. Предупреждение об остановке показывается только при фактически незавершённом запуске; проверка backend согласована с UI, stale карточка не разрешает обход активной работы. Состояния не смешивают ACTIVE scope, READY_FOR_ACCEPTANCE и running execution; возврат завершённого проекта из архива не запускает его снова.

В основном sidebar постоянно видна текущая стадия плана/оркестратора и состояния E: подготовка, подключение, готовый пакет ждёт канал, отправка/ожидание прочтения, обработка результата O, активная проверка/интеграция, terminal receipts, очистка, итоговый ответ, complete. Показывать известную причину и длительность неизменной стадии. Результат read не означает запущенную проверку. Если физическая активность известна без операции — «Обрабатывает результат»; неизвестное ожидание обозначать честно. Никаких фиктивных процентов/ETA или потока модельных сообщений пользователю. Native/HTTP используют общий contract. Старый скрытый блок parallel не должен прятать стадии orchestrated; не выводить устаревшие кнопки управления.

## Проверки

Изолированные fixtures с настоящими API/Kit/Git и подставленной физической моделью: prepare до enrollment, ready до/после авторизации, медленный E рядом с быстрым, идемпотентность, Pause/Continue/restart/смена attempt/digest/удаление/UNKNOWN. Полный 2E→две acceptance/integration→DOCS→cleanup→complete без посещения карточек и без дополнительного модельного ready-хода для разрешённого dispatch.

Контролируемые задержки UI refresh и telemetry не задерживают функциональный путь. Экспорт связывает обе стороны, отличает clocks/unknown/gaps, ограничивает данные и не выводит секреты. UI fixture проверяет промежуток 3/3+active и complete, обновление стадий и отсутствие ложного «План выполнен». Регрессии single writer, busy/draft, read/yield/observed сохранены.

Дополнительно: готовый E до prepare не требует отдельного вызова dispatch; авторизация до ready не требует нового хода O; уже ожидающий ready гасится без ложной квитанции UNKNOWN. Медленный UI/диагностика одного участника не создаёт очередь функциональных запросов другого. Проверить запуск DOCS при активном текстовом ходе O, финальный ход до окончания acceptance E и complete только после всех доказательств; очистка null/PENDING/DONE, повтор после restart и отсутствие дублирующих проверок неизменившегося main. Контролируемые тесты считают число вызовов и событий, а не обещают скорость реальной модели.

Проверить архивирование running/paused/finalizing/complete и незакрытого принятого/непринятого scope: complete не требует предупреждения об остановке, running требует подтверждения; приёмка не выдумывается, возврат не даёт новый grant.

Полный набор: unit-all, architecture, kit-check и kit-assignments, executor-channel, chatgpt-plugin, electron-smoke, release-tooling, upgrade при изменении Kit. Живое ускорение, точные задержки хоста и проверка экранов — следующий пользовательский тест, не PASS по fixtures. Согласовать role-protocol/startup/Kit/MCP/schema/backend errors.

## Поставка

Отдельная DOCS переносит итоговые контракты в модули и удаляет эту выпущенную спецификацию с точным Git blob для required context. Свободный следующий номер app/Kit, versioned content-addressed панель. Один sourceCommit для macOS/Windows/Linux, очистка только разрешённых Python-кэшей перед каждой сборкой, строгая подпись/состав. Штатная установка готового bundle в /Applications без остановки службы; pending отдельно. GitHub Release с проверенными tag/assets/digests; новый scope остаётся до приёмки пользователя.
