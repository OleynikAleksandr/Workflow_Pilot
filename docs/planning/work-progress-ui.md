# Понятный ход работ: левый sidebar и панель Workflow Pilot

Спецификация выпуска 0.5.25. Основа — интерактивный прототип «Ход работ Workflow Pilot» (версия 8), согласованный с пользователем 22.10.2026. Отладка панелей и общения агентов закончена: служебные данные уходят из основного вида, а ход работ показывается понятно и в динамике.

## 1. Цель

Пользователь в любой момент без знания внутренних терминов видит:
- в левом sidebar приложения — состояние плана, все его задачи со стадиями выполнения и все свои действия (запуск, пауза, проблема, приёмка, Review);
- в правой панели Workflow Pilot (ChatGPT) — всё, что происходит прямо сейчас у всех участников, с живым временем, и историю уже произошедшего.

Тишина больше не выглядит зависанием: у каждого идущего действия есть спиннер и тикающее время, у долгой проверки коммита — счётчик проверок.

## 2. Распределение информации

| Место | Назначение | Содержит |
| --- | --- | --- |
| Левый sidebar | управление и обзор плана | дерево сессий, карточка плана: этап, прогресс, задачи со стадиями, кнопка выполнения, проблема с одним действием, подсказка приёмки, Review |
| Правая панель | динамика всех участников | шапка, «Сейчас», свёрнутая «История», свёрнутая «Диагностика» |

Одна сущность не повторяется в одном месте с разной детализацией. Управляющих кнопок плана в панели нет.

## 3. Левый sidebar

### 3.1. Дерево проектов и сессий

- У сессии, участник которой сейчас выполняет действие, в строке дерева — маленький спиннер. Текста о ходе работ под карточкой сессии нет.
- Уведомление сессии `session-notice` не показывает нормальный старт («читает стартовый контекст 2 из 3», «контекст восстановлен»): эти события показывает панель. Ошибка старта, требующая действия пользователя, показывается в блоке проблемы (3.4) с указанием создать новую сессию через меню проекта.
- Кнопка «Новая сессия» (`new-context-session`) удаляется вместе с обработчиком. Новые сессии создаются через меню проекта «Новый Chat / Новый Work».
- Пункты «Повторить», «Отменить ожидание», «Наблюдать» для незавершённого старта сохраняются там, где они нужны для восстановления, но только в состоянии, требующем действия.

### 3.2. Карточка плана: три зоны

Карточка занимает доступную высоту sidebar и делится на три зоны:

1. **Верх, закреплён:** короткое название плана; этап плана со спиннером, пока идёт работа («Подготовка», «Обсуждение плана», «План готов», «Запуск», «Выполнение», «Нужно внимание», «Завершение», «Ждёт приёмки»); полоска и подпись «в main N из M».
2. **Середина, прокручивается:** только список задач плана. При смене состояния список сам прокручивается к первой задаче с проблемой, иначе к первой выполняемой; ручная прокрутка пользователя между обновлениями сохраняется.
3. **Низ, закреплён:** одна кнопка выполнения плана («Начать выполнение плана» / «Пауза» / «Продолжить»); блок проблемы (3.4); подсказка приёмки; переключатель Review.

Большой план не выталкивает кнопку, проблему и Review за пределы видимой области.

### 3.3. Строка задачи

- Значок: ✓ — влита в main; спиннер — выполняется; «!» — нужно внимание; ○ — не начата.
- Первая строка: ID и название полностью, без обрезки режимом.
- Вторая строка: текущая стадия в действующих формулировках приложения (`assignmentStage`, `executorStatus`, `projectExecutionPlan`: «Задание оркестратора в доставке · чтение не подтверждено», «Выполняет поручение оркестратора», «Вопрос оркестратору · ожидаем решение», «Результат отправлен · ожидаем проверку оркестратора», «Интегрируется», «Интеграция проверена» и т. д.); для незавершённой задачи после стадии — режим («· Параллельно», «· Последовательно», «· Оркестратор в main»); справа — время на текущей стадии для выполняемой задачи или задачи с проблемой.
- Для проверки коммита стадия называет проверку и счётчик по данным Kit (раздел 6): «Kit проверяет коммит · unit-all · 2 из 3».
- Нажатие на начатую незавершённую задачу открывает чат её исполнителя (как сейчас); выбранная задача подсвечена.
- Убираются: подсказка «DOCS checks:[] в Kit…», отдельные «На этой стадии MM:SS» и «Работа · ожидание» без подписи. Накопленные таймеры работы и ожидания доступны в «Диагностике» панели.

### 3.4. Блок проблемы

Появляется только когда нужно действие пользователя или работа действительно остановилась: неизвестный исход команды или отправки, эскалация, конфликт или провал интеграции, ошибка старта сессии, участник без событий дольше порога. Содержит заголовок («T003 молчит 12 мин»), одну фразу причины и одну кнопку действия («Открыть чат T003», «Разобрать неизвестный исход», «Открыть меню проекта»). Существующие действия `command-issues` и восстановления сохраняются и переносятся сюда. Остальные состояния — нейтральные.

### 3.5. Что удаляется из карточки плана

- `agent-time` (время выбранной сессии без подписи);
- `plan-status`, `plan-note`, `execution-message` как отдельные дублирующие строки: их смысл — в этапе, прогрессе и подсказке приёмки;
- `execution-stages` («План · На этой стадии 03:05») и пустая рамка `execution-next-action`;
- длинная цель плана в заголовке: заголовок — короткое название, цель доступна во всплывающей подсказке.

Сохраняются без изменения смысла: `conversation-recovery`, `workspace-health`, `error-banner`, настройки, legacy `assignment-card` для начатых parallel-планов.

### 3.6. Без активного плана

Карточка показывает этап («Подготовка», «Обсуждение плана»), Review и, при необходимости, блок проблемы. Список задач и прогресс появляются после публикации плана. Для sequential/parallel-планов используется та же карточка; режим выполнения у задач берётся из плана.

## 4. Правая панель Workflow Pilot

### 4.1. Шапка

Название плана (или «Workflow Pilot» до плана), этап, «в main N из M», справа — какой чат открыт («открыт чат оркестратора», «открыт чат T002», «открыт чат обсуждения»).

### 4.2. «Сейчас»

- Одна строка на каждое текущее действие любого участника: оркестратор, исполнители, приложение, Kit. Одновременные действия показываются все.
- Порядок: проблемы, затем действующие участники, затем ожидающие.
- Значок: спиннер — действие идёт; «·» — ожидание (без спиннера); «!» — проблема.
- Текст «кто — что — сколько»: «T001 Kit проверяет коммит · тесты 2 из 3», «Оркестратор ← результат T001 · проверяет изменения и тесты», «T001 ждёт приёмки результата». Справа — тикающее время текущего действия.
- Сообщение в пути видно с обеих сторон: «T002 → вопрос оркестратору · ждёт ответа» и «Оркестратор ← вопрос от T002 · отвечает».
- Строки участника, чей чат открыт, выделены рамкой.
- Нормальный старт сессии («читает стартовый контекст · часть 2 из 3») показывается здесь, а не под карточкой сессии.

### 4.3. «История»

- Свёрнута по умолчанию; в заголовке — число событий с правильным склонением.
- Закончившиеся события, свежие сверху: время по часам, ✓ или «!», текст. Сообщения со стрелками: «10:19 Оркестратор → T002 решение: JSON {count, sum, avg}».
- Закончившиеся ожидания событиями не считаются и в историю не попадают.
- Служебная механика как событие не показывается: `ready`/`recovery`, их замена (`superseded`), квитанции чтения, yield, конец хода, повторные проверки. Пользователь видит итог шага.
- Раскрытие истории не сбрасывается обновлением данных и тиканьем времени.

### 4.4. «Диагностика»

Свёрнута по умолчанию. Сюда переносятся все нынешние разделы панели без потери функций: подтверждение участника и legacy bind/enable, разрешения и «Остановить отправку плана», возможности SDK и локальные события, roster с ID назначений, поколением и physical-состоянием, outbox/intents, лента сообщений с UUID и квитанциями, журнал запуска с фильтрами, «Обновить», «Экспорт журнала», «Скачать JSONL», build, накопленные таймеры работы и ожидания исполнителей (данные приходят в снимке плагина вместе с `workProgress`).

### 4.5. Роли

Основной вид одинаков у оркестратора, исполнителя и обсуждающего чата: панель показывает ход всего плана проекта, к которому принадлежит разговор. Отличается только выделение строк своего участника. Текст сообщений в «Сейчас» и «Истории» — краткое превью без секретов; полный текст остаётся в чатах. `workProgress` проекта передаётся в инструментах `status` (view `panel`) и `sync` (`src/control/plugin/communication.mjs`) всем участникам плана; правила видимости сырых сообщений, назначений и «Диагностики» для E и S не меняются. Панель обновляет «Сейчас» без перезапуска ожидания: `wait` просыпается при смене `workProgress`, иначе панель делает ограниченный периодический `status`.

### 4.6. Словарь

Один модуль надписей в `src/contracts` для sidebar, HTTP-клиента и панели: виды сообщений (задание, вопрос, решение, уточнение, результат, принят, на доработку, итог), действия участников и ожиданий, этапы плана. Стадии задач в sidebar берутся из действующих функций без переименования. В основном виде нет UUID, ID назначений, номеров поколений, кодов `SDK accepted`, `Kit RUNNING`, `pending/claimed`.

## 5. Единая палитра

Панель и sidebar используют одни токены — палитру нынешнего sidebar из `src/frontend/desktop/ui/index.html`: светлая (фон `#f4f6f8`, карточки `#fff`, линия `#dae4e9`, текст `#243346`, вторичный `#708092`, акцент `#087e80`, выделение `#e4f1f0`/`#bddad7`) и тёмная (фон `#1b1d22`, карточки `#22272d`, линия `#363e48`, текст `#e7edf4`, вторичный `#9aa8b6`, акцент `#7fd0cb`, выделение `#203536`/`#356061`, предупреждение `#dfac74`). Действуют явные значения этого раздела (прототип v8): они заменяют прежние `--line` и тёмный `--teal` sidebar. Токены хранятся в одном модуле `src/contracts/palette.mjs`: шлюз HTTP-клиента уже раздаёт `contracts/`, правило границ renderer разрешает этот импорт, сборка панели встраивает модуль. Sidebar вставляет из модуля элемент `<style>` в рамках действующей CSP (`style-src 'unsafe-inline'`), без внешних CSS-файлов и без расширения CSP. Фон окна до первого показа (`application.mjs`, `client.mjs`, `src/frontend/web/index.html`) сверяется с теми же значениями. Шрифт системный. Панель следует теме хоста (prefers-color-scheme), sidebar — выбранной теме приложения. Спиннер — общий, с упрощением при `prefers-reduced-motion`.

## 6. Kit: прогресс проверок коммита

Сейчас во время `commit --task` проверки идут минутами без видимых признаков. Kit записывает в состояние текущей транзакции машинный прогресс (версия задаётся в `package.json` и `src/lib/common.mjs`): ID задачи, ID текущей проверки, её номер и общее число, время начала проверки и время начала всего прогона; запись атомарная, очищается при завершении или отмене транзакции. Запись лежит в git-dir того checkout, где идёт коммит: у исполнителя — git-dir его worktree, у оркестратора и последовательного плана — git-dir main. Приложение читает её рядом с наблюдением команд (`command-activity`) и состоянием назначений (`parallel-kit.mjs` уже вычисляет git-dir дочерних worktree); `transaction.json` дочерних git-dir добавляется в наблюдаемые входы, чтобы смена номера проверки обновляла снимок. Прогресс показывается в стадии задачи и в «Сейчас». Отсутствие записи — нормальное состояние старого Kit; старый Kit продолжает работать без счётчика. Изменение требует новой версии Kit (1.9.5) со штатным обновлением checkout и проверкой upgrade.

## 7. Данные

- В backend одна проекция хода работ на проект (`workProgress`): этап, прогресс, задачи со стадиями и временем, текущие действия, история, проблема. Источники уже есть: план Kit, `execution.view`, `planActivity`, стадии назначений, `executorStatus`, журнал WAL сообщений и квитанций, `command-activity`, состояние интеграции, startup-прогресс, прогресс проверок Kit.
- Sidebar (native и HTTP-клиент) получает проекцию через существующий снимок модели и SSE; панель — через существующий снимок плагина. Клиенты только рисуют. Новый scheduler, очередь или хранилище не создаются.
- Время текущего действия — наблюдаемое монотонное время backend (`activityClock`); после перезапуска службы отсчёт начинается заново, как сейчас. Время событий истории — из долговременных записей WAL и Kit.
- История ограничена (последние события плана) и строится заново из долговременных источников после перезапуска.
- Порог «нет новых событий» — константа контракта, не новая настройка.

## 8. Совместимость

- Одинаково на macOS, Windows, Linux, во встроенном окне службы и HTTP-клиенте.
- Начатые sequential/parallel-планы и dialogue_version 0 отображаются той же карточкой; legacy-функции панели доступны в «Диагностике».
- Границы Control/Execution/Frontend и клиент/backend сохраняются; внешние DOM-экспорты сохраняются или заменяются с обновлением тестов.

## 9. Приёмка

Автоматически: проекция и словарь покрыты модульными тестами; сквозная регрессия проходит сценарий прототипа (старт, обсуждение, публикация, запуск, отправка заданий, параллельная работа, вопрос, проверка коммита со счётчиком, сдача, слияние, проблема, документация, завершение, приёмка) и сверяет sidebar и панель; большой план проверяет закреплённые зоны; обе темы используют одни токены; `electron-smoke` актуализирован под новый интерфейс и проходит. Живая проверка интерфейса выполняется пользователем после установки.

## 10. Не входит

Человеческий словарь стадий задач в sidebar (формулировки остаются нынешними), передача роли оркестратора новой сессии, изменение протокола диалога O/E, серверная конфигурация VPS.
