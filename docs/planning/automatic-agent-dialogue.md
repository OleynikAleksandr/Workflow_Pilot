# Автоматический диалог оркестратора и исполнителей

## 1. Поручение и результат

19.10.2026 пользователь согласовал следующий этап: после обычного обсуждения, Review и публикации плана одна кнопка «Начать выполнение плана» автоматически подключает исполнителей и позволяет оркестратору разрешать их технические блокировки без пользователя. Новый scope реализуется здесь одним агентом, последовательно; это прямое исключение пользователя из обычного режима разработки через назначения. Сейчас поручены спецификация и to-do, реализация не запущена.

База — исходники выпуска 0.5.4. Прежний scope закрыт пользователем как предположительно выполненный, коммит закрытия 87a92ea22963dd1af1a23a2cb2451e096af732d5. Отчёт Workflow_Pilot_Panel_Test_Results_2026-10-18.md подтверждает обмен в неактивной сессии Electron и завершение обмена между закрытием и открытием интерфейса с оставленными службами. Номер фактически работавшего build в заключительной серии отдельно не снят. Это не доказательство восстановления старой панели Chrome, автоматического подключения новых разговоров или выполнения реальных назначений.

Основной результат: пользователь открывает проект и будущего оркестратора, обсуждает задачу, при включённом Review согласует спецификацию/план и нажимает существующую кнопку запуска. Дальше не копирует run/participant, не вызывает join вручную, не открывает чаты/панели исполнителей, не нажимает отдельные Enable и не пишет «продолжай» при обычной технической блокировке. Живой минимум — два параллельных исполнителя и третий после их интеграции; модель данных и автоматические проверки поддерживают одного оркестратора и пять исполнителей с существующим ограничением max_workers.

## 2. Существующая база и границы

Сохранить роли, Review, назначения/worktree, интеграции и доказательства DONE Workflow Kit; создание исполнителей остаётся в Control/ParallelExecution через Kit. Панель открывает канал разговора, а не создаёт самостоятельную систему назначения задач. Первое сообщение и полный recovery нового разговора по-прежнему автоматически передаются существующим DOM-механизмом. До запуска плана обсуждение и Review продолжают существующий путь. После готовности канала назначения, продолжения, вопросы/решения, итоговые и delivery-поручения данного плана получают уведомление через плагин.

Control управляет привязкой к проекту/плану, назначениями, разрешением и очередью. Execution выполняет IO/журнал/мост и наблюдение страницы. Frontend использует SDK. PluginCommunication получает проверенные факты плана через узкий контракт Control; не читает Kit и файловую систему напрямую. Сохранить публичные DOM-экспорты, просмотр страниц, ввод пользователя и текущий observer занятости/черновика. Не строить универсальный диспетчер или второй scheduler.

Изменяются исходники packages/workflow-kit; установленный Kit и managed-секции обновляются только installer. Не менять donor, VPS, провайдеров моделей и не добавлять платный API. Автоматические тесты — изолированные fixtures без модельных запросов и записи в рабочие профили. Живые опыты выполняет пользователь в отдельном экспериментальном workspace после поставки. Формы, сценарии и граница приёмки — [проверки](automatic-agent-dialogue-acceptance.md).

## 3. Автоматическая регистрация и первый запуск

### Будущий оркестратор

До первого сообщения backend резервирует подключение для точных project_id и local_session_id. Scope ещё может отсутствовать. Стартовый контекст после полного чтения recovery предписывает один вызов расширенного workflow_pilot_panel с непрозрачным enrollment_ticket. Существующее правило «для первого ответа не вызывай MCP проекта» получает узкое исключение именно для регистрации панели; повторная загрузка recovery, запуск плана и лишние модельные запросы этим не разрешаются.

Инструмент принимает host metadata каждого вызова, проверяет приглашение и связывает локальную сессию с хешем идентичности ChatGPT. Название чата, URL, выбранный sidebar, переданный session_id и заявление роли не заменяют проверки. Это подключение существующей локальной сессии: не создавать дополнительную external-сессию через старый connectExternal. Публикация плана связывает его только с подтверждённым execution_origin_session_id; другой кандидат не захватывает роль автоматически. Пока план не запущен, панель показывает готовность без разрешения на рабочие уведомления.

### Исполнители после кнопки запуска

Backend создаёт обычное назначение Kit, worktree и локальную сессию, выдаёт приглашение, ограниченное этим назначением, и добавляет его в первоначальный контекст. Исполнитель читает пакет, вызывает тот же инструмент панели и завершает загрузочный ход. Работу task:start начинает по первому рабочему уведомлению после подтверждённых SDK/bind/разрешения и окончания загрузочного хода. Это устраняет гонку между ещё не подключённой панелью и началом задачи.

Один вызов совмещает регистрацию и возврат прежнего UI resource. Свежий запрос панели автоматически получает своё назначение и делает bind; отдельный join, ручные поля и выбор среди прежних экспериментальных запусков в рабочем режиме отсутствуют. Инструменты read/send не открывают новую панель. Повтор bootstrap для той же identity идемпотентен, потерянный ответ не создаёт второго участника. Повтор чужой identity, заменённое назначение, просроченное/отозванное приглашение отклоняются.

Приглашение — случайная ограниченная возможность первичной регистрации; сервер хранит хеш и точную область, использует ограниченный срок и одно привязывание. Исходное значение передаётся только целевым стартовым контекстом, не попадает в Git, общий журнал, список участников или экспорт. Повтор той же регистрации возвращает результат, но не переносит привязку. После связывания действуют свежие host metadata. Возобновление уже известного разговора не требует нового копирования приглашения.

Готовность: зарегистрирован → SDK подключён → привязка подтверждена → разрешён текущим планом → ожидает. Успех MCP-вызова открытия не означает монтирование панели. До готовности конкретного участника рабочие сообщения остаются в очереди; другое назначение не подставляется. Ограниченная попытка восстановления SDK/связи не создаёт новых модельных ходов и дубликатов стартового сообщения. Если хост требует ручного открытия/подключения плагина, показывать точное препятствие; живую автоматизацию не считать пройденной.

## 4. Участники, сообщения и адресация

Рабочий запуск связан с project_id, scope_id и поколением выполнения. Участники хранятся по participant_id; роль — свойство, а не ключ O/E. Оркестратор один, исполнителей несколько. Каждый исполнитель имеет local_session_id, assignment_id, task_id, поколение назначения и проверенную identity. Проверять принадлежность и активность назначения при регистрации, чтении и перед отправкой. Завершённый/заменённый исполнитель не получает новые поручения.

Модель обращается к своей роли и назначению без копирования транспортных UUID: исполнитель отправляет вопрос своему оркестратору; оркестратор отвечает по исходному message_id/block_id либо выбирает действующее assignment_id из серверного реестра. Отправитель и область определяются сервером. Оркестратору доступен реестр своего плана, исполнителю — собственное назначение и относящиеся сообщения. Один разговор оркестратора и одна панель обслуживают очередь всех исполнителей.

Конверт: event_id/message_id, проект/scope/поколение, assignment_id/task_id, проверенные отправитель/адресат, тип, ссылка на исходное событие/блокировку, данные решения или ссылка на контекст. В типах различаются старт/продолжение назначения, question/decision, результат/интеграция и финальное поручение. Содержание агента не расширяет полномочия. Большой recovery и доказательства читаются через MCP по проверенной ссылке, а не обрезаются под лимит текста уведомления. Реестр и envelope не возвращают чужие worktree, приглашения или raw host metadata.

Один источник истины для задачи — Kit. task:block и assignment:message остаются каноническими сигналами; координатор переносит их в канал с устойчивым ключом из signal_id. Агент не дублирует одно событие отдельно через CLI и send_message. Доставка, чтение, принятие решения и выполненный коммит — разные состояния. DONE требует прежних проверок/интеграции. Старый ответ не снимает новую блокировку того же назначения: решение связано с конкретным block_id/question_id; совместимость прежних сигналов описать и проверить отдельно, не переинтерпретировать старый журнал молча.

Хранить очередь, idempotency, разрешение и квитанции с прежним правилом «подтверждение после сохранения». Между журналом Kit и каналом возможен сбой: повтор согласования по устойчивому ключу не теряет и не дублирует событие. Старые экспериментальные O/E-запуски и их экспорт сохраняются, не получают разрешение плана автоматически. Совместимость формата хранилища и нового протокола проверяется до записи; неизвестная версия явно отклоняется, исходный журнал не переписывается ради миграции.

## 5. Доставка, разрешение и жизненный цикл

Кнопка запуска выдаёт backend-разрешение конкретному плану и его назначениям. Панели получают его свежим запросом без отдельных Enable. Разрешение действует во время работы плана; 30-минутный экспериментальный таймер не прерывает задачу. Повторная привязка/короткая техническая lease не означает новое пользовательское согласие. Устаревший исторический tool-result не выдаёт разрешения и не меняет свежую привязку.

Существующий observer сообщает занятость, незавершённые команды и черновик адресата. Панель перед SDK Send получает серверный допуск с актуальной identity, состоянием плана и поколения; занятый адресат ждёт, без второго параллельного Send в тот же разговор. Использовать события существующего observer, без опроса активной моделью. FIFO с проверкой актуальности на разговор; неактуальный ответ отмечается и не исполняется. UNKNOWN сохраняется и не повторяется автоматически ни через SDK, ни через DOM. Разрыв claim/report не возвращает сообщение в pending. В первой версии объединять несколько событий в один ход необязательно.

В новом режиме единственный маршрут рабочих уведомлений — плагин. Удалить конкурирующий DOM Send именно для подключённого назначения, включая автопродолжения, сигналы и итоговые поручения. Начальный контекст и предшествующий запуску Review остаются штатными. Legacy-планы сохраняют прежний маршрут; выбор фиксируется в состоянии, незаметного переключения при ошибке нет. Сбой канала виден как отсутствие готовности/ожидание восстановления; неизвестный исход — внимание с сохранением очереди.

Пауза не выдаёт новых назначений. Пока выполняющиеся задачи доходят до безопасной точки, допускаются относящиеся к ним вопросы/решения; отсутствие новой задачи для ремонта не должно оставлять паузу вечной: заблокированное назначение без активных команд можно припарковать и продолжить после кнопки. Ручной Stop запрещает новые отправки немедленно, уже переданный SDK-запрос не отменяет. Отзыв связи участника отражается в состоянии плана и не исправляется скрытым Enable.

Закрытие интерфейса при живом backend не отзывает разрешение и не уничтожает страницы. Перезагрузка службы/компьютера сохраняет назначения/сообщения, аннулирует прежний допуск и показывает одну кнопку «Продолжить план»; после неё штатно восстанавливаются страницы, привязки и разрешение. Повторный первоначальный контекст и UNKNOWN-отправка не воспроизводятся. Новый scope, отмена, архив проекта и замена назначения не наследуют старое разрешение.

Завершение включает финальные интеграции, delivery при его наличии, cleanup и итоговый ответ оркестратора; канал не отключается раньше их доставки/проверки. После завершения выполнения новые рабочие уведомления запрещены, ожидать ручного archive/приёмки не нужно. Связь до READY_FOR_ACCEPTANCE согласовать с фактическим финальным этапом ExecutionControl, чтобы не отрезать последний обязательный ход. Полное закрытие/уничтожение страницы хостом не является доказанной поддержкой фонового SDK; после восстановления нужна наблюдаемая готовность.

## 6. Инструкции разрешения блокировок

Исполнитель самостоятельно исправляет обычную проблему в разрешённых границах. Если решение неизвестно или попытки не дали прогресса, вызывает task:block с фактической ошибкой, предпринятыми действиями, состоянием файлов/команд и точкой продолжения. Сохраняет worktree и завершает текущий ход, но задача остаётся незавершённой, в ожидании решения. Не просит пользователя установить зависимости или написать «продолжай» вместо обращения к оркестратору. Другие независимые исполнители продолжают работу.

Оркестратор читает вопрос и контекст назначения, принимает решение, отвечает по конкретной блокировке и проверяет последующее возобновление. Может поручить локальное исправление тому же исполнителю, исправить разрешённую общую среду либо добавить необходимое назначение в текущий scope. Уточнение не выдаётся за новый бесконтрольный план. Исправление среды оркестратором требует исключительного владения соответствующей операцией: исполнитель в этот момент не меняет те же файлы/среду. Изменения исходников проходят штатные назначения/проверки/интеграцию; запрет обычной реализации в main для orchestrated-плана не обходить.

Обращение к пользователю — только для отсутствующих полномочий, доступа/секрета, изменения объёма либо неразрешимой проблемы; причина и выполненные попытки конкретны. Обычная установка зависимостей в worktree не является автоматическим поводом для эскалации. Повторная блокировка должна содержать новое наблюдение; одинаковая ошибка без прогресса не запускает бесконечный обмен или повторы побочных эффектов. Сохранять попытки/решения и предел автоматического цикла, после исчерпания — осмысленная эскалация без ложного DONE.

Каноническое ролевое поведение — в исходнике recovery Kit. Стартовый контекст добавляет только привязку, bootstrap и ссылку на этот протокол. Перед выпуском сверить project/global AGENTS, получаемые recovery/шаблоны Kit, startupRules MCP, описания инструментов и backend-ошибки. Изменяемый установленный Kit не править вручную. Открытые старые разговоры получают новую версию инструкций штатным адресным обновлением без повторного task:start/работы.

## 7. Поставка и критерий завершения

Последовательность разработки: реестр/сохранение → автоматический bootstrap и разрешение → доставка сигналов/продолжений → инструкции и блокировки → общая матрица и сценарии приёмки → согласование версий → DOCS → общая сборка → штатная установка → публикация. Каждая задача имеет проверки из текущей конфигурации Kit. При изменении исходников Kit включить kit-check, обновить его версию/installer-совместимость; новый комплект приложения и панели согласован по build/protocol. Номер следующего свободного выпуска проверить перед закреплением, старые теги не перезаписывать.

DOCS переносит действующие требования в контракты и сценарий приёмки, включая plugin-plan-lifetime.md; выпущенные временные спецификации удаляет без потери отложенного. Три платформы из одного sourceCommit; перед каждой production-сборкой удалить проверенные Python-кэши по AGENTS, проверки Python выполнять с -B/PYTHONDONTWRITEBYTECODE. Готовый macOS-комплект установить штатным installer в /Applications/Workflow Pilot.app без пересборки, переподписи или остановки службы агентом; при занятой службе оставить pending для пользователя.

Технический план заканчивается поставкой готового проверочного комплекта и сценариев. Живые S1–S3 остаются отдельным обязательным условием пользовательской приёмки; fixtures и техническое DONE их не заменяют. После результата пользователя: принять и закрыть либо адресно plan:extend для исправления. Реализация, запуск живых агентов и новый выпуск не выполняются в ходе подготовки этой спецификации.
