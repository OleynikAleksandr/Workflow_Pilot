# Диалог O/E: надёжность, переход и приёмка

Обязательная вторая часть [спецификации рефакторинга](orchestrator-owned-dialogue.md), scope `orchestrator-owned-dialogue-refactor`. Подготовка с Review, реализация здесь одним агентом после отдельного поручения. Нельзя считать этот объём выполненным только исправлением reply gate или обнаружением коммита.

## Источники состояния и границы

Сохранять Control/Execution/Frontend: Control без прямого IO, Execution без знаний о смысловом плане, frontend только API/contracts. Использовать действующие SessionRuntimes, ParallelExecution, DialogueDelivery, PluginCommunication и Kit, не создавать второй scheduler или параллельный plan ledger.

Kit владеет задачами/назначениями, ограничениями, проверками, коммитами, блокировками, попытками исправления, приёмкой и Git-интеграцией. WAL связи владеет текстами/снимками контекста, авторством, адресацией, доставкой, квитанциями и состоянием обработки сообщения. UI — проекция этих источников. Наличие message.persisted/accepted/read/handled, результат E и INTEGRATED/DONE — разные факты.

Для сообщения с эффектом Kit (блокировка, решение, разрешение задания, result/acceptance/новая попытка) использовать сохраняемое намерение и единый operation/idempotency ID. Порядок: сохранить неподлежащий доставке intent с payload → выполнить/проверить эффект Kit с тем же ID → зафиксировать готовое сообщение в WAL → разрешить SDK-доставку. После сбоя reconciliation проверяет Kit и продолжает ту же операцию. Сбой до эффекта, после Kit и до публикации, после публикации и до ответа не создаёт повторного эффекта/сообщения. Незавершённый intent виден диагностике; ложного «отправлено» нет. Не обещать транзакцию между Git и WAL без такого журнала.

Обычные task/context payload не смешивать с техническими effect-полями. Исторический текст неизменяем; новая версия контекста/задания — отдельное сообщение с явной заменой предыдущей версии в том же разрешённом scope. Изменение критериев вне утверждённой задачи требует изменения плана, а не текста сообщения.

## Готовность и автоматический запуск

Путь: Start → Kit assignment/worktree → backend page → DOM-bootstrap E → постоянная identity разговора → регистрация → mount/SDK/binding → окончание bootstrap → service ready O → O task → рабочий ход E.

Каждое условие проверять отдельно. Загруженная страница и composer не равны готовности SDK, успешный workflow_pilot_panel не равен живой панели. Фоновые страницы должны пройти этот путь без выбора карточки, показа окна, фокуса или пользовательского клика.

Расследовать фактическую задержку 0.5.7 на контуре SessionRuntimes/ContextSession/experience/observer/native page. Добавить причины ожидания и события переходов для всех E, включая невидимые. Воспроизвести отсутствие выбранной страницы в изолированном Electron/backend fixture; устранять доказанную причину. Не считать вызов select/show скрытой «автоматизацией» пользовательского клика и не открывать окна агентом.

Подготовка до отправки допускает ограниченное восстановление на изменении реальной readiness. Уже начатая DOM-отправка sending/sent/unknown не повторяется. Внешняя временная lifecycle-занятость и собственная общая подготовка сохраняют исправления 0.5.7. Поздний callback после Stop/удаления/смены поколения не запускает E. Старое пустое представление панели из истории не доказывает текущую SDK-сессию.

## Ходы и доставка без видимой пользовательской реплики

Для каждого получателя хранить текущую обработку входящего сообщения. После SDK accepted и явного read адресат выполняет действие, отправляет нужные исходящие сообщения, вызывает workflow_assignment_yield для обработанных входящих и заканчивает ответ. `yield` принимает только прочитанные сообщения текущей доставки/попытки; повтор безопасен, чужое/непрочитанное/устаревшее сообщение отвергается.

Исходящие сообщения агента разрешены во время его собственного хода, иначе E не сможет спросить O, а O выдать задачу. Gate ограничивает новое входящее пробуждение адресата, не его исходящую очередь. Вопрос не удерживает отправителя в физически занятом состоянии до получения ответа: после yield и окончания хода он доступен для clarification/decision. Бизнес-состояние «ожидает ответа» сохраняется отдельно.

Освобождение transport gate требует коррелированного yield и безопасного завершения физического хода после начала текущей доставки. Backend наблюдает idle/not busy, отсутствие отправки/активных локальных команд и актуальную identity; не требует роста userMessagesRevision или появления обычной пользовательской реплики. Ранний yield при продолжающемся ответе не открывает вход. Старый idle-снимок до вызова SDK не открывает вход: observer должен подтвердить состояние после текущей доставки/квитанции. Предусмотреть заключительный текст после yield; отсутствие наблюдаемого завершения означает диагностируемое ожидание, не запуск поверх работающего агента.

Если хост не даёт достаточного события завершения, backend делает ограниченную read-only сверку страницы через существующий observer. Такая сверка не запускает модель и не отправляет текст. Она привязана к одному незавершённому gate, останавливается при разрешении/отмене и не превращается в бессрочный таймер генераций. Тайм-аут сообщает техническую причину; сам по себе не доказывает остановку или разрешение новой доставки.

Для O сериализовать входящие пробуждения. Пока O обрабатывает E1, результат E2 сохраняется; после завершения хода автоматически доставляется следующий. Нет зависимости E2 от ответа E1, кроме явных зависимостей плана/общего ресурса. Для одного получателя FIFO; ответы связаны с конкретным вопросом/назначением, а не «последним сообщением вообще».

Завершение обработки входящего task фиксируется yield при отправке question/result. Ответ на вопрос приходит отдельным входящим сообщением, которое само получает read/yield; не держать исходный task в очереди до окончательного DONE и не создавать циклическую блокировку. Один O способен выдать несколько заданий в одном ходе и завершить все прочитанные service ready сообщения одной квитанцией со списком message_id.

Получение SDK accepted не равно доставке модели/чтению. При неизвестном исходе SDK сохранить UNKNOWN и запретить слепой повтор. Наблюдение read/yield по тому же message_id может уточнить UNKNOWN без повторной отправки. Когда фактов недостаточно, показать неопределённость; отсутствие живой панели не включает DOM fallback.

## Разрешения, пауза и восстановление

Разрешение связано с одним scope и поколением. Оно действует пока план выполняется; короткий SDK lease служит только проверке живого экземпляра. При обычной работе никаких пользовательских продлений. Закрытие клиентского окна не отзывает разрешение и не останавливает backend.

Пауза/Stop запрещают новые назначения, входящие пробуждения и интеграции; уже принятый хостом запрос не отменяется задним числом. Активный E может безопасно сохранить результат/вопрос как outbox pending без нового пробуждения. Continue выдаёт актуальное поколение и продолжает очередь без повторного задания. Подтверждения для старой попытки не применяются к новой. Изменение заголовка/просмотр sidebar не меняют адресата.

После restart сохраняются назначения, контекст, сообщения, корреляции, result/acceptance и незавершённые операции. По текущему контракту пользователь один раз нажимает Continue после перезапуска службы; затем индивидуальных Enable/ID нет. Если startup отправлен, существующий чат восстанавливается без повторного DOM-bootstrap. Неизвестный адрес/исход не разрешает создавать дубль. При пересоздании панели используется актуальный content-addressed ресурс; ошибка старой панели должна назвать требуемое действие без ложной готовности.

Отсутствие панели или отключение SDK во время плана сохраняет очередь. Проверенные recovery-уведомления идут через доступный рабочий канал; если он недоступен, UI сообщает технический блокер без скрытой DOM-подмены. Возможность самого ChatGPT восстановить iframe в закрытом/открытом чате остаётся живой проверкой, её нельзя объявлять гарантированной по fixtures.

Удаление/убрать проект продолжают работать при незавершённом плане, dirty worktree, UNKNOWN и pending intent. Действующие собственные операции прекращаются, права отзываются, поздние ответы не возвращают удалённый проект. Соседние проекты, общий backend и donor не затрагиваются.

## Интерфейс и диагностика

Каждая карточка показывает задачу и конкретного E, затем одну фактическую стадию: подготовка страницы, bootstrap, ожидание панели/SDK, ожидание задания O, работа, вопрос O, ожидание уточнения/решения, результат отправлен, проверка O, доработка, интеграция, завершено или конкретная ошибка. Две одинаковые надписи допустимы при одинаковой реальной стадии, но не скрывают разных исполнителей/причин ожидания.

Панель O показывает входящие и исходящие сообщения всех своих назначений, авторов и адресатов, задачу, связанные вопросы/результаты и отдельные persisted/accepted/read/handled. E видит собственный диалог с O. Содержательное авторство O/E отличается от backend-событий. Пользователь понимает, где ожидается действие и от кого; отдельные ручные кнопки запуска E/Enable не добавляются.

Диагностика фоновых сессий не зависит от выбора карточки: этап, причина ожидания, версия панели/протокола, generation, message/assignment/attempt correlation, SDK invocation/result, receipt, физическое завершение, Kit proof/acceptance/integration. Экспорт — последовательный снимок с фиксированным through_seq, страничным продолжением и явными пробелами/тайм-аутами. Client telemetry gap не объявляется потерей серверных событий. Секреты, enrollment tickets, bearer/raw host metadata в логи не выводятся; чтение контекста ограничено адресатом.

## Обязательные автоматические проверки

Проверять через реальные входы API/CLI/Start, Control, Execution adapters, очередь, staged HTML/SDK/MCP, Kit и Git. Физический ChatGPT/модель заменяются только на обозначенной границе fixture. Не выдавать искусственный userMessagesRevision++ за поведение SDK. Без модельных команд и записи в рабочие профили.

1. Два и пять E: один Start, невидимые страницы, ни одного select/show; минимальный DOM-bootstrap, автоматические панели, service ready O, отдельные O-authored tasks и адресный контекст. Проверить shared runtime contention и независимость выбранного sidebar.
2. Контекст: O получает полный recovery как прежде; E через DOM получает только правила/identity/bootstrap. В task и последующих чтениях отсутствует ненужный контекст соседа/всего проекта. Большой выбранный контекст читается всеми частями, недоступный/подменённый digest даёт ошибку, не обрезку.
3. Недостающие данные до task:start; блокировка после старта; E question → O clarification → E facts → O decision/context → E продолжает. Одна и та же блокировка, уточнения не снимают её и не исчерпывают попытки, без участия пользователя. Общая среда имеет одного владельца.
4. Два результата во время занятого O: адресация/авторство, FIFO, автоматическое второе пробуждение, отсутствие циклического gate. SDK без нового user bubble/turn ID; ранний yield, финальный текст после yield, старый idle, delayed observer, disconnect, read-after-UNKNOWN. Повтор не создаёт новый ход.
5. Реальные commits → E result → O проверка → acceptance → O integration → DONE main. Без result/acceptance merge не начинается в новом режиме. Поддельный/устаревший commit, грязный worktree, pending transaction, новый SHA после acceptance, два параллельных merge, конфликт/check failure и restart/continue сохраняют доказательства.
6. Revision_request до интеграции: новая попытка, сохранение старого commit/proof, новый result/acceptance; позднее решение старой попытке отвергнуто. После интеграции — новая корректирующая задача. DOCS только после зависимостей; delivery после DOCS; канал остаётся до итоговой обработки O.
7. Fault injection до/после каждой записи intent/Kit/WAL/receipt, crash/restart, дубли, неверный scope/получатель, закрытая панель, busy/draft, Stop/Continue, отмена/удаление, чужие проекты. Нет повторов DOM/SDK UNKNOWN и ложного DONE.
8. Upgrade/legacy: новый план, активный старый, READY E без отчёта, уже integrated E, старый iframe/resource, миграция при безопасной паузе, отказ при неопределённости и восстановление. Старые данные не переписываются ради теста.

Назначенные checks: unit-all, architecture, kit-check, electron-smoke, executor-channel, chatgpt-plugin, migration-compatibility и release-tooling по относящимся задачам. На macOS проверки адаптеров Windows/Linux остаются fixtures. Ролевые инструкции проверяются по фактическому каталогу MCP, startup и recovery, не только наличию строки в одном файле.

## Живые опыты после отдельной реализации и выпуска

Все результаты записывать отдельно от fixtures: версия приложения/Kit/панели и URI, workspace/scope, начало/конец, граница журнала, фактические действия пользователя, DOM и SDK раздельно. Нужные идентификаторы собирает система, пользователь их не переносит.

A. Два E и контекст. Пользователь обсуждает маленький двухмодульный проект без Review и нажимает Start один раз, остаётся в O, не посещает E. O выдаёт разные задачи/контекст; оба автоматически подключаются, работают, отправляют result; O интегрирует и доводит DOCS/итог. PASS требует весь цикл, не только двух чистых коммитов.

B. Диалог. В спецификации тестового задания явно предусмотрено, что один E получает от O дополнительное правило только по запросу. E обнаруживает нехватку, спрашивает; O уточняет деталь, E отвечает; O передаёт решение; E продолжает и присылает результат. Второй E независимо заканчивает. Обычная разрешённая проблема окружения проверяется отдельной веткой с сохранением состояния. Пользователь не пишет «продолжай» и не переносит ответы.

C. Доработка. O обоснованно возвращает результат до слияния; E выполняет новую разрешённую попытку и отправляет новый result. Только актуальная acceptance допускает интеграцию. Один зависимый пункт запускается после обеих интеграций.

D. Несколько E и фон. Четыре-пять адресатов, встречные сообщения и занятый O; закрыть только клиентское окно при живом backend, затем открыть и сопоставить события. Отдельно restart → один Continue; отдельно Stop, UNKNOWN и удаление незавершённого проекта. Не объединять подтверждения разных опытов в общий PASS.

Любое ручное открытие E/панели, Enable, копирование ID, рабочее DOM-сообщение после bootstrap, backend-авторство содержательного task/result или автоматический merge без O — FAIL целевого сценария. Хостовое обязательное подтверждение отдельно фиксируется как ограничение автономности, а не обходится.

## Выполнение и поставка будущего плана

Последовательные области: контракт Kit и доказательства → рабочий model API/адресация → обработка ходов → автоматический минимальный bootstrap → канонические роли/контекст → управление заданиями/приёмкой/интеграциями O → блокировки и доработка → восстановление/совместимость → интерфейс/диагностика → сквозные регрессии и версия. Конкретные файлы, checks и зависимости заданы в to-do. Review проверяет обе части и полный нормализованный план.

DOCS перед сборкой сверяет действующие контракты, переносит выпущенное содержание этих спецификаций в modules и удаляет временные документы с точными Git blob-ссылками для required context. Невыполненные смежные follow-up сохраняются. Каждый документ не более 28000 байт UTF-8; исключение — текущий to-do.

Delivery: RELEASE — комплект macOS arm64/Windows x64/Linux x64 из одного sourceCommit; INSTALL — штатная доставка готового проверенного macOS bundle, включая /Applications/Workflow Pilot.app, без пересборки/переподписи; PUBLISH — GitHub Release с полным комплектом/digests. Перед каждой production/Kit сборкой очистить только проверенные Python-кэши tools/codex-app-server-mcp без перехода по симлинкам, Python запускать -B. Номер следующего выпуска проверить перед изменением; old tags не перезаписывать. Не закрывать окно и не останавливать службу: installer при работающем backend оставляет проверенный pending, переключает пользователь.

Сейчас подготовка плана не запускает T001, модели исполнителей, сборку или публикацию релиза. Успешное Review означает согласованность плана; живую приёмку A–D выполняет пользователь после поставки. Donor, VPS, аккаунты и cookies вне scope.
