# Диалог O/E: надёжность, переход и приёмка

Обязательная часть [спецификации](orchestrator-owned-dialogue.md), scope `orchestrator-owned-dialogue-refactor`.

## Источники состояния и границы

IO проходит через Execution, frontend — API/contracts. SessionRuntimes, ParallelExecution, DialogueDelivery, PluginCommunication и Kit сохраняют существующие границы без второго scheduler/плана. Kit хранит работу/proof, WAL — сообщения/контекст/receipts, UI — их проекцию. persisted/accepted/read/handled, result и INTEGRATED/DONE различаются.

Для сообщения с эффектом Kit (блокировка, решение, разрешение задания, result/acceptance/новая попытка) использовать сохраняемое намерение и единый operation/idempotency ID. Порядок: сохранить неподлежащий доставке intent с payload → выполнить/проверить эффект Kit с тем же ID → зафиксировать готовое сообщение в WAL → разрешить SDK-доставку. После сбоя reconciliation проверяет Kit и продолжает ту же операцию. Сбой до эффекта, после Kit и до публикации, после публикации и до ответа не создаёт повторного эффекта/сообщения. Незавершённый intent виден диагностике; ложного «отправлено» нет. Не обещать транзакцию между Git и WAL без такого журнала.

Payload task/context отделён от effect-полей. История неизменяема; новая версия явно заменяет прежнюю отдельным сообщением. Изменение критериев вне задачи требует изменения плана.

## Готовность и автоматический запуск

Путь: Start → assignment/worktree → page → DOM-bootstrap → identity/регистрация → mount/SDK/binding → конец bootstrap → ready O → O task → E. Условия проверяются отдельно без select/show/focus. Composer, вызов панели и старое представление из истории не доказывают живой SDK.

Задержку 0.5.7 исследовать через настоящие SessionRuntimes/ContextSession/experience/observer/native page в изолированном Electron/backend fixture. Причины ожидания и переходы невидимых E должны наблюдаться. Устранять воспроизведённую причину без открытия окон агентом. Ограниченное восстановление до Send зависит от реальной readiness; sending/sent/unknown не повторяются. Сохранить исправления общей подготовки/lifecycle 0.5.7; поздние callbacks после Stop/удаления/смены поколения не запускают E.

## Ходы и доставка без видимой пользовательской реплики

Каждый получатель хранит текущую обработку: SDK accepted → read → действие/исходящие → workflow_assignment_yield → конец ответа. Yield идемпотентен для собственных прочитанных сообщений текущей доставки/попытки, отвергает чужие/непрочитанные/устаревшие. Входящий gate не запрещает исходящие. После question/yield/конца хода разрешена clarification/decision; бизнес-ожидание ответа отдельно.

Освобождение transport gate требует коррелированного yield и безопасного завершения физического хода после начала текущей доставки. Backend наблюдает idle/not busy, отсутствие отправки/активных локальных команд и актуальную identity; не требует роста userMessagesRevision или появления обычной пользовательской реплики. Ранний yield при продолжающемся ответе не открывает вход. Старый idle-снимок до вызова SDK не открывает вход: observer должен подтвердить состояние после текущей доставки/квитанции. Предусмотреть заключительный текст после yield; отсутствие наблюдаемого завершения означает диагностируемое ожидание, не запуск поверх работающего агента.

При недостаточном событии завершения backend ограниченно сверяет текущий gate через read-only observer, без модели/отправки. Сверка прекращается при разрешении/отмене; тайм-аут диагностирует ожидание, не разрешает доставку.

FIFO O сохраняет E2 до конца обработки E1; другие зависимости — только план/общие ресурсы. Ответ связан с вопросом/назначением. Yield task при question/result освобождает транспорт до DONE; отдельный ответ получает собственный read/yield. O может выдать несколько задач за ход и подтвердить прочитанные ready списком message_id.

SDK accepted не доказывает чтение. UNKNOWN запрещает resend; read/yield того же ID может уточнить исход. Недостаток фактов показывается как неопределённость, отсутствие панели не включает DOM fallback.

## Разрешения, пауза и восстановление

Разрешение относится к scope/поколению и действует при выполнении плана без пользовательских продлений; SDK lease проверяет живой экземпляр. Закрытие клиента не отзывает разрешение и не останавливает backend.

Пауза/Stop запрещают новые назначения, входящие пробуждения и интеграции; уже принятый хостом запрос не отменяется задним числом. Активный E может безопасно сохранить результат/вопрос как outbox pending без нового пробуждения. Continue выдаёт актуальное поколение и продолжает очередь без повторного задания. Подтверждения для старой попытки не применяются к новой. Изменение заголовка/просмотр sidebar не меняют адресата.

Restart сохраняет назначения, контекст, сообщения/корреляции, result/acceptance и операции; один Continue без Enable/ID. Отправленный bootstrap и неизвестный исход/адрес не повторяются. Новая панель использует content-addressed ресурс, старая сообщает несовместимость. Без SDK очередь сохраняется, UI показывает блокер без DOM fallback; восстановление iframe ChatGPT проверяется живьём.

Удаление/убрать проект продолжают работать при незавершённом плане, dirty worktree, UNKNOWN и pending intent. Действующие собственные операции прекращаются, права отзываются, поздние ответы не возвращают удалённый проект. Соседние проекты, общий backend и donor не затрагиваются.

## Интерфейс и диагностика

Карточка различает задачу/E и фактическую стадию: страница, bootstrap, панель/SDK, задание O, работа, вопрос, уточнение/решение, result, проверка O, доработка, интеграция, завершение/ошибка. Одинаковая стадия не скрывает identity/причину ожидания. O видит свои входящие/исходящие по всем E; E — собственный диалог. Показаны автор/адресат, задача, корреляция и persisted/accepted/read/handled; backend-события отделены от авторства O/E. Новых кнопок запуска E/Enable нет.

Диагностика фоновых сессий не зависит от выбора карточки: этап, причина ожидания, версия панели/протокола, generation, message/assignment/attempt correlation, SDK invocation/result, receipt, физическое завершение, Kit proof/acceptance/integration. Экспорт — последовательный снимок с фиксированным through_seq, страничным продолжением и явными пробелами/тайм-аутами. Client telemetry gap не объявляется потерей серверных событий. Секреты, enrollment tickets, bearer/raw host metadata в логи не выводятся; чтение контекста ограничено адресатом.

## Обязательные автоматические проверки

Проверять через реальные входы API/CLI/Start, Control, Execution adapters, очередь, staged HTML/SDK/MCP, Kit и Git. Физический ChatGPT/модель заменяются только на обозначенной границе fixture. Не выдавать искусственный userMessagesRevision++ за поведение SDK. Без модельных команд и записи в рабочие профили.

1. Два и пять E: один Start, невидимые страницы, ни одного select/show; минимальный DOM-bootstrap, автоматические панели, service ready O, отдельные O-authored tasks и адресный контекст. Проверить shared runtime contention и независимость выбранного sidebar.
2. Контекст: O получает полный recovery как прежде; E через DOM получает только правила/identity/bootstrap. В task и последующих чтениях отсутствует ненужный контекст соседа/всего проекта. Большой выбранный контекст читается всеми частями, недоступный/подменённый digest даёт ошибку, не обрезку.
3. Недостающие данные до task:start; блокировка после старта; E question → O clarification → E facts → O decision/context → E продолжает. Одна и та же блокировка, уточнения не снимают её и не исчерпывают попытки, без участия пользователя. Общая среда имеет одного владельца.
4. Два результата во время занятого O: адресация/авторство, FIFO, автоматическое второе пробуждение, отсутствие циклического gate. SDK без нового user bubble/turn ID; ранний yield, финальный текст после yield, старый idle, delayed observer, disconnect, read-after-UNKNOWN. Повтор не создаёт новый ход.
5. Реальные commits → E result → O проверка → acceptance → O integration → DONE main. Без result/acceptance merge не начинается в новом режиме. Поддельный/устаревший commit, грязный worktree, pending transaction, новый SHA после acceptance, два параллельных merge, конфликт/check failure и restart/continue сохраняют доказательства.
6. Revision_request до интеграции: новая попытка, сохранение старого commit/proof, новый result/acceptance; позднее решение старой попытке отвергнуто. После интеграции — новая корректирующая задача. DOCS только после зависимостей; delivery после DOCS; канал остаётся до итоговой обработки O.
7. Fault injection до/после каждой записи intent/Kit/WAL/receipt, crash/restart, дубли, неверный scope/получатель, закрытая панель, busy/draft, Stop/Continue, отмена/удаление, чужие проекты. Нет повторов DOM/SDK UNKNOWN и ложного DONE.
8. Upgrade/legacy: новый план, активный старый, READY E без отчёта, уже integrated E, старый iframe/resource, миграция при безопасной паузе, отказ при неопределённости и восстановление. Старые данные не переписываются ради теста.

Назначенные checks: unit-all, architecture, kit-check, electron-smoke, executor-channel, chatgpt-plugin, migration-compatibility и release-tooling по относящимся задачам. На macOS проверки адаптеров Windows/Linux остаются fixtures. Ролевые инструкции проверяются по фактическому каталогу MCP, startup и recovery, не только наличию строки в одном файле.

## Живые опыты после отдельной реализации и выпуска

Все результаты записывать отдельно от fixtures: версия приложения/Kit/панели и URI, workspace/scope, начало/конец, граница журнала, фактические действия пользователя, DOM и SDK раздельно. Нужные идентификаторы собирает система, пользователь их не переносит.

A. Два E и контекст. Пользователь обсуждает маленький двухмодульный проект без Review и нажимает Start один раз, остаётся в O, не посещает E. O выдаёт разные задачи/контекст; оба автоматически подключаются, работают, отправляют result; O интегрирует и доводит DOCS/итог. PASS требует весь цикл, не только двух чистых коммитов.

B. Диалог. В спецификации тестового задания явно предусмотрено, что один E получает от O дополнительное правило только по запросу. E обнаруживает нехватку, спрашивает; O уточняет деталь, E отвечает; O передаёт решение; E продолжает и присылает результат. Второй E независимо заканчивает. Обычная разрешённая проблема окружения проверяется отдельной веткой с сохранением состояния. Пользователь не пишет «продолжай» и не переносит ответы.

C. Доработка. O обоснованно возвращает результат до слияния; E выполняет новую разрешённую попытку и отправляет новый result. Только актуальная acceptance допускает интеграцию. Один зависимый пункт запускается после обеих интеграций.

D. Несколько E и фон. Четыре-пять адресатов, встречные сообщения и занятый O; закрыть только клиентское окно при живом backend, затем открыть и сопоставить события. Отдельно restart → один Continue; отдельно Stop, UNKNOWN и удаление незавершённого проекта. Не объединять подтверждения разных опытов в общий PASS.

Любое ручное открытие E/панели, Enable, копирование ID, рабочее DOM-сообщение после bootstrap, backend-авторство содержательного task/result или автоматический merge без O — FAIL целевого сценария. Хостовое обязательное подтверждение отдельно фиксируется как ограничение автономности, а не обходится.
