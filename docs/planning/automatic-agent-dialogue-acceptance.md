# Проверка автоматического подключения и разрешения блокировок

Часть спецификации [автоматического диалога](automatic-agent-dialogue.md). Исходное состояние всех новых живых сценариев — NOT_RUN. Приёмка относится к встроенному Workflow Pilot, к фактическим версиям приложения/панели/backend/Kit. Chrome, другие клиенты, сон компьютера и работа при выключенной службе не подразумеваются.

## 1. Главный критерий

Пользователь создаёт проектную сессию, получает автоматически открытую панель оркестратора, обсуждает и публикует план, затем нажимает «Начать выполнение плана». Дальше не открывает чаты/панели исполнителей, не подключает каждому плагин вручную, не копирует идентификаторы, не нажимает Enable и не отправляет «продолжай». Работа даёт файлы, проверенные коммиты и интеграции, а не только текстовый ответ.

Наличие ручного действия для регистрации/связи означает FAIL автоматизации соответствующего сценария. Пользовательские разрешения, потребованные самим ChatGPT, фиксировать отдельно: их не обходить и не скрывать общим PASS. Первичная настройка самого подключения Workflow Pilot/входа в ChatGPT выполняется до сценария; отдельная настройка каждого нового чата не входит в допустимые предварительные условия.

## 2. Изолированные автоматические проверки

- Настоящие staged HTML, SDK, Python MCP, Control/Execution и Kit CLI/Git; никаких живых модельных команд. Поддержать Chat-исполнителей и оркестратора Chat/Work. Начало проверять через существующие пользовательские входы контекста и кнопки плана.
- Bootstrap до scope; публикация без запуска; два/пять приглашений; один оркестратор, несколько исполнителей; уже используемая/чужая identity; копия/просроченное приглашение; потерянный ответ; повтор регистрации; новый panel_instance; смена scope/назначения; одновременно открытые старые панели. Нет лишней external-сессии и регистрации по sidebar/URL.
- Гонка первой загрузки: ответ MCP раньше SDK, SDK до конца модельного хода, задержка/ошибка handshake, mount после возврата в чат. До готовности рабочий Send не происходит; восстановление не повторяет стартовый контекст и не создаёт модельный опрос. Исторические tool-result не управляют актуальным разрешением.
- Один Start разрешает все назначения, включая последующие в этом плане; время больше 30 минут не обрывает работу. Пауза/Stop/архив, безопасная остановка заблокированного назначения, завершение/финальный ход, restart с одним Continue, поздний Enable/Stop и замена исполнителя. Нет наследования разрешения следующим scope.
- Сигнал Kit → долговечное событие канала → чтение → решение → продолжение: обрыв между записями, duplicate/conflict, неизвестный исход Send, потеря claim/report, явное SDK rejection. Нет повторной работы и DOM-дубля. Ответ на предыдущую блокировку не снимает следующую. Чужое назначение/план не получает решение.
- Пять отправителей → один оркестратор: правильные labels/task/assignment, последовательная доставка, сохранение сообщений пока адресат занят или имеет черновик. Наблюдение событий страницы не подменять вызовами модели.
- Регрессии действующей оркестрации: max_workers, последовательные барьеры, worktree cleanup, Review, finalization/delivery, legacy-маршрут, основные сайдбары и общий MCP-каталог. Старый журнал опыта и его экспорт доступны; неизвестный новый формат блокируется явно.
- Согласованность реально доставляемых инструкций: startupMessage, role recovery, шаблоны, MCP startupRules/tool descriptions и ошибки. Bootstrap не конфликтует с запретом MCP в первом ответе; исполнитель после task:block ждёт адресное решение, а после commit не берёт чужую задачу.

Обязательные проверки назначаются микрозадачам: unit-all, architecture, executor-channel; electron-smoke на интеграции UI/жизненного цикла; kit-check на изменении Kit и итоговом этапе. Отдельный повтор уже пройденного не нужен без относящихся изменений. Сбой любой обязательной проверки исправляется до DONE.

### Проверки контрактов и промежуточных коммитов

До готовности доставки в T003 новый режим подключения не включается по умолчанию. T002 сохраняет legacy-маршрут действующих планов и проверяет новый bootstrap изолированно; выбор маршрута записывается в состоянии плана. Каждый промежуточный коммит проходит прежние проверки без ослабления assertions и без исполнителя, навсегда ожидающего первого поручения.

Для оркестратора отдельно проверить bootstrap и доставку в Chat и Work при Chat-исполнителях. Неподдерживаемый режим хоста отображается как конкретное препятствие. Контекст сверх лимита тела уведомления передаётся проверенной ссылкой и читается через MCP: тесты проверяют полный текст без обрезания, принадлежность участнику/назначению и отказ чужой identity. Это относится также к финальным и delivery-поручениям.

Регистрация расширенным workflow_pilot_panel изменяет состояние: readOnlyHint должен быть false, остальные annotations должны соответствовать фактическому контракту. Экспериментальные join/probe сохраняются только для legacy-запусков; backend отклоняет их применение к рабочему плану. Описания каталога явно разделяют этот режим и автоматическую регистрацию. Recover остаётся чтением актуального состояния; отдельный ручной enable не является шагом рабочего сценария. Executor-channel проверяет новый каталог и hints без исключения неудобных проверок. Обязательное подтверждение ChatGPT для нового чата записывается в S1 отдельным фактом и означает FAIL автоматизации; разрешения хоста не обходятся.

Смысловые изменения исходных инструкций Kit (WORKFLOW.md, PROTOTYPE.md) заканчиваются в T004/T006. DOCS сверяет их согласованность и может исправить ссылки; если эти исходники изменены после T006, до RELEASE повторяются unit-all и kit-check с сохранением результатов. В DOCS также сверяются docs/acceptance/orchestrated-execution.md и docs/modules/execution.md: корреляция блокировок, автоматическое продолжение, парковка при паузе и граница Execution должны соответствовать реализации.

## 3. Живой минимальный план с тремя назначениями

Среда: отдельный Workflow_Pilot_Plugin_Communication_Experiment либо новый изолированный тестовый репозиторий внутри него, без изменения продуктового checkout и старого run probe-20261018-1748. Пользователь запускает опыт; разработчик готовит инструкции и файлы теста, но не управляет мышью/клавиатурой и не инициирует модели при автоматических проверках.

Перед опытом записать точные version/build/protocol/sourceCommit/Kit, наличие действующей службы, новый project/scope, соответствие ролей и время. Использовать новые разговоры без заранее настроенных панелей исполнителей. Оркестратор имеет обычный проектный startup и автоматически открывает свою панель. Снимок экспериментального плана разрешает два параллельных исполнителя; третье назначение зависит от интеграции первых двух. Это настройки опыта, не разрешение делегировать реализацию основного scope.

### S1. Автоматическое создание двух исполнителей

Две независимые небольшие задачи работают с разными файлами, например форматирование строк и проверка входных данных. Каждая имеет содержательное задание, тесты и отдельный коммит. После одного Start приложение создаёт два назначения/worktree/Chat-разговора. Оба агента сами вызывают панель, регистрируются и получают рабочее уведомление после готовности.

PASS: два разных проверенных назначения и разговора, обе панели готовы без пользовательского открытия, работа началась, маршрутизация не зависит от выбранного sidebar. Если подключение плагина/монтирование требует визита пользователя — FAIL, дальнейший успех обмена не исправляет этот результат. Сначала подтвердить S1, затем делать выводы по остальным сценариям.

### S2. Разрешение блокировки и продолжение без пользователя

В одной из задач предусмотреть реальный разрешимый сбой окружения или тестовой локальной зависимости. Исполнитель сначала пытается исправить его в разрешённых границах. Чтобы проверить именно диалог, условие сценария содержит решение, доступное оркестратору из полного задания, но не исполнителю: например выбор из двух допустимых локальных пакетов, который нельзя угадывать. Не создавать скрытых повреждений, не трогать глобальную среду и не фабриковать ошибку в отчёте.

Исполнитель сохраняет состояние, сообщает фактическую проблему через task:block и завершает ход. Оркестратор автоматически получает точный вопрос, исследует причину и отвечает конкретным решением по block_id. Исполнитель получает уведомление, проверяет актуальность решения, продолжает ту же задачу, устраняет проблему, проходит тесты и делает commit --task. Другой исполнитель продолжает независимую работу. Если исправление выполняет сам оркестратор, отдельно подтвердить отсутствие одновременного владельца изменяемой среды.

PASS: пользователь не исправлял окружение и не продолжал агента; подтверждены вопрос/прочтение/решение/возобновление/проверки/коммит и интеграция. Сообщение «решение отправлено» без продолжения и результата не является PASS. Успех самостоятельного исправления исполнителем без вопроса полезен, но не засчитывает этот сценарий диалога.

### S3. Следующее назначение и корректное завершение

После проверенной интеграции первых двух задач создаётся третий исполнитель: небольшая итоговая функция использует результаты обеих предыдущих. Его панель регистрируется автоматически под тем же разрешением плана; новое пользовательское действие не требуется. Оркестратор получает его результат, штатно завершает проверки/интеграцию, необходимые DOCS и cleanup, выдаёт итог. Служебные назначения DOCS, если Kit их добавил, подчиняются тем же правилам и не подменяют третью содержательную задачу.

PASS: барьер зависимостей соблюдён, третий исполнитель подключён автоматически, общая проверка main прошла, обязательный итог доставлен до отключения связи; после завершения нет новых рабочих уведомлений и бесконечных подтверждений. При закрытии интерфейса пользователь фиксирует время; завершение обмена после закрытия и получение совершенно нового события после закрытия различаются в отчёте.

## 4. Доказательства и расширения

Для S1–S3: outcome PASS/FAIL/NOT_RUN, версии, список ручных действий (ожидается только обычная подготовка и один Start), project/scope, назначения/роли, времена событий, очищенный экспорт с фиксированной through_seq, коммиты и результаты проверок/интеграции. Отсутствующий экспорт/телеметрия ограничивает вывод; не придумывать события и причины. Read не означает выполненную задачу; accepted не означает read.

Автоматически обязательно проверить пять исполнителей. Живой запуск пяти, ответ занятому оркестратору, смена назначения, повторная блокировка, пауза/возобновление и перезагрузка с одной кнопкой Continue — следующая расширенная приёмка; S1–S3 не объявляют её пройденной. Сохранение привязки после restart и право возобновить работу проверяются раздельно.

Готовый выпуск и инструкции передаются пользователю после DOCS/RELEASE/INSTALL/PUBLISH. Пока живой отчёт не получен, итог разработки: «готово к проверке автоматического подключения и автономного продолжения», а не «автономность доказана». Дефекты идут в plan:extend по поручению пользователя; архив нового плана требует отдельной приёмки.
