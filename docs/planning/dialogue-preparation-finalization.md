# Подготовка поручений и завершение связи

Следующий раунд после 0.5.9: один Start, O готовит поручения одновременно с запуском E; отправка только после подтверждения канала. После DOCS, поставки, очистки и итоговых квитанций выполнение становится complete и «Пауза» исчезает. Приёмка пользователем остаётся отдельной. Разработка здесь одним агентом.

Сохраняются [контракт диалога](../modules/assignment-dialogue.md), [надёжность](../modules/assignment-dialogue-reliability.md), зависимости и доказательства Kit. Backend не выбирает контекст и не сочиняет задачи; рабочие сообщения идут через SDK без DOM fallback. Рабочие профили и живой тест не используются для экспериментов разработки.

## Основание

В Workflow_Pilot_Test01 на 0.5.9 интегрированы все 3 задачи, worktree и ветки очищены, но оставалась «Пауза». Последнее acceptance DOCS имело read/yield без reply_observed; повторялся ASSIGNMENT_CHANGED для observed, grant оставался running/active. Cleanup удаляет worktree, а finalize ждёт channelSettled: причинную гонку закрепить регрессией, не считать установленной только по корреляции.

DOCS 20.10.2026, Europe/Madrid: сессия 09:33:28 → ready 09:34:05 → O read 09:34:23 → task 09:35:08 → E read 09:35:29. До работы 121 с, интервал O read → task 45 с. Это интервалы событий, не чистое время генерации модели. Ускорение подтвердить новым опытом, без числового SLA по одному измерению.

## Параллельная подготовка

1. Scheduler закрепляет допустимое назначение и уведомляет O о подготовке до ожидания bootstrap. Подключение E продолжается независимо; уведомления допускают объединение и не дублируют работу.
2. O выбирает задачу и достаточный контекст, сохраняет долговечный черновик через модельный API. Текст, contexts и digest принадлежат O; привязка — project/scope/task/assignment/attempt и версия требований. Черновик не является сообщением E, task grant или SDK-вызовом.
3. После актуальных registration/binding/SDK и физического конца bootstrap O отправляет черновик по сохранённой ссылке. Ready может прийти до окончания подготовки: тогда отправка возможна в том же ходе. Backend повторно проверяет готовность и назначение перед эффектом; ранний send отклоняется без grant, текст сохраняется.
4. Далее существующий intent → Kit → WAL → SDK. Один ключ не создаёт второй эффект, UNKNOWN не повторяется. Backend не отправляет черновик без действия O, медленный E не задерживает соседей, ожидание не создаёт модельного polling. Использовать нынешние API/хранилища, без второго scheduler/плана.

Pause запрещает отправки/новые пробуждения, активный O может сохранить текст. Continue заново проверяет канал; restart требует общего Continue и не отправляет черновики автоматически. Изменение scope/назначения/попытки/требований запрещает прежнее поручение. Generation требует повторной проверки допуска, не потери текста. O сверяет использованные исходники; посторонний коммит не уничтожает все черновики.

DOCS и зависимые задачи готовятся одновременно с их запуском только после проверенных интеграций предшественников: итоговый контекст должен быть актуален.

## Завершение и очистка

Регрессия: последний acceptance → read/yield → ранняя cleanup → поздний observed. Проверить Kit, Control, runtime identity и итоговый вход O целиком.

Порядок: DONE/интеграции → последние квитанции и свежий физический конец E → delivery → cleanup/проверка O → итоговая обработка и физический конец O → долговечный complete и отзыв grant.

Cleanup откладывает удаление занятых назначений с точной причиной и автоматически продолжает запрос после доказанного завершения. Не допускать цикла ожиданий, фиктивных read/yield/observed или отключения identity/проверки активных команд.

Для уже очищенного назначения ограничить восстановление прежней завершающей квитанцией, её message/assignment/attempt/host identity и доказательством конца хода. Терминальная запись не разрешает новую работу, отправки или чужой контекст. Недостаток доказательств показывает причину ожидания, не complete и не бесконечный поток одинаковых denied.

Complete идемпотентен при restart/повторах/нескольких клиентах. Все DONE с незаконченной финализацией показываются как «Завершение» с причиной; остановка остаётся доступна. После complete нет активной «Паузы»/«Продолжить» этого запуска; карточка O, план и панель согласованы, scope остаётся READY_FOR_ACCEPTANCE. Косметическая замена кнопки не исправляет runtime.

## Инструкции, диагностика и приёмка

Согласовать role-protocol, startup/recovery, шаблоны, фактическую MCP-схему/описания и backend validation. Перечислить yield.reason: awaiting_reply, tasks_sent, result_sent, handled; объяснить выбор. Yield — обработка входа и конец хода, не DONE.

Журнал различает назначение, наблюдаемое начало/сохранение подготовки, готовность, отправку, SDK accepted/read, result/acceptance/integration, receipts/cleanup/complete. Корреляция без секретов и raw host metadata; не смешивать модель, доставку и Git, не выдавать метку вызова за начало скрытого рассуждения.

- Start для 2 и 5 E без открытия карточек: задержка bootstrap доказывает перекрытие подготовки; до ready нет grant/публикации E/SDK send, затем отправляется сохранённый текст.
- Ready до/после подготовки, занятый O, медленный E, дубли, stale attempt/identity, Pause/Continue, restart, удаление и UNKNOWN не создают повторных поручений.
- После двух интеграций автоматически запускаются DOCS и подготовка O; авторство и актуальный контекст подтверждены.
- Реальные Kit/Git/API в изолированном fixture проверяют последний result → acceptance → integration → receipts → cleanup → complete, раннюю очистку, поздний observed и уже удалённый worktree. Нет фиктивных квитанций и зависшего grant.
- Native/HTTP одинаково показывают 3/3 и завершение, без автоматической пользовательской приёмки. Restart сохраняет complete.
- MCP enum yield проверен фактическим вызовом; правильные значения проходят сразу, неверное даёт понятную ошибку. Старые планы и пакетная обработка результатов сохранены.
- Обязательны unit-all, architecture, обе kit-check/kit-assignments, executor-channel, chatgpt-plugin, electron-smoke и delivery-проверки. Фикстуры без моделей/рабочих профилей.
- После выпуска пользователь повторяет опыт без посещения карточек, сравнивает DOCS с базой 121 с и проверяет complete. Непройденная ветка question/clarification/decision отдельно, fixtures не означают живую приёмку.
