# Параллельная подготовка поручений и завершение связи

## Результат и границы

Следующий раунд после 0.5.9. Пользователь поручил добавить изменения в план; реализация и выпуск этим документом не объявляются начатыми. Разработка выполняется здесь одним агентом. Существующий scope и завершённые задачи сохраняются; автоматической приёмки или архивирования нет.

После Start оркестратор O готовит содержание поручений одновременно с механическим созданием и подключением исполнителей E. Отправляет только по подтверждённому каналу. После выполнения, интеграций, DOCS, предусмотренной поставки и итоговой обработки сообщений выполнение автоматически завершается: разрешение связи отозвано, кнопка «Пауза» отсутствует. Пользовательская приёмка scope остаётся отдельным действием.

Сохраняются один Start, адресный диалог, авторство O, минимальный bootstrap E, зависимости Kit и отсутствие рабочих DOM fallback. Бэкенд не придумывает задачи или контекст. Подготовка не вызывает task:start и не создаёт разрешение работы E.

## Основание

В живом тесте Workflow_Pilot_Test01 на 0.5.9 три задачи интегрированы, worktree и ветки очищены. Пользователь подтвердил 3/3 в интерфейсе, но кнопка оставалась «Пауза».

Для DOCS 20.10.2026 (Europe/Madrid): сессия создана в 09:33:28, ready сохранено в 09:34:05, прочитано O в 09:34:23, task сохранено в 09:35:08 и прочитано E в 09:35:29. До начала работы прошло около 121 секунды. Из них примерно 45 секунд между чтением ready и сохранением задания; это интервал событий, а не измерение чистого времени генерации модели. Ускорение необходимо подтвердить новым опытом, числовой SLA по одному тесту не устанавливается.

После DOCS acceptance были read и yield, но не было подтверждения физического завершения E. В журнале повторялось PLUGIN_COMMUNICATION_ASSIGNMENT_CHANGED для observed, а разрешение оставалось running/active. Код cleanup удаляет интегрированный worktree, тогда как finalize ждёт channelSettled. Это основание воспроизвести гонку очистки и последней квитанции; конкретную причинную цепочку закрепить регрессионным тестом до исправления. Успешная интеграция не равна завершению транспортной обработки.

## Подготовка одновременно с запуском

1. Start разрешает план. Существующий scheduler определяет допустимые назначения по зависимостям и лимиту E. После закрепления identity назначения, до ожидания bootstrap, сохраняется адресное служебное уведомление O о доступной подготовке. Подключение страниц продолжается независимо от хода O. Для нескольких назначений допускается объединённое уведомление; дубли не порождают повторную подготовку.
2. O читает требования и выбирает содержание задания и достаточные материалы каждого E. Подготовленное поручение сохраняется как собственный черновик O, доступный через модельный API после окончания хода. Черновик привязан к project/scope/task/assignment/attempt, версии требований и исходному состоянию. Сохраняются полный текст, выбранные contexts, digest и стабильный идентификатор операции. Это не опубликованное сообщение E, не task grant и не SDK-вызов.
3. Регистрация, привязка, SDK и физический конец bootstrap проверяются отдельно. Только их актуальное подтверждение означает готовность рабочего канала. Страница, карточка, сохранённый participant или старая readiness-квитанция недостаточны.
4. Получив ready, O отправляет ранее подготовленное поручение штатным рабочим API по ссылке на черновик. Если готовность наступила во время подготовки, O может отправить в том же ходе после проверки. Backend повторно проверяет канал и назначение непосредственно перед эффектом; ранняя отправка получает предметный отказ без grant и без доставки. Черновик остаётся пригодным для разрешённого повторного обращения.
5. После подтверждения выполняется существующий путь intent → Kit grant → WAL → SDK. Повторы одинакового ключа возвращают прежний результат; UNKNOWN не отправляется повторно. Backend не превращает черновик в отправку без действия O. Готовые E не ждут медленного соседа. Обычное ожидание не вызывает модельный polling.

Унифицировать контракт подготовить/отправить без параллельного универсального диспетчера. При реализации выбрать минимальное расширение существующего assignment API; схема и описание обязаны отличать черновик, сообщение и разрешение. Использовать нынешние хранилища Kit/WAL с явным владельцем каждого факта, не создавать второй план.

Pause запрещает отправку и новые пробуждения, уже активный O может сохранить подготовленный текст. Continue заново проверяет readiness и актуальность. Restart не отправляет черновик автоматически и сохраняет правило общего Continue. Смена назначения/попытки/требований или удаление проекта не позволяет отправить прежнее поручение. Изменение generation само по себе не теряет текст, но требует повторной проверки допуска. Изменившийся исходный код проверяется относительно использованных O источников; посторонний коммит не должен без причины уничтожать все черновики.

DOCS: подготовка начинается после подтверждённых интеграций предшественников одновременно с запуском DOCS E; до этого нельзя выдавать устаревшую итоговую документацию. Последующие зависимые задания также соблюдают доказательства интеграции.

## Завершение и очистка

Воспроизвести сценарий последнего acceptance: read → yield → ранняя assignment:cleanup → поздний observed. Проверить Kit, Control, runtime identity и финальный вход O вместе, а не только отображение кнопки.

Канонический порядок: проверенные DONE и нужные интеграции → обработка последних квитанций E и свежий физический конец их ходов → оставшиеся delivery → итоговая cleanup/проверка O → обработка итогового поручения и физический конец O → долговечный complete и отзыв разрешения связи.

Ранняя cleanup не должна уничтожать единственный источник подтверждения конца E. Штатная операция откладывает удаление занятых назначений с точной причиной; после действительного завершения автоматически продолжает тот же запрос без пользователя. Не создавать цикл, где завершение E ждёт удаления, а удаление ждёт новой работы E. Не подделывать read/yield/observed; не отключать проверку identity и активных команд.

Для уже очищенного назначения разделить проверку права на новую работу и обработку ранее разрешённой завершающей квитанции. Ограниченное восстановление возможно только для сохранённых message/assignment/attempt/host identity и доказанного конца хода. Tombstone/терминальная запись не разрешает новые команды, новые отправки или чтение чужого контекста. Если доказательств нет, показать конкретную причину ожидания; не объявлять complete и не создавать бесконечный поток одинаковых operation.denied.

Complete идемпотентен при restart, повторном callback и нескольких клиентах. Отдельно сохраняются выполнение плана, транспортное завершение и пользовательская приёмка. При всех DONE, но незаконченной финализации интерфейс показывает «Завершение» и причину. После complete нет активной «Паузы» или «Продолжить» завершённого запуска; 3/3, карточка O и панель согласованы. До complete штатная остановка остаётся доступна. Не скрывать зависание одной косметической заменой кнопки.

## Инструкции и наблюдаемость

Согласовать role-protocol, startup/recovery, шаблоны Kit, фактические MCP descriptions/schema и backend validation. Явно перечислить разрешённые yield.reason: awaiting_reply, tasks_sent, result_sent, handled; проверить enum и объяснить выбор. Yield означает обработку входа и завершение хода, не DONE.

Журнал различает назначение, начало/сохранение подготовки O, готовность канала, отправку, SDK accepted, E read, result, acceptance, интеграцию, квитанции, cleanup и complete. Все события коррелированы, без секретов и raw host metadata. Интервалы модели, доставки и Git не смешиваются. Метки начала подготовки фиксируют наблюдаемый вызов, не скрытое начало рассуждения модели.

## Приёмка

- Через Start два и пять E подключаются без выбора карточек. Управляемая задержка bootstrap доказывает перекрытие с подготовкой O; до ready нет task grant/публикации E/SDK send. После ready O отправляет сохранённый текст без повторного выбора полного контекста.
- Проверены ready до/после подготовки, занятый O, медленный E, дубли уведомлений, устаревшая попытка/identity, Pause/Continue, restart, удаление и UNKNOWN. Нет повторной задачи и рабочих DOM-вводов.
- Две интеграции автоматически запускают DOCS и подготовку его актуального поручения. Содержание остаётся авторством O, backend передаёт только служебные факты.
- Полный путь последний result → acceptance → integration → receipt → cleanup → finalization → complete проверен реальными Kit/Git/API в изолированном fixture. Отдельно воспроизведены ранняя cleanup, поздний observed и существующий очищенный worktree. Нет фиктивного observed и зависшего running grant.
- Native и HTTP клиенты показывают одинаковое завершение и 3/3, после complete кнопки запуска завершённого выполнения не активны; scope остаётся READY_FOR_ACCEPTANCE до приёмки пользователя.
- Фактическая MCP-схема перечисляет yield.reason; правильные значения проходят сразу, неверное получает понятную ошибку. Старые планы и доставка нескольких результатов не регрессируют.
- Полная проверка включает unit-all, architecture, kit-check и kit-assignments, executor-channel, chatgpt-plugin, electron-smoke; релизные проверки по delivery-задачам. Фикстуры не запускают модели и не меняют живой тест.
- После выпуска пользователь повторяет живой опыт без открытия карточек. Сравнить этапы DOCS с указанной базой, проверить автоматическое complete. Отдельная непроверенная ветка question/clarification/decision не объявляется принятой этим опытом.

## Поставка

После реализации отдельная DOCS переносит действующий контракт в модули и удаляет эту временную спецификацию с сохранением корректных Git-ссылок. Затем общий выпуск трёх ОС из одного sourceCommit, установка готового собственного macOS bundle и публикация GitHub. Перед production-сборкой очистка только генерируемых Python-кэшей по AGENTS.md. Работающую службу не останавливать; pending установку отличать от активной версии. Номер выпуска выбрать свободный при подготовке релиза.
