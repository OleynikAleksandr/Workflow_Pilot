# Повторная приёмка дефектов D001–D011

Цель Workflow Pilot 0.5.34 / Kit 1.10.0 / панель `0.5.34-communication-5` (протокол 5, роли 9): предсказуемый Start/Continue, подготовленные до Start поручения и одно место текущих сообщений. Источники — все три Desktop-журнала тестирования 0.5.33 от 25.10.2026, перенесённые в требования scope `release-0533-defects`. Исходные наблюдения и рабочие спецификации сохраняются в Git; четвёртого журнала и архивных копий нет.

**Автоматические проверки реализации выполнены через Kit. Новая живая приёмка всех строк ниже — NOT_RUN.** Реальные ChatGPT/аккаунт/SDK, macOS-окна/assistive technology, native Windows/Linux, iPad/Tailscale и живые тайминги автоматическими fixtures не подтверждаются. Пакеты, подпись, установка и GitHub подтверждаются отдельно RELEASE/INSTALL/PUBLISH, manifest и GitHub Release. DOCS с `verification_ids:[]` не перезапускает приложение и не создаёт PASS его проверок.

Канонические контракты: [текущие действия](../modules/current-actions.md), [ранние поручения](../modules/prepared-tasks.md), [исполнение](../modules/orchestrated-execution.md), [канал и надёжность](../modules/assignment-dialogue-reliability.md), [Chat-only startup](../modules/chat-only-startup.md). Невыполненные старые требования в остальных docs/planning сохраняются.

## Связный автоматический цикл

Тест `D001-D011 cycle` использует новый временный Git-проект, API Start/Continue, Control/Execution, файловые stores/WAL, настоящие Kit/Git и MCP/SDK adapters. Физический ChatGPT, модельные ответы и lifecycle-команды подставлены на обозначенной границе; модельные ходы и рабочие профили не запускаются.

1. До публикации сохраняются подготовленные T001/T002, зависимая T003 и DOCS. Проверяются выбранные байты/hash, не только краткий brief.
2. Остаются root/nested `.DS_Store`, добавляется настоящий тестовый пользовательский файл. Start и повторный Continue дают MAIN_DIRTY с его точным путём, без E и SDK-эффектов.
3. Удаляется только тестовый пользовательский файл; Finder metadata сохраняется. Один Continue создаёт ровно два независимых назначения.
4. Во время их работы истекает lease O. Панель восстанавливает актуальные sync/generation, не переписывая binding поздним callback и не повторяя Send.
5. Проходят task/context_request, question/clarification/facts/decision, revision, result, acceptance точного SHA и integration; затем T003, DOCS, terminal receipts, cleanup и complete.
6. Сверяются количество intent/SDK/назначений, проверенные SHA и отсутствие второго prepare/ready хода O для плановой подготовки. Закрытие scope этим не имитируется.

Отдельные fault fixtures покрывают сохранение/утрату структурированного STOPPED, потерю ответа sync/SDK, WAL и Kit→WAL, stale author/scope/attempt, pause/revoke, повтор Continue, restart до/после авторизации и поздние callbacks. UNKNOWN сохраняет запрет повтора. Настоящий child receipt watcher при подключении один раз сверяет текущее состояние, закрывая промежуток до первого fs.watch события; детерминированный тест доказывает отсутствие постоянного polling, 12 параллельных запусков F04 проверили реальную файловую замену.

## Повторный пользовательский опыт

Использовать новый одноразовый тестовый workspace, собственные папки/Git/назначения. Не изменять Workflow_Pilot, donor, Test_001, рабочие cookies/службы или чужой scope ради проверки. Никаких ручных ID/join/Enable, удаления WAL/transaction, reset/force или повторного неизвестного Send. Для restart/сетевых опытов нужна отдельная доказанно собственная служба; [границы опытов прерывания](interruption-recovery.md) сохраняются.

1. Подтвердить фактически работающую службу 0.5.34, проектный Kit 1.10.0 и **новую** панель с правильным build. Обновить инструменты коннектора и открыть панель заново; совпадение только протокола не доказывает свежий HTML. Не очищать профиль/историю.
2. Новый Chat получает одну короткую URL-команду с тикетом; полный контекст — панелью. Подтвердить все части/SHA. Проверить D001/D007 после повторного открытия: свой адрес сохранён, исторического успеха под сессией нет. Реальную ошибку и конфликт записать отдельно без перепривязки.
3. Передать задачу на две независимые микрозадачи, зависимую demo и DOCS, `release=false`. При обсуждении виден «Агент». До выбора режима нет плана слева. Выбор доступен в одном месте; после выбора оркестрации роль O меняется сразу, карточка нейтральна, затем уходит в историю по read.
4. Пока O готовит план, текущая строка говорит об этом. При запуске Review — рецензирование/Claude/действительный раунд, до запуска — ожидание. Слева Review не повторяет динамические сообщения. Подготовленные поручения всех задач/DOCS существуют до окончательного Review; публикация их не отправляет.
5. После публикации слева настоящий план и одна кнопка Start. Справа полная инструкция проверки/запуска, видимая при узкой панели. Прогнать обе темы, 320/480/900 CSS px и 100/200% текста, длинный ID. Проверить клавиатуру, focus после SSE и отсутствие ежесекундных объявлений таймера assistive technology.
6. В одноразовом проекте создать root/nested Finder metadata: она игнорируется installer-правилом. Добавить отдельный пользовательский файл. Start должен дать точную блокировку и «Продолжить», без назначения/Send. Повтор при dirty ничего не меняет. Убрать/зафиксировать только свои тестовые изменения, затем один Continue — два E, без нового хода O для написания поручений. Tracked изменения по-прежнему блокируют; ничего автоматически не коммитится и не удаляется.
7. При разрешённом отдельном опыте смены lease/generation проследить один status→sync→wait O и точные причины generation-mismatch/lease-expired/sdk-unavailable/plan-paused. Уже accepted сообщение остаётся ожиданием чтения, не превращается в «ещё не доставлено». E не ждёт поручение O бесконечно. Ручной Stop/пауза удерживаются; UNKNOWN не повторяется.
8. Проверить вопросы, результат/приёмку/интеграцию, зависимую задачу и DOCS. Различать сохранено, авторизовано, accepted, read, task:start, result, acceptance, main DONE и complete. Отдельно сравнить времена создания, принятия, read и yield; интервалы не называются скрытым рассуждением модели.
9. Закрыть/не подключать MCP-панель и открыть «Текущие действия» из приложения. Один доступный выбор, без новой модели. Native скрывает страницу, после закрытия возвращает тот же документ; HTTP без iframe тоже даёт ответить и возвращает изображение. Переключить сессии/проекты, проверить pending выбора соседа и CAS из двух клиентов. Реальный iPad/Tailscale проверяется отдельно.
10. После проверенных интеграций, DOCS, terminal receipts, cleanup и конца итогового ответа — complete и ожидание приёмки. Пользователь отдельно принимает результат и поручает закрыть scope. Архив проекта не означает приёмку плана.

## Запись результата

Для каждой строки D001–D011 записать PASS/FAIL/NOT_RUN, версию службы/Kit/панели, платформу/клиент, безопасную последовательность, фактический и ожидаемый результат, снимок/очищенные события при необходимости. Фиксировать project/scope/task/assignment/attempt, message ID, source/integration SHA и времена с зоной; ticket/q/raw metadata/секреты не собирать. Время ожидания канала отделять от очереди, подготовки и обработки модели.

Один успешный путь не закрывает отрицательные/восстановительные случаи. Фактическое отсутствие измерения не заменяется нулём. Недоступная native платформа остаётся NOT_RUN. Выпуск архивов и fixture PASS не являются пользовательской приёмкой; scope остаётся READY_FOR_ACCEPTANCE после всего плана, пока пользователь явно не примет его.
