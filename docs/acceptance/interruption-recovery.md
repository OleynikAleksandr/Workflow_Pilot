# Workflow Pilot — протокол живой проверки прерываний O/E

**Статус документа:** подготовлен для будущей ручной приёмки; **живые сценарии O1/O2/E1/E2/NET/UI/RESTART — NOT_RUN**.
**Область:** отдельный одноразовый orchestrated-проект, тестовые разговоры и собственные Git/Kit/WAL. Рабочие профили, общий backend и существующие проекты не участвуют.
**Основание:** [спецификация](../planning/recovery-and-interruption-2026-10.md), раздел II; канонический план — `.harness/plans/todo-plan.md`, scope `recovery-status-interruptions` (план разработки, **не** workspace испытаний).

Для 0.5.34 дополнительно действует [повторная приёмка D001–D011](release-0534-defects.md): ранние поручения, lease/generation, dirty Start/Continue и единая область внимания. Она не превращает прежние живые NOT_RUN в PASS.

## 1. Что доказано и чего пока не проверяли

В исходниках **автоматически выполнены** изолированные проверки на временных Git worktree и WAL:

- **O1/O2:** точный принятый SHA, тестовые прерывания Kit до создания merge-коммита и после него, восстановление без второго merge/acceptance;
- **E1:** checked commit до result, повторное открытие назначения без нового коммита;
- **E2:** актуальный `block_id`, отказ неверному ID, независимый сохранённый DONE;
- **NET/UNKNOWN:** потеря SDK-ответа моделируется без реального отключения сети, после восстановления WAL запрещены повторный claim/verify и второй `send.intent`.

Тесты: `tests/automatic-agent-dialogue.test.mjs`, `tests/fixtures/automatic-agent-dialogue.mjs`, `tests/plugin-communication-store.test.mjs`; коммит `b57306a`. **PASS фикстуры не означает PASS живого опыта**: ChatGPT, сеть и рабочий backend не испытывались. Все живые итоги первоначально **NOT_RUN**.

## 2. Безопасные предусловия — обязательны перед каждым сценарием

1. Использовать **новый одноразовый** проект, отдельный от `Workflow_Pilot`, `Workflow_Pilot_Test_07` и любых существующих пользовательских проектов. В плане: две независимые небольшие ES-module задачи, одна зависимая demo-задача, DOCS, `release=false`, без сборки/установки. Только тестовые данные, без внешних сервисов и необратимых действий. Для O/E требуется `execution_strategy=orchestrated`, `dialogue_version=1`. Фиксировать версию тестового приложения, Kit и commit до запуска.
2. Убедиться, что тестовый проект имеет **собственные** папку, Git worktree, сообщения и WAL; для RESTART — также **собственный backend profile/dataDir, identity и порт**. Если независимость не доказана, **NOT_RUN**, не пытаться «временно» остановить общую службу.
3. Сначала завершить создание плана, затем пользователь нажимает «Начать выполнение плана». Разделять кнопку плана **«Пауза/Продолжить»** (авторизация всего scope) и кнопку ChatGPT **Stop** (только текущая генерация). Команда `Продолжай` отправляется в **том же тестовом чате** только после проверки исхода; не создавать второй O, E, план или работу.
4. Сохранить исходную точку: время с часов тестового хоста и локальную зону, `scope_id`, `task_id`, `assignment_id`, `attempt`, `block_id` при наличии, **полный** `source_commit`, `result_id`, `acceptance`, `message_id`, `integration_commit` и Git HEAD. Секреты, содержимое сообщений и токены **не собирать**. Закрепить один Git baseline для сопоставления количества merge.
5. Перед нажатием Stop/offline/restart убедиться, что контрольная точка **подтверждена Kit или WAL**, а не только текстом модели/визуальным значком. Для изменения сети, повреждения контекста или разрыва IPC нет автоматического разрешения повторять эффект.
6. После каждого опыта отдельно проверить: Kit `DONE`, source/result/acceptance на **той же попытке** и SHA, ровно один integration commit на назначение, отсутствие нового назначения/второго Send, неизменность других проектов. Не удалять журналы, ветки или worktree до сохранения сверки. Очистка — только штатный Kit и только тестовых INTEGRATED-назначений.

**Остановка проверки:** не подтверждён SDK/merge/Kit, WAL неконсистентен, неизвестен backend или нет безопасной точки. В тестовом UI прекратить действия; при нарушении записать `FAIL`, без опыта — `NOT_RUN`. Запрещены повторный Send/acceptance, `git reset --hard`, `git worktree remove --force`, удаление `transaction.json` и обход Kit.

## 3. Команды сверки — **только в каталоге тестового main**

Все команды здесь **только для чтения**. Выполнять их в терминале одноразового checkout. Не подставлять путь рабочего `Workflow_Pilot`; при ошибке каталога прекратить сценарий.

```sh
# cd /ABSOLUTE/PATH/TO/ISOLATED-TEST-MAIN
./scripts/workflow status
./scripts/workflow validate
./scripts/workflow integration:status
git rev-parse HEAD
git status --porcelain=v1
git log --format='%h %s' -n 12
git worktree list --porcelain

# Для конкретного сохранённого назначения; заменить TEST_ASSIGNMENT_ID:
./scripts/workflow assignment:status --id TEST_ASSIGNMENT_ID
./scripts/workflow assignment:dialogue-status --id TEST_ASSIGNMENT_ID
# До cleanup и только если worktree ещё существует:
git -C /ABSOLUTE/PATH/TO/TEST-WORKTREE rev-parse HEAD
git -C /ABSOLUTE/PATH/TO/TEST-WORKTREE status --porcelain=v1
```

Записать `BASE` как фактический SHA исходного main. Для подсчёта merge-коммитов в **том же** тестовом main:

```sh
git rev-list --count --merges BASE_SHA..HEAD
git log --merges --format='%H %P %s' BASE_SHA..HEAD
```

Заменить `BASE_SHA` реальным baseline и сравнивать число/полные SHA **до и после одного сценария**. Появление другого служебного коммита Kit само по себе не доказывает второй merge; проверять источник и Git parents. `validate` сверяет Kit/Git, **не является запуском application tests**; `DOCS checks:[]` означает, что Kit не запускал проверки приложения этим коммитом.

**Квитанции и журнал связи:** в тестовой панели открыть диагностический журнал/Export и сопоставить только `seq`, `event_type`, `message_id`, `assignment_id`, `task_id`, `attempt`, идентификатор операции, стадии `delivery/read/yield` и **достоверные** Git SHA. Проверять события `message.persisted`, `send.intent`, `sdk.invoked`, `sdk.accepted` (если есть), `message.read`, `assignment.transport_closed`; отсутствие события нельзя заменять предположением. Рядом фиксировать статус Kit `assignment:dialogue-status` и статус интеграции. **Сырой WAL и полный экспорт не публиковать и не прикладывать**: там могут находиться пользовательский текст, адреса, identity или ключи. Копировать только вручную обезличенную таблицу событий; не читать/выводить `enrollment_ticket`, `credentials`, `secrets`, cookies, токены или текст контекста. Каталоги WAL, включая `.git/workflow-kit`, не чистить вручную.

Наблюдаемые стадии не взаимозаменяемы: `prepared` — подготовлено; `authorized` — Kit разрешил, но SDK ещё не доставил; `pending` — сообщение сохранено **без доказанной доставки**; `claimed` — попытка начата; `accepted` — хост принял, **чтение ещё не доказано**; `read` — сообщение получено адресатом; `yield` — обработка заявлена; `reply_observed` — физическое завершение наблюдено; `source_commit` — проверенный исходный коммит E; `INTEGRATED`/Kit DONE — подтверждение main. `UNKNOWN` требует сверки и **никогда не разрешает повтор SDK Send только из-за тайм-аута**.

### 4.1. Порядок выполнения каждой строки

1. Создать **отдельный** fixture-проект с требуемыми независимыми задачами; подготовить тестовые чаты O/E. Проверить отсутствие связи с рабочим профилем, кнопку выполнения и документируемую версию.
2. Выполнить блок команд раздела 3 **до действия**; сохранить обезличенный снимок Git/Kit и последовательности событий, включая количество checked source/result/acceptance на нужное назначение.
3. Дождаться **точной** контрольной точки из матрицы. Если автоматический переход слишком быстрый и окно не наблюдается, не гоняться за ним Stop/kill, не включать тестовые fault flags на пользовательском backend: **NOT_RUN** с причиной «точка не зафиксирована».
4. Выполнить только одно указанное действие Stop, NET либо restart. Stop генерации не отменяет уже завершённый Git-эффект; если локальная команда всё ещё выполняется, не инициировать повтор и отметить `UNKNOWN` до сверки. Пауза плана — отдельное действие и не подменяет Stop.
5. Сразу сверить `status`, `assignment:status`, `assignment:dialogue-status`, `integration:status`, `git log`, `git worktree list` и **обезличенный** WAL; проверить что адресат, попытка, `block_id` и source не изменились. После восстановления сети/процесса заново считать эти данные, а не полагаться на старый UI.
6. При **известном** исходе отправить **«Продолжай» в исходном чате** ровно один раз; ждать штатного ответа/Kit-статуса, **не запускать** вторую идентичную SDK-доставку. При `UNKNOWN` — остановиться на диагностике, не форсировать retry; согласовать отдельное восстановление после проверки.
7. Собрать снимок **после**, сопоставить SHA/merge-count/Kit DONE/количество намерений и квитанций. Присвоить итог по разделу 6. При необходимости продолжить только штатную `assignment:cleanup` **в тестовом main**, после подтверждённой приёмки и отсутствия неизвестных операций.

### 4.2. Особенности NET и RESTART

**NET:** не выключать Wi-Fi/Ethernet/Tailscale, VPN, туннель или интернет **на Mac/хосте с общим backend**. Для эксперимента нужен второй сетевой клиент либо гостевая UTM VM с собственным сетевым интерфейсом, где прерывание не затрагивает хост. Если изоляцию сети нельзя доказать, строка остаётся `NOT_RUN`. Отключение сети не равно ChatGPT Stop: генерация и локальный backend могут продолжиться, а подтверждение SDK потеряться. После возврата сети не нажимать Send/повтор по одному признаку `pending/UNKNOWN`.

**RESTART:** используйте только отдельный экземпляр backend, с изолированным `dataDir/profile`, backend identity, WAL и портом; убедитесь, что приложение не использует рабочий профиль через ошибочно общую переменную среды/симлинк. Не пытайтесь поднимать второй backend поверх того же WAL и не убивайте общий процесс. Для проверки устойчивости Kit-транзакции при рестарте сначала на **изолированном** checkout зафиксировать наличие `transaction.json`; пока транзакция не закрыта, `PROJECT_RECOVERY_REQUIRED` ожидаемо запрещает bootstrap; после штатного восстановления Kit блокировка должна сняться **без кнопки плана**, но это не даёт права включать автопродолжение. Если есть реально выполняемый процесс/неизвестный Send — не выполнять принудительную остановку, пока не получена безопасная точка. Без отдельного backend испытание `NOT_RUN`.

## 5. Проверка отсутствия дублей и загрязнения

Сравнивать *одно и то же* назначение, попытку и SHA, не просто количество сообщений. Успех требует:

| Доказательство | Что сверять |
| --- | --- |
| Исход E | Один и тот же checked `source_commit` до/после; подтверждённый Kit receipt, отсутствие второго task commit/нового assignment. |
| Работа O | Одна действующая acceptance по `result_id + source_commit + attempt`; второй вызов того же `operation_id` — идемпотентный, не новый эффект. |
| Git/Kit интеграция | `integration:status` без незавершённого журнала в конце; один merge для данного assignment/source; Kit `commit_status=DONE` ровно один раз. При прерывании до окончания — документировать `PENDING/UNKNOWN`, **не** объявлять DONE. |
| Транспорт | Один сохранённый intent по `message_id/idempotency_key`; `sdk accepted` ≠ `read`; `UNKNOWN` не разрешает второй claim/SDK Send. |
| Независимые задачи | DONE уже завершённого E и его Git SHA не изменились из-за остановки другого E; нет посторонних изменений в main/соседнем проекте. |
| Границы восстановления | WAL и Git читаемы, подтверждённое состояние совпадает с UI; если `READY_FOR_ACCEPTANCE` при всех DONE, интерфейс сообщает о завершении с ожиданием пользовательской приёмки, а не об активном выполнении. |

Нельзя выводить `PASS` из молчания UI, отсутствия ошибок в консоли, тайм-аута или сообщения модели «готово». Должны совпасть **квитанции и Git**. Если проверка не выполнена либо журналы недоступны, итог `NOT_RUN` (или `FAIL`, если реально воспроизведено нарушение), с указанием недостающего доказательства.

## 6. Шаблон протокола результата — заполняет человек

Начальное состояние всех **живых** строк: `NOT_RUN`. Каждый запуск документируется отдельно; при повторе указать новый experiment ID, не перезаписывать ранний FAIL.

| Поле | Запись |
| --- | --- |
| Эксперимент / сценарий | `<ID / O1…RESTART>` |
| Начало / конец / часовой пояс | `<дата-время>` / `<дата-время>` / `<TZ>` |
| Изоляция | `<идентификатор одноразового проекта, TEST_ONLY, для NET — гостевой интерфейс; для RESTART — отдельный backend profile/identity>` |
| Версия приложения / Kit / commit | `<build>` / `<Kit>` / `<source SHA>` |
| Scope / task / assignment / attempt | `<scope_id>` / `<task_id>` / `<assignment_id>` / `<N>` |
| Контрольная точка | `<конкретная Kit/WAL-квитанция + seq и исходный Git HEAD>` |
| Действие | `<Stop у O/E, сеть гостя, UI close или перезапуск изолированного backend>` |
| До → после | `<source SHA, result_id, acceptance ID, block_id, integration SHA, counts SDK intent и Git merges>` |
| Kit/WAL/Worktree | `<обезличенные результаты status, dialogue-status, integration-status, rev-parse и worktree-list>` |
| Наблюдаемый код/сообщение | `<код и обезличенная причина; UNKNOWN не перезаписывать как success>` |
| **Живой итог** | **NOT_RUN** / `PASS` / `FAIL` |
| Обоснование / непроверенное свойство | `<почему PASS либо конкретная причина FAIL/NOT_RUN>` |
| Ответственный / согласие на следующий опыт | `<локальная запись пользователя>` |

**Правило выставления статуса:** `PASS` — все предусловия, вмешательство и указанные доказательства реально наблюдались и совпали; `FAIL` — вмешательство проведено и наблюдалось конкретное нарушение инварианта (сохранить обезличенный код ошибки); `NOT_RUN` — не запускали, не достигли безопасной точки или не смогли собрать необходимые данные. Отдельно для каждого ID можно приложить ссылку на локальный **обезличенный** отчёт, но не экспортировать сырой WAL в переписку.
