# Workflow Pilot

Workflow Pilot 0.5.39 — локальные проекты, Workflow Kit 1.10.4 и обычный ChatGPT Chat, собственный MCP-исполнитель и [панель](../modules/chatgpt-plugin.md). Репозиторий: https://github.com/OleynikAleksandr/Workflow_Pilot. [Донор](../../PROVENANCE.md) заморожен; его профиль, cookies и службы не импортируются.

Перед первой страницей ChatGPT backend подготавливает [официальное расширение поиска](../modules/chatgpt-search-extension.md) в своей persistent session: проверенная автоматическая загрузка/установка, затем локальный кэш. Новые сессии используют [Chat-only URL-start](../modules/chat-only-startup.md): короткий `q`, сохранённая попытка и отдельные подтверждения регистрации, адреса и контекста. Выбора режима и чтения старых Work-сессий нет. Schema 9 добавляет отдельный случайный workspaceId, сохраняя projectId/sessionId прежних Chat; вход и принадлежность страницы проверяются независимо от переключателя. [Выбор пользователя](../modules/user-choice.md), роли, Kit и SDK-диалог сохраняются. [Живая приёмка](../acceptance/chat-only-startup.md) ChatGPT и native Windows/Linux остаётся NOT_RUN.

## Устройство

Backend — фоновая служба с Control, Execution, Kit, stores, страницами ChatGPT, MCP и туннелем. Закрытие клиента не останавливает работу; повторное открытие возвращает живую страницу без повторного recovery. Все три ОС используют встроенное окно службы с настоящей страницей; отдельный HTTP-клиент служит проверке и iPad через Tailscale. Один диалог — одна backend-страница; второй браузер того же разговора не штатный сценарий.

| Слой | Ответственность и граница |
| --- | --- |
| Frontend/client | Окно/sidebar/ввод, только backend API и contracts |
| Backend host | Identity/профиль/API, lease/SSE/журнал, модель Desktop и остановка |
| Control | Проекты/роли/контекст, Review и выполнение, проверка назначения и разрешения; IO только через ExecutionFacade |
| Execution | Процессы/файлы/службы/страницы/observer/приватный мост/WAL; без Control, Frontend и Kit |
| Kit CLI | Один current plan на checkout, назначения, сигналы, проверки и доказательства Git-интеграции |

`main.mjs` выбирает режим: встроенное окно, `--http-client` или `--backend-host`. In-process desktop — только dev smoke, packaged его не допускает. Control не импортирует Electron/fs/child_process; клиент не получает shell/CDP/stores. Allowlist IPC/API, проверка источника, bearer/Host/Origin, lease управления и журнал до эффекта сохраняются. Неизвестный реальный эффект не повторяется; восстановление SDK-уведомления описано отдельно. Dependency-cruiser запрещает циклы и обход фасадов; публичные chatgpt-dom/composer/experience/pageScript сохранены. Источники Kit — packages/workflow-kit, Python MCP — tools/codex-app-server-mcp, UI плагина — src/frontend/plugin; staged resources генерируются.

## Выполнение и диалог

Все рабочие сообщения O/E/приложения используют [постоянный SDK](../modules/sdk-messaging.md). Панель сразу передаёт доступное сообщение; busy, черновик, активная команда, read/yield прежнего входа не задерживают SDK. Один незавершённый вызов на получателя, независимые адресаты; очерёдность обработки определяет ChatGPT. Режимов, профильных файлов и активирующих скриптов нет. [Автоматическая проверка](../acceptance/sdk-messaging.md) отделена от живого ChatGPT, который пока NOT_RUN.

До Review/публикации O сохраняет полные task_brief/prepared_task и неизменяемые байты контекста всех обычных задач и DOCS. После Start backend механически связывает согласованный пакет с настоящим assignment/attempt и отдельно авторизует по свежему grant; каждый E получает его по готовности без нового хода O для сочинения. Старые brief-only планы сохраняют поздний prepare. [Авторская подготовка](../modules/prepared-tasks.md), [рабочий диалог](../modules/assignment-dialogue.md).

Одна кнопка Start/Пауза/Continue и Review сохранены. Новые orchestrated-планы имеют dialogue_version=1: O выбирает задачи/контекст, ведёт уточнения и принимает конкретные результаты перед интеграцией. Backend создаёт допустимые назначения, доставляет сообщения и пробуждает агентов; Kit хранит план/proof, WAL — текст/receipts. Автоматического merge по READY в новом режиме нет.

Новый Chat получает короткую URL-команду открытия панели с тикетом. Первая часть [контекста](../modules/orchestrator-startup.md) приходит в результате MCP; остальные части и SHA подтверждаются в том же ходе. DOM-ввод не участвует; наблюдатели входа/документа/черновика сохранены; переключатель режима не нужен. E ждёт отдельное task/context от O; bootstrap не запускает план.

Для S проверка актуальности обязательна **до** первой выдачи; после сохранённого возврата части 0 WAL допускает дочитать исходный SHA-снимок при изменившейся ревизии плана, не выдавая grant и не ослабляя binding/полноту/запрет superseded. Desktop/HTTP использует сохранённое `startup.complete` как источник истины поверх исторического `delivery=pending`, показывает `reading`, `stale` и терминальные ошибки без вечного spinner. После рестарта незавершённая Kit-транзакция удерживает только свой проект; существующий watcher и проверка готовности снимают удержание после штатного закрытия, **без** автоматического запуска плана и без подмены ручного OFF. При открытой/непроверенной транзакции новый startup отклоняется с `PROJECT_RECOVERY_REQUIRED`; кнопка плана остаётся штатной перепроверкой.

Intent → идемпотентный Kit → WAL сохраняет эффект между сбоями. После SDK accepted следующий pending доступен немедленно; квитанции read/yield и физического окончания принадлежат отдельным сообщениям и нужны для terminal/cleanup/complete. Новый notification_version=1 сохраняет UNKNOWN попытки, но не блокирует новые сообщения: максимум три уведомления одного message_id с задержками 2/5 с; read останавливает повторы. Старый непроверенный Review/continuation Send сохраняет запрет повтора. Закрытие окна сохраняет backend; restart требует одного Continue. Пауза запрещает новые рабочие доставки, назначения и интеграции нового диалога; текущая работа может сохранить outbox. DOCS/delivery/cleanup/итог и доказанные receipts предшествуют отключению связи.

Нажатие долговечно завершает выбор пользователя. `user-choice` и Review передаются тем же SDK даже при занятом агенте; принятие хостом, чтение и обработка различаются. Непрочитанный accepted UI-вход не задерживает следующую отправку. Start не обнуляет UNKNOWN. Review сохраняется в Kit до адресной WAL-записи; получатель фиксируется при нажатии. Sync/wait читает канонический Review; события подготовки, запуска, отзывов, позиций и публикации сохраняются после очистки. Ожидаемая reservation своего E нейтральна; identity/stale и неизвестный legacy-эффект остаются отказами.

Терминальная acceptance требует read/yield/физического конца E и подтверждения backend в Kit до удаления worktree. DOCS после проверенных интеграций может запускаться при продолжающемся текстовом ответе O; итог O может обрабатываться до последних acceptance E. Ранняя cleanup остаётся PENDING и автоматически продолжается. Complete требует cleanup DONE, конца итогового O, чистого main и отсутствия команд; restart сохраняет завершение. [Текущие действия](../modules/current-actions.md) показывают одну главную причину, точные роли/стадии/адресатов и независимую работу. В sidebar только нейтральный агент и опубликованный план с одной кнопкой; выбор/startup/таймеры/Review не дублируются. 3/3 интеграции отличаются от complete. После него явно ожидается приёмка пользователя; архив проекта её не заменяет и не предупреждает об остановке уже завершённого плана.

Прогресс backend/SSE отличает **результаты E** (checked source_commit/Kit proof) от **интеграций main** (Kit DONE). `prepared`, `authorized`, сохранённый `pending`, SDK accepted, read и Kit RUNNING показываются как разные факты; `UNKNOWN` не угадывается. Все DONE и `READY_FOR_ACCEPTANCE` показывают ожидание приёмки, даже когда scope ещё ACTIVE. Метка `DOCS checks:[]` означает, что документальный коммит **не выполнял application tests**; их PASS подтверждается записями проверок ранее выполненных задач, а не DOCS.

Новые фоновое readiness и статус каждого E проверяются без выбора sidebar. URI панели — SHA-256 полного HTML, MCP обслуживает неизменяемый snapshot; старый iframe не обновляется от переустановки. Рабочие проекты/профили тестами не меняются. Старые планы сохраняют контракт; переход активного 0.5.7 — [явная миграция в паузе](../modules/assignment-dialogue-reliability.md#переход-старого-плана). Удаление незавершённого проекта сохраняет адресную остановку, журнал очистки и защиту соседей.

В 0.5.18 readiness обычной новой сессии проверяется без выбора карточки, новый проект раскрыт. Подготовка контекста показывает готовые части, отменяется с сохранением паузы и повторяется без блокировки sidebar. Заменяется только проверенное собственное зависшее вложение; UNKNOWN не разрешает повтор Send. Принудительная остановка в меню требует подтверждения, не ждёт агентов и ограничивает очистку двумя секундами. Адресные fixtures пройдены; восстановление внешней обработки файлов и живые меню требуют пользовательской проверки.

В совместимом пути вложений повторная часть получает уникальное имя и распознаётся при допустимом переименовании и замене карточки. Неполный или изменённый пользователем пакет не отправляется. Диагностика различает загрузку, обработку и отсутствие наблюдаемого прогресса без текста файлов. Адресные проверки пройдены; первоначальное плавающее зависание требует живых данных, его устранение пока не заявлено. [Контракт вложений](../modules/browser.md).

MAIN_DIRTY до выдачи даёт paused/blocked и «Продолжить» с безопасными путями. Свежий Continue не повторяет UNKNOWN и не снимает ручной Stop. Installer Kit доставляет общее `.DS_Store` для workspace/worktree, сохраняя пользовательские правила и блокировку настоящих правок. Смена SDK generation/lease восстанавливается единственным status→sync→wait; running и исторический handshake сами по себе не означают живую панель. Сохранённая собственная Chat-привязка не теряется из-за старого lost, чужой документ не признаётся своим. Наблюдатель child receipts при подключении один раз сверяет состояние без постоянного polling.

[Раннее имя сессии](../modules/session-titles.md) агент задаёт в первом содержательном ходе до режима/Review/плана через workflow_session_set_title. Нужна свежая host identity; manual → scope → topic → page. Локальная запись и ChatGPT-title sync различаются; новый topic несовместим с data downgrade в 0.5.35. [Приёмка 0.5.36](../acceptance/session-choice-and-delivery.md) остаётся NOT_RUN в живых чатах.

## Проверка и готовность

Запуск/установка — [README](../../README.md); состав — release-manifest.json. Installer обновляет Applications готовым bundle, при работающей службе оставляет проверенный pending; переключает версию пользователь.

Автоматические проверки используют изолированные HTTP API/runtime/SDK/MCP/Kit/Git/Electron fixtures без модельных ходов и рабочих профилей. Включают два и пять E, авторизацию до binding и отправку после него без лишнего ready-хода, многоходовую блокировку, result/revision/acceptance/интеграции, перекрытие DOCS и финализации, раннюю cleanup и complete. После 0.5.23 дополнительные регрессии проверили два прерывания Kit merge (до и после Git-коммита), checked E commit до result, независимый block_id и утрату SDK-ответа с WAL restart без повторного Send. `unit-all` и назначенные checks выполнялись в коммитах исправлений/тестов; документальная задача DOCS с `verification_ids:[]` их не перезапускает. В живом контрольном 0.5.10 подтверждены три интеграции, очистка и complete; новые оптимизации 0.5.12 ожидают живого измерения. A–D 0.5.24 и новые O1/O2/E1/E2/NET/UI/RESTART — **NOT_RUN**. Изолированный `electron-smoke` проходит путь первого/нового Chat через панель и настоящее поисковое расширение; отдельный native fixture проверяет cold install, offline restart и повреждение кэша. Только официальный CRX скачивается по сети; ChatGPT отвечает локальный HTTPS-host. [Граница старых проверок](../modules/automatic-agent-dialogue-acceptance.md), [новый плейбук](../acceptance/interruption-recovery.md).

Pending: полная macOS-служба/Finder/Dock/Spotlight/меню/clipboard/файлы, оркестрация/архив/восстановление E/to-do с настоящими чатами, встроенное/HTTP-окно, iPad через реальный Tailscale/мобильную сеть. Native Windows/Linux, UTM и clean-install отложены. Secure MCP Tunnel собственный; VPS без собственного маршрута — setup-required. История выпусков хранится в Git.
