# Форма плана реализации

Деление на задачи выбирай по проверяемому результату, смысловым зависимостям, контрактам и пересечениям записи. Учитывай необходимый контекст, риски интеграции и стоимость координации и проверок. Не задавай нормативов числа файлов, строк или задач и не выдумывай порог выгоды parallel. Снимок разрешает вариант, но не предписывает его: execution_reason объясняет выбор с учётом поручения пользователя. Benchmark для этого решения не нужен.

Объём реализации и рабочая спецификация определяются в диалоге. Процесс плана, DOCS и delivery задан Workflow Core; SPEC ниже — форма требований. Запиши только данные задачи, служебные поля создаёт Kit.

```json
{
  "id":"prototype-001",
  "spec":"docs/planning/prototype.md",
  "objective":"Пользователь получает работающий результат",
  "stack":"Node.js",
  "checks":[{"id":"test","executable":"node","args":["--test"],"kind":"test"}],
  "tasks":[{"id":"T001","title":"Реализовать основной сценарий","files":["src/main.mjs","tests/main.test.mjs"],"checks":["test"],"acceptance":["Сценарий и обработка ошибок работают"]}]
}
```

Сохрани JSON в `.harness/runtime/plan.json`, вызови `./scripts/workflow plan:create --input .harness/runtime/plan.json`. Подставь существующий стек и реальные проверки; Node не обязателен. spec — существующий документ требований. Небольшой самостоятельный результат может составлять одну микрозадачу.

files — предполагаемые пути; acceptance, why, commit, dependencies уточняются при необходимости. checks — ID проверок конфигурации. Для delivery используется verification_kind package или installed и проверка того же kind с evidence; форму показывает task:start --help. Контекст задачи выбирается через context_pack в plan:apply; не копируй шаблоны в проект.

Для нового диалога O/E до Review обязательно заполни `tasks[].task_brief`: полное стабильное поручение до 12000 байт UTF-8 (цель, границы, критерии, проверки), и `prepared_task:{"version":1,"contexts":[{"source":"docs/modules/example.md","text":"полный выбранный контекст","commit":"точный SHA при наличии"}]}`. Без выбранных дополнительных источников contexts может быть пустым. Не включай секреты/адреса чатов; каждый источник вместе с оформлением ≤28000 байт, сумма в бюджете проекта. Kit сохраняет неизменяемые байты и SHA, связывает с автором/project/scope/semantic task digest. Для DOCS перечисли id `DOCS`, title, files, task_brief и prepared_task явно; нормализация сохранит содержание. Стабильные инструкции зависимых задач готовы заранее, проверенные факты зависимостей добавляет backend. Публикация не разрешает исполнение. После Start приложение механически связывает и авторизует согласованный пакет для настоящего назначения и доставляет каждому E по готовности без нового хода O. Старые brief-only планы сохраняют поздний prepare/dispatch. Явная актуализация ещё не начатой задачи: task:update с task_brief и новым prepared_task без старого digest; plan:extend принимает те же поля новых задач и prepared_tasks по ID для изменённых задач/DOCS. Изменённая подготовка участвует в новом согласовании, старые байты не подменяются новым чтением файла.

Для нового плана с настройками выполнения передай вместе `parallel_allowed` (boolean), `max_workers` (целое ≥ 1), `execution_strategy` (`sequential`/`parallel`/`orchestrated`) и непустую `execution_reason`. Это снимок новой основной сессии, не текущих Settings. Отсутствие всех четырёх полей сохраняет legacy-последовательность. OFF или лимит 1 исключают parallel, но допускают orchestrated с последовательными назначениями; ON не обязывает выбирать parallel. Зависимости нового плана должны стоять раньше задачи.

У задачи `parallel_safe` — boolean, по умолчанию false при нормализации нового плана. false означает исключительное выполнение: в parallel-плане задачу также получает отдельный исполнитель. true требует конкретных путей записи; glob/неизвестная область запрещены. Пересечение областей допустимо в плане, но исключает совместную выдачу. Общая спецификация в documentation_paths тоже считается областью записи; read-only контекст задаётся через context_pack, а не предполагается по имени файла.

Review получает нормализованные поля и включает их в digest согласованной пары. Служебный commit_ref не заполняй: DONE родительской задачи parallel-плана требует роли integration с operation_id и source_commit. Собственный SHA интеграции восстанавливается из Git. Коммит локального задания не подтверждает родительское DONE; операции назначения и слияния реализуются отдельно от этой формы.

После публикации parallel-плана завершите ответ и передайте выполнение Web Pilot. Основной чат не вызывает task:start и commit его задач в main. Все задачи, включая основу и исключительные, выполняются в назначениях. Запуском управляет только пользователь: кнопка выполнения плана в Workflow Pilot («Начать выполнение плана» / «Пауза» / «Продолжить»). Пауза оставляет план ожидающим; новый план не запускается сам. Агент кнопкой не управляет и не просит включать другие режимы.

План сессии Workflow Pilot создаётся только после выбора режима пользователем: сначала `./scripts/workflow plan:mode-request` с рекомендацией, затем сообщение с выбором. В любом режиме план указывает `execution_origin_session_id` — Session ID этой сессии — и `execution_strategy` выбранного режима; иначе Kit отвечает EXECUTION_MODE_REQUIRED/EXECUTION_MODE_MISMATCH. `sequential` — эта сессия выполняет задачи сама по порядку в main.

План оркестратора (`orchestrated`) публикует сессия-оркестратор Workflow Pilot. Нужны `execution_origin_session_id` — Session ID из recovery — и `release` (boolean). Kit всегда добавляет DOCS. При `release: true` после DOCS перечисли delivery-задачи по `delivery_tail` конфигурации; при false их нет. `parallel_safe` различает параллельные и последовательные назначения в worktree; true требует разрешения и лимита > 1. `context_pack` задаёт документы задачи с семантикой выбранной версии диалога ниже. После публикации сообщи о кнопке «Начать выполнение плана».

При `dialogue_version: 1` task.context_pack — рекомендуемый список для O. Он сам выбирает нужные материалы и отправляет task/context через рабочий канал. E получает обязательные ограничения проекта отдельным полным слоем; недостающее спрашивает у O. O проверяет каждый result и принимает его точный SHA до integration:start/continue, не ожидая общего итогового поручения. Старые планы автоматически передают E его task.context_pack и сохраняют финальное поручение. READY не означает DONE main. Проверь общий main и дай итог; worktree-сервер не доказывает проверку main. Не архивируй план и не останавливай сервер без отдельного поручения пользователя.
